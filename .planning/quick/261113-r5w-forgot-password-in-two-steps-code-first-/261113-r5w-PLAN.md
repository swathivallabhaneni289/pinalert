# Quick 261113-r5w: Forgot password in two steps, code first, then the new password

## Why

On 2026-11-13, while resetting a test account's password, the owner said: "i think we should have code confirmation and then we should be able make a new password". Today the reset code screen asks for the code and the new password together (web/templates/login_gate.html.tmpl `#code-new-wrap`, web/static/js/auth.js `setCodeMode` and the submit near line 727, `POST /api/auth/reset/code` with `{code, password}`, `CredentialService.ConfirmReset` in internal/service/credentials_signin.go). It becomes two steps. Sign up stays exactly as it is.

## Design (follow it; where the code disagrees with an assumption here, keep the intent and note it in the SUMMARY)

Server
1. Migration `internal/store/migrations/00025_add_auth_code_verified.sql` (check 00025 is still the next free number; use the next free one if not): `ALTER TABLE auth_codes ADD COLUMN verified_at TIMESTAMPTZ;` plus a CHECK that `verified_at` is NULL unless `purpose = 'reset' AND delivery = 'code'`. A goose Down that drops the CHECK and the column. Nothing else in the schema changes.
2. Queries (sqlc, then `sqlc generate`; match the existing query file and naming style):
   - mark a row verified: `UPDATE auth_codes SET verified_at = now() WHERE id = $1 AND used_at IS NULL AND verified_at IS NULL AND expires_at > now() AND purpose = 'reset' AND delivery = 'code'`, returning the rows affected.
   - `GetLatestAuthCode` (or a sibling) must also return `verified_at` so the service and `LiveCode` can see it.
3. Service:
   - New `CheckResetCode(ctx, sessionID, rawCode) error` (step one). The latest row of this browser inside the resume window must be purpose reset and unused; `cleanTypedCode`; `proveCode` (it counts the try before the compare, as today); then mark the row verified (0 rows affected means ErrWrongCode). Every refusal is ErrWrongCode, exactly like today, so an address with no account (a `no_account` row) gets the same answer as a wrong code. It sets no password and spends nothing. Confirming an already verified row again is fine (answer OK without another write) as long as it is still inside its window.
   - `ConfirmReset` loses its code argument: `ConfirmReset(ctx, sessionID, newPassword) error` (step two). The latest row of this browser must be purpose reset, delivery code, unused, `verified_at` set and `now < verified_at + CodeTTL`; otherwise ErrWrongCode. `checkPassword` first (a refused password changes nothing and keeps the confirm). Then the same lookup, hash and one transaction as today: `lockAddress`, `setPasswordNewEpoch`, spend the row (adapt `spend` so it takes the row id and email; `ConsumeAuthCode` must still be conditional on `used_at IS NULL` so two parallel step two calls cannot both win), `clearThrottle`, `LogOutAllDevices`. Keep every existing comment about ordering (SK-05, CR-S02) true.
   - A newer code (Resend, or Forgot password again) is a newer row, so the verified older row is no longer the latest and step two refuses: that is intended.
   - `LiveCode` gains `Verified bool` (true when the row is a verified reset row still inside `verified_at + CodeTTL`), so the page can render step two after a reload. `SpentCode` keeps working as today.
4. Handlers and routes:
   - `POST /api/auth/reset/code` becomes step one: body `{code}`, answer 200 `{"code_ok": true}`. It keeps `gate.ReserveCodeTry`, cancelled on success as today.
   - New `POST /api/auth/reset/password`: body `{password}`, answer 200 `{"password_set": true}` (the existing `PasswordSetResponse`). It takes a token from the same code try bucket (the hash is costly), cancelled on success and on a refused password. Same `authReady`, `decodeAuthBody`, `extendWriteDeadline` rules as its siblings where they apply, the same `cop.Handler`, and add it everywhere the other `/api/auth/reset*` routes are listed (the exempt set comment and code near router.go line 592, the route list near line 899, any allow list or test that enumerates auth routes).
   - Swagger annotations for both; regenerate with `make swag` (swag is installed at ~/go/bin/swag). Keep the swag @license.name line "Unlicensed (all rights reserved)".
   - The sign in page handler (internal/api/handlers/auth.go near line 243, where `LiveCode` is read) passes the verified state to the template.

Page (login_gate.html.tmpl and auth.js), words kept short
5. Reset step one: the existing code screen without the new password box. Title "Reset your password", the existing lead ("We emailed ... Type the 6 digit code from that email."), the code box, the primary button "Confirm code", Resend and Change email as today. A wrong code shows the existing refusal and counts toward the existing fifth try switch off.
6. Reset step two, after a confirmed code: the code box, its label and Resend are hidden; the lead becomes "Code confirmed. Choose a new password."; the New password box with Show and the rule line "At least 8 characters." (from the template value, as today); the primary button "Set new password"; Change email stays as the way out. Focus moves to the New password box. Success does exactly what `finishReset` does today. A refused password shows its error on the password box. If the confirm has run out or a newer code replaced it (the server answers with the wrong code error), go back to step one with the message "That code is wrong or has expired." and Resend available.
7. A reload during step two renders step two (from `LiveCode.Verified`); a reload during step one renders step one. The `{{if eq .CodeMode "reset"}}` branches gain the step. Sign up's code screen and its button "Create account" do not change at all.
