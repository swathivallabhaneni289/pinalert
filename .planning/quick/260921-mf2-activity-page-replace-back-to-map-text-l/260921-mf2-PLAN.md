<geometry>
Worked out from the shipped CSS, not guessed. All values resolve from main.css tokens:
`--space-md: 16px`, `--space-lg: 24px`, `--touch-target-min: 44px`, and a global
`*, *::before, *::after { box-sizing: border-box }` at main.css line 167.

**The account button's line.** `.app-header` is `position: fixed; top: var(--space-md); right:
var(--space-md)` (auth.css line 242). `.account-trigger` is exactly 44px square (auth.css line 249).
So the account button's border box spans y 16px to 60px, and its vertical center is y 38px.

**Current back link.** `.profile-page` has `padding: calc(var(--touch-target-min) + var(--space-lg))
... ` which is 68px of top padding (auth.css line 362). The back link is the first in-flow child
with `min-height: var(--touch-target-min)`, so it spans y 68px to 112px, center y 90px. That is
52px below the account button's center. This is the "looks really odd" the user reported.

**Chosen fix: keep the control in normal flow, drop `.profile-page` padding-top to
`var(--space-md)`.** Body margin is 0, `.profile-page` has no top margin, and a parent's padding-top
blocks margin collapse through it, so the first in-flow child's border box starts at exactly 16px.
Give the control `height: var(--touch-target-min)` and its border box spans y 16px to 60px, center
y 38px. Identical to the account button. No magic numbers, both sides read the same two tokens.

**Horizontal alignment is free.** Because the control is in flow inside `.profile-page`'s padding
box, its left edge is the content column's left edge by construction, the same left edge as
`.profile-email` and the Activity `<h2>`. No offset arithmetic, and it cannot drift if the column
width or padding ever changes.

**Why in flow and not fixed.** A fixed control would stay glued to the account button on scroll, but
would need a hand-computed `left: max(var(--space-lg), calc(50% - 320px + var(--space-lg)))` to track
the centered column, would overlay content as the page scrolls, and would take the control out of
flow so the content below needs its own compensating padding. That is the same magic-number coupling
that produced the current misalignment. The in-flow version aligns exactly at resting scroll
position and scrolls away with the content, which is the correct behavior for a page-level control.
**State this tradeoff plainly in SUMMARY.md**: the two controls share a line at scroll top, not
while scrolled.

**Overlap check, 1440px viewport.** Column outer width 640px (border-box, includes its 24px side
padding), centered, so x 400 to 1040; content box x 424 to 1016. Control occupies x 424 to 468.
Account button occupies x 1380 to 1424. Clearance 912px.

**Overlap check, 375px viewport.** Column is 375px wide (below the 640px cap), content box x 24 to
351. Control occupies x 24 to 68. Account button occupies x 315 to 359. Clearance 247px.
Both controls occupy y 16 to 60, one line, no collision.

**Collision threshold.** They touch when `24 + 44 > W - 60`, that is `W < 128px`. Below any real
device. For W at or above 640px the column is capped and centered, so the control's right edge is
`(W - 640) / 2 + 68` and the button's left edge is `W - 60`; the inequality has no positive
solution, so no collision at any desktop width.

**Content clearance.** The 68px top padding existed only to keep content out from under the fixed
header. The 44px control now occupies that clearance band, and it sits on the left where the header
(which is 44px wide, flush right) does not reach. With `margin: 0 0 var(--space-lg) 0` on the
control, the email row's top moves from y 128px to y 84px. Record that before and after pair in
SUMMARY.md so the user can sanity check "balanced".
