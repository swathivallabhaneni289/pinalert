# Removed reports get a reason, the poster can ask for review up to 3 times, the moderator can restore

## Why

7.1 UAT, 2026-11-17 and 2026-11-18, after quick 261117-vvb (flags hide for review, bell rows to the
poster). The owner:
- "If like the user asks who got their account reported, asks for like a second review, we need to
  make sure that is also built properly."
- "if there is a chance, like, they want to ask again, and if I like want to let them like post like
  let people see it again after like a review, I think I should have like an option to like let them
  do it also. in the admin page."
- "I just don't want it to like look really wordy. And I think we should also like mention why we
  removed it. All these options when you're like keeping them as buttons ... I just don't want them
  to be like looking really wordy with long words"
- Agreed table, then "yes". Phone and laptop the same (standing rule).

Agreed with the owner:

| Where | What it shows |
|---|---|
| The moderator's Remove button | Pick one reason: **Spam**, **Abusive**, **False**, **Dangerous**, **Other** |
| The poster's bell row "Your report was removed after review." | Opens a box: "Why: False". An optional note and **Ask for review** |
| Moderator page, top list **Review asks** | Report, why, their note. Buttons **Restore** and **Keep removed** |
| Moderator page, **Removed** list | **Restore** on any removed report |
| The poster's bell, the answer | "Your report is back." or "Your report stays removed." |

They can ask up to 3 times per report, one at a time. Nobody is told who flagged. Told earlier and
still true: a report shown again cannot be hidden by flags again and sends no phone alerts.

Reports only. Comment moderation is unchanged.

## What changes

### 1. Data (migration `00027`, the next free number; a Down that undoes it safely)

- **The reason for a removal.** Every move to `removed` records one reason: `spam`, `abusive`,
  `false`, `dangerous`, `other` from a moderator, or `text_check` when the late text check removes
  it. Store it on the report (for example `reports.removed_reason`, nullable, CHECK on the closed
  list) so the box reads the current removal's reason in one place. Also record it on the moderator
  action row (`moderation_actions.reason`, nullable, same list without `text_check`). Reports
  removed before 00027 have no reason (NULL).
- **Moderator actions.** Extend the `moderation_actions` action CHECK with `restore` and
  `keep_removed`.
- **Review asks.** A new table (for example `report_review_asks`): id, report, asking account (both
  `ON DELETE CASCADE`), note (nullable text, at most 200 characters, CHECK), created, answered at,
  answer (`restored` or `kept_removed`), answering moderator. A partial unique index allows at most
  one open (unanswered) ask per report. At most 3 asks per report in total, decided in the same
  transaction as the insert under the report row lock, so concurrent asks cannot pass the cap.
- **Bell rows that can repeat.** Today `uq_updates_own_report` (00026) keeps one own row per
  (account, report, kind) with `ON CONFLICT DO NOTHING`, so a second "stays removed" or a second
  "removed" (after Restore, then Remove again) would be dropped silently. Decision: **an own row
  that happens again comes back as unread and newest** (upsert on that key: move its time to now
  and make it unread the way the bell judges unread; no second row). This keeps the bell from
  piling up. Apply it to every own kind, old and new.
- Down: drop the new table and columns, restore the old CHECKs. A report that was restored stays
  `clear`. Nothing else moves.

### 2. Removing needs a reason (moderator)

- Report Remove, from every list it appears in (Hidden by flags, Flagged by people, Flagged by the
  automatic check, Text check not finished, Find report), opens a small box built on the existing
  `.logout-confirm` pattern (only its buttons close it, nothing outlined on open, the page stays
  still): title **Why remove?**, five choices **Spam**, **Abusive**, **False**, **Dangerous**,
  **Other** as one radio group of real buttons, then **Cancel** and **Remove**. Remove stays off
  until a reason is picked. No hint lines.
- The Remove API requires a valid reason and answers 400 without one. The late text check writes
  `text_check`. Keep behaves as today and clears no reason it does not need to.
- Comment Remove is unchanged (no reason).

### 3. The poster's box

- Opened by tapping the poster's own `own_removed` row ("Your report was removed after review.") or
  `own_stays_removed` row ("Your report stays removed."), in the bell list and in the full updates
  list (`/profile?part=updates`), on phone and laptop. The removed row stops linking to `/policy`
  (drop `PolicyLink` if nothing else uses it). These rows are buttons that open the box, and they
  carry the new mark while unread, like link rows (extend vvb's `marksNew` in updates.js and
  `OwnPlain` in `fillUpdatesPart` and profile.html.tmpl).
- Same `.logout-confirm` pattern. Render the box at the top level of the page (not inside the bell
  dropdown), so no scrolling or clipped parent can cut it off on iPhone Safari.
- Words, nothing more:
  - Title: **Removed**
  - **Why: Spam** / **Why: Abusive** / **Why: False** / **Why: Dangerous** / **Why: Other** /
    **Why: Text check**. No Why line when the report has no recorded reason.
  - Can ask: a box labelled **Note (optional)** (no placeholder, at most 200 characters), then
    **Close** and **Ask for review**.
  - Asked and waiting: the line **Asked.** and **Close**.
  - Three asks used and answered: the line **No asks left.** and **Close**.
- After a successful ask the box shows **Asked.** in place; no extra toast text beyond what the
  page already does for a sent action.
- The box never shows the report's words, flag counts, flagger identity, places or the moderator.

### 4. Poster API

- `GET` the box state for one report and `POST` an ask (with an optional note), under the existing
  report API style (for example `/api/reports/{id}/review-ask`). Only the report's author, only
  while the report is `removed`. Every other case (not signed in aside, which follows the API's
  usual 401) answers 404 with nothing revealed. An ask while one is open, or after 3, answers 409
  with a plain line. The note is trimmed, capped and stored as plain text; it is never in any public
  JSON, never logged, never sent to the text check provider.
- Swagger annotations for the new and changed routes, in the file's style. Keep the
  `@license.name` line exactly as it is.

### 5. The moderator page (phone and laptop)

- A new first section **Review asks**: each open ask, oldest first, showing the report as other
  cards do, **Why: X** (when known) and **Note:** their note (when given). Buttons **Restore** and
  **Keep removed**.
- A new section **Removed**: reports removed in the last 30 days, newest first, at most 100, each
  with **Why: X** (when known) and **Restore**.
- Section heads with counts like the others. Few words, no descriptive sublines beyond what the
  other sections have.

### 6. Restore and Keep removed (service)

- **Restore** (from either list): `removed` to `clear`, clears the removal reason, dismisses open
  flags, stamps `review_kept_at` (so flags can never hide it again and vvb's push gate keeps it
  from ever pushing), closes an open ask as `restored`, records a `restore` action, and writes the
  poster's `own_restored` row: **Your report is back.**, linking to `/?report=<id>` when the report
  is available. The time it lasts is not extended; an expired report comes back into Past only.
- **Keep removed** (only with an open ask): closes the ask as `kept_removed`, records a
  `keep_removed` action, writes `own_stays_removed`: **Your report stays removed.**, which opens the
  box (the poster may ask again while fewer than 3 asks are used).
- Both take the same report row lock as vvb's Keep; a repeated or stale answer answers 409 and
  writes nothing. Moderator only.
- A later Remove of a restored report works as today, needs a reason, and brings `own_removed`
  back as unread. The ask count carries over (3 per report in total).
- Rating: a restored report counts by its votes like any shown report; a removal counts exactly as
  a removal does today. Asks change nothing in the rating.
- Bell only: no phone notification, no email, for any of the new rows. They count toward the same
  hourly limits as the other own rows.
