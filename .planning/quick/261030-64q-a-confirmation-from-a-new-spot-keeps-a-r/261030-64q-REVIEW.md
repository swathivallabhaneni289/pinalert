## Warnings

### WR-01: The fading note's negative push pins now pass whatever the visibility is

**File:** `internal/service/pushworker_test.go:686-689`

**Issue:** The amendment gave the `fadesSoon` mutation (facts that fade in 30 minutes) only to the "fading, live" sent case (line 684). Four negative cases still use the default report facts, which fade 5 hours out (`pushrecipients_test.go:68`):

- still active but provisional;
- hidden since;
- retracted since;
- withheld since.

With the new `!f.ExpiresAt.After(now.Add(FadingLead))` clause at `pushworker.go:800`, all four return `not_eligible` from the time check alone.

**Scenario:** someone removes `MayNotifyAboutReport` from the `UpdateFading` case, so a Provisional, Hidden or Retracted report's fading note reaches the phone. All four cases still pass. The Live requirement for fading notes (review S-01, 2026-10-25) is no longer pinned.

**Fix:** give each of the four cases the facts that fade soon, so only visibility can make them fail.

```go
{name: "fading, still active but provisional", ..., want: "not_eligible", mutate: fadesSoon},
{name: "fading, hidden since", ..., want: "not_eligible", mutate: fadesSoon},
{name: "fading, retracted since", ..., want: "not_eligible", mutate: fadesSoon},
{name: "fading, withheld since", ..., want: "not_eligible", mutate: fadesSoon},
```

### WR-02: TestDemoParityWithSQL cannot see an extension, but TRUST-MODEL says it checks one

**Files:** `internal/demo/parity_db_test.go:93`, `docs/TRUST-MODEL.md:273`

**Issue:** TRUST-MODEL says the Demo world applies the same rule "and `TestDemoParityWithSQL` checks it against the SQL". That test was not changed, and it cannot tell an extension from no extension:

- The scenario's A and B confirms land milliseconds after posting, so each extension adds only milliseconds.

**Scenario:** a regression makes `memQuerier.InsertVoteExtending` never extend. Then the Demo and the SQL disagree on every fade time after a confirm, but both still show 28800 seconds and the parity test passes. `TestMemQuerierExtendsLikeSQL` compares the twin with `ExtendedExpiry`, the Go function. Nothing compares the twin with the database.

**Fix:** use the smallest of these that is enough:

- add `ConfirmExtends bool` to `viewSnap`;
- add a scenario step that can see the extension, such as a report seeded through `testutil.InsertStoredReport` on the SQL side and the matching seed on the world side, with a fade time several hours earlier than vote time plus 8 hours;
- or, at minimum, correct the sentence in TRUST-MODEL so that it names `TestMemQuerierExtendsLikeSQL`, not the parity test, as the twin's check.

### WR-03: One report can now send up to four "fades in about an hour" phone notes

**Files:** `internal/store/queries/updates.sql:128-138`, `internal/store/queries/push.sql:476-500`, `docs/TRUST-MODEL.md:269`, `docs/PUSH.md:112`

**Issue:** `MarkFadingAndInsertUpdate` re-arms whenever `fading_for` differs from `expires_at`. Before this change `expires_at` never moved, so each report and account got at most one fading row. Now every extension that lands in the last hour re-arms it. `EnqueueChangedFromUpdates` queues one `changed` push per update row. Only Apple devices are held to one push per report (`deviceSkipsRepeatPush`).

**Scenario (medium report, Android, Changes on):**

| Time | Event | Note |
|---|---|---|
| T | Posted, fades at T+8 | |
| T+7 | Fading row | Note 1 |
| T+7:30 | New spot confirm, fades at T+15:30 | |
| T+14:30 | Fading row | Note 2 |
| T+15 | New spot confirm, fades at T+23 | |
| T+22 | Fading row | Note 3 |
| T+22:30 | New spot confirm, fades at T+24 (the cap) | |
| T+23 | Fading row | Note 4 |

That is four phone notes about one report, and the first three turned out false. A Critical report can produce three. The hour gap and the hourly limit of 4 bound it, but this goes against "few, never piled up" (owner 2026-10-28). Both docs also understate it: they say the bell "may write one more" fading row, when it can write up to three more.

**Fix:** send the fading note to the phone at most once per account and report. Keep re-arming the bell if it is wanted. For example, in `EnqueueChangedFromUpdates`, skip a `fading` update when a `changed` row for an earlier `fading` update of the same account and report already exists:

```sql
AND NOT (
    u.kind = 'fading'
    AND EXISTS (
        SELECT 1 FROM push_outbox o
        JOIN updates u2 ON u2.id = o.update_id
        WHERE o.account_id = u.account_id AND o.report_id = u.report_id
          AND o.kind = 'changed' AND u2.kind = 'fading'
    )
)
```

Then change "one more" in both docs to the real bound.

## Info

### IN-01: The browser's time fade dims an extended report much earlier in absolute time

**Files:** `web/static/js/app.js:1180-1195`, `web/static/js/trust.js:784-795`

**Issue:** `ageStage` divides by `expires_at - created_at`, which is the whole extended life. The server caps its own window at `ExpiryDuration`. `fadeStage` takes the worse of the two stages, and the server sends no stage for a Critical report, so for Critical the time stage decides alone.

**Scenario:** a Critical report confirmed from a new spot at T+30 is capped at T+48.

- At T+36, six hours after a fresh confirmation, the time stage is aging (12 of 48 hours left).
- At T+42 it is stale, with 6 hours still left.
- An unextended Critical report goes stale only in its last 3 hours.

TRUST-MODEL:267 describes this design ("looks fresh again"), so it is intended. The absolute effect is not written down anywhere.

**Fix:** have the server send the life the window uses (min of the life and `ExpiryDuration`) for the browser to divide by. That keeps the browser free of numbers. Or document the effect in TRUST-MODEL.

### IN-02: When no extension runs, the returned fade time comes from the statement's snapshot

**File:** `internal/store/queries/extend.sql:79`

**Issue:** If `extended` returns no row, the final SELECT returns the snapshot's `expires_at` without a lock. A concurrent extension that committed before this statement returns can leave the vote answer's fade time older than the feed's for that one response. The harm is small, because the client refetches after every vote and the currency window is capped.

**Fix:** none needed. Optionally, add a line to point (b) of the header comment.

### IN-03: A confirm cast while a report is resolved uses up that spot and that person for good

**Files:** `internal/store/queries/extend.sql:68-76`, `internal/service/trust.go:686-694`

**Issue:** On a resolved report Go passes Extend false, but the confirm row is still written. After the reporter reopens, the NOT EXISTS check finds that row. Neither that cell nor that account can ever extend the report. The DB test at `expiry_extend_db_test.go:291` uses a different account and spot after the reopen, so it does not show this.

**Fix:** accept it and add one sentence to TRUST-MODEL rule 7. Or limit the NOT EXISTS check to rows that did extend, which would need a marker column, so it is probably not worth it.

### IN-04: A queued Critical or Reliable push keeps its own expiry, copied before the extension

**Files:** `internal/service/pushdispatch.go:509`, `internal/service/pushworker.go:442`, `internal/store/queries/push.sql:719`

**Issue:** `push_outbox.expires_at` is `min(report fade time, now + window)` at queue time.

**Scenario:** a Critical push is queued with 40 minutes left, and a new spot confirmation then extends the report by 8 hours. If the send fails and a retry is still queued past the old fade time, `SkipStalePushes` (`o.expires_at <= now`) and the worker's `!run.now.Before(claim.ExpiresAt)` drop it as stale while the report is live. This needs a retry to run long. The new fading skip itself never touches a Critical push.

**Fix:** none needed at this scale. Optionally, make the stale check use only the report's `expires_at` for kinds whose window is longer than what was left.

## Checked and fine

**Gaming the rule:**

- **Confirm, dispute, confirm:** the NOT EXISTS check reads the append only log, not the standing votes, so the loop never extends twice. Votes have no DELETE or UPDATE anywhere, and accounts are soft deleted, so the log cannot be reset.
- **Change of vote:** the account check (`v.account_id = nv.account_id`) stops a second extension.
- **Retracted then re-cast confirm:** blocked by the same two checks. There is a DB test case for each.
- **Reporter's own vote:** step 4 of `CastVote` refuses a content vote on your own report. Excluding the reporter's rows only helps strangers.
- **A NULL reporter** (pre 1.1 report): `IS DISTINCT FROM NULL` counts every row, which is correct.
- **Expired report:** cannot be revived. `CastVote` step 6 refuses it, `mayExtend` checks it in Go, and `r.expires_at > nv.created_at` checks it in SQL.

**Correctness:**

- **Atomicity:** the vote and the move are in one statement.
- **Concurrency:** under read committed, the update re-checks the changed row and `GREATEST` only moves later, so concurrent extensions are not lost. The FK's KEY SHARE lock is compatible with the update's NO KEY UPDATE lock, so they cannot deadlock.
- **A1:** enforced in Go through `Resolve` and `mayExtend` before the write. The resolved then reopened DB test tells the two cases apart.
- **The one column:** every reader I grepped reads the stored `reports.expires_at`. That covers the feed, Past and Ended nearby, reliability judging, `RecentReportsForPush`, `SkipStalePushes`, `PushReportFacts`, updates, comments, moderation and the profile reports. No Go or SQL code works out an expiry from `created_at`, apart from Submit.
- **Still current window:** `buildCurrency` caps the life at `ExpiryDuration`, so the window stays at the normal lifetime over 4.

**Parity:** the vote answer is built from the fade time the write returned. The client refetches after every vote. `TestCastVoteTrustMatchesFeedAfterExtension` compares trust with `reflect.DeepEqual` on two cases that can tell them apart.

**Push:** the fading skip sits only in the `UpdateFading` case of `eventStillHolds`. The Critical, Reliable and follow paths are untouched. Notes stay silent.

**Demo twin:** `memQuerier.InsertVoteExtending` applies the same new spot, new person, reporter exclusion, Extend and no revival rules through `ExtendedExpiry`. The seed comment's 56 minutes matches its 2 minute vote gap.

**Copy:**

- `formatFade` adds "unless confirmed again" only when `confirm_extends === true`.
- `ConfirmExtends` is false for finished views and at the cap.
- The Disclaimer sentence is true for every report Submit makes.
- `trust.js` is unchanged.

**Tests:** the amended Disclaimer pin keeps the old sentence as a must-not-contain, so it was not weakened. The `formatFade` pin now requires the flag check.
