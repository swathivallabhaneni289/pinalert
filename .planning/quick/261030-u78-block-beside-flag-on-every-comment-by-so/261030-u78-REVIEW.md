# Quick 261030-u78: Code Review Report

**Reviewed:** 2026-10-30
**Depth:** deep (diff d8c5733b..d2b00fd1, call chains traced into comments.go, people.go, people.sql, comments.sql, profile.go, account_username.go, app.js)
**Files Reviewed:** 23
**Status:** issues_found

## Summary

The server side is mostly sound. `blockPair` keeps Block's order (block row, then
`endFollowPair` blocker to blocked, then blocked to blocker, one `now`) and its exact error
text. `BlockableAuthor` maps every refusal, including `ErrReportNotFound`, to `ErrCommentGone`,
so the route has one 404. That 404 is written by the same `writeFieldError` call the like route
uses, so the bytes match. Blocks are ignored, so a commenter who blocked the caller answers 204
like anyone else. The router builds `comments` before `peopleOpts` (and replaces a nil
`deps.Comments`, so no typed nil reaches the interface). Both gate tables and the swagger row
carry the route. The license line reads "Unlicensed (all rights reserved)" once in each of
docs.go, swagger.json and swagger.yaml and in router.go:507. Usernames reach the page only
through textContent, `Pinalert.setText` and `setAttribute`. A clear reply is always listed
(Post refuses a reply to a gone parent, and moderation only moves pending to clear or removed),
so the route cannot reach a clear comment the list hides, except C4's blocked author placeholder,
which was accepted.

The one serious defect is the "pending username" residual. Its stated premise is false in this
codebase. The confirm box, docs/MODERATION.md and the SUMMARY all promise something the code
never does, and the block it creates cannot be undone from the UI. The other findings are an
oracle on the follow totals, a count mismatch in Settings, focus loss in comments.js, and
reload gaps.

## Critical Issues

### CR-01: Blocking a "New member" commenter cannot be undone, and the box and docs promise a recheck that does not exist

**File:** `web/static/js/comments.js:100`, `docs/MODERATION.md:244-248`, `internal/service/people.go:616-628` (BlockedPeople), `internal/service/people.go:599-609` (UnblockChanged), `internal/service/people.go:247-258` (the only clearing path)

**Issue:** The plan accepted T-u78-11 because "a pending name is checked again first on every
read, so it normally clears when the checker answers". The code does no such recheck:

- `MarkUsernameScreenClear` has exactly one caller, `SetProfilePublic` (people.go:253). It runs
  only when the owner of that name turns Let others follow me on.
- `AccountService.UsernamesFor` (account_username.go:97) only labels a name pending and has no
  production caller.
- `CommentsForReport` reads `a.username_screen` straight from the row (comments.sql:167).
- `saveUsername` (profile.go:651) returns early when the same name is saved again, so re-saving
  does not rescreen either.

A username saved pending (borderline, provider outage, spent quota, timeout) therefore stays
pending until its owner makes their profile public. That may never happen, and for a private
commenter it usually won't.

Failure scenario: Ben sees a comment by "New member" and taps Block. The box tells him "They show
in Settings, Blocked people, once their username is checked. You can unblock them there." He
confirms, and the route answers 204. `BlockedPeople` skips the row because its screen is not
clear. The profile Unblock (`UnblockChanged`) is keyed by a username Ben never saw. The commenter
has no public face, so there is no profile Unblock button. Ben now has a permanent block he
cannot see or remove, and their comments stay hidden from him. The block has also ended the
follows both ways and deleted the queued follow notes, so it cannot be undone silently. Three
texts state the false premise as fact:

- the box line at comments.js:100
- the MODERATION.md sentence "A pending name is checked again first on every read, so it normally clears when the checker answers"
- the SUMMARY residual paragraph

The acceptance of T-u78-11 does not stand, because its reason is wrong.

**Fix (fuller, preferred):** list a block whose name is not clear in Settings, Blocked people
under a neutral label ("Someone whose name is not shown yet"). Give it an unblock keyed on an
opaque per-blocker handle, for example a signed `blocked_id` or the `person_blocks` row's own key
if one is added. Never expose the pending username. Sketch:

```go
// BlockedPeople: keep pending rows instead of skipping them.
if r.UsernameScreen == nil || *r.UsernameScreen != UsernameScreenClear {
    out = append(out, PersonEntry{Hidden: true, Handle: s.blockHandle(accountID, r.BlockedID)})
    continue
}
```

**Fix (minimal, if the owner prefers):** make the box line and the doc tell the truth, and add a
backlog item for the fuller fix. For example, change the box line to "They may not show in
Settings, Blocked people, until their username is checked." Then fix MODERATION.md:246 to say
that a pending name clears only when its owner turns their profile on, so such a block can stay
unlisted and cannot be taken back from Settings until then.

## Warnings

### WR-01: Settings' Blocked count now routinely disagrees with the Blocked people list

**File:** `internal/store/queries/people.sql:338-345` (CountBlocked), `internal/service/people.go:632-643` (Counts)

**Issue:** `CountBlocked` filters on `a.deleted_at IS NULL AND a.username IS NOT NULL` but not on
`username_screen`. `BlockedPeople` skips every name that is not clear. Before this task a block
needed `publicFace` (screen clear), so a mismatch needed a rename after the block. Now every
Block on a New member comment raises the Settings count by one and adds nothing to the list
(see CR-01). Failure scenario: Settings reads "Blocked 3" and the list shows two names, with no
way to find or remove the third.

**Fix:** make the count and the list agree. Either add `AND a.username_screen = 'clear'` to
`CountBlocked`, or (with the CR-01 fuller fix) list the hidden rows so the count is right.

### WR-02: The follow totals tell the blocker that a "New member" commenter follows them, or is someone they follow

**File:** `internal/service/people_comment_block.go:37` (blockPair from a comment), `internal/store/queries/people.sql:217-224` (FollowCounts), `internal/service/people.go:632-643` and `:737-744` (totals shown in Settings and the lists)

**Issue:** `blockPair` ends the follows both ways. `FollowCounts` counts every active follow
(D-03: the totals include people shown only as a number), and Settings shows those totals.
Failure scenario: Ann has a public profile with 12 followers, 3 of them shown only as "and 3
others". She blocks a New member comment. Followers drops to 11 and "and 3 others" becomes "and 2
others", so she learns that the unscreened commenter follows her. Unblocking and repeating on
other comments narrows it further, limited only by the people action bucket. The same works on
Following. For a commenter whose clear name is shown this was already possible through
`remove-follower` by username, so that case is not new. For a pending or unscreened name, which
the feature promises to keep unlinkable, it is new: the block links the anonymous comment to a
specific follow relationship. The plan's threat table has no row for it, and MODERATION.md
does not mention it.

**Fix:** this is inherent in D-12 (a block ends follows), so it needs an owner decision. Either
record it as an accepted residual in MODERATION.md and the threat model, or, for an author whose
screen is not clear, refuse the comment Block with the same 404. That second option would drop
New member Block, which the owner asked for, so ask first.

### WR-03: Focus falls to the page body when the comment vanished or turned into a placeholder while the box was open or the request was out

**File:** `web/static/js/comments.js:183-189` (onBlockBoxClose), `:945`, `:957`, `:962` (sendBlock), `:735` (writeActions)

**Issue:** The 30 second poll keeps running while the modal is open, and `mergeRoots`
(comments.js:1201) can remove the rec or rewrite it as a placeholder. Then:

- **Cancel or Escape:** `onBlockBoxClose` focuses `asked.opener`. That node is either detached,
  or inside a `meta` row that is `hidden` on a placeholder, so focus is lost.
- **Block, then a 404 or a failure:** `sendBlock` calls `writeActions(rec)` and then
  `rec.block.focus()`. `writeActions` recomputes `rec.block.hidden` without looking at
  `deleted`, `removed` or `hidden` (line 735). That unhides the button inside a hidden meta row,
  and the focus call lands on an element that cannot be seen or reached.
- **The 404 path also calls `load()`,** which may remove the node.

Keyboard and screen reader users lose their place exactly when the action fails.

**Fix:** when the opener is not usable, fall back to the heading. Also make `writeActions` keep
Block hidden on a placeholder:

```js
function focusBlockOrHeading(rec) {
  if (rec.block.isConnected && !rec.meta.hidden && !rec.block.hidden) {
    rec.block.focus();
  } else {
    heading.focus({ preventScroll: true });
  }
}
// writeActions
var gone = data.deleted === true || data.removed === true || data.hidden === true;
rec.block.hidden = gone || mine || held || data.is_own === true || data.author_kind === 'deleted_account';
```

Use the same check in `onBlockBoxClose`. Store a `heading` fallback on `asked` when opening.

### WR-04: "The blocked person's words go at once" fails for middle pages and for list reads already in flight

**File:** `web/static/js/comments.js:971-979` (afterBlock), `:1201-1231` (mergeRoots), `:1482` (loadMore), `:1125` (rereadTail)

**Issue:** `afterBlock` calls `load()`. That rereads the first page and, once Show more was used,
the last page read (`loadTail`). `mergeRoots` removes stale roots only inside the range each
answer covers. Root pages between the first and the last are never reread, so the blocked
person's words there stay on screen. A later poll never clears them either. This needs more
than 100 top level comments (three pages at `CommentPageSize` 50), so it is rare during an
emergency but real.

Separately, `stopLoad` aborts only `inflight`. A `loadMore` or `rereadTail` request that left
before the block, and was answered before the block row was written, can land after the reload.
Its `mergeRoots` or `placeReplies` then puts the blocked person's words back until the next poll.

**Fix:** after a 204, either reset the list to the first page (`clearList()` then `load()`, as a
fresh open does), or reread every page up to `lastPageAfter`. Bump a generation counter that
`loadMore` and `rereadTail` check before writing, so their stale answers are dropped.

## Info

### IN-01: sendBlock has no busy guard of its own

**File:** `web/static/js/comments.js:942-950`

**Issue:** Only `onBlock` checks `rec.blockBusy`. The box's yes handler and the `window.confirm`
fallback both call `sendBlock` directly. The modal makes a second send impossible today, but a
future caller or a fast double tap through a box that closes before the click lands would send
two POSTs.

**Fix:** start `sendBlock` with `if (rec.blockBusy) { return; }`.

### IN-02: Refusal paths have different costs

**File:** `internal/service/comments_block_author.go:32-48`

**Issue:** An unknown id costs one query. A withheld or old report costs two or three. An own
comment or one by a deleted author costs the full report check. In principle the timing tells
"a comment with this id exists on a report you cannot see". Like and Flag already give that away
in their bodies (field report versus field comment), and the route is bucket limited, so this
adds nothing new.

**Fix:** none needed now. Note it in the threat model if the uniform 404 is ever relied on more
strongly.

### IN-03: Route refusal cases lack a positive control; one subtest asserts nothing about rows

**File:** `internal/api/handlers/comment_block_author_e2e_test.go:32-41`, `:72-79`, `:110-125`

**Issue:** `u78Report` seeds reports under an unbound session (`u78-seeded-session`). No clear
comment on a report seeded that way is shown to answer 204. If such a report were never listed
for an unrelated reason, the withheld, ended and Rescue 404 cases would still pass. The service
test does have a faded flood positive control on its own rig, so the rules themselves are
covered. The subtest "a commenter who blocked the caller still answers 204" checks only the
status, not that the reporter's own block row was written.

**Fix:** add one case where a clear comment on a `u78Report(t, e, "flood", "clear", time.Hour,
time.Hour)` report answers 204. In the subtest, assert the reporter to cat row exists.

### IN-04: An account deleted between BlockableAuthor and BlockAccount leaves an orphan block

**File:** `internal/service/people_comment_block.go:33-37`, `internal/store/queries/people.sql:315-317`

**Issue:** C2 refuses a deleted author, but the check and the insert are separate statements.
`BlockAccount` inserts with no `deleted_at` guard. A deletion that commits in between (it removes
blocks first) leaves a row that cannot be listed or removed (T-u78-06). The window is tiny.

**Fix:** `INSERT ... SELECT ... WHERE EXISTS (SELECT 1 FROM accounts WHERE id = blocked_id AND
deleted_at IS NULL)`, or accept it and note it under T-u78-06.
