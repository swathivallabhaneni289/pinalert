# Phase quick-261030-u78 Plan 01: Block beside Flag on every comment by someone else Summary

A signed in reader can now block the author of any comment they can see, private and pending profiles included, from a real Block button right after Flag; it runs through the same block tail as a profile block, answers 204 or one byte equal 404, and reloads the list so the blocked person's words go at once.

## What was built

1. Service (commit 79bdf3cd). `CommentService.BlockableAuthor` applies the Flag report check (`actOnComment`), then refuses a finished Rescue report, a deleted, removed or held comment, the reader's own comment and a deleted author account, every refusal as `ErrCommentGone`. `PeopleService.BlockCommentAuthor` calls it and then the new `blockPair` tail, which `Block` now uses too (block row first, follows end both ways with reason blocked through `endFollowPair`, queued follow notes of the pair deleted). A people service without the comment source refuses everything.
2. Route (commit e2107ef9). `POST /api/comments/{id}/block-author` behind the gate and `PeopleActionMiddleware`, no body or `{}`, 204, one 404 body for every refusal, 400 for a malformed id. Swagger regenerated with `make swag` (only docs.go, swagger.json, swagger.yaml changed; the license line is unchanged). `docs/MODERATION.md` has the Block beside Flag bullet and the three new test names.
3. Browser (commit 13bb9840). `comments.js` builds a `button.comment__block` right after Flag, with its own `.logout-confirm` box (`comment_block_confirm.html.tmpl`, included in `index.html.tmpl`), the owner's two lines, one POST from the box's Block button only, a toast, focus on the comments heading and an immediate list reload. CSS: `.comment__block` joined Flag's shared rules in comments.css and phone.css.

## Choices (Claude's discretion, C1 to C6)

- C1. The uniform 404 is the comment not available body (field comment, `CommentGoneMessage`, no-store), byte equal to the like route's answer for a deleted comment; a report the reader cannot see gets the same body, so the route has one refusal.
- C2. A comment whose author account is deleted is refused with the uniform 404 and shows no Block button, since account deletion removes blocks and a later row could never be listed or removed.
- C3. Block stays available on a report whose comments are closed, as Flag does (a safety action).
- C4. An existing block answers 204 with no special case; a clear comment of someone already blocked also answers 204 (low accepted residual T-u78-07).
- C5. For a name not shown (new_member) the box second line says the person shows in Settings, Blocked people once their username is checked.
- C6. A 404 reloads the list and shows no toast; 429, other failures and offline show the existing calm error line and change nothing.

## Rule and spec notes

- 09-UI-SPEC item 17 (commenter names stay plain text) holds: the only addition to a comment is the Block button.
- The comment box uses the owner's own lines, not the profile box lines of 09-UI-SPEC.
- Accepted residual (T-u78-11, also in docs/MODERATION.md): a block on a commenter whose username is still pending shows in Settings, Blocked people only once the name clears, because D-16 never lists an unscreened name. A pending name is checked again first on every read, so it normally clears when the checker answers. A name that never clears leaves that block in place and not listed, which is the safe direction, since it only hides that person's comments from the blocker. No new route was added for it.
- Docs grep (`git grep -n -i block -- web/templates web/static/js docs`): no line says Block exists only on a profile, so TRUST-MODEL.md, PUSH.md and the Policy needed nothing; the Policy date and `CurrentTermsVersion` stay at 2026-10-29.
