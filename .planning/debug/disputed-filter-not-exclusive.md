## Resolution

root_cause: "internal/service/feed.go's Visibility.ListableInFeed(includeDisputed bool) (lines 43-54) implements an ADDITIVE filter, not an exclusive one: for VisibilityLive and VisibilityProvisional it returns true unconditionally, regardless of includeDisputed — only VisibilityHidden's return value depends on includeDisputed. report.go's Nearby() (line 451) calls this once per report as the sole visibility filter for GET /api/reports (its only production call site — ReportsByAccount/Activity has no visibility filter at all and cannot be affected); there is no other filtering anywhere else in the request path (SQL carries no visibility predicate by design; the JSON handler in reports.go only parses the flag and passes it through; feed.js/app.js/map.js render the server's array verbatim with zero client-side filtering, and map.js's marker-reconcile loop already clears stale pins correctly on an empty result). The result: when show_disputed=true, the feed returns Live + Provisional + Hidden (everything except Retracted) instead of Hidden alone, so a freshly posted, entirely un-disputed report (which resolves to Provisional via service.Resolve) is included in the 'disputed' view exactly as the user reported. This is a deliberate, documented, and TESTED contract as of the current code — not a stray wiring bug — asserted in FOUR places: feed.go's own ListableInFeed doc comment, 02-RESEARCH.md's data-flow diagram ('?show_disputed=true adds {Hidden}', lines 168-169), and two test suites (feed_test.go's TestListableInFeed/TestNearbyHidesDisputedUnlessRequested, and the HTTP-level feed_visibility_e2e_test.go's TestShowDisputedRevealsHiddenReports, whose own assertion message reads 'the toggle should add reports, not replace the view'). D-10/D-11's actual LOCKED TEXT in 02-CONTEXT.md does not itself mandate additivity — it only requires Hidden reports to be reachable via the toggle — so the additive reading was carried into 02-RESEARCH.md's diagram and feed.go's implementation/tests, one layer below the locked decision itself; fixing this does not conflict with D-10/D-11's own wording. The toggle's rendered label ('Show disputed reports', pinned verbatim by 02-UI-SPEC.md's Copywriting Contract) needs no wording change — it already reads accurately under exclusive semantics, arguably more accurately than under the current additive one. The UAT gap doc already records the user approving this exact reversal twice (2026-09-18 backlog 999.2, repeated and approved 2026-09-21/22)."
fix: "NOT IMPLEMENTED (goal: find_root_cause_only). Suggested direction: change ListableInFeed's switch so the Live/Provisional case also branches on includeDisputed — return true only when !includeDisputed, matching Hidden's existing includeDisputed-gated case; Retracted stays false unconditionally (D-12, untouched). Concretely: `case VisibilityLive, VisibilityProvisional: return !includeDisputed` and `case VisibilityHidden: return includeDisputed`. This makes the toggle a true partition: exactly one of the two views contains any given non-retracted report, never both, never neither. Note the pre-existing, unaffected interaction this creates visibility into: a critical/rescue_needed report disputed past the threshold still resolves to Live (D-06's critical-bypass rung sits above the dispute rung in Resolve), so it will never appear in the disputed view even when heavily disputed — worth a one-line callout in the fix so it isn't mistaken for a new regression. Accompanying changes needed (not just the one function): (1) feed_test.go's TestListableInFeed — flip the 'included' cases for Live/Provisional to want=false; (2) feed_test.go's TestNearbyHidesDisputedUnlessRequested — rewrite the two subtests asserting report 2 (unvoted/Provisional) and report 3 (Live) stay present under includeDisputed=true to instead assert they are ABSENT, updating their names/comments off 'the toggle adds Hidden reports, never removes Provisional ones'; (3) feed_visibility_e2e_test.go's TestShowDisputedRevealsHiddenReports — flip the controlID assertion to expect absence under show_disputed=true, and correct its doc comment; (4) feed.go's own ListableInFeed doc comment (lines 30-42), which currently documents additive behavior by name, including the 'likely future mistake' warning that (ironically) anticipated the wrong confusion; (5) 02-RESEARCH.md's data-flow diagram (lines 168-169), which states the additive contract in its own ASCII sketch and needs the matching one-line correction; (6) reports.go's swagger @Description/@Param text (lines 305-306, 315) to state the view becomes exclusive, then regenerate docs/docs.go + docs/swagger.json/yaml via the swag toolchain (do not hand-edit the generated files). NOT needed: the toggle's own rendered copy ('Show disputed reports', template lines 38-40 / 02-UI-SPEC.md line 290 / asserted verbatim by votes_contract_test.go:1110) — this text is unchanged by the fix and already reads correctly under exclusive semantics; the Activity/profile page and its ReportsByAccount query — untouched, no visibility filter to begin with; map.js — its existing marker-reconcile-by-id loop already clears all pins correctly when the disputed view legitimately returns zero reports. Once fixed, the UAT's own retest note (Test 9, 02-UAT.md lines 173-180) should be re-run: with a live report present, the disputed view will now be empty, making the reload-persistence and no-unfiltered-flash halves of Test 9 easy to judge for the first time."
