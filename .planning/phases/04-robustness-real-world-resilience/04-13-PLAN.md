## Phase Goal

**As a** person reading or reporting during an emergency, often on a weak phone connection, **I want to** keep reading, posting and confirming reports when the signal is bad, knowing abusive posts are screened out and that the site says plainly it is unofficial, **so that** the reporting loop keeps working and I am not misled about what Pinalert is.

**This plan's step (MVP slice S4 "weak network main page", first plan):** after this plan, on a weak connection the main page keeps its list and says "Last updated N minutes ago" instead of the "Couldn't load reports" panel, a stalled poll times out after 10 seconds, and when the list has not loaded in about 6 seconds a notice says "Taking long? Open the low data view." even when unpkg hangs (D-17, D-20, P4-A12, P4-A19, P4-A24). Before this plan a failed poll with rows on screen kept the rows but showed the full "Couldn't load reports" panel with Retry below them (a failed tab, chip or place change cleared the list down to that panel; after this plan it still clears the list, with the stale line in place of the panel: rule C4), a stalled request hung forever, and a hung unpkg left a blank page with no way out.

**Accepted interim states (MVP framing, no human check runs before 04-27):**
- The link "Open the low data view." targets `/low`, which 04-18 (wave 5) serves; until then it answers 404, as 04-06 accepted for `/disclaimer`.
- The card's hide rule already reads `html[data-modal-open]`, which only `Pinalert.lockPage` (04-19, wave 6) sets. Until then the open report form's backdrop (z-index 1100) paints over the card (z-index 1000).
- The card's Queue row ("{N} waiting to send." with "Show waiting reports") needs `queue.js`, which 04-22 (wave 7) creates; 04-22 inserts it between `#notice-slow` and `#notice-stale` with the class `notice-card__row` and follows the re-sync rule below. The Waiting to send strip also goes above `#feed-stale` in 04-22, so the list pane order below the Phase 3.1 blocks is `p#filter-line`, the queue strip, `#feed-stale`, `#report-list` (03.1 hand off); the tab strip, `#feed-status`, the heading, `#feed-note`, `#place-line` and `#filter-line` above them are not touched.

## How the new rules compose with the built store (Phase 3 review rounds 1 to 3)

The built `fetchReports(options)` in `app.js` already carries four mechanisms from the Phase 3 review fixes (`03-REVIEW-FIX.md`, `03-REVIEW-FIX-2.md`, `03-REVIEW-FIX-3.md`), which Phase 3.1 plan 05 widened from the disputed boolean to the tab, the chip and the centre. Each is pinned by an existing test that this plan runs unedited, and none of them moves:

- **Applied marker.** `fetchSeq` numbers every call. `lastAppliedSeq` is set in exactly one place, the success write, and a failure never moves it (`TestFetchReportsDropsOnlyResponsesOlderThanTheLastApplied`).
- **Write floor.** `writeFloor` is raised when a call made with `{ afterWrite: true }` starts (`votes.js` `onControlsClick` and `submitReport` pass it; the 30 second poll, Retry now, a tab press, a chip, a place pick or Back to my location, the back forward cache listener and `map.js` pass nothing). `isStale()` drops any response below it. The poll skips while the view is `past`.
- **Stale guard.** `isStale()` is `return mySeq < lastAppliedSeq || mySeq < writeFloor || sentView !== state.view ||` followed on the next line by `sentCategory !== state.category || sentLat !== state.center.lat || sentLon !== state.center.lon;` (Phase 3.1 plan 05). Both handlers test it first and return `whenFresh()`, which is `undefined` when newer data is already applied and otherwise the newest call's promise (`newestFetch`), so a dropped call resolves only once the store is fresh.
- **Tab drop** (called the Show disputed drop before Phase 3.1). The success write records `rowsFor = { view: sentView, category: sentCategory, lat: sentLat, lon: sentLon };`. A failure that is not stale empties `state.reports` (and `state.recent` and `state.cut`) when `if (!rowsMatchStore()) {` holds, so rows never sit under a tab, chip or place they do not match (`TestFeedErrorStateKeepsStaleRows`).

The new rules sit on top of them. Each is pinned by `TestFetchReportsBackgroundRefreshAndTimeout` or `TestFeedRenderKeepsRowsOnError` and shown by the Node sandbox runs in Tasks 1 and 2:

| # | Rule |
|---|------|
| C1 | `state.hasLoaded = true;` and `state.lastUpdatedAt = Date.now();` are written once each, in the success write, after the stale test and after `lastAppliedSeq = mySeq;`, before the final `notify();`. A response dropped as stale sets neither: the list on screen did not change, so neither did its age. Both use the device clock, never `nowMs()`, because the stale line measures an interval on one clock. |
| C2 | A timeout, an abort or any other rejection that is not stale is a failed poll: `status = 'error'`, `error = err`, `notify()`, plus the tab drop when it applies, and nothing else. It moves none of `lastAppliedSeq` (the one `lastAppliedSeq = mySeq;` stays in the success write), `writeFloor` (raised only when a call starts), `hasLoaded` and `lastUpdatedAt`. No branch tests the error's name: a `TimeoutError` (native signal) and an `AbortError` (fallback) are ordinary rejections. The rows stay, so the stale line shows with the old `lastUpdatedAt`, and an older call still in flight can still apply later. |
| C3 | A response that `isStale()` drops is neither a failed poll nor a good one: no status change and no `notify()`, so `render` does not run and the stale line neither appears, nor changes, nor announces. That covers the late timeout of a call newer data already replaced, of a call older than the write floor and of a call sent for another tab, chip or centre. |
| C4 | The tab drop leaves `hasLoaded` true and `lastUpdatedAt` unchanged, so P4-A19 holds as written: a list had loaded, every later call is a background refresh and the first load panel does not return. `render` then shows the stale line, hides the list, clears the rows through `clearRows()` (focus restored) and draws no empty state, because after a failed fetch the page cannot say the list is empty. The same holds for a loaded empty list whose next poll fails: the stale line shows and its empty state waits for the next good poll. |
| C5 | A timed out refetch after a write leaves the write floor raised: an older poll that lands later is dropped, the store stays in `error` and `votes.js` shows its saved but not refreshed sentence. The 10 second limit also bounds how long `votes.js` and `submitReport` wait, since they wait on `fetchReports` or on the newest call through `whenFresh()`; before this plan that wait had no limit. |
| C6 | `isBackgroundRefresh` keeps the Phase 3 line `state.status === 'ok' \|\| state.reports.length > 0` and then widens it with `if (state.hasLoaded === true) { isBackgroundRefresh = true; }`. The widening adds the two cases the Phase 3 line misses, both with no rows on screen: a loaded empty list whose poll failed, and a list the tab drop emptied. Every call counts, `afterWrite` calls and filter changes included, and only a call made while `hasLoaded` is false enters `loading`. |
| C7 | The 10 second limit starts when the request is built and covers the wait for the headers and for the body. The signal travels in `url = new Request(url, { signal: signal });`, so the call stays `pending = fetch(url)`. With the fallback, the abort timer is cleared first thing in both handlers, before the stale test, so a stale response clears it too. |
| C8 | Retry now calls `Pinalert.fetchReports()` with no options, so it never raises the floor. The stale branch and the leave branch of `renderStale` both leave the button enabled. A dropped response runs no render, so the button can stay disabled until the newest call settles; that call always ends in a `notify()`, at the latest after 10 seconds, so the button is never left disabled. |
| C9 | The enter announcement is made once, on the transition into the stale state, and a further failure while stale announces nothing. The leave announcement is made once, on the transition from `error` to `ok`. The 60 second figure refresh and a dropped response announce nothing. |
