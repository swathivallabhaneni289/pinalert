## Phase Goal

**As a** person reading or reporting during an emergency, often on a weak phone connection, **I want to** keep reading, posting and confirming reports when the signal is bad, knowing abusive posts are screened out and that the site says plainly it is unofficial, **so that** the reporting loop keeps working and I am not misled about what Pinalert is.

**This plan's step (slice S7 "flag and moderate", its first plan):** after this plan, a signed in person can flag someone else's report once with one of five reasons through `POST /api/reports/{id}/flag`, limited per account, never hiding it, with own report 403, withheld or missing 404 and repeat 409, and the feed tells each viewer which reports they already flagged. Before this plan a reader had no way to send a bad post to the moderators at all. 04-23 then gives the moderator the Flagged list built from these rows, and 04-24 puts the "Flag this report" control and dialog in the opened report (the popup, in every Phase 3.1 tab) and on the Low data row on top of this route; a main page list row holds no control since Phase 3.1 (P4-A7 amended).

<objective>
Build the server half of the Flag control (ROBUST-09, ROBUST-04; D-09, D-10, D-11, D-12, R-01, R-04): the flag service and its copy, the gated and rate limited flag route, the per viewer `viewer_flagged` marker on the feed, and the published API reference for all of it.

Increments, task by task:
- After Task 1: the flag rules are provable in isolation. Five reasons, labels and four messages exist once in package `service`; `FlagService.Flag` refuses a bad reason, a missing or withheld report, your own report and a repeat, in that order, and can only read the vote context row and insert a flag row.
- After Task 2: a signed in person can flag through the real router: 201, 400, 403, 404, 409 and a 429 with the exact wait, keyed on the account, with the backstop when configured; a flag provably changes nothing a reader sees. Proven end to end on `p4_0420`.
- After Task 3: each viewer's feed says which reports they already flagged (the author is never told), and the flag route, its two bodies and `viewer_flagged` are in OpenAPI with a drift guard.

Purpose: D-09 lets the people nearby send a bad post to the owner without giving any group the power to hide a real emergency (a flag only queues it); D-11's roomy flag allowance only stops one account flooding the moderator screen.

Decisions this plan settles (the outline leaves them open; each is recorded in the SUMMARY and the owner can veto it):
1. **Gate shape.** A route scoped `r.With(<gate>.FlagMiddleware())`, the same shape as `VoteMiddleware`: the IP backstop first (through the shared helper), then the flag bucket keyed `acct:<id>`. Every admitted attempt costs one token and **nothing is refunded**, matching the vote bucket's reasoning (RESEARCH Area C item 4: each attempt costs a `ReportVoteContext` read). D-11 left the flag limit to Claude's discretion; a 409, 404 or 400 therefore costs a token, which the burst of 10 absorbs.
2. **Expired reports can be flagged.** The pinned 404 is "missing or withheld" only; D-08 Remove works on any post; and the dialog reads 409 as "already flagged" (UI-SPEC "Dialog states"), so an expiry refusal would mislabel the control. A Phase 3.1 Past row can therefore be flagged.
3. **Check order.** Reason, then the context read, then withheld, then own report, then insert. Withheld before own means an author's own held or removed report answers 404 like any missing report, the same order 04-07 gave `CastVote`.
4. **400 shapes.** A missing or unknown reason (including `{}`) is 400 field `reason` with `service.FlagReasonMessage`; a body that is not JSON, has an unknown key, has a wrong type or exceeds the cap is 400 field `body` with the existing decode sentence every JSON handler already writes; a bad path id is `parseReportID`'s existing 400 field `id`.
5. **Copy.** The four server messages reuse the dialog's own wording where the dialog has one (Copywriting Contract "Flag this report"), so two wordings cannot exist: 400 is the Validation line, 404 the Report gone outcome, 409 the Already flagged outcome; 403 has no dialog counterpart (the control is never shown on your own report).
