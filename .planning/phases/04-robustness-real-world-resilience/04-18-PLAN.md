# Plan 04-18: Read the Low data view

## Phase Goal

**As a** person reading or reporting during an emergency, often on a weak phone connection, **I want to** keep reading, posting and confirming reports when the signal is bad, knowing abusive posts are screened out and that the site says plainly it is unofficial, **so that** the reporting loop keeps working and I am not misled about what Pinalert is.

**This plan's step (MVP slice S5 "Low data view", after 04-10):** a signed in person can open `/low`, a text only page with no map that lists Active reports at once from the last known position using the same trust block and rows, remembers the choice per device and redirects a bare `/`, under the asset policy (no map library, raster image or web font) with response compression (D-13, D-14, D-16 reading, D-17 cookie, R-08, R-09, P4-A14, P4-A22, orchestrator decision 2). Before this plan the only way to read reports was the map page, which waits for Leaflet and MapLibre from unpkg; after it a person on a weak connection can read the Active list without a single map byte.

## Decisions recorded in this plan

- **Open item 1 default kept:** route `/low`, cookie `pinalert_low_data`. **Open item 4 default kept:** position timeout 8 seconds (as `map.js`), Low data poll 60 seconds. **Open item 25 default kept:** client rendered rows, `low.js` with its own row function over the shared builders.
- **Secure flag:** `requestIsHTTPS(r)` is `r.TLS != nil` or `X-Forwarded-Proto` equal to `https` (case insensitive). The hosting proxy terminates TLS, so `r.TLS` alone would never set the flag in production; the header only decides how strict the person's own preference cookie is and is never used for any authority decision, so a forged value only affects the forger.
- **Redirect order in `Page`:** `full=1` is checked first (clear and go to `/`), then the bare `/` cookie redirect; any other query string renders the main page. `RawQuery == ""` is the bare test.
- **Fetch ordering on the Low page:** `showListFor` sets the store centre immediately (so votes and polls use the newest position) and chains its own `Pinalert.fetchReports()` after the previous Low data request settles, so a slow response for the stored position can never overwrite the list for the fresh position. `app.js` is not edited (04-17 owns it this wave).
- **Focus fallback after a poll removes the focused row's last neighbour:** `#low-report` when it exists (04-19 adds it), else `#low-full`.
