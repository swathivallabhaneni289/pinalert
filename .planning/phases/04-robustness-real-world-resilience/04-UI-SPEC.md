# Phase 4: UI Design Contract

> Visual and interaction contract for Phase 4: the disclaimer bar, the Disclaimer and Policy pages, the Low data view and its ways in, the offline queue, submit outcomes (rejected, held, removed, rate limited), the Flag control and the moderator screen. Generated by gsd-ui-researcher, to be verified by gsd-ui-checker.

---

## Source of Truth and Scope

**Scope source:** `04-CONTEXT.md` (D-01 to D-24, R-01 to R-10 locked, Deferred Ideas out of scope). The Phase 4 entry in `ROADMAP.md` and `REQUIREMENTS.md` is stale and is not used for scope. Every surface below is specified fully: the cut order in `04-CONTEXT.md` is only the planner's suggestion.

**Token source of truth:** `web/static/css/main.css` and the approved `03-UI-SPEC.md` (Design System, Spacing Scale, Component Geometry, Typography and Color sections). This contract carries them forward by pointer and does not restate them. Phase 3 is approved but not built, so this contract plans against the Phase 3 design (`trust.css`, `trust.js`, the popup card, the shared severity label, `--shadow-popup`) as well as against today's code. Where today's code differs from Phase 3 the Phase 3 design is assumed to ship first.

**Format baseline:** `03-UI-SPEC.md`. Amendments are numbered P4-A1 and up so they never collide with Phase 3's A1 to A74. A plain "A60" or "A65" in this document always means the Phase 3 amendment of that number.

**Inputs read for this contract:** `04-CONTEXT.md`, `03-UI-SPEC.md`, `03-CONTEXT.md` cross phase hand offs, `01.1-UI-SPEC.md` (login page, account menu, verify outcome), `01-UI-SPEC.md` (report modal, feed row, tokens), the sketch findings skill (popup structure and trust block), the Phase 3.1 and 3.2 entries in `ROADMAP.md`, `PITFALLS.md` (Pitfalls 3, 6, 8 and the 429 copy row), `PROJECT-NOTES.md` lines 84 to 102, and the shipped templates, CSS, JS and `web/*_contract_test.go`.

**Sample data rule:** every number, name and sentence quoted in an example is sample data unless it is marked as exact copy. Real values come from the server and from the one numbers setting (D-22). The browser holds no threshold, no allowance and no trust formula.

**Stack:** Go `html/template`, vanilla JS, hand written CSS. No framework, no build step, no new library. Tool: none.

**What this phase designs, in order:**

1. The disclaimer bar and the top chrome wrapper that carries it (every full page).
2. The Disclaimer page and the Policy page (public).
3. The Low data view (its own page, text only, post and vote).
4. Ways in to the Low data view, the remembered device choice and "Open full version".
5. The offline queue ("Waiting to send"), the queued row states, the "Written 4 hours ago" label and the "Last updated N minutes ago" stale list state.
6. Submit outcomes: rejected text, held, removed after review, and the rate limit message for reports, votes, vote changes and the Flag control.
7. The Flag control (the quiet control in the popup, the list row and the Low data view) and its dialog.
8. The moderator screen.
9. The cross cutting contract: state matrix, interactions, copy, motion, accessibility, hand off.

**Not designed here:** comments and the report page (Phase 8), official feeds and demo mode (Phase 5), an installable app, service worker or Web Push (backlog 999.3), the author deleting their own report, image screening, account sanctions, state aware helplines. All are in Deferred Ideas. There is no police message and no police feature inside any flow (D-09): police guidance is plain text on the two legal pages only.

## Rules this contract must obey (standing rules)

These are the owner's saved rules for this repository, quoted so the planner and executor see them. They bind every section below.

1. **Read only research.** The UI researcher writes only this file. Nobody runs the Go test suite against `pinalert_test` or `pinalert` (the suite truncates them and they hold the owner's manual testing data). Use a disposable database, never ports 8080 or 8090, and tell every subagent.
2. **No images in the repository.** No screenshots, no PNG or other image exports. Check visuals in a browser or with computed style probes.
3. **No em dash and no en dash anywhere**: not in contract prose, not in user visible copy, not in notes or return messages. Use a comma, a colon, a period or parentheses. Hyphens inside identifiers, file names, slugs and CSS class names are fine.
4. **The site must never look vibe coded.** Never specify: purple gradients or gradient heavy backgrounds; pill shaped buttons (rounded rectangles with a modest radius are fine; round icon badges and slider tracks are not pill buttons); fake reviews, testimonials or invented numbers or metrics of any kind; hero text of any kind (no headline or tagline block above the app); emoji used as icons (use SVG icons or plain text); scroll triggered or showy animation (transitions stay short and restrained: hover, press, focus, state change).
5. **The Low data view is never called "light" or "lite"** in any name or copy (class names, file names, route names, comments, strings), because the Light and Dark theme toggle owns those words. A grep test over the new templates, CSS and JS is part of the hand off.

Additional rules carried from the project: no `!important`; every new `display` rule on an element that can carry `hidden` has `:not([hidden])` in its head (the repo's standing trap, Phase 3 A35); every report authored string reaches the DOM through `Pinalert.setText` and never a markup parsing sink (Phase 1 T-01-03, D-05); geometry is written as `var(--space-*)` tokens and `var(--touch-target-min)` (Phase 3 A53).

## Vocabulary (one word, one meaning)

The word "report" already means three things in the product. This table fixes them so copy and accessible names never blur them.

| Word or phrase | Means | Where it appears |
|----------------|-------|------------------|

| device | the phone, tablet or computer the person is using. User strings say "this device", never "this phone", because the same strings show on the desktop column and match the Policy page and D-17 | strip lines, toasts, signed out row, Low data note, login panel note |

## Component Geometry

Geometry, not spacing. Every padding, gap, margin, inset and offset is written as the matching `var(--space-*)` token and every 44px minimum as `var(--touch-target-min)` (Phase 3 A53). The px figures are resolved values only. Allowed dimension literals with no token: the 360px notice card cap, the 420px login panel cap (the width of `.login-card`), the 640px page frame (also the Low data view and moderator screen frames), the 20px native radio, 1px hairlines, 8px radii and the 4px severity bar. Everything else is a token or a calc of tokens.

### The bar token

```
:root                           { --disclaimer-bar-height: calc(var(--space-xs) * 2 + var(--font-size-label) * var(--line-height-label) * 3 + 1px); }   /* 67.8px, 3 lines */
@media (min-width: 480px)       { :root { --disclaimer-bar-height: calc(var(--space-xs) * 2 + var(--font-size-label) * var(--line-height-label) * 2 + 1px); } }   /* 48.2px, 2 lines */
@media (min-width: 900px)       { :root { --disclaimer-bar-height: calc(var(--space-xs) * 2 + var(--font-size-label) * var(--line-height-label) + 1px); } }   /* 28.6px, 1 line */
```

The tiers are the line caps at default text size and the system font stack: **3 lines below 480px (at 320px and 360px), 2 lines from 480px to 899.98px, 1 line from 900px up.** At 320px the bar text area is 304px wide (8px side padding), which holds the roughly 110 character line in 3 lines with room for a wide system font. The 1 line tier starts at 900px so it matches the two pane breakpoint and leaves 868px for the line. The token is the bar's `min-height` (never `height`), so a longer wording or larger text makes the bar taller instead of clipping. Because the account trigger is positioned from the bar's own bottom edge (P4-A1), a taller bar never overlaps it. What a taller bar can do is make the map and the login page taller than the viewport (the token is smaller than the real bar), which scrolls the page by the difference.

**Measured at larger text (same arithmetic, estimates for the planner to replace with real figures in V-42).** The 14px label scales with the text size, the line height stays 1.4, the sentence is about 113 characters at about 0.5em per character, and the bar adds two 4px paddings and the 1px border. At 320px wide the text area is 304px. At **150 percent** text (21px, 29.4px lines) the sentence needs about 5 lines, so the bar is about 156px (4 lines would be 126.6px) against the 67.8px token, and the map page scrolls by about 88px. At **200 percent** text (28px, 39.2px lines) it needs about 6 lines, so the bar is about 244px against the 67.8px token (about 43 percent of a 568px screen, and nearly all of a 256px tall one); at 360px wide (344px text area) it needs about 5 lines and 205px. The 200 percent figure is an **accepted exception to "thin"**: D-21 says the bar is always visible and not closable, so it cannot be shortened or dismissed. A non sticky bar at large text or on short viewports is the alternative, listed in Open items as an option and not applied here. Because the token stays the contract at default size, the account menu does not size itself from it (P4-A11) and `scroll-padding-top` is set from it (P4-A25).

### Plain button states (P4-A28)

## Surface: Offline Queue and the Stale List (D-18 to D-20)

**Focal point:** the "Waiting to send" heading and its Send now button. **Hierarchy:** the strip comes before the list, because a saved report is the person's own data at risk, then the stale line, then the list. It is a website feature only: no service worker, no installable app, no push (D-18). The queue works while the page is open, or the next time it is opened with a signal. Votes, vote changes and flags are never saved for later (a vote needs a live position and the report may have changed, D-18; a flag is online only, D-09). Only a new report can be saved.

### When a report is saved

**One rule decides what queues a report, everywhere in this contract (D-18, real request outcomes, not `navigator.onLine`):** a failed request with no HTTP answer, a 10 second timeout, or a 502, 503 or 504 queues the report, and so does the person tapping **Send after the wait** on a form blocked by a 429 (below). Every other answer, including a 500 with a body, keeps the form open with its message (Submit Outcomes). On saving after a failed request, the form closes and the toast reads **"No signal. Your report is saved on this device and will send when you're back online."** (6 seconds, P4-A12). The queue retries when the page gets an `online` event, when the page loads, on a timer (default every 30 seconds) and on Send now. A saved report never expires and is never discarded for age (D-19). It keeps trying until it sends or the person discards it. The server stamps `created_at` and `expires_at` when the report arrives (R-05), so the normal expiry starts at upload.

**What a retry from the queue does with each answer** (the same rule, applied to a saved row): no answer, timeout, 502, 503 or 504 leaves the row waiting and it retries (status "Pinalert didn't answer. Trying again." for the three 5xx codes, "Waiting for a signal." for no answer or a timeout); 429 makes the row Blocked; 401 makes the row "Sign in again" (below); a repeated request id means the server already has the report, so the row is **treated as sent** (the row leaves the strip and the toast reads "Report sent.", never "Not sent"); every other answer, including a 500 with a body, makes the row Rejected with the server's message and it is never retried by itself.

**Send after the wait (owner decision, 2026-10-05).** When the server answers 429 to a report submitted from the open form (the main page form or the Low data form, they share it), the form stays open with the limit message and the typed text (D-12) and also offers the secondary button **Send after the wait** (`#send-after-wait`, a 44px outlined `.btn` directly under `#form-error`, hidden otherwise by the `hidden` attribute, which the `.btn[hidden]` rule in `chrome.css` makes effective, see CSS rules to keep). It exists only for report submissions: votes, vote changes and flags are never saved for later (D-18, D-09). Tapping it saves the report to the device queue as a Blocked by a limit row (Queued rows below, with the 112 link for a serious report), closes the form, shows the toast **"Report saved on this device. It will send when the wait is over."** (3 seconds) and returns focus to the control that opened the form. The row then lives in the Waiting to send strip and on the Activity page like any saved report, with Discard report, and retries by itself when the wait is over (D-12, D-18). The honest limit below applies unchanged (it sends while the page is open, or the next time it is opened). The request id (R-05) is created when the report is first submitted from the form, so the later retry from the queue can never insert twice.

A saved report belongs to the account that wrote it (D-20). The key is a **stable account id rendered by the server** (`data-account-id` on the page shell element: `id="app-shell"` on the main page and the Low data view, the `<main class="profile-page">` element on the Activity page), stored on each row by `queue.js` and compared on every read. It is never the email text (the templates expose only the email as text) and is never shown. A different person who logs in on the same phone **never sees it, is never offered it, and is not told it exists**: it is not drawn, not counted and not announced. It stays on the phone until its author logs in again and it sends, or the author discards it. The Policy page says saved reports stay on the phone until sent or discarded, unless the browser clears them (the honest limit below).

**More than one tab.** `queue.js` runs on three page types and IndexedDB is shared, so two open tabs could both flush the same row and each show "Sending.". A send takes a guard first: the Web Locks API (`navigator.locks.request` with `ifAvailable`) where it exists, otherwise a persisted sending lease written on the row (a "sending until" time a little past the 10 second request timeout, read and checked before a send starts). A row held by another tab's lease shows "Sending." and is not sent again by this tab. The server request id keeps even a missed guard from inserting twice (R-05), and a repeated id answer is read as sent (above).

**Honest storage limit (D-20).** Browsers can still delete saved data (private browsing closing, very low storage, Safari removing a site's storage after about 7 days without use). The page asks the browser to keep the storage. When saving to the device fails (a browser that blocks it), the report is kept in memory only and the strip says so: the help line becomes **"This browser can't keep reports for later. Keep this page open until they send."** and the save toast becomes "No signal. Your report is kept on this page only. Keep the page open until it sends.". The Policy page states the same limit in its cookies and storage list.

Copy tests: the Go side test covers the server composed form messages (up to "Your text is still here.", with the serious wording for a serious post) and asserts the 429 body fields (a serious post carries `serious: true` and the number); a JS copy test covers the queue status table and the appended sentence (dash free, plain character set with the straight apostrophe allowed, the 112 sentence present only for the serious variant, the number taken from the body, built as a link by DOM calls with `href` equal to `tel:` plus that number). The live announcement and the V-42 check cover the queued row too (below).

**Discard report.** Tapping it replaces the buttons with an inline confirmation in the row (Phase 3 A16 pattern): the question "Discard this saved report? It won't be sent." (16px), then **Keep saved report** (neutral, first in the DOM and on screen, takes focus) and **Yes, discard report** (destructive fill, P4-A17). A named group (`role="group"`, `aria-labelledby` on the question). Escape closes it and returns focus to Discard report (P4-A5). After a confirmed discard the row leaves, the toast reads "Saved report discarded.", and focus follows the rule below.

**Edit and resend.** Opens the report form prefilled with the saved category, severity, description, location and shelter fields, with a note under the title: "Not sent. {REASON}" (the reason already says what to do, so there is no second instruction; `.inline-note` look, no role). Posting from the form replaces the saved row. Closing the form without posting leaves the saved row as it was. On the main page and the Low data view the form is the one on that page. On the **Activity page there is no form**: Edit and resend is a link to the page that has one (the Low data view when this device's default is the Low data view, otherwise the main page) with the saved report's id in the query, and that page opens the form prefilled. The saved row stays in the strip until it is replaced or discarded.

**Focus.** After a row leaves the strip, if focus was inside it: the next row's first button, else the previous row's first button, else (the strip is gone) the first report row of the list, else the Report an emergency button. A poll or a state change never moves focus.

### Written 4 hours ago (D-19, P4-A8)

A report sent more than 30 minutes after it was written carries a second meta line under "{Category} · {time}": **"Written 4 hours ago"** (the figure is sample data: the word "Written " plus the shipped `Pinalert.relativeTime` string of the written time, so a shorter gap reads "Written 45 min ago", the helper is not changed). ### The stale list on the main page (D-20, P4-A19)

When the signal drops, or a list poll times out (P4-A19: a 10 second timeout, so a stalled connection is also a failed poll), the list stays on screen. In the list pane, directly above the list (below the strip): a stale line, 14px, the **`.inline-note` look** (neutral `--color-text` left border, no alert icon, no role: it is passive text and `#notice-live` announces the change): **"Last updated 4 minutes ago. Trying again."** with a 44px **Retry now** button beside it (wrapping under at 320px). The figure refreshes every 60 seconds without a live announcement. The exact time format is the one in the Low data view section (the stale line spells out "minutes", the row meta uses the shipped "N min ago").

### Announcements (`#notice-live`, polite)

Announce only on transitions, never on a timer: the first save ("1 report waiting to send."), each result ("Report sent.", "Report not sent. {REASON}", and a row becoming blocked, by a retry or by Send after the wait: "Report waiting to send. It will send by itself in {WAIT}." with "In an emergency, call 112 now." added for a serious report, the number from the 429 body, as plain text with no link), a row needing sign in ("Report waiting. Sign in again to send it."), entering the stale state ("Connection lost. Showing reports from 4 minutes ago.") and leaving it ("Back online. The list is up to date."), and the Slow row appearing ("Taking long? Open the low data view."). The countdown figures in rows (the wait text and the minute figures) are never in a live region.

### Wait format (shared by the queue, the form, votes and the Flag control)

The server sends the wait in seconds (`Retry-After`). The client shows it rounded **up**, never down, so a person is never told a time that has not passed: under 60 seconds "{N} seconds" ("1 second"); from 60 seconds to under 60 minutes the number of minutes rounded up, "{N} minutes" ("1 minute"); from 60 minutes the number of hours rounded up, "{N} hours" ("1 hour"). A message in the form, in `.vote-error` or in the Flag dialog is fixed when it is shown (the next attempt replaces it). **A queued row's wait text is not fixed**: `queue.js` stores a retry time and recomputes the wait on the same 60 second tick as the "Last updated" lines, with no live announcement, and it updates only the wait text node (it never recreates the status line or the 112 link, so keyboard focus on the link stays put), so a row blocked for 15 minutes never still says 15 minutes after ten have passed. It is not a per second countdown (Default: nothing is announced every second; the Phase 1.1 resend countdown stays only on its button label). When the wait reaches zero the row retries by itself and its status changes to "Sending.".

### Rejected text messages (outcome 3, server authored)

Abusive text (hate, harassment, sexual content at a high score) is rejected for every severity, including critical and Rescue needed (D-03). **Any provider category outside hate, harassment and sexual never rejects**: violence and self harm words alone never reject, because genuine disaster reports use them, and the illicit categories and the rest are not in the reject set either. Such text posts as borderline (D-04, outcome 8) when it scores near the line. The gibberish rule (D-05) rejects long runs of one character and text with no real words, counted in characters, not bytes (R-06). So there are exactly four reject reasons, and each message names its problem (D-03 "the message names the problem") and says what to do. There is no catch all "This text can't be posted" message, because no other reject reason exists:

| Reason | Message (exact) |
|--------|-----------------|
| Hateful | This text looks hateful, so it can't be posted. Reword it and try again. |
| Harassing | This text looks like harassment, so it can't be posted. Reword it and try again. |
| Sexual | This text looks sexual, so it can't be posted. Reword it and try again. |
| Gibberish | This text looks like random characters, so it can't be posted. Reword it and try again. |

The planner may refine the wording inside this plain style. All four are generic (nothing in them is tied to reports), so Phase 8 comments and Phase 9 nicknames reuse them as they are. The same messages fill the `{REASON}` of a rejected queued row. There is no appeal link inside the form: the Policy page carries the contact line when one is set.

### Rate limit messages (outcome 4 and the others, D-12)

Every limit message states **exactly how long to wait** in the Wait Format (Offline Queue section), keeps what the person typed, and appears **inline** next to what they were doing (not in the toast, which hides after 3 seconds). The server sends a `Retry-After` header with every block. The messages never name the limit numbers and never say "too many requests".

## Surface: Flag Control and Dialog (D-09)

**Focal point:** the question "What is wrong with this report?". **Hierarchy:** the reasons, one line of reassurance, two buttons. The control that opens it is deliberately quiet, so it is never read as a fourth main button.

### The control (P4-A6, P4-A7)

* Visible text **"Flag this report"**, 14px regular, `--color-text`, underlined, no fill, no border, no icon (Component Geometry). It sits last in the popup's actions block, last in the feed row body and last in the Low data row, never inside `.vote-controls`.
* Accessible name: "Flag this report, {Category}, {time}" (starts with the visible words, so it matches speech control, and is different from the plus button's "Report an emergency").
* **Not shown** on the viewer's own report (you cannot flag your own report), on the Activity page, on the moderator screen, or on any report in a state that is not in a feed.
* One built by one shared builder (`flag.js`) and updated in place on each poll. A poll never moves focus, never closes the dialog and never re-enables a sending button.
* **Event isolation (P4-A7).** The builder stops propagation of the click and of Enter and Space keydown on the control, without `preventDefault`, the same shape as `votes.js` `createVoteBlock`, so a tap or key press on it never runs a feed row's `activateRow` (select the row, fly the map, switch a phone to the map view) and its own keyboard activation is not cancelled by the row's `preventDefault`. This restates Phase 3 Interaction Contract item 7 ("Enter and Space on any control inside a row never activate the row") for this control, and is pinned by a source test like `TestVoteClickDoesNotActivateItsRow`.
* **Flagged state.** After the person has flagged this report, the control reads **"Flagged"** and stays a focusable button with `aria-disabled="true"`: `--color-text` text (not muted, see Color), no underline, `cursor: default`, activation does nothing. **The accessible name changes with the text**: the builder rewrites `aria-label` and the visible text together, to "Flagged, {Category}, {time}" (it starts with the visible word, so the name always contains the visible label), instead of leaving the "Flag this report" name that would announce an action the control no longer performs. The server tells the client which reports this account already flagged (a batched read like the other per account flags, Default); if it does not, the state is learned from the 409 answer (below). The box height does not change, so the row does not move.

### The dialog

The shell is the existing modal (`.modal-backdrop` and `.modal-panel`, z-index 1100, `role="dialog"`, `aria-modal="true"`, `aria-labelledby` on the title, focus trap). While it is open the page behind is locked and inert (P4-A26: `overflow: hidden` on the document, `overscroll-behavior: contain` on the panel, `inert` on everything off the backdrop's own path (never on the backdrop or its ancestors), `aria-hidden` where `inert` is unsupported), so a long Low data page or the main list view cannot scroll under the backdrop.

## Interaction Contract

1. **The bar.** The Disclaimer link navigates to the Disclaimer page. Nothing else on the bar is interactive. It cannot be closed or hidden and it keeps no state.
2. **Opening the Low data view.** Any of: the login page link, the account menu item, the "Open the low data view." link in the notice card, the bookmarkable address (for a logged out visitor the access gate sends it to `/login?low=1`, so the choice is remembered and Continue lands on the Low data view), or a main page redirect for a device that already chose it. Serving the page remembers the choice for the device (Ways In). The page asks for no new browser permission when location is already allowed.
3. **Open full version.** Goes to `/?full=1`, which turns the default off and lands on the main page.
4. **Reading the Low data list.** The list renders at once from the stored position, then updates in place when the fresh position arrives. A poll (default 60 seconds) updates text, classes and attributes in place and never moves focus, closes the dialog or form, collapses an open trust panel, or re enables a busy button.
5. **Voting (main page and Low data view).** The Phase 3 contract unchanged: location first (silent refresh when permission is already given), buttons disable in flight, the server answer drives every surface, no optimistic count. New: a vote that is rate limited shows the wait message in `.vote-error`, and while a wait is known no further vote request is sent for it. Votes are never saved offline.
6. **Posting.** Open the form, fill it, Post report. Outcomes are in Submit Outcomes: published (also when borderline), held, rejected (form stays open), rate limited (form stays open, text kept, with Send after the wait, which saves the report to the queue and closes the form), no HTTP answer, a timeout, a 502, 503 or 504 (saved to the queue and the form closes), any other answer (form stays open). Typed text is never lost on a rejection, a limit or a failed request. While the form is open the page behind is locked and inert (P4-A26).
7. **The queue.** Saves on a failed request, a timeout, a 502, 503 or 504, and on Send after the wait from a blocked form, retries on `online`, on page load, on a timer and on Send now. Discard report asks first. Edit and resend opens a prefilled form. A saved report never expires and belongs to its author's account. An answer for an already used request id counts as sent. A queued row's wait text refreshes on the 60 second tick.
8. **Flagging a report.** Flag this report opens the dialog. Choose a reason, Send to moderators. Online only. A flag never hides a post.
9. **Moderating.** Find, Keep report, Remove report (confirmed). Online only. The lists refresh only on Refresh lists and after an action.
10. **Escape order.** Phase 3 A23 and A70 stand, with these additions (P4-A5): while the Flag dialog or the Low data report form is open, the Phase 3 `trust.js` listener does nothing. **The Flag dialog closes at once on Escape** (nothing sent, focus returns to the control that opened it). **The Low data view form** handles Escape itself (ask to close, with the discard confirmation when the form has input). An inline Discard or Remove confirmation closes on Escape inside its own module and returns focus to the button that opened it.
11. **Keyboard.** Every control is reachable and operable. Focus order per surface is in each surface section. Enter and Space on the quiet control and the dialog buttons behave as native buttons, and the quiet control's Enter, Space and click never reach a row (restating Phase 3 Interaction Contract item 7: Enter and Space on any control inside a row never activate the row; P4-A7). Radio reasons move with the arrow keys. A modal traps Tab and returns focus to its opener on close.
12. **Touch.** Every target is at least 44px (the named bar link exception). Nothing is hover only: reasons, hints, scores and the "what the actions do" sentences are always visible text.

## Accessibility

* **Contrast.** Text 4.5:1 and non text 3:1 on every surface and theme. The new pairs the planner's contrast test resolves are listed in Color. Muted text only on `--color-bg`.
* **State is never colour alone.** Every new state is words: the held and removed labels, the stale line, the queued row statuses, the location states, the "Flagged" text. `.inline-error` carries a leading icon and a text message, and `.inline-note` carries text only, so neither depends on its border colour. The bar and the legal pages use no colour at all.
* **Touch targets** are at least 44px for every control (the bar link is the one named inline exception). Radio reason rows are 44px tall as a whole row.
* **Keyboard.** Every control is reachable and operable. Focus rings are the global 2px `:focus-visible` ring, unchanged. The Flag dialog and the report form trap Tab and return focus to their opener. Inline confirmations take focus on the neutral button (first in the DOM) and close on Escape.
* **Focus order by page** (summary, details in the surface sections): bar link, account trigger, then the page. Main page: Report an emergency (plus button), the list pane controls, strip, stale line, rows (row, trust toggle, Confirm, Dispute, Mark resolved, Flag this report). Low data view: Open full version, Report an emergency, Retry position or Retry now when shown, strip, rows (trust toggle, Confirm, Dispute, Flag this report; the row itself is not a tab stop). Activity: strip, rows. Moderator: Refresh lists, find box, Find report, each list in order.
* **Screen readers.** Names and roles: the bar is a named `aside`; the Flag control is "Flag this report, {Category}, {time}"; the dialog is a named modal dialog with a radiogroup in a fieldset; the Low data location block is a fieldset with a legend and a status paragraph; the strip heading names the strip; the moderator buttons carry the report id; every confirmation is a named group.
* **Live regions (the whole inventory).** `#toast` (existing, polite). `#notice-live` (new, visually hidden, polite, a body level element on every page that loads `queue.js` and left out of the `lockPage` inert walk): the first save, each queue result (sent, not sent, blocked by a retry or by Send after the wait with the 112 sentence for a serious report, sign in needed), entering and leaving the stale state on the main page and the Low data view, the slow message. **`role="alert"` is carried only by real failures, set on the element by the code that shows it** (never by a class): `#form-error`, `.vote-error`, the Flag dialog failure message, a moderator row action failure and the moderator Refresh failure (P4-A16). The stale list line, the queued row statuses, the dialog validation prompt, the Edit and resend note and everything inside `#mod-find-result` have no role. The Low data basis line and the location status paragraph (polite, announce only when their text changes). `#mod-find-result` (polite). Nothing announces on a timer or a countdown, the bar is not live, and the minute figures and wait figures in "Last updated" lines and queued rows are never in a live region.
* **Reflow and zoom.** At 320 CSS px and at 400 percent zoom nothing scrolls sideways. Rows, tiles, labels and buttons wrap their text rather than clip. The bar grows taller instead of clipping (min height). Named, accepted exception: at 150 and 200 percent text size the bar is taller than its token (about 156px and about 244px at 320px wide, estimates in Component Geometry), so the map and the login page are taller than the viewport and scroll by the difference, and at 200 percent the bar covers about 43 percent of a 568px screen. D-21 makes the bar always visible and not closable, so this is accepted as an exception to "thin"; a non sticky bar at large text is the alternative in Open items. The account trigger never overlaps the bar (P4-A1), `scroll-padding-top` keeps focused controls out from under it (P4-A25), and the account menu measures its own height (P4-A11). Dialogs and the form lock and inert the page behind them (P4-A26).
* **Language.** The interface language is English. Report text may be in any script (Hindi, Telugu, Tamil, mixed): it is inserted as plain text, wraps anywhere and is never clamped on moderator rows. The system font stack covers the scripts.
* **Forced colors.** Per Color: borders in `CanvasText`, destructive fills lose their colour and the word and position carry the meaning, no information is carried by a background alone.
