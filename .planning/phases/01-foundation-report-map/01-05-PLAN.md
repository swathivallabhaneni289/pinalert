## Phase Goal

A visitor can submit a location-tagged emergency report and see it alongside other nearby reports
on a live map, without creating an account.

> **User-story format not locked.** ROADMAP.md's `**Goal:**` line states an actor and a capability
> but no `so that` outcome, so it does not satisfy the three-slot MVP user-story form. Reproduced
> verbatim above; the planner must not invent the missing clause. Run `/gsd mvp-phase 1` to lock a
> canonical story if the strict form is wanted.

<objective>
Replace plan 01-04's deliberately thin submission modal with the full design contract: the 3×3
category icon grid (D-04, D-01), the accessible animated severity slider (D-05), the refined
GPS-prefilled draggable marker (D-02), the conditional shelter-capacity fields (FOUND-06), every
inline validation message from the Copywriting Contract, and the submit / posting / success /
failure / discard states.

This is the MVP refinement step, not new scope: the path already works end to end after plan 01-04,
and this plan makes it good. D-05 is the sharpest constraint here — the user explicitly rejected a
purely decorative slider, so the number-plus-word readout, the 44px touch target, the visible focus
ring, arrow-key operation, and the screen-reader announcement are requirements, not polish. During
an emergency, an ambiguous severity control produces a wrong severity, and severity drives both the
expiry tier (D-14) and, from Phase 2 onward, triage order.

This plan owns exactly two files and runs in parallel with plans 01-06 and 01-07. It must not edit
`index.html.tmpl`, `main.css`, `app.js`, `map.js`, or `feed.js` — every hook it needs already exists
in the DOM contract and the token layer.

Purpose: make the one screen where a person under stress enters data actually usable.
Output: the production submission modal.
</objective>

    Wire the severity control on the existing native `<input type="range" id="severity" min="1"
    max="3" step="1">`. Keep the native element — do not replace it with a custom widget. The native
    range input already ships correct arrow-key, Home/End and Page-Up/Down handling and
    `role="slider"` semantics; a hand-built substitute would have to reimplement all of that and, on
    the evidence of most attempts, get the keyboard and screen-reader behaviour subtly wrong. This is
    the one control on the form whose value drives both the report's expiry tier (D-14) and, from
    Phase 2 onward, triage ordering, so an ambiguous or inoperable control has real consequences.

    On every `input` event: update `#severity-readout` with the number-and-word form from
    `Pinalert.SEVERITY_LABELS` — "1 · Low", "2 · Medium", "3 · Critical" — rendered in the Display
    type role; set the element's `aria-valuetext` to the same string, because a screen reader
    announcing only "2" does not convey "Medium" and D-05 makes that announcement mandatory; and set
    a severity context class on the slider's wrapper so the track fill, thumb, and readout all take
    the matching traffic-light colour from `--severity-current`.

    Animate the transition (D-05's "smooth animated transition as it moves") with a CSS transition on
    the track fill and thumb colour — the exact easing and duration are Claude's discretion per
    CONTEXT.md, so pick something short and unobtrusive, in the region of 150ms with a standard ease.
    Wrap the transition in a `prefers-reduced-motion: reduce` guard that disables it; motion
    sensitivity is a real accessibility need and the control must remain fully usable without the
    animation.

    Style the slider in `modal.css`: a track showing filled progress in `--severity-current` against
    `--color-surface`, a thumb of at least `--touch-target-min` in both dimensions (the WCAG 2.5.5
    floor, and the practical minimum for a wet or shaking hand on a phone), and cross-browser thumb
    and track pseudo-element rules for both the WebKit and Firefox range implementations. The
    `:focus-visible` outline from `main.css` must remain visible on the thumb — do not suppress the
    default outline without replacing it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server error response → modal DOM | `{field, message}` strings originate outside the page and are rendered into `#form-error` |
| visitor input → `POST /api/reports` | Client-side validation is a usability layer; the server check is authoritative |
| browser geolocation → report coordinate | Visitor-supplied, visible in the readout before submission |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-03 | Tampering | server-supplied error strings rendered into `#form-error` | high | mitigate | Every string from a response reaches the DOM as text content via `Pinalert.setText`; a grep gate fails the build on a markup-parsing sink in `modal.js` |
| T-01-21 | Tampering | client-side validation treated as the control | high | mitigate | The modal mirrors the server's enum, length, range and shelter-capacity rules for usability only; the server revalidates everything and remains the sole authority, so bypassing the browser gains nothing |
| T-01-07 | Tampering | payload field injection from the client | medium | mitigate | The submit payload is assembled field by field from known controls; `expires_at`, `created_at`, `geohash`, `id` and `session_id` are never sent, and the server rejects unknown JSON fields outright |
| T-01-22 | Information Disclosure | shelter headcount on a public feed | low | accept | Headcount is an optional, self-reported, coarse operational figure about a shelter rather than personal data about an individual; it is the point of FOUND-06 |
| T-01-18 | Information Disclosure | precise geolocation | medium | accept | Requested only when the modal opens, shown in the readout before submission, and fully optional — denial falls back to tap-to-place |
</threat_model>
