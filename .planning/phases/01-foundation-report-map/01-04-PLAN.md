## Phase Goal

A visitor can submit a location-tagged emergency report and see it alongside other nearby reports
on a live map, without creating an account.

> **User-story format not locked.** ROADMAP.md's `**Goal:**` line states an actor and a capability
> but no `so that` outcome, so it does not satisfy the three-slot MVP user-story form. Reproduced
> verbatim above; the planner must not invent the missing clause. Run `/gsd mvp-phase 1` to lock a
> canonical story if the strict form is wanted.

<objective>
Close the Walking Skeleton. After this plan a real person opens a browser, sees nearby reports as
pins on a live OpenStreetMap, taps the floating "+" button, drags a GPS-prefilled marker to the
right spot, submits, and watches their own pin appear — against the real API and real Postgres from
plan 01-03, with no signup.

This plan also fixes the **frontend contracts** that make wave 4 parallelisable: the DOM skeleton in
`index.html.tmpl`, and `window.Pinalert` — one shared client store that owns the single
`GET /api/reports` fetch. Plans 01-05 and 01-06 read from that store and never fetch independently,
which is what makes D-06's "map and list always in sync" a structural property rather than a bug
waiting to happen (01-RESEARCH.md Pattern 3).

Requirements landed here: FOUND-04 (reports as pins on a Leaflet/OpenStreetMap map), FOUND-02
(submitting a report, in its thinnest usable form), FOUND-03 (the client consumes the nearby query).
Decisions realised: D-03 (modal over the map, spatial context never lost), D-09 (persistent floating
action button), D-02 (GPS pre-fills a draggable marker the visitor can correct), and the D-12
severity-coloured badge treatment applied to map pins.

The modal built here is deliberately thin — a plain category control, the native range input, a
description field. Plan 01-05 replaces it with the full UI-SPEC modal (3×3 icon grid, animated
accessible slider, shelter fields, validation copy, discard confirmation). That is the MVP
refinement sequence, not a shortcut: the thin version exists so the end-to-end path is real and
demonstrable one wave earlier.

Purpose: prove the whole stack works from a browser.
Output: a working, if plain, Pinalert.
</objective>

    Write `web/static/js/app.js` defining `window.Pinalert` — the single shared client store. Plans
    01-05 and 01-06 build entirely against this surface, so treat every name below as a contract:

    `Pinalert.CATEGORIES` (the nine slugs, in the server's declared order), `Pinalert.SEVERITIES`
    (`low`, `medium`, `critical`), `Pinalert.CAPACITY_STATUSES`, `Pinalert.SEVERITY_LABELS`
    (`{low: '1 · Low', medium: '2 · Medium', critical: '3 · Critical'}` — the numeric-plus-word form
    D-05 makes mandatory), and `Pinalert.CATEGORY_LABELS` (human labels for the meta line).
    `Pinalert.config` holds the fallback centre, default radius and poll interval read from the
    shell's data attributes. `Pinalert.state` holds `{reports, status, error, selectedId, center}`
    where `status` is one of `idle`, `loading`, `ok`, `error`.

    Behaviour surface: `Pinalert.subscribe(fn)` registers a listener called with the state on every
    transition and returns an unsubscribe function; `Pinalert.setCenter(lat, lon)`;
    `Pinalert.fetchReports()` performs the one and only `GET /api/reports?lat=&lon=&radius_km=`
    call, sets `status` to `loading` then `ok` or `error`, and notifies; `Pinalert.startPolling()`
    refreshes on an interval and leaves `status` alone on a background refresh so the list does not
    flash skeletons on every poll; `Pinalert.submitReport(payload)` POSTs to `/api/reports`,
    resolves with the created report or rejects with the server's `{field, message}` shape, and
    refreshes on success; `Pinalert.select(id, source)` and `Pinalert.onSelect(fn)` carry selection
    between panels with `source` set to `map` or `list` so neither echoes an event back.

    Formatting helpers, defined once here because both the map and the list need identical output:
    `Pinalert.severityClass(report)` returning the matching `sev-*` class;
    `Pinalert.iconPath(category)` returning `/static/icons/{category}.svg` **only after checking the
    category against `Pinalert.CATEGORIES`**, falling back to `other.svg` for anything unrecognised,
    so a value from the API can never be interpolated into a path or attribute unchecked;
    `Pinalert.relativeTime(iso)` producing "4 min ago"; and `Pinalert.ageStage(report)` returning
    `fresh`, `aging`, or `stale` — compute the lifetime as `expires_at − created_at` and the
    remaining fraction as `(expires_at − now) / lifetime`, then map above 0.25 to fresh, 0.125 to
    0.25 to aging, and below 0.125 to stale. That is D-15's "fades over roughly the last quarter of
    its lifetime" expressed as D-17's three discrete desaturation stages; the corresponding
    `.age-*` classes already exist in `main.css`, so this function returns a class suffix and does no
    styling itself. Plan 01-06 calls the same function for list rows, which is why it lives here.

    Add `Pinalert.setText(el, value)` assigning a string to an element as text content only. Every
    piece of report-authored data — descriptions above all — must reach the DOM through this helper
    or an equivalent text-node assignment. Report text is written by strangers and rendered in other
    visitors' browsers; if it is concatenated into a markup string that the browser then parses, a
    crafted description becomes script execution for every reader in the area. `html/template`
    protects only the server-rendered shell, not anything JavaScript builds from a fetched response.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API response → client DOM | Report descriptions are authored by anonymous strangers and rendered in other visitors' browsers — the highest-value boundary in this plan |
| third-party CDN → visitor browser | Leaflet's CSS and JS execute with full page privileges |
| browser geolocation → report coordinate | The visitor's own device supplies the location; the server validates the range |
| template data → rendered HTML | Server-side values interpolated by `html/template` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-03 | Tampering | report description rendered by `map.js` into popups and by `modal.js` into error copy | high | mitigate | All report-authored strings reach the DOM through `Pinalert.setText` (text-node assignment); popups are built as DOM elements and passed to `bindPopup` as elements rather than as markup strings; a grep gate on every JS file fails the build on a markup-parsing sink. `html/template` covers only the server-rendered shell, so this control is the whole defence for client-built DOM |
| T-01-16 | Tampering | Leaflet loaded from a third-party CDN | high | mitigate | Version-pinned 1.9.4 URL with a Subresource Integrity `integrity` hash and `crossorigin="anonymous"`, so a modified CDN payload is refused by the browser rather than executed |
| T-01-17 | Tampering | category value interpolated into an icon path | medium | mitigate | `Pinalert.iconPath` validates the value against the known nine-slug list and falls back to `other.svg`, so an unexpected API value cannot be reflected into an attribute or traverse a path |
| T-01-18 | Information Disclosure | precise geolocation | medium | accept | Submitting a precise coordinate is the product's core function and the visitor drags the marker themselves, seeing the exact value in the readout before submitting. Geolocation is requested only when the report modal is opened, never on page load, and denial is a fully supported path |
| T-01-19 | Information Disclosure | OSM tile requests reveal the visitor's viewport to a third party | low | accept | Unavoidable for a free, no-API-key map and explicitly chosen in PROJECT.md's budget constraint; the tile server sees a viewport, not a report |
| T-01-20 | Denial of Service | polling load from an idle tab | low | mitigate | A single 30-second interval on one endpoint, with background refreshes leaving the status untouched; no per-panel duplicate polling because both panels read one shared store |
</threat_model>
