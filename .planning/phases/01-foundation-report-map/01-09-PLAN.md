Close the single blocker `/gsd-verify-work 01` recorded on the **retest** of UAT Test 1 in
`01-UAT.md` (the last entry in its `## Gaps` section). This is surgical repair of an already-shipped
phase — not new scope. The root cause is fully confirmed; no further debugging is required.

**The gap (blocker, UAT Test 1 retest).** The primary map container rendered by
`web/templates/index.html.tmpl:22` has **no CSS rule anywhere** in `main.css`, `modal.css` or
`feed.css` giving it a height — confirmed by grep across all three shipped stylesheets, which return
exactly one map-ish id selector: `#modal-map` in `modal.css:22`, a *different* Leaflet instance
inside the report modal, and the precise reason that one renders fine while the primary one does
not. Its ancestor chain gives it nothing either: `.pane--map` inherits only
`.pane { min-height: 0; overflow: hidden; position: relative; }`, and its parent `.app-shell` is a
CSS grid with `min-height: 100vh` and no `grid-template-rows`. The FAB (`.fab`) is `position: fixed`,
so it is out of normal flow and contributes nothing to the pane's content height. With no in-flow
content of any height, the container collapses to 0px, and `L.map(container)` in `map.js`'s `init()`
initialises Leaflet against a zero-height viewport. There is no area for tiles to paint into, so the
user sees solid black where the map should be.

This defect shipped with plan 01-04 (the walking skeleton) and has been invisible the entire time:
the modal-backdrop bug that 01-08 just fixed painted a full-viewport black scrim over the whole page
on every load, hiding the already-broken map underneath it. Now that 01-08 has landed, this is the
next thing blocking Test 1 and, behind it, seven other still-pending UAT tests.

**Why the fix is a viewport unit on the container itself, and not a percentage.** A `height: 100%`
on an element resolves against its parent's *definite* height; if the parent's height is `auto` the
percentage resolves to `auto`, which is 0 here — it would look like a fix in the stylesheet and
change nothing in the browser. Making a percentage chain correct would mean relying on CSS Grid's
"stretch auto tracks" step distributing the shell's `min-height` free space into an implicit row, and
then on that stretched grid item's size counting as *definite* for its child's percentage resolution.
Both of those hold per spec and in current engines, but this plan deliberately does not depend on
either: giving the container a **viewport-relative height of its own** makes the resolution
self-contained, works identically in both layout modes, and additionally makes the pane's grid row
non-zero from content alone — so the layout is correct whether or not the stretch step contributes
anything. This is the same reasoning `#modal-map` already embodies with its fixed `220px`.

Purpose: make the primary map — the phase's headline deliverable (FOUND-04) — actually visible, and
lock it with a regression test so a 0-height map cannot ship silently a third time.

Output: one id selector in `main.css`'s layout-containers section, one viewport-unit consistency fix
on the shell in the same block, and one narrow Go test.

**Known and accepted, not a new gap.** In the >=900px split view (D-06), the grid row grows to
whichever pane is taller. With a very long report list the row exceeds the viewport, the map sits at
the top of its column at viewport height, and the rest of that column is empty background. At the
3-5 reports UAT Test 5 exercises, the list is shorter than the viewport and this never appears. Do
**not** redesign the shell into an internally-scrolling layout to avoid it — that would change
page-scroll behaviour nothing in this phase has been UAT'd against.

**Test 1 is not closed by this plan.** After it lands, re-run `/gsd-verify-work 01` from Test 1
onward; Tests 2, 3, 4, 5, 6, 7, 9 and 10 all remain `[pending]` behind this blocker.

**Step 0 — confirm the one open question before you write anything (expected outcome stated).**
The gap analysis flagged a possible second, functional defect: a Leaflet instance that initialises
while its container is `display: none` renders against a stale zero size and needs an explicit
`invalidateSize()` once shown. Confirm the two facts that make this a non-issue here, so the fix can
stay CSS-only:

  1. The template hard-codes `data-view="map"` on the shell, and the narrow-screen rules only hide
     `.pane--map` when `data-view` is `list`. So at page load, in **both** layouts, the map pane is
     rendered (`display: block`) when `map.js`'s `init()` runs — the map never initialises inside a
     hidden pane.
  2. `web/static/js/feed.js`'s `switchView()` already dispatches a window resize event when
     returning to map view, with a comment explaining that Leaflet's default `trackResize` option
     listens for exactly that event and calls the map's own `invalidateSize()` in response — which
     is precisely what a map hidden-then-shown via a display toggle needs.

If both hold, note it in the SUMMARY and change no JavaScript. **If either turns out to be false,
stop and report it rather than expanding this plan's scope** — a JS change would need its own
planning round, and the verify gates below will reject a JS edit.

**Step 1 — the height rule in `web/static/css/main.css`.**
Work inside the "Layout containers (D-06 wide-screen split view, D-07 narrow-screen map-default with
toggle)" section that currently holds `.app-shell`, `.pane` and the two breakpoint blocks (around
lines 366-433). Do not touch any other section of the file.

  a. Add a new rule targeting the primary map container by its id — the id the template gives the
     Leaflet div at `index.html.tmpl:22`. Place it immediately after the `.pane` rule and before
     `.view-toggle`, so it reads in DOM order. Declare `height` **twice** in that block: first with
     a `100vh` value as a legacy fallback, then with a `100dvh` value on the following line. Later
     declaration wins in any engine that understands dynamic viewport units; an engine that does not
     discards the second declaration and keeps the first. Use the dynamic form as the effective
     value because on mobile browsers the static viewport unit is the *large* viewport — taller than
     the visible area while the address bar is showing — which would push the bottom of the map
     behind browser chrome on exactly the device class these UAT screenshots come from.
     Add no `width` declaration: the container is a block-level div and already fills its pane's
     inline size. Add no `position`, no `min-height`, no `z-index` — the pane is already
     `position: relative` and the FAB already sits above Leaflet's panes on `z-index: 1000`.

  b. In the `.app-shell` rule directly above, apply the **same** two-declaration treatment to its
     existing `min-height`: keep the current `100vh` line as the fallback and add a `100dvh` line
     immediately after it. This is not scope creep — a shell floored at the large viewport unit
     while the map is sized to the dynamic one leaves a strip of body background under the map and a
     phantom few-pixels page scroll on mobile. Both boxes must be stated in the same unit family.
     Change nothing else in `.app-shell`: `display: grid`, `grid-template-columns: 1fr` and both
     breakpoint blocks stay exactly as they are.

  c. Write an explanatory comment above the new rule covering, in your own words: that Leaflet sizes
     its map viewport from the container's own box, so a zero-height container paints no tiles at
     all; that this container is the last in-flow box in its pane (the FAB is fixed-position and
     contributes no content height), so nothing upstream was giving the pane's grid row a size; that
     the height is stated in a viewport unit rather than as a fraction of the parent precisely so the
     resolution is self-contained and does not depend on the grid's stretch behaviour or on a
     stretched item's size counting as definite for a child; and that the paired declaration is a
     legacy fallback, not a duplicate to be tidied away. Name `TestPrimaryMapHasResolvedHeight` in
     the comment as the gate that fails the build if this rule is removed, mirroring how the
     backdrop rule's comment names `TestModalBackdropHiddenGuard`.
     **Keep the section comment's existing lead-in phrase `Layout containers` verbatim** — leave the
     rest of that comment body alone.

  d. Do **not** edit `web/static/css/modal.css`. `#modal-map`'s `height: 220px` already works, is
     unrelated to this gap, and a verify gate asserts that file is byte-unchanged.

**Step 2 — the regression test in `web/css_contract_test.go`.**
Add exactly one new test function, `TestPrimaryMapHasResolvedHeight`, to the existing file in package
`web`. Reuse the file's existing `stripCSSComments` helper and its rule-parsing technique — do not
duplicate or rewrite either. The test:

  - Walks every `*.css` file under `static/css` in `StaticFS` with `fs.WalkDir`, reading each with
    `fs.ReadFile`, exactly as `TestModalBackdropHiddenGuard` does.
  - Strips block comments, splits the text on the closing-brace character to get one chunk per rule,
    and for each chunk takes everything after the LAST opening-brace character as the declaration
    body and everything before it as the selector head. Splitting on the last brace rather than the
    first is what keeps a rule nested inside a media query parsing correctly instead of mistaking the
    at-rule preamble for a selector.
  - Splits each selector head on the comma, trims each resulting selector, and treats a selector as
    targeting the primary map container when its **last whitespace-separated field** equals the
    primary map id selector. Matching the last field (rather than a plain substring search) is
    load-bearing twice over: it lets a descendant-qualified form still match, and it prevents a false
    positive on the modal's own map id, which is a different element this test must not police.
  - Collects, for every matching rule, each `height` or `min-height` declaration by splitting the
    declaration body on the semicolon and each declaration on its first colon, trimming both sides.
  - Asserts (A) at least one matching rule was found in `static/css/main.css`, and (B) at least one
    collected value is self-resolving — i.e. its text carries a viewport-height unit or an absolute
    length unit, rather than being a fraction of its parent or a keyword. Implement (B) as a small
    check for the presence of a viewport-height unit suffix or an absolute length suffix in the
    value text; note in a code comment that testing for the viewport-height suffix alone also covers
    the dynamic, small and large variants, since each of those contains it.

  - Both failure messages must be self-explaining, because a future developer will meet them cold:
    (A) states that the primary map container has no height rule in the shipped CSS, that this is
    exactly the UAT Test 1 blocker, and that Leaflet paints nothing into a zero-height container.
    (B) must be **honest about what it is really locking**: it encodes *this fix's strategy* — a
    height the container resolves by itself — and not an absolute rule of CSS. A parent-relative
    height is perfectly legitimate when every ancestor up to a definitely-sized box has a definite
    height, which the shell's grid does not currently guarantee; a developer who deliberately builds
    that chain should update this test alongside it rather than fight it.

  - Give the test a doc comment stating the honest limit of its claim: static inspection of the
    shipped CSS can prove a height-establishing rule exists on the right selector, but it **cannot**
    prove the resulting computed height is non-zero in a real browser's layout — that is what the
    human-check in this plan's verify block covers, and the two are complementary, not redundant.

Keep the test to this one concern. Do not generalise `web/css_contract_test.go` into a CSS linter, do
not add a third test function, and do not modify `TestModalBackdropHiddenGuard` or
`stripCSSComments`.

Before committing, confirm the test actually bites: temporarily remove the new rule from `main.css`,
watch `TestPrimaryMapHasResolvedHeight` fail, then restore it.

Scope reminder — this plan implements D-06 (split view: the map fills its half at wide widths) and
D-07 (narrow screens default to a full-screen map with a toggle). It does not restyle, reposition or
otherwise touch anything else.
