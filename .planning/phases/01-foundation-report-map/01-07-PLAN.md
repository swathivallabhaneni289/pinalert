## Phase Goal

A visitor can submit a location-tagged emergency report and see it alongside other nearby reports
on a live map, without creating an account.

> **User-story format not locked.** ROADMAP.md's `**Goal:**` line states an actor and a capability
> but no `so that` outcome, so it does not satisfy the three-slot MVP user-story form. Reproduced
> verbatim above; the planner must not invent the missing clause. Run `/gsd mvp-phase 1` to lock a
> canonical story if the strict form is wanted.

<objective>
Ship OPS-01: the JSON API documented via a browsable OpenAPI/Swagger spec at a stable URL, generated
from the handler code rather than hand-maintained alongside it.

This matters beyond the requirement. PROJECT.md's Key Decisions commit to an API-first Go backend
with the website as its first client, so that a PWA or native app can arrive later with no backend
rewrite — a documented contract is what makes that claim real rather than aspirational. And for a
portfolio project whose whole purpose is demonstrable engineering signal, a live, browsable API
reference is the artifact a reviewer opens first.

Generated-from-code is the point: a hand-written spec file starts drifting from the handlers the
first time a field changes, and a stale contract is worse than none. This plan also adds a drift
guard that fails the build if the published schema ever starts documenting a session identifier —
the same information-disclosure control plan 01-03 enforces on the runtime response, applied to the
document that tells the world what the response contains.

This plan owns Go files only and runs in parallel with plans 01-05 and 01-06, which own frontend
files exclusively.

Purpose: make the API contract public, accurate, and self-maintaining.
Output: `/swagger/index.html` served by the app.
</objective>

    Add the general API annotation block above `NewRouter` in `internal/api/router.go`: `@title
    Pinalert API`, `@version 1.0`, `@description` naming this an anonymous, crowd-reported local
    emergency feed and stating plainly that it is unofficial and not a substitute for emergency
    services, `@BasePath /api`, plus a licence and contact line. Note in the description that the

    In `internal/api/handlers/reports.go`, promote the request and response structures to exported,
    explicitly-declared types so `swag` can reference them by name: a submit-request type carrying
    exactly the seven client-settable fields, a report-response type carrying exactly the twelve
    public fields (id, category, severity, description, latitude, longitude, geohash,
    shelter_capacity_status, shelter_headcount, created_at, expires_at, distance_km), a list-response
    wrapper, and an error-response type carrying the field/message pair. These types must remain
    hand-declared field by field and must never embed or alias a store row — the whole point is that
    adding a column to the `reports` table cannot silently change either the runtime response or its
    published documentation.

    Annotate both operations. For `SubmitReport`: summary and description, `@Tags reports`,
    `@Accept json`, `@Produce json`, `@Param body`, and `@Success 201` / `@Failure 400` /
    `@Failure 500` referencing the declared types, plus a note that the anonymous session cookie is
    issued automatically and no authentication is required. For `NearbyReports`: `@Param` entries for
    `lat`, `lon` and `radius_km` documenting that the first two are required, their valid ranges, and
    that `radius_km` defaults to 10 and is bounded to 50, plus `@Success 200` / `@Failure 400`.

    Document the enumerations on the struct fields themselves using swag's `enums` tag so the
    generated spec lists all nine category slugs, all three severity values, and all four capacity
    statuses. Derive them from the constants in `internal/service` rather than retyping the strings,
    or if the tag syntax requires literals, add a comment pointing at the service package as the
    source of truth. A reader of the spec should be able to submit a valid report without reading any
    Go code.

    Run `swag init -g internal/api/router.go -o docs` (the `make swag` target already exists) and
    commit `docs/docs.go`, `docs/swagger.json` and `docs/swagger.yaml`. Committing the output is what
    lets CI stay a plain build/vet/test with no swag binary, matching the same reasoning that put the
    sqlc output in the repository.

    Mount the Swagger UI in `internal/api/router.go`: import `httpSwagger
    "github.com/swaggo/http-swagger/v2"` and blank-import `_ "pinalert/docs"`, then register
    `r.Get("/swagger/*", httpSwagger.Handler(httpSwagger.URL("/swagger/doc.json")))`. Use the `/v2`
    module path specifically — the v1 package is a different, older module and the officially
    published chi example uses `/v2`. The v2 handler serves its UI assets from the binary, so the
    documentation page needs no third-party CDN request at view time, consistent with the
    self-hosted-assets posture the rest of the frontend takes.

    Mount `/swagger/*` outside the `/api` group so its middleware stack stays independent, and leave
    it publicly reachable: OPS-01 asks for a stable, browsable URL, and this is a public read-only
    API with no privileged operations to hide. `/swagger/index.html` is the stable URL; record it as
    such.

    Write `internal/api/handlers/swagger_test.go` with two tests. `TestSwaggerDocServed` — the name
    01-VALIDATION.md's verification map specifies — drives the real router through `httptest` and
    asserts that `GET /swagger/doc.json` returns 200 with a body that parses as JSON and carries a
    `swagger` or `openapi` version key, and that `GET /swagger/index.html` returns 200 with an HTML
    content type. `TestSwaggerSpecCoversRoutes` is the drift guard: it loads the committed
    `docs/swagger.json` and asserts that both `/reports` operations are present, that every one of
    the nine category slugs and three severity values appears, and — critically — that no schema
    property anywhere in the document is named `session_id` or `sessionId`. That last assertion is
    the published-schema counterpart to plan 01-03's runtime control: a session identifier must never
    reach a client, and it must never be advertised as part of the contract either, because a
    documented field is an invitation for a future change to start populating it. Neither test needs
    a database, so both run under `-short`.

    Extend `README.md` with an "API documentation" section naming `/swagger/index.html` as the
    browsable reference and `/swagger/doc.json` as the raw spec, noting that the document is Swagger
    2.0 generated by `swag`, and stating that `make swag` must be re-run and the `docs/` output
    re-committed whenever a handler's request or response shape changes — with the drift guard as the
    backstop that catches a forgotten regeneration.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| published spec → the internet | The document tells anyone exactly what the API accepts and returns |
| Swagger UI "Try it out" → live API | The documentation page can issue real requests against the running service |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-02 | Information Disclosure | the published response schema | high | mitigate | `TestSwaggerSpecCoversRoutes` fails the build if any schema property named `session_id` or `sessionId` appears in the spec, and the response types are hand-declared rather than derived from a store row — so a new table column cannot silently become a documented, then populated, public field |
| T-01-25 | Information Disclosure | spec examples and descriptions | medium | mitigate | Examples use obviously synthetic coordinates and text; no real session id, DSN, secret, or internal hostname appears in any annotation, and only the two public `/api/reports` operations are documented — no internal or operational route is advertised |
| T-01-16 | Tampering | Swagger UI asset delivery | medium | mitigate | `http-swagger/v2` serves its UI assets from the compiled binary, so the documentation page loads no third-party script that a compromised CDN could replace |
| T-01-26 | Repudiation | spec drifting from actual handler behaviour | medium | mitigate | The spec is generated from handler doc-comments rather than hand-authored, and the drift guard asserts route and enum coverage against the committed document, so a forgotten `make swag` fails CI instead of shipping a lie |
| T-01-27 | Denial of Service | "Try it out" issuing live writes against production | low | accept | The API is anonymous and public by design, and `POST /api/reports` is already reachable by anyone; the documentation page grants no capability a plain HTTP client lacks. Phase 4's ROBUST-04 rate limiting is the real control here and is correctly scoped there |
</threat_model>
