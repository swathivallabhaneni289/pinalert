<objective>
Close 01-14's remaining human-check item (D4 in `01-14-SUMMARY.md`) by actually running it live
with the human tester, instead of a second isolated-worktree agent that has no browser access.
01-14's own Mechanism 1 fix (stroke-width 2 -> 3) turned out to be the wrong lever: a live retest
found the modal category grid still unreadable, traced this session to the real cause (the

map pins and feed rows, which were never part of the complaint).
</objective>

<process_deviation>
**This plan was NOT executed via `/gsd-execute-phase` or a spawned `gsd-executor` agent.** It was
authored and executed directly by the orchestrating session, live, in the same conversation as
the human tester, for two reasons discovered in sequence:

1. **The verification gap is structural, not a diagnosis-quality problem.** 01-13 and 01-14 both
   ran the standard UAT -> diagnose -> plan -> check -> execute loop correctly, and both produced
   agents that self-reported passing gates. But 01-14's actual defect only became visible on a
   real device, in a real browser, looking at real rendered pixels — something no isolated
   worktree agent (or the orchestrator itself, reasoning from source) can substitute for. A third
   round of the same loop would have produced a third plan optimizing for a computed floor
   (stroke-width, contrast ratio) rather than the actual human-perceived defect.
2. **A live server-cache investigation had to happen in the same loop as the fix**, because the
   first two attempts to show the human tester a fix appeared to fail — not because the fix was
   wrong, but because (a) five stale/orphaned `go run ./cmd/server` processes were serving
   pre-fix embedded assets, and (b) even after killing those, the browser's own HTTP cache
   (`Cache-Control: public, max-age=3600` on every static asset) kept serving old CSS/JS under
   the same unversioned URL. Diagnosing and fixing the *verification channel itself* had to
   happen inline with the human tester's live feedback — it cannot be planned in advance or
   delegated to an isolated agent, since the whole point was confirming what a specific human,
   on a specific machine, in a specific browser, actually sees right now.

This PLAN.md is written retroactively, after the fix already landed and was confirmed live by
the human tester in both dark and light mode. It documents what happened and why, in the same
structure as every other plan in this phase, so the phase's paper trail stays complete and
auditable — not as a prescription for an executor to follow.
</process_deviation>

<task type="manual" number="1">
<name>Diagnose why the modal grid was still unreadable after 01-14, live with the tester</name>
<action>
Consulted the advisor after the second failed retest attempt (01-14's stroke-width fix, confirmed
mechanically correct by `go test`, still reported as illegible by the human tester). The advisor
identified that `.category-tile { color: var(--color-text-muted) }` — never touched by 01-14,
which only changed stroke-width and added a badge-only `--badge-glyph-fg` mechanism — was still
in effect for the modal tile context specifically, and that a third diagnose/plan/execute loop

CSS (not source, the actual bytes a `curl` against the running server returned) before editing
anything.
</action>

<task type="manual" number="2">
<name>Fix the modal glyph color directly; verify both tile states</name>
<action>
Added `.category-tile .icon-glyph { color: var(--color-text) }` and, to avoid breaking the
selected-tile inversion (`.category-tile--selected` already sets `color: var(--color-bg)` on a
`--color-text` background — a same-specificity glyph override would win regardless of selected
state without an explicit counter-rule), added
`.category-tile--selected .icon-glyph { color: var(--color-bg) }` immediately after it. Verified
both rules exist in the served CSS via `curl` against the running server before asking the human
tester to look. This is the actual fix: dark-mode contrast against `--color-surface` went from
~7:1 (`--color-text-muted`) to ~17.7:1 (`--color-text`).
</action>
<verify>go build ./... && go vet ./... && go test ./... all pass; curl against the running server's exact served URL shows both new rules present.</verify>
<done>Human tester's next message moved on to a different topic (the map, not the modal) without repeating the modal complaint — the strongest signal available that this specific fix worked.</done>
</task>

<task type="manual" number="3">
<name>Diagnose and fix why the tester still couldn't see any change (server + browser cache)</name>
<action>
Found five running `go run ./cmd/server` processes (via `lsof`/`ps`), all compiled before the
day's fix commits — two were orphaned binaries left over from earlier isolated-worktree agent
sessions whose worktrees had already been deleted. Killed all five, started one fresh server.
Then found a second, independent cache layer: `router.go`'s `staticFileServer` sends
`Cache-Control: public, max-age=3600` on every static asset, and the template referenced each
asset by a fixed, unversioned URL — so even a correctly-restarted server could not force an
already-loaded browser tab to re-fetch changed CSS/JS. Fixed by threading a process-start-time
`AssetVersion` (cmd/server/main.go, via strconv.FormatInt(time.Now().Unix(), 10)) through
handlers.PageConfig into every local `<link>`/`<script>` tag in index.html.tmpl as a `?v=`
query string — external CDN tags (already SRI-pinned and version-locked) were deliberately left
untouched.
</action>
<verify>go build/vet/test all pass; curl against "/" shows versioned URLs; curl against the exact versioned URL returns the current CSS content, confirmed byte-for-byte against the source on disk.</verify>
<done>Server restarts during the remainder of this session reliably showed the human tester the current state without further cache confusion.</done>
</task>

<task type="manual" number="4">
<name>Revert 01-14's stroke-width change and reduce badge glyph size on direct request</name>
<action>
Once the color fix (Task 2) was confirmed working for the modal, the human tester explicitly
asked for the map pin icons to look "how it used to be" — 01-14's stroke-width increase
(2 -> 3), applied uniformly to all nine shared SVG files, had visibly thickened the map-pin and
feed-row badge icons too, an unrequested side effect on a UI area the tester had explicitly said
was already fine, back when the modal was first reported broken. Reverted all nine SVGs'
stroke-width from 3 to 2. This made `TestCategoryGlyphInkCoverageAcrossRenderContexts` fail (it
asserted a >=2.5 floor), so removed that test and its exclusive helpers (`extractAttr`,
`findDeclValue`, `parsePx`, `parsePercent`, the ink-floor/ceiling constants) rather than leave a
gate asserting something now deliberately false — `01-REVIEW.md`'s WR-05 had already found the
test's per-context assertions added little independent verification beyond a single uniform
stroke-width check, reinforcing removal over patching. `TestBadgeGlyphContrastAcrossAgeStagesAndThemes`
(01-14 Mechanism 2, unrelated to stroke-width) was left untouched and still passes. A follow-up
"still feel big" report (about the map pins, confirmed via screenshot) was addressed by reducing
`.icon-badge .icon-glyph` and `.report-row .icon-badge .icon-glyph` from 55% to 48% of their
badge box in both main.css and feed.css (kept in sync, as the existing code comment already
required).
</action>
<verify>go build/vet/test all pass with no changes needed elsewhere; curl against the running server confirms stroke-width="2" served on all nine icons and 48% sizing served in main.css.</verify>
