## Phase Goal

A visitor can submit a location-tagged emergency report and see it alongside other nearby reports
on a live map, without creating an account.

> **User-story format not locked.** ROADMAP.md's `**Goal:**` line states an actor and a capability
> but no `so that` outcome, so it does not satisfy the three-slot MVP user-story form. Reproduced
> verbatim above; the planner must not invent the missing clause. Run `/gsd mvp-phase 1` to lock a
> canonical story if the strict form is wanted.

<objective>
Make the reporting loop real on the server: an anonymous visitor gets a tamper-resistant session,
POSTs a report, and GETs it back from a proximity query — proven end to end by an automated HTTP
test against a real Postgres. This is the Walking Skeleton's first working slice; plan 01-04 puts
the same loop in a browser.

Requirements landed here: FOUND-01 (anonymous session, no signup), FOUND-02 (nine categories per
D-01, three severities, free-text description), FOUND-03 (nearby feed via indexed bounding-box
prefilter then Haversine, never a full-table scan), FOUND-05 (expiry as a read-time predicate on
every query, not a background sweep), FOUND-06 (shelter-open capacity status with optional
headcount). D-14's two-tier severity expiry (24h critical / 8h low-medium) is computed and
materialised here.

Two architectural rules this plan establishes for the whole project: one `GET /api/reports`
endpoint serves both the map and the list (01-RESEARCH.md Pattern 3 — two independently-polled
endpoints would silently desync the D-06 side-by-side view), and `expires_at` is materialised at
write time so the read-time gate stays a plain indexed comparison (Pattern 1).

Purpose: everything after this plan is a consumer of this contract.
Output: a running Go server with a working, tested submit-and-read API.
</objective>

    Write `internal/session/cookie.go` in package `session`, transcribing 01-RESEARCH.md's
    "Anonymous session cookie (HMAC-signed)" example into a `Manager` type. `NewManager(secret
    []byte, secure bool) (*Manager, error)` rejects an empty secret. `Manager.NewID()` draws 16
    bytes from `crypto/rand` — the cryptographically secure generator, never the general-purpose
    pseudo-random package, whose output is predictable from observed values and would let an
    attacker guess future ids — and base64url-encodes them. `Manager.Sign(id)` returns
    `id + "." + base64url(HMAC-SHA256(secret, id))`. `Manager.Verify(signed) (id string, ok bool)`
    splits on the first separator, recomputes the MAC, and compares with `hmac.Equal` so the
    comparison takes the same time regardless of how many leading bytes match — a byte-by-byte
    comparison leaks, through response timing, how much of a guessed signature was correct.

    Add `Manager.Middleware(persist func(ctx context.Context, id string) error) func(http.Handler)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /api/reports` | Fully untrusted, unauthenticated input crosses here: JSON body, headers, cookie |
| browser → `GET /api/reports` | Untrusted query parameters control the scan window |
| cookie jar → session middleware | The client holds and can attempt to modify its own identity token |
| service layer → Postgres | All SQL is sqlc-generated and parameterised; no string concatenation |
| store row → JSON response | The point at which an internal column could leak to the public |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Spoofing | `internal/session/cookie.go` — session forgery/replay | high | mitigate | Opaque `crypto/rand` id plus HMAC-SHA256 signature verified with `hmac.Equal`; a client cannot mint a valid signature without `SESSION_SECRET`, and any tampered cookie is discarded and replaced rather than trusted |
| T-01-02 | Information Disclosure | `NearbyReports` query and the report JSON response | high | mitigate | Both query projections enumerate columns individually, and the handler declares its own response struct field by field rather than marshalling a store row, so `session_id` cannot reach a client. Enforced by `TestNearbyReportsExcludesSessionID` and by a grep gate on the query file |
| T-01-04 | Tampering | SQL injection via report fields or query params | high | mitigate | Every query is sqlc-generated and parameterised by construction; no query string is assembled by concatenation anywhere in the store layer |
| T-01-06 | Tampering / Availability | `SESSION_SECRET` handling in `cmd/server/main.go` | high | mitigate | Fatal exit when unset outside `ENV=development`; the process never generates a random secret at startup, which on a sleep-prone free tier would invalidate every session on every cold start and destroy the reputation continuity Phase 2 depends on |
| T-01-07 | Tampering | client-supplied `expires_at` / `created_at` / `geohash` / `id` | high | mitigate | The submit input type carries only the seven client-settable fields; expiry, creation time, geohash and id are computed server-side from `time.Now().UTC()` and the validated severity, and the decoder rejects unknown JSON fields so an attempt to set them is a loud 400 rather than a silent drop |
| T-01-08 | Denial of Service | unbounded request body or scan window | medium | mitigate | `MaxBytesReader` caps the POST body at 64 KB, description length is capped at 1000 characters, and `radius_km` is bounded to 50 so a single request cannot demand an arbitrarily wide Haversine evaluation |
| T-01-05 | Tampering | CSRF on `POST /api/reports` | low | accept | `SameSite=Lax` prevents the session cookie riding a cross-site form POST. No CSRF token is added because anonymous report creation carries no account-takeover consequence and there is no authenticated action to ride. Traceable to 01-RESEARCH.md Assumption A5; revisit if Phase 2's voting makes a forged cross-site action consequential |
| T-01-15 | Information Disclosure | error responses | medium | mitigate | Validation failures return only a field name and a user-safe message; every other failure returns a generic 500 with the detail logged server-side, so database errors and driver messages never reach a client |
