<objective>
Close the two `status: diagnosed` gaps `01-UAT.md` records against Tests 2 and 6 — the follow-on
issues the human tester surfaced when they retested plan 01-13's CSS-mask fix. 01-13 correctly fixed
what it set out to fix (glyphs are no longer solid black in dark mode; that gap is `status: resolved`
and stays resolved). What the retest then exposed is that a *visible* glyph is not the same as an
*identifiable* one. The user's words: "It's not that clear... I can't see which one it is."

The diagnosis is complete — `.planning/debug/category-glyph-legibility.md` traced it to two additive
mechanisms with file-and-line evidence and computed numbers. No further investigation is required,
and this plan must not re-open or re-architect 01-13's mask mechanism, which the diagnosis explicitly
cleared as correctly implemented.

**Mechanism 1 — stroke-only source artwork (all three render contexts, both themes).** All nine
category icons are Lucide line art: `fill="none"`, `stroke-width="2"`, on a 24-unit viewBox, with
zero filled shapes. Used as a CSS mask, only the opaque stroke path is unmasked, so the rendered
glyph is a hairline whose physical width is `stroke-width x (render box px / 24)`:

| Context | Render box | Physical stroke today |
|---------|-----------|-----------------------|
| Map pin badge (`.icon-badge--pin`, 44px box, glyph at 55%) | 24.2px | 2.017px |
| Modal category tile (`#category-grid` glyph, fixed 24px) | 24.0px | 2.000px |
| Feed row badge (`.icon-badge--sm`, 32px box, glyph at 55%) | 17.6px | 1.467px |

This is not a colour-contrast defect: the unselected dark tile pairing computes to ~7:1, passing AAA,
and light mode's equivalent (~4.3:1) is objectively worse yet drew no complaint. The bottleneck is
ink AREA, which the stroke-only geometry caps regardless of colour token.

**Mechanism 2 — genuine WCAG point-contrast failure, badge contexts only.** `.icon-badge` paints its
glyph `color: var(--color-bg)` over a `--severity-current` fill, and the age ramp rewrites that fill
without touching the foreground. The diagnosis computed the stale stage (2.36:1 dark, 1.60:1 light —
both below WCAG 1.4.11's 3:1 graphical-object floor). **Planning re-derived the full matrix and found
the failure is wider than the diagnosis recorded, in light mode especially.** Contrast of the current
glyph foreground against each badge fill (planner-computed; the Task 2 gate re-derives these and is
the authority):

| Severity | Theme | Fresh | Aging | Stale |
|----------|-------|-------|-------|-------|
| Low | light | 3.06 | **2.33** | **1.60** |
| Medium | light | **2.94** | **2.19** | **1.60** |
| Critical | light | 5.44 | 3.04 | **1.60** |
| Low | dark | 10.14 | 5.12 | **2.36** |
| Medium | dark | 9.33 | 4.98 | **2.36** |
| Critical | dark | 6.03 | 3.71 | **2.36** |

Nine of eighteen pairings fail. This is a widening of what the gap entry *computed*, not of what it
*claims*: its truth statement is "sufficient WCAG point-contrast against its badge background, **at
every age stage**". Fixing only the stale stage would leave light-mode aging at 2.19:1 — the same
defect, same mechanism, re-openable by the next audit. All eighteen are in scope, and this expansion
is flagged here deliberately rather than absorbed silently.

**What this plan deliberately does not decide.** It does not prescribe a stroke-width number, a
colour hex, or a token. Those are implementation decisions. What it does fix is the *bar*: each
mechanism ships with a computed automated gate that fails on today's shipped values, so "changed" and
"fixed" cannot be confused. It also folds in 01-REVIEW.md's WR-01 (a dead badge-scoped sizing selector
plus a coverage hole in the guard meant to catch exactly that residue), because WR-01 lives in the two
files Task 1 already edits.

Purpose: make the product's category vocabulary readable at a glance during an emergency, which is
the reason the user escalated a cosmetically-minor issue in the first place.
Output: heavier glyph artwork, an age-aware badge foreground, two computed contract gates, and a
human confirmation that a person can actually name each category at the smallest size shipped.

This task closes Mechanism 2: the badge glyph foreground never adapts when the age ramp rewrites the
badge fill underneath it. Independently shippable — it touches no artwork and no sizing rule.

**The one structural constraint, and why it is not negotiable.** The corrected foreground must reach
the badge by CSS custom-property INHERITANCE, declared in the same `.age-*` rules that already write
`--severity-current`. It must NOT be delivered by a descendant selector or a compound selector,
because the two badge contexts disagree about where the age class lands: `map.js:144` builds
`icon-badge icon-badge--pin {sev} {age}` — age class on the badge element itself — while `feed.js:169`
applies the age class to the row `<li>` ancestor and leaves the badge bare. A descendant form covers
only the feed row; a compound form covers only the map pin. Each ships a fix that looks correct in
whichever context the author happened to open. An inherited custom property covers both, and is also
what makes the gate below able to resolve the foreground statically.

Give `.icon-badge`'s `color` a `var(--your-property, var(--existing-token))` shape so an age stage that
declares no override falls through to today's value, and the property name stays discoverable from the
one rule that consumes it.

**The target.** Every pairing in the eighteen-row matrix in this plan's objective must reach at least
3.0:1 — WCAG 1.4.11's graphical-object floor, which is the standard the gap entry itself names. Nine
currently fail.

**What you must preserve while getting there.** D-12: a badge stays a solid severity-coloured circle
with a single neutral glyph knocked out of it (the map-pin/marker pattern). Do not restyle it into an
outline, a ring, a two-tone plate, or a glyph with its own background. D-17: the age ramp remains
desaturation toward gray, three discrete stages, never opacity. D-11: severity keeps its traffic-light
mapping. D-13: the two themes stay genuinely distinct palettes, not one inverted into the other.

**A worked option that provably clears the matrix.** Planning verified this one; it is offered so you
are not solving a colour-search problem from scratch, not as a mandate. Declare the override in the
aging and stale rules only, pointing at the existing `--color-text` token — which is theme-aware
already, so no theme block needs editing:
- light: stale 10.58:1; aging 5.56-7.74:1
- dark: stale 7.49:1; aging 3.45-4.77:1
Fresh keeps today's foreground and already passes in five of six cases (dark 6.03-10.14, light low
3.06, light critical 5.44).

That leaves exactly one failure: **light-mode fresh medium, at 2.94:1** — about 2% short of the floor.
Two routes, both legitimate, neither pre-picked:
- Darken light `--color-severity-medium` just enough to clear the floor. Visually imperceptible, but it
  changes a hex that D-11 approved and `01-UI-SPEC.md` documents, so both the token and the spec must
  move together (see the doc-sync rule below).
- Give the medium severity its own foreground. **If you take this route, scope it per theme.** A bare
  `.sev-medium { --your-property: ... }` inverts correctly in light mode and simultaneously destroys
  dark fresh medium, dropping it from 9.33:1 to roughly 1.90:1 — the gate will catch it, but know it
  going in.

**The theme-block trap, if your fix touches any token value.** There are four theme sources in
`main.css`, not two: the base `:root` block and `:root[data-theme="light"]` both carry light values;
`@media (prefers-color-scheme: dark) :root` and `:root[data-theme="dark"]` both carry dark values.
Editing one member of a pair and not the other ships a fix that works for OS-preference users and not
for explicit-toggle users, or vice versa. The gate asserts pairwise equality for every token the
matrix consumes, so a half-applied edit fails rather than escaping.

**Doc sync, conditional.** If — and only if — your fix changes a hex that `01-UI-SPEC.md` documents,
update that document's colour table in the same commit so it does not become stale documentation of a
value the code no longer holds. If your fix only adds a foreground override that references an
existing token, `01-UI-SPEC.md` needs no edit and must not receive a cosmetic one.

**The gate: `TestBadgeGlyphContrastAcrossAgeStagesAndThemes` in `web/css_contract_test.go`.**

Same conventions as its neighbours: embedded tree only, `stripCSSComments`, split-on-last-opening-brace
rule parsing, loud failure over silent skip. Build it in five layers:

1. **Token tables.** Parse the four theme sources into a light table and a dark table. Distinguish them
   by the trimmed selector head: an exact `:root`, the two attribute-selector forms, and — the one that
   bites — the media block, whose head after a last-brace split retains its `@media` preamble, so it is
   identified by that preamble and not by any substring search for the word it contains. Assert pairwise
   equality across each theme's two sources for every token the matrix consumes. `t.Fatalf` on a token
   the matrix needs and no source declares.
2. **Badge fill per severity and age stage.** Resolve `--severity-current` from the shipped rules rather
   than hardcoding the ramp: read each `.sev-*` rule's `--severity-base`, then read each `.age-*` rule's
   `--severity-current`. Support exactly three value forms — a passthrough of the severity base, a
   passthrough of the stale token, and the `color-mix(in srgb, A P%, B Q%)` form. Implement the mix as a
   weighted per-channel average of the gamma-encoded sRGB bytes, which is what `in srgb` interpolation
   means; do not linearise first. Any fourth form must `t.Fatalf` telling the reader to extend the
   resolver rather than delete the pairing.
3. **Glyph foreground per age stage.** Parse `.icon-badge`'s own `color` declaration and accept exactly
   two shapes: a bare `var(--token)`, or `var(--override, var(--token))`. From the second, take the
   override property's name and look for it **in the rule whose trimmed selector head is exactly
   `.age-{stage}`** — an exact match on the whole head, never a substring search for the stage name.
   Where that rule declares the property, it is that stage's foreground; otherwise the base token applies.
   **Derive the override name from the CSS — do not hardcode it** — so the test tracks a rename instead of
   silently falling back.

   The exact-head match is load-bearing, not fussiness: it is what makes a wrongly-shaped fix
   self-detecting. A compound form such as a badge-class-and-age-class selector, or a descendant form,
   would satisfy a substring search while covering only one of the two badge contexts (see the structural
   constraint above) — the resolver would compute a passing ratio for a fix that is broken in the browser.
   With an exact-head match, those shapes leave the `.age-*` rules bare, the resolver falls through to the
   base token, and the failing ratios reappear as they should. Say this in the doc comment; a future
   reader must not "simplify" it into a `strings.Contains`.
4. **Contrast.** Standard WCAG relative luminance (the sRGB channel transfer function, then the
   0.2126/0.7152/0.0722 weights) and the `(L1+0.05)/(L2+0.05)` ratio.
5. **The matrix.** Assert at least 3.0:1 for all three severities x all three age stages x both themes.
   Assert the loop actually ran eighteen pairings before reporting success. On failure, name the
   severity, stage, theme, both resolved hexes, and the computed ratio to two decimals — a bare boolean
   failure here costs the next reader the whole derivation. `t.Logf` the full eighteen-row table so the
   numbers are copyable into the SUMMARY.

Honest-limits doc comment, same as its neighbours: point contrast is a necessary condition for a
readable glyph, not a sufficient one — it says nothing about whether the shape is identifiable, which
is Mechanism 1's concern and Task 3's check.

Record in the SUMMARY: which route was taken for light fresh medium, and the resulting eighteen ratios.
