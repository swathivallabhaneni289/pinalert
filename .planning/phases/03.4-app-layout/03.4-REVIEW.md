## Critical Issues

### CR-01: The home area stores whatever name the client sends, so a building or street name is kept, against D-25 and the profile.go privacy claim

**File:** `internal/service/profile.go:7-8, 144-158` (with `internal/api/handlers/me.go:154-169`)
**Classification:** BLOCKER
**Issue:** The header of profile.go promises: "nothing in the database can say where an account lives more precisely than about 5 km". D-25 says the home area is "a town or area, never a street". The server enforces neither. `ValidateProfileUpdate` checks only that the name is non empty, at most 120 runes and free of Cc control characters, then stores it verbatim in `accounts.home_area_name`. Only the cell is coarsened.

Both client paths feed it point of interest names:
- `web/static/js/welcome.js:41` runs step 3's search against `/api/geocode`, and step 4 prefills the home area from that pick (welcome.js:240-243).
- `placeShortName` (welcome.js:344) sends `result.name`.
- Settings and step 4 use `/api/geocode/place`. That shares the same `search` routine and so returns the same granularity (geocode/client.go:209, 753).

The geocoder's own fixture shows the kind of result that comes back: `{"name":"Sai Residency","display_name":"Sai Residency, Road No 12, Banjara Hills, Hyderabad..."}` (internal/geocode/order_test.go:83).

**Failure scenario:**
1. At step 3, a new user types the name of their apartment block to centre the map and picks "Sai Residency".
2. Step 4 prefills Home area with "Sai Residency". The user taps Continue.
3. The database now holds `home_area_name = 'Sai Residency'` plus a 5 km cell around it. Together they identify the person's building.
4. A direct `PATCH /api/me/profile` can store any 120 character text in the same way, for example "Flat 4B, 12th Main Road, Indiranagar".

This is the exact precision the design said would never be stored, and step 3 tells the user their exact spot is never stored.
**Fix:** Have the server decide the name, not the client. Choose one:
- (a) Accept only a point, and derive a settlement level name server side from the cell or a reverse lookup at locality level.
- (b) Accept a result token issued by `/api/geocode/place` that the server can check is a settlement or area level result, rejecting POI, building and street results.

Either way, correct the profile.go header comment until the claim is true. The browser reviewer should also look at welcome.js:41 and 240-243 (the step 3 to step 4 prefill).

### WR-01: Consent is enforced only on HTML GETs; an account that never agreed can post and vote through /api/

**File:** `internal/api/onboarding.go:51-55`
**Classification:** WARNING (a deliberate decision to confirm, not a silent bug)
**Issue:** `requireOnboarded` passes every `/api/` path and every non GET method. The reason given is orchestrator decision 5: queued offline sends and people part way through the flow must never meet a new 4xx. That reason covers accounts that agreed to an older version, or are mid flow. It also covers accounts with no consent record at all, including one that tapped Disagree. Such an account can call `POST /api/reports`, the five vote routes and the flag route directly, so the "Only Agree moves on" rule (D-27) holds only for the HTML shell. CLAUDE.md flags IT Rules 2021 exposure, so the consent record has legal weight.
**Failure scenario:** A user taps Disagree, then posts a report with curl or a saved request from an earlier session. It is stored and shown nearby, and `terms_version` is NULL.
**Fix:** If decision 5 was meant only for accounts that agreed to some version, refuse write routes (POST /api/reports, the votes and the flag) with a 403 field `terms` when `acc.TermsVersion == ""`. Keep the pass through for an older non empty version, so queued sends after a terms bump still go through. If the open API is intended, record that in the decision log next to ROBUST-08's risk note.

### WR-02: The name check rejects only Cc control characters, so zero width and bidi override names are stored

**File:** `internal/service/profile.go:110-118, 128-139`
**Classification:** WARNING
**Issue:** `cleanText` refuses only `unicode.IsControl` (category Cc). Format characters (Cf) pass, for example U+200B zero width space, U+202E right to left override and U+2066 to U+2069 isolates. `strings.TrimSpace` does not remove them. The 400 message says "Use letters, numbers and spaces in your name.", which the rule does not enforce.
**Failure scenario:** Today:
- `{"display_name":"​"}` stores a one rune invisible name that passes the CHECK constraint (length 1).
- `{"display_name":"‮redro"}` stores a name that displays reversed.

Names are shown only to their owner today. Phases 3.2 and 9 make names public, and these stored values will not be checked again.
**Fix:** Reject `unicode.Is(unicode.Cf, r)` as well as Cc (or allow only L, M, N, Zs and a small punctuation set). Treat a name whose runes are all Cf or whitespace as empty. Apply the same rule to the home area name. Change the message to match whatever rule is chosen.

### WR-03: UpdateProfile writes the name and the home area in two statements with no transaction

**File:** `internal/service/profile.go:237-254`
**Classification:** WARNING
**Issue:** `SetAccountDisplayName` and `SetAccountHomeArea` are separate UPDATEs. The comment "a refusal changes nothing" is true for validation errors only. If the second write fails (a connection drop or a statement timeout), the name is committed, the handler answers 500 (me.go:182-185), and the browser shows "save failed" even though half the change is stored.
**Failure scenario:** Step 4 sends a name and a home area. The home area UPDATE fails. The client retries or gives up, believing nothing changed, but the name is already set. Settings then shows a name the person thinks was not saved.
**Fix:** Write both in one statement, for example one `UpdateAccountProfile` query using `CASE WHEN sqlc.arg(set_name) THEN sqlc.narg(display_name) ELSE display_name END` for each column. Or run the two queries in a pgx transaction, as `ModerationTx` does elsewhere.

## Critical Issues

### CR-01: A link to a finished report is a dead end when the browser has no saved position

**Files:**
- `web/static/js/feed.js:946-954` (handleFocus redirect)
- `web/static/js/ended-nearby.js:342-352` (load)
- `web/static/js/moderate.js:303-305` (moderator link)
- `web/static/js/map.js:362-365, 434-436` (saveReaderFix)

**Issue:** This phase sends every link to a resolved or faded report to `/profile?part=ended&report=ID`:
- `feed.js` does it with `location.replace` once the focus answer says `resolved` or `past`;
- `moderate.js` builds that address directly for moderators.

On that page, `load()` reads `PinalertPosition.read()`. When it gets null, it shows the location state and
returns before any request, so `chosenId` is never sent. A position is saved only from a device fix
(`saveReaderFix` saves only when `own === true`, and welcome.js saves only after Allow location).

The server's focus answer does not need the reader's centre. `internal/service/historyread.go:395-397` says
FocusOK "holds outside the radius and outside the history window when the report is still listed in some
view". Before this phase, the same link opened the report on Nearby's Past tab from the fallback centre
(old `feed.js:1216-1221`, `selectTabOnScreen`). So a path that used to work now fails.

**Failure scenarios:**
1. A reader refuses location, or has never granted it on this browser, and taps a shared `/?report=123` for a
   resolved report. Nearby loads from the fallback centre and gets `focus.status === 'ok'` with view
   `resolved`. It redirects to `/profile?part=ended&report=123`, which shows "Ended nearby needs your
   location". No row and no toast appear, and the report is never shown.
2. A moderator on a laptop that never granted location clicks a resolved report's link in the moderation
   queue (`moderate.js:304`) and lands on the same empty state.

**Fix:** when the address carries a report id, read even without a saved position. Use the fallback centre
for the request and draw only the linked row:

```js
function load(quiet) {
  var position = readPosition();
  var seq = ++readSeq;
  fillDistances(position);
  if (!position && chosenId === null) {
    if (quiet !== true) { showState('location'); }
    return Promise.resolve(null);
  }
  var centre = position || { lat: Pinalert.config.fallbackLat, lon: Pinalert.config.fallbackLon };
  // ...build the URL from centre; when !position, render only linked.report
  // (skip the two groups) and keep the "needs your location" line visible.
}
```

A narrower option: in `feed.js handleFocus`, redirect only when `PinalertPosition.read()` is not null.
Otherwise keep the reader on Nearby and show the finished report's pin from the focus answer.

### WR-03: In Settings, a save that answers late closes a window opened since, and one flag covers both windows

**Files:**
- `web/static/js/settings.js:288-316` (openWindow resets `saving`)
- `web/static/js/settings.js:364-387` (saveName)
- `web/static/js/settings.js:499-528` (afterHomeSave, saveHomeArea)

**Issue:**
- `openWindow` always sets `saving = false`.
- `saveName` and `saveHomeArea` close their window when the answer arrives, without checking that it is
  still the same window session.
- Both windows share the one `saving` flag.

**Failure scenarios:**
1. **Late answer closes the new window:** on a slow connection the person saves a name, presses Escape, opens
   Name again (the field shows the old name, because the row is not updated yet) and starts typing. The first
   PATCH answers, `setRow` runs, and `closeWindow('name', true)` closes the window they are typing in. Their
   edit is lost.
2. **Double save:** if they press Save again in the reopened window before the first answer (allowed, because
   `saving` was reset), two PATCHes go out.
3. **Flag cleared by the other window:** a home save that answers while a name save is in flight runs
   `afterHomeSave` and sets `saving = false` for the name window too.

**Fix:** give each window session a token and ignore answers from an older session, with one flag per
window:

```js
var session = 0;
function openWindow(which) { session += 1; /* ... */ }
function saveName() {
  var mine = session;
  return patchProfile(...).then(function (answer) {
    if (mine !== session) { if (answer.ok) { setRow(...); } return; }
    // ...as now
  });
}
```
