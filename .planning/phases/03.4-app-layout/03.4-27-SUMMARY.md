# Phase 3.4 Plan 27: Skeptic review fixes Summary

**Joiners in Indic and Persian names are accepted where the script needs them and refused everywhere else, every kept position now has an owner on every page that writes or reads it, and a reopened Settings window shows what an earlier save stored.**

## Findings

### S-1 Names with the zero width joiner or non joiner: fixed

Reproduced: `TestNameJoinersFollowTheContextualRule` (new, in `internal/service/profile_test.go`) failed first for all seven accepted cases, for both the display name and the home area name (commit 79b393b).

Fix (commit 72d0a5a): `cleanText` in `internal/service/profile.go` now allows U+200D only when the rune before it is a virama (canonical combining class 9), and U+200C when the rune before it is a virama or when the nearest non mark rune on each side is an Arabic script letter. Every other control and format character is still refused. The top comment says what is allowed and why. Error messages are unchanged.

Accepted by the test: Malayalam chillu with a trailing joiner, Marathi eyelash ra, Sinhala Sri, Bengali ya phala, Devanagari non joiner after a virama, a Persian word with a non joiner between letters, and one with a combining mark before the non joiner. Refused: joiner or non joiner inside a Latin word, lone joiners, a name that starts with a joiner, joiner or non joiner after a letter that is not a virama, a non joiner between Latin and Arabic, a trailing non joiner after Arabic, a joiner followed by a zero width space, and the cases plan 24 already refused (U+200B, U+202E, U+2066, U+FEFF).

`go.mod` changes by one line only: `golang.org/x/text v0.41.0` moves from indirect to a direct require. `go.sum` is unchanged.

### S-2 Kept position with no owner: fixed

Reproduced: five new low page tests, one new position test and `TestWelcomeRendersOwnAccountID` failed first (commit 0a5a59d). `/low` cannot be reached without an account (`TestLowPageRenders`, "no account is a 500"), so low.js always has an account id on a real page and no path needed keeping.

Fix (commit 752b04c):
- `position.js` `save` answers false and writes nothing when the page carries no account id. The comment on the take over branch now says only values from before this plan are ownerless.
- `welcomeViewModel` has `AccountID` (from the account the handler already has) and `welcome.html.tmpl` renders it as `data-account-id` on the flow root, so the step 3 save has an owner.
- `low.js` reads the page's account from `[data-account-id]` with the same id pattern. It stores the account with the position; on read it uses its own value, removes another account's value and returns nothing, and takes over an ownerless value (writing it back with this account and its own time). A page without an account id reads nothing, removes nothing and writes nothing. Only the one key is ever removed. Every storage access is in try/catch.

### S-3 Reopened Settings window keeps the old value: fixed

Reproduced: three of the six new tests in `web/settings_window_test.mjs` failed first (the name refill, the home refill and the removal refill); the three "left alone" and "refused save" guards passed already, as expected (commit 0a5a59d).

Fix (commit 25e4ae8): `settings.js` remembers per opening the value each field was filled with (`nameFilled`, `homeFilled`). When a successful answer arrives for a save sent from an earlier opening while the same window is open again, `refillAfterEarlierSave` refills the field only if it still holds that value (and, for the home area, no place is picked), then works out the Save and Remove state again from the flags. A field the person changed is left alone. A refused save refills nothing. The same helper covers the home area removal.
