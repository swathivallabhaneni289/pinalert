## Cause, change and proof per defect

### 1. The laptop shell was 2px taller than the window (T13.10c, P4.08.1b)

- **Cause.** Not a border on the bars and not the strip. Both bars are border-box and measured exactly 48px (strip) and 63px (top bar) at 1280x800. The top bar token is 61px (44px control row, 8px above and below, 1px hairline), but the bar was 63px, because its tallest child, the place search form, was 46px: the `.map-search__field` is a 44px control wrapped in its own 1px border on both sides. The shell, the panes and `#map` subtract the 61px token, so they ended 2px past the window (scrollHeight was innerHeight + 2 at 1280x800, 1280x720 and 1000x900, light and dark). On the phone the field has no border (phone.css), so it was already 44px there.
- **Change.** app-bar.css, inside the existing `@media (min-width: 900px)` block: `.map-search__field { margin-block: -1px; }`, with a comment. The border now hangs into the bar's 8px padding, the form is 44px, the bar is 61px, and the drawn field looks the same as before (46px). The token, the phone block, phone.css and sheet.js are untouched. The only user of the class is the top bar (templates/place_search.html.tmpl, included from app_bar.html.tmpl).
- **Pin.** `TestLaptopNearbyShellFitsWindow` (laptop_nearby_contract_test.go) pins the 61px token, the bar's floor, padding and hairline, border-box on everything, the field's 44px floor and border, the margin in the 900px block only, and that neither the base rule nor phone.css holds it.
- **Probe after the fix** (own scratch server, 1280x800, 1280x720, 1000x900, light and dark, Chromium): top bar 61px, scrollHeight equals innerHeight, and the bottoms of `#app-shell`, both panes and `#map` equal the window height.

### 4. ResizeObserver loop error on laptop Nearby (P4.N1.3b)

- **Cause.** Fixing finding 1 did not remove it. Neither map.js observer writes layout in its callback (`watchMapBox` sets a timer, the popup observer uses requestAnimationFrame). The writer is theme.js: `measureBar` was the strip observer's callback and set `--disclaimer-bar-height` on the root inside the delivery. The notice strip and `#app-shell` are both direct children of the body (index.html.tmpl), so they are at the same depth; the token write resized the shell, which sheet.js observes, in the same pass, and the browser cannot deliver an observation at the same depth in that pass. It then raised "ResizeObserver loop completed with undelivered notifications". The old comment in theme.js ("there is no ResizeObserver loop") was wrong. A probe that logged every observer delivery showed the order strip, shell, map at 150 and 200 percent in both engines.
- **Change.** theme.js (a file outside the plan's list, see Deviations): the strip observer now calls `scheduleMeasure`, which asks for one `requestAnimationFrame` and then calls `measureBar`. The first measurement and the window resize listener still write at once. The comment is corrected. map.js is unchanged, and the map is still told its size (the settle timer and `invalidateSize` are as plan 20 left them; the probe shows the map observer still fires after the shell at both text sizes).
- **Pins.** `TestBarTokenFollowsTheRealBar` is amended with the dated note "Amended 2026-10-17 by Phase 3.4 plan 21 (plan 17 finding 4)": it now requires `new ResizeObserver(scheduleMeasure).observe(barEl)`, refuses `new ResizeObserver(measureBar)`, requires `scheduleMeasure` to call `measureBar` from a `requestAnimationFrame` callback and to read or write no layout itself. Nothing was weakened. New `TestMapObserversNeverWriteLayoutInTheCallback` pins that map.js has exactly two observers, that `invalidateSize` runs only inside the settle timer (so the map is still told its size), and that the popup card observer relays out only inside `requestAnimationFrame`.
- **Probe after the fix** (laptop Nearby, 1280x800, text 100, 150 and 200 percent): no error in Chromium or WebKit (before: Chromium 150 and 200 percent, WebKit 150 and 200 percent and a page error).

### 5. My activity row at 320px and 200 percent text (T11.8o, T11.8p): NOT FIXED

- **Not old behaviour.** At the phase start commit 022ce30 the same label and rule (`.trust-signal__text { overflow-wrap: anywhere }`, trust.css, byte for byte the same) gave a clean result: exported with `git archive` into the harness work folder, built and probed at 320px with 200 percent text, the label "Report needs re-confirming" broke "Report needs" / "re-confirming" (a space break, text 198px wide, toggle 196px tall). So the plan's "if it predates 022ce30, change nothing" branch does not apply.
- **Cause.** Width, not the wrap rule. Plan 07's phone card (phone.css, the card grid `minmax(0, 1fr) auto` with the areas "what distance") puts the What happened cell beside the distance. At 200 percent text the `auto` distance column takes about 131px of the 254px inside the card, so the What cell is 123px (178px at 100 percent) and the label's text box is 95px (126px at 100 percent). The longest word, "confirming", is about 150px at that size, so it cannot fit on a line of its own.
- **What I tried, by injecting CSS in the probe (Chromium, 320px, 200 percent):** `overflow-wrap: break-word` on the label breaks it the same way ("confirm" / "ing"); `overflow-wrap: normal` keeps "confirming" whole but it sticks out of the face (text right edge 189.8px against a face right edge of 156.1px), which the harness fit checks and the clipping signals row would reject. Both engines show the same numbers. `hyphens: auto` would also count as a mid word break. So no rule that reaches the label can pass T11.8o and T11.8p at that width.
- **Measured widths** (Chromium and WebKit agree): What cell 177.8px at 100 percent and 123.1px at 200 percent; distance cell 76.2px and 130.9px; label text box 125.8px and 95.1px; toggle 103.2px and 523.9px tall for the long label.
- **Why it was not changed here.** The only places that decide those widths are phone.css's card grid rules (rule 9 forbids editing the file, and plan truth 4 keeps phone rules in its one narrow block), and the shared `.trust-signal__text` rule in trust.css (changing it would change the map popup and the feed rows). Moving phone grid rules into activity.css would also put phone rules outside phone.css. No `activity_trust_contract_test.go` test was added, because a pin that forbids `overflow-wrap: anywhere` on the label would fail against the current shared rule and could not be made to pass without changing trust.css.
- **Suggested fix for the owner or a follow up plan** (phone.css, outside this plan): let the What cell have its own full width row on the phone card, for example the areas "what what" over "distance distance", or give the distance column a share limit so the What cell keeps at least the width of the longest label word. A browser pass should then re-run T11.8o and T11.8p.
