### CR-01 (fixed, ended-nearby.js)

With no kept position and a `report` id in the address (`/profile?part=ended&report=ID`), `load()` used to show the location state and send nothing, so a shared link, Nearby's redirect and the moderator link all ended on an empty page. It now sends the one read (still the single `fetch(` the contract pins) from `Pinalert.config.fallbackLat/Lon` with the id, and draws only the linked row. The reports around the fallback centre are not drawn. The row is drawn from a copy with `distance_km: null`, so its cell reads Unknown (otherwise it would say a number, or "about N km" for a finished Rescue, measured from nobody). The hub count stays empty and the location state stays on screen under the row. With a link that is too old, unavailable or not finished the part is just the location state, and the toast is told once. A take back on that row reads the part again the same way. Without a link, and without a position, nothing is requested, as before. The server still decides what the reader may see (T-34-98): the client sends one id.

The profile page has no `#app-shell`, so `Pinalert.config.fallbackLat/Lon` come from app.js's defaults (12.9716, 77.5946). These are the same numbers as `fallbackLat` and `fallbackLon` in cmd/server/main.go today. Exposing them on the profile page would need a handler change, which is outside this plan, so it is noted here.

### WR-01 (fixed, position.js)

Reproduced by reading: `savedAt` was never read and nothing removed the key. `position.js` now saves `{lat, lon, savedAt, account}` where `account` is the page's `data-account-id` (profile, Nearby, Low, Settings and Alerts already render it; the offline queue keys by it). `read()` returns a fix only for the account that saved it. A fix owned by another account is not returned and its key is removed, so the next person on a shared phone does not get the previous one's place (T-34-97). Only `pinalert.lowLastPosition` is ever removed: the offline queue and the theme choice are untouched (tested). No age limit was added, as the plan says. A page with no account id (the first time flow) can still save and reads nothing.

A value with no owner (written by the Low data view, by the first time flow, or by a browser from before this change, and also what the browser harness seeds) is taken over by the first account that reads it and written back under that account. My first version dropped such values; the first harness run (results-20261017T052837.txt) then failed 64 Ended nearby cases in test 14 and 4 in test 18 because the harness seeds the key without an account. That is why ownerless values are now claimed, not dropped. The cost: a value with no owner that was written by another person is given to the first account that reads it. After that it is owned.

Residual, not changed because the file is outside this plan: `low.js` has its own copy of the key and writes it with no account, and reads it with no check. On the Low data view a later account can still read a fix the earlier account saved on that same view. One line in `low.js` `storePosition` (add the page's `data-account-id`) would close it. No clear on log out was added: `position.js` is not loaded on Settings, Low or Alerts, where the log out form is, and the account key makes the clear unnecessary for the pages that read it.

### WR-02 (fixed, reader.js)

Reproduced by reading: `FOCUSABLE` was the X and the box only, and the box wrapped to the X. The trap is now built from the live window with the selector settings.js and account-menu.js use (`button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])`), skipping anything under `[hidden]`, so Tab and Shift Tab reach the Call 112 `tel:` link and the two `mailto:` links. The title (`tabindex="-1"`) is not a stop. One existing assertion changed legitimately ("Tab stays inside the window": the last stop is now the last link, not the box) with a dated amendment note in the test.

### WR-03 (fixed, settings.js)

Reproduced by reading and by the failing cases. Each opening of a window increments a `session`; a save remembers the session it was sent under, and an answer from another session updates the row (`setRow`) but never closes, clears or writes a refusal into the window open now. The one `saving` flag is now `savingName` and `savingHome`, cleared only by the answer of their own save, never by opening or closing (so a save still out is still out, and a reopened Name window cannot send a second PATCH). Remove home area uses the home flag.

### WR-04 (fixed, show-menu.js)

Reproduced by reading (account-menu.js:170 `stopPropagation` on its trigger means a bubble listener on `document` never sees the click) and by a capture aware fake document in the test. The outside click listener is now added and removed with the capture flag, like the bell list in app-bar.js. The contract pin in `show_menu_contract_test.go` has a dated amendment note.

### WR-05 (fixed, feed.js and app-bar.js)

The reviewer had only read this. It was run: a scratch server on 8761 with two origins (127.0.0.1 and localhost), a page on one origin linking to a second page that does `location.replace('/c')`. In both Chromium and WebKit, at the final page `document.referrer` was the same origin page that had been replaced (`http://localhost:8761/a?report=1`), `history.length` was 3, and `history.back()` went to the other origin's page. So the back arrow's test (`sameOriginReferrer() && history.length > 1`) sends the person off the site. Typing the address or using a bookmark gives the same result, since the referrer of a scripted `replace` is always the page that called it.

feed.js now ends the redirect address with `&from=link` (`REDIRECT_MARK`; the server ignores unknown parameters) and app-bar.js follows the arrow's own address when `from=link` is in the address. The three `replaced` assertions in `feed_groups_test.mjs` carry a dated amendment note. Moderator links (`moderate.js`) do not replace the history entry and are unchanged.

### WR-06 (fixed, ended-nearby.js)

Reproduced by the failing cases. Focus is not put on the part title as the reviewer suggested, because `phone.css` hides `.activity-part__title` on the phone part screen (`display: none`), where focusing it would do nothing. Try again now holds focus on the skeleton (`tabindex="-1"`, on screen while the read is out) and, when the read settles, moves it to Try again (a second failure), the first row, the empty block or the location line, each with `tabindex="-1"`. If the person moved focus elsewhere meanwhile, it is left alone.

### WR-07 (fixed, profile.html.tmpl)

The reviewer had marked this unverified. It was run in a scratch page: `a.js` (deferred, runs a `fetch` and logs `typeof window.X` when it answers) and `b.js` (deferred after it, served 1.5 s late, defines `X`). In both Chromium and WebKit the log read `fast ran`, `answer in, X is undefined`, `slow ran`: the browser delivers a fetch answer while it waits for a later deferred script. So on a cold, slow connection the first Ended nearby read can draw before `PinalertTrust` exists, `render` throws a ReferenceError and the `.catch` shows "Couldn't load reports". The fix moves `ended-cards.js` and `ended-nearby.js` after `visibility.js` and `trust.js` in profile.html.tmpl (the pinned orders still hold; activity.js and queue.js do not call them). A `DOMContentLoaded` start was not used because `readyState` is already `interactive` while deferred scripts run and every node test expects the first read to start with the script. The order is pinned in `code_review_p25_contract_test.go`.
