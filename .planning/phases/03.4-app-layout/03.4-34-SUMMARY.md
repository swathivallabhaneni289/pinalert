# Phase 3.4 Plan 34: The home area search finds more places Summary

**Text with no comma or only a PIN code now gets the Use "Gayathri Nagar, Vijayawada" row placed in the right town, and a search with no close match asks for the town, all inside the existing cap of four upstream requests.**

## What the owner's three causes turned out to be

1. **Bengaluru lean.** No page ever sent a near point for the home area. `welcome.js` and `settings.js` send the text only, and the server's handler passes `lat` and `lon` through only when the request carries them. A live Photon call for "Benz Circle Vijayawada" with the areas layers and no lat or lon returned only Bengaluru circles (Bandi Reddy Circle Ward, Gandhi Circle, St. Mark's Circle Plaza, Nethaji Circle). So the lean is Photon's own ranking on the word Circle, not a made up centre, and nothing was removed. What fixes that example is the typed row below. Truth 1 is pinned by tests so it cannot start happening: a Go test (no lat or lon reaches Photon without a near point), a node test in each page (the URL is the text only, with a stored device fix and a Bengaluru fallback centre both seeded in the step 4 test), and a contract test (no `lat=`, `lon=` or `fallback` in either file). No near point is sent from a device fix either (key decision 2).
2. **No comma.** `parseTypedHome` only made a typed row from `first, town`. Now a single part is split (see below).
3. **PIN only.** `stripTrailing` dropped the PIN before anything could use it. It now returns the PIN it dropped.

## What changed

### Go (`internal/geocode`)
- `typed.go`: `typedHome` also holds `lead`, `streetLike`, `bare` and `pin`. `resolveWithoutComma` splits text with no comma: the last two words, then the last one, are the town candidates. A candidate is accepted when the answer in hand names it in a label (no request), else when one areas lookup finds a city level row of that name. Then `resolveByPin` looks the PIN up once as an any place search, which returns Photon's postcode row, and takes the town that row names. The same PIN lookup is the fallback when a comma form town cannot be placed (a state typed as the town). The existing guards stay: digits or street words in the neighbourhood, names under 3 letters and names over 120 letters never get a row, and a street address gets no lookup at all.
- `areas.go`: `photonIsCityLevel`, `photonRegion`, `regionName` (city, else county without a trailing (Urban) or District).
- `photon.go`, `client.go`: two unexported fields on `Result` (`cityLevel`, `region`, set by the Photon reader only, never serialised) and `Answer.NoCloseMatch`, set by `SearchReaderAreas` only. `SearchReaderAreas` now runs the typed logic for text with no comma too.
- `noCloseMatch`: true when no row is typed and no row's name is a close spelling of, starts with, or is a start of what was typed. A street address never sets it.

### Handler and docs
- `place.go`: `PlaceResponse` is `GeocodeResponse` plus `no_match` (omitted unless true, and only ever true with `kind=area`). The swagger annotation points at it; `docs/` regenerated into the scratchpad with `swag init` and copied in (diff: the new definition and the description).

### Pages
- `welcome.js` and `settings.js`: `MESSAGE_NOT_FOUND = 'Not found. Add your town, for example: Gayathri Nagar, Vijayawada'`. It shows when the answer has no rows, or when `no_match === true` and no row is typed. The rows stay listed next to the line. The old No matches found line is gone from these two files only (the map search and the report form keep theirs). Both pages share the same code, so phone and laptop behave the same.

## Worst case upstream requests for one typed search
**4**, the unchanged per search cap (`maxUpstreamPerSearch`). Every new lookup (a town probe, the PIN) goes through the `typedLookup.photon` method that refuses a request when 4 are used, takes its Photon token by the reader rule, and is answered from the cache on a repeat. The longest path is: areas search 1, two town probes (two word then one word) 2, PIN 1, and then no request is left for the any place search, so the PIN row's point is used. `TestSplitAndPinLookupsStayInsideTheCapOfFour` pins exactly 4 for that path and for a search whose own tries used all 4 (no extra lookup is sent). A repeat of the same text sends 0. The per account budget (8 then 1 a second), the process limiters, the 400 ms typing pause and the 1 second typed gap are unchanged.

Cost to know: a text of three or more words whose last two words are not locality words spends one town probe on the two word candidate even when the answer in hand already names the one word town. It is bounded by the cap, and it is why 'Kharghar Navi Mumbai' comes out right.

## Deviations from Plan

**1. [Interpretation of truth 1] No near point is sent at all.** The plan reads as if the pages sent the fallback centre. They never did, and the Bengaluru circles are Photon's ranking with no centre. I kept the rule as a pinned fact instead of sending a device fix (which the plan allows): a person in Bengaluru typing a Vijayawada area would be pulled the wrong way, and Settings does not load `position.js`. The saved home area centre is not on either page either. Say if a device fix should be sent after all.

**2. [Rule 3 - response shape] `no_match` is a new field.** The plan's file list names `place.go` (only if needed) and docs; the flag needed the shape change, so `PlaceResponse` lives in `place.go` and `docs/` was regenerated. `geocode.go` (the report search) is untouched and never carries it.

**3. [Rule 2 - missing coverage] The old No matches found line is replaced in these two fields.** An empty answer is also "no close match and no typed row", so it shows the new sentence. The map search (`map-tools.js`) and the report form keep theirs.

**4. [Rule 1 - found by review] PIN fallback for a typed town that cannot be placed.** The first version only used the PIN when no town was typed; "Gayathri Nagar, Andhra Pradesh, 520008" (a state as the town, which the areas layers never return) got no row. It now falls back to the PIN. Test added.

**5. [Small extension] More locality words than the plan names** are never taken as a town (nagar, colony, circle, hills, park, sector, block and others, listed in `typed.go`).

**6. [Process] 12 live calls**, more than a handful, listed above, so the five results could be replayed from recorded rows rather than sent again.

## Known limits
- A town accepted from the answer in hand is not checked for city level; only a probed town is.
- The PIN town for a postcode row with no city and no county is not found, so no row is placed (the status line then asks for the town).
- The PIN town is the district or county the postcode row names: 560034 would read "Bangalore South", not Bengaluru.
- The typed row for text with no comma never uses the Photon search for a name that is only a landmark (Benz Circle works because the bus stop carries the name).
- Step 3 and the report form are unchanged.
