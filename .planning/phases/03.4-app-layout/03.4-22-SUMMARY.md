## Mechanism chosen and why

Cause (from plan 21, re-measured here): the phone card grid is `minmax(0, 1fr) auto` with the last row "what distance". The `auto` distance column grows with the text, so the What happened cell is left with too little width for the longest word of the label, "confirming".

The change is inside phone.css's one narrow media block, three small pieces:

1. `main.profile-page > .activity-part .profile-report-list` (the existing list rule) gains `container: activity-list / inline-size`. The list is the card's parent, so it can be queried while the card itself is restyled. Inline-size containment also gives the list layout containment; the only `position: absolute` descendants in the cards sit under their own `position: relative` parents (the trust counter separator), no fixed element lives in the list, so nothing else changes.
2. `@container activity-list (max-width: 17em)` after the card rules (same specificity, so order wins): the card areas become `"disc status" "report report" "when when" "what what" "distance distance"`, and the distance cell gets `padding: 0; border-top: 0`.
3. Why a container query in em and not a media query: the harness (and the type size tokens) enlarge text by scaling the `--font-size-*` tokens, so the viewport never changes. A container query reads `em` from the container's own computed font size, which is the body size token (16px at 100 percent), so it follows the text size.

Threshold: the label breaks inside a word when the label's text box is narrower than the word, which is about `W < 102 + 177 s` (W the list width, s the text scale) with the widest distance wording "under 100 m away" (133px at 100 percent, 238px at 200 percent). A threshold of N em acts when `W < 16 N s`. N = 17 acts a little before the failure at every phone width: the list is 288px at a 320px screen, 17em is 272px at 100 percent so the query is off, and it turns on at about 1.06 times the type size at 320, 1.2 at 360 and 1.32 at 390. The short "Unknown" distance (what a report without a distance shows) would not have needed this until about 1.75 times, so the card restacks a little earlier than strictly needed for short distance wordings. I chose the widest wording because a mid-word break must never happen for any real row. Documented trade: at a given text size every row on a screen restacks together, whatever its own distance says.

Stacked distance: kept right aligned (as drawn); no second hairline under What happened and no left padding.

The shared CSS parser (`p16ParseCSS`) records a rule nested in an at-rule with the innermost prelude as `Media`, so the new container query is read as `@container activity-list (max-width: 17em)` and the "only the 899.98px block" check failed. I did not touch the shared parser; I added a dated note ("Amended 2026-10-17 by Phase 3.4 plan 22 (plan 17 finding 5)") and the check now also accepts exactly that one media string. Nothing was weakened: the new test proves from the raw text that the query sits inside the narrow block. Commit 03ee8bc.

**2. Process: test written after the change, one commit.** The CSS was written first and the contract test second (RED was seen only for the existing test, which failed on the nested rule), and both went in one `fix(03.4-22)` commit instead of a `test` commit followed by a `fix` commit. ## Not fixed / limits

- Pure em cannot tell rows apart: at a text size where the widest distance wording would break the label, every row on the screen restacks, including rows whose own distance is short. This is the price of a size based mechanism without changing markup.
- A real viewport narrower than 320px (list under 272px) restacks at 100 percent text. That is below the supported minimum, and it is the width where the label would need it anyway.
