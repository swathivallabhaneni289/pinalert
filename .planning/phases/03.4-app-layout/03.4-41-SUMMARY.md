# Phase 3.4 Plan 41: A report address opens its report on a fresh phone load Summary

**An address /?report=ID now opens its report view on a fresh load when the first list request is already out before feed.js runs. The fix is one condition in `Pinalert.openReport` (app.js): it also asks for the list again while a request is out that left without the id.**

## Cause

1. All page scripts are deferred and run in order, each when its own download is done, and the event loop may run a task between two of them.
2. map.js starts the map in `centerOnVisitor`, which waits for an async permission answer and then calls `boot()`, which sends the first `GET /api/reports`.
3. On a slow load that request leaves before feed.js has run. The request has no `report=` id.
4. feed.js then calls `Pinalert.openReport(id)`. No pin exists yet, so it only kept the id (`setFocusId`) and asked again only when `state.hasLoaded`. The first answer had not landed, so no second request was made.
5. The answer to the request already out carried no focus. Nothing opened the report, and the id waited for the next poll 30 seconds later.

What the orchestrator saw as a highlighted fire row was the critical report row's own pink tint (critical rows are tinted); the selected row has a grey fill. After the fix the same row is selected and the view opens.

The comment in feed.js ("guaranteed to precede the first fetch") was wrong for this case. It now says so and points to the fix.

## Reproduction and proof

Not reproduced on a plain fast load (the report view opened with a kept fix, with no kept fix, and in the ask mode). Reproduced in Playwright WebKit by holding feed.js back 600 ms with the list answer held 2 s, and in the iPhone 17 Pro simulator's own Safari the same way, through a small delaying reverse proxy kept in the scratchpad outside the repo (port 8787, feed.js held 600 ms, list answer held 2 s):

| Run | Before the fix | After the fix |
| --- | -------------- | ------------- |
| Simulator Safari, ?report=1, held feed.js | Nearby with the list, the pins and the fire row tinted, no report view, no selected row | the phone report view open: top row Back, bell, gear, the 160px map strip with the pin centred, the card, Confirm and Dispute, Mark resolved, Flag, the trust block, and the bottom bar |
| Simulator Safari, Back (the popup close anchor) | not reached | Nearby again, popup closed, the report row selected, the address without the id |
| Simulator Safari, ?report=99999 | not run | the "This report is no longer available" view, with Back and Report |
| Playwright WebKit phone, feed.js held 0, 600, 1000, 1900 ms | held 600, 1000, 1900 failed (no popup, no selected row) | all four open |
| Playwright WebKit phone, kept fix, feed.js held 600 | failed | opens |
| Playwright Chromium phone, held 600 | not run | opens |
| Playwright laptop (1280 by 800) Chromium held 0, 600, 1000, WebKit held 600 | not run | the popup opens |

Screenshots were looked at one by one and kept outside the repo (scratchpad). The simulator session was deleted and the driver stopped.

The laptop did not change: the only code touched is shared start up logic, and the laptop opens its popup for the same address as before (on a quick load) and now also on the slow load.
