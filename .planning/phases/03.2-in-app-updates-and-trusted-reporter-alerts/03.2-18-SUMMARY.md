# Phase 3.2 Plan 18: W1, a sign in again no longer revives a revoked session Summary

Signing in again on a browser whose session was revoked (Log out of all devices) or whose account was deleted now always gets a fresh session id, so a copy of the old cookie stays refused.

## The gap

03.2-VERIFICATION.md W1: `VerifyTokenAndBind` rotated the session id only when the account was deleted or a different account signed in. For the same account, `BindSessionAccount` set `revoked_at = NULL` on the same id. A cookie copied from that browser before Log out of all devices worked again once the owner signed back in there, which is the case the button exists to end.

## What changed

- `internal/service/auth.go`: `rotate = bound && gone`. The same-account comparison is gone. The doc comment, the step 4b description and the zero-rows comment now say why: a revived id brings back every copy of the old cookie.
- `internal/store/queries/sessions.sql` `BindSessionAccount`: the upsert's `DO UPDATE` no longer sets `revoked_at = NULL`, and its `WHERE` now reads `sessions.revoked_at IS NULL AND (sessions.account_id IS NULL OR sessions.account_id = EXCLUDED.account_id)`. A revoked row returns 0 rows, which the service's existing fallback turns into a fresh id. A bound row still never moves to another account.
- `sqlc generate` (v1.31.1) changed only `internal/store/sqlc/sessions.sql.go` (the comment and SQL text).
