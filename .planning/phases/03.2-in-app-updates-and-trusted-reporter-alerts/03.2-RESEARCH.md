## Summary

The phase is almost entirely a composition problem. Every input it needs already exists: `Resolve` is the single visibility authority, `BuildTrust` builds the one trust object, `ViewOf` (Phase 3.1, landed) maps a visibility plus expiry to a tab, `CurrentVotesForReports` is the batched vote read, the reporter signal (`ReporterSignals`) already carries the Reliable tag, and `ReportService.Nearby` already measures distance from a client supplied point with no stored location. What is missing is storage for read state, mutes and a per report cursor, a service that decides events from those inputs, a small gated API, and the UI (bell, list, mute control, settings, Reliable filter).

The recommended shape is lazy and read driven. A separate gated endpoint `GET /api/updates` is called by a new self contained script on every page that has a header, on the same 30 second interval. On each call the server loads the account's open followed reports (posted or voted, derived from existing tables), resolves each one with the same pipeline the feed uses, compares the result with a per (account, report) cursor row, and writes at most one update per report per hour using a single atomic statement. The "within 1 hour of expiring" event is just another comparison against `expires_at` in the same pass, so no scheduler is needed. Reliable reporter alerts reuse `Nearby` with the reader's current anchor and are gated on `Resolve` returning Live, which is also how critical and rescue needed reports notify immediately without any second copy of the critical rule.

Three things need an owner answer before planning can finish: where the bell lives on a phone (the account icon is hidden under 900px), whether the bell opens a short list or the Activity page, and where the alert settings live on a phone. Phase 3.1 is also only 5 of 16 plans executed (`ROADMAP.md` Phase 03.1), so the report link, the `focus` object and the history service that this phase's links and the Reliable filter plug into are not on main yet.

**Primary recommendation:** Build NOTIF-01 to NOTIF-03 first as one vertical slice (migration 00007, cursor and updates queries, a pure `DecideUpdate` function, `UpdatesService.Refresh`, `GET /api/updates`, the bell script), then NOTIF-04 and NOTIF-05 as a separable later wave, and start planning only after Phase 3.1's plan 03.1-16 has merged.

Why no `source_account_id` on `updates`: the per reporter cap can be counted by joining `updates` to `reports` to `sessions` at check time, so the recipient to reporter link is not duplicated at rest `[ASSUMED]`. The join is bounded to one recipient and one hour.

### Pattern 1: the pure decision function
**What:** `DecideUpdate(in DecideInput) Decision` takes the cursor row (or none), the current `Visibility`, `ViewOf`, `expiresAt`, the account's own latest vote time on that report, whether the report is muted and `now`. It returns either nothing, a silent baseline write, or one event with the new cursor. It performs no I/O and holds no clock, exactly like `Resolve` and `ClassifyOutcome`, so it is table testable with injected times.

**Rules, in order** `[ASSUMED: design]`:
1. Muted: do nothing and write nothing.
2. No cursor row: adopt the current visibility as the baseline and emit nothing. This is what stops a first load flooding the bell for a person who already has 40 votes on open reports.
3. Self caused: if the account's own latest vote on this report is newer than `adopted_at`, adopt the current visibility silently. This is the "you hear about your own action" fix (Pitfall 3).
4. State change: if the current visibility is Live, Hidden or Retracted and differs from `last_state`, and the hour cap allows, emit `reached_live`, `hidden` or `resolved`, set `last_state`, `last_update_at = now`. If it is Provisional, emit nothing and do not move `last_state`. If the cap blocks, change nothing, so the next poll re-checks against the then current state (a change that reverts inside the hour is never reported, which is intended).
5. Fading: if `ViewOf` is active, `now < expires_at <= now + 1h`, `fading_for != expires_at`, and the cap allows, emit `fading` and set `fading_for = expires_at`. Never after expiry, because votes are refused then and the state is frozen.

### Pattern 2: exactly once without a transaction
Two tabs or two devices will poll in the same second. One statement does the compare and swap and the insert together, so only the winner writes:

```sql
-- name: AdvanceCursorAndInsertUpdate :one
WITH moved AS (
    UPDATE update_cursors
       SET last_state = sqlc.arg(new_state), last_update_at = sqlc.arg(now)::timestamptz
     WHERE account_id = sqlc.arg(account_id) AND report_id = sqlc.arg(report_id)
       AND last_state = sqlc.arg(old_state)
       AND (last_update_at IS NULL OR last_update_at <= sqlc.arg(cap_edge)::timestamptz)
    RETURNING account_id, report_id
)
INSERT INTO updates (account_id, report_id, kind, created_at)
SELECT account_id, report_id, sqlc.arg(kind), sqlc.arg(now)::timestamptz FROM moved
RETURNING id;
```
Zero rows returned means another request won or the cap blocked; both are fine. The repo has no transactions on the vote path by design (T-02-02), and a single statement with a data modifying CTE should be atomic in Postgres `[ASSUMED: from PostgreSQL documentation knowledge, not fetched this session; prove it with the concurrent test in the Validation Architecture]`. The alert insert uses the partial unique index with `ON CONFLICT DO NOTHING`.

### Pattern 3: the followed set is derived and bounded
`FollowedOpenReports(account_id, now, row_cap)`: unexpired reports the account posted (join `sessions` on `account_id`, uses `idx_reports_session_expires`) UNION unexpired reports the account has any vote row on (`votes.account_id`, any kind, uses `idx_votes_account_kind_report_created`). Only unexpired reports can change state, so the set is bounded by report lifetime (8 or 24 hours). Cap rows (about 200, newest first) and document that a heavy account loses the oldest. Select no session id and no voter cell (T-01-02).

Any vote kind counts, so a person who only marked a report resolved or took the mark back still follows it. The existing content only `VotedReportsByAccount` would miss them. `[ASSUMED: owner question 13]`

### Pattern 4: alerts reuse the feed pipeline
`Refresh` calls `ReportService.Nearby` with the anchor and the alert radius, then keeps a `ReportView` only when:
`Visibility == VisibilityLive` and `ViewOf == active` and `Trust.Reporter.Tag == ReporterReliable` and not `IsOwnReport` and not already followed by this account and not muted and `created_at >= enabled_at` and the per reporter cap allows.

The per reporter cap needs the reporter account id, which `ReportView` does not carry. Add an unexported field set inside `Nearby` (handlers map fields explicitly, so it can never reach the wire) or give `UpdatesService` its own thin variant that keeps `reporterByReport`. Do not return an account id through any exported field. `[ASSUMED]`

Anchor: `state.center` in the client is the point the feed was loaded around (a GPS fix, a searched place or the fallback) and has an `own` flag `[VERIFIED: web/static/js/app.js]`. Dragging the map does not reload the list (03.1 D-14), so "where the reader is looking" is that feed centre, not the live map view. Alerts only evaluate when the request carries coordinates and the setting is on. The coordinates are used for one call and never written.

### Pattern 5: words at read time, link at click time
Rows store `kind` and `report_id` only. `UpdatesForAccount` loads the reports in one batch, builds `BuildTrust` for each and writes the sentence from the kind plus the current trust facts, so a count can never be stale and the update says what the popup says now. If the report has since become unlisted for this reader (Phase 4 held or removed, or no longer found), the row is shown as "no longer available" with no detail. The link is `/?report=ID`; 03.1 UI-SPEC decisions 5 and 8 make a bare id land on the right tab, and `?view=resolved&report=ID` also works `[CITED: 03.1-UI-SPEC.md]`. Never store the view word in a row: it goes stale (a report that was Live is Past tomorrow).

Never put the description, coordinates, a place name or an account in an update. Phase 4 D-05 records that descriptions can hold addresses and phone numbers, and 03.1 D-23 strips both from finished Rescue reports `[CITED: 04-CONTEXT.md D-05, 03.1-CONTEXT.md D-23]`. A link that opens a finished Rescue report goes through 03.1's coarsening path, so it needs no extra work here.

### Pattern 6: the Reliable only filter
A closed `reporter` query parameter on `GET /api/reports` (empty or `reliable`, anything else is a 400, like `view` and `category` in 03.1). Applied in `ReportService` after `Resolve` and `BuildTrust`, like `ListableInFeed`: keep when the tag is reliable or the report passes the critical predicate. Because the service owns the predicate, JavaScript copies no rule. It must apply to all three tabs so the map follows the list. The URL holds it, nothing is remembered (03.1 D-18). The 3.1 filter line and the "Nothing matches your filters" empty state must name it, and the HIST-04 "what happened recently" line must stay off while it is on.

### Seam for Phase 3.3 (installable app and phone alerts)

`ROADMAP.md` now has Phase 03.3 (inserted 2026-10-15, commit 2e9da50), which depends on this phase and delivers "the updates and the Reliable alert rule" as phone notifications while the site is closed. 03.3 criteria: critical and rescue needed only, a rough area of about 5 km stored for opted in people, capped per person per hour, sent "from the same decision the feed uses", and a tap opens `/?report=ID`. `[VERIFIED: ROADMAP.md Phase 03.3]`

What this means for 3.2:
- **In 3.2 the bell poll is the only producer of updates.** Nothing is created while the app is closed, so 3.3 cannot simply "send" 3.2's updates. It needs a second trigger.
- **The second trigger belongs to 3.3.** The natural one is write time: after a successful `CastVote`, evaluate every follower of that report (skipping the voter as the actor), and evaluate a new critical or rescue needed report from `Submit` only through `Resolve` and the same `MayNotifyAboutReport` predicate, never blind. The fading check can run on any incoming request, because the host sleeps. Alerts based on client coordinates cannot be pushed; push uses the stored rough area (PWA-03) instead.
- **Keep the shared pieces keyed by (account, report), never by the requesting reader.** `DecideUpdate`, the cursor rows, `MayNotifyAboutReport`, `UpdateKind`, the word builders and the per reporter cap query must take an account id as a parameter and must not read it from request context inside the decision code, so both triggers share one set of rules and one cap.
- **Do not build any push, service worker, VAPID or stored area code in 3.2.** Do keep the `updates` rows free of anything channel specific, so a push send can be recorded against the same row (or its own table) later.
- **The in-app bell must keep working for people who never install or who refuse push** (03.3 criterion 5); nothing in 3.2 may assume push exists.

### Anti-Patterns to Avoid
- **Notify from `Submit`.** `Submit` never calls `Resolve`; a hook there bypasses the provisional gate by construction.
- **A visibility check in SQL for alerts.** TRUST-02 and T-02-04: SQL stays blind, Go decides.
- **Copying the critical rule.** `criticalBypass` is unexported so a second copy cannot be written. Rely on `Resolve` returning Live.
- **Storing counts or words in `updates`.** They go stale and could contradict the popup.
- **Writing the map centre or `distance_km` anywhere.**
- **A GET that changes only the caller's own rows is acceptable here; a GET that touches anyone else's rows is not.** `Refresh` writes only rows keyed to the gate's account id.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Visibility of a report | A second state machine in the updates code | `BuildVoteTally` + `Resolve` + `ViewOf` | One authority (TRUST-02); `TestWithheldInNoView` in Phase 4 loops the view predicates |
| Distance and radius | A new Haversine or bounding box | `Nearby` / `BoundingBox` | Already proven and index tested |
| Reporter reliability | A new tag computation | `Trust.Reporter.Tag` from `ReporterSignals` | The rating is already composed and tested |
| Exactly once insert | Application locks | One CTE statement, partial unique index | Matches the repo's no transaction stance |
| Scheduling the fading event | A ticker or cron | Compare `expires_at` on the poll | The host sleeps; scope note 3 |
| Account menu behaviour | A second dropdown implementation | The pattern in `account-menu.js` (Escape, Tab trap, outside click) | Same accessibility contract and tests |
| Wording | Strings in JavaScript | Server written sentences from `BuildTrust` facts | "No threshold may live in JavaScript" (Phase 3) |

**Key insight:** the cheapest way to meet "never bypass the provisional gate" is to have no code path that decides eligibility except by reading `Resolve`'s answer.

## Common Pitfalls

### Pitfall 1: Riding the feed request freezes the bell
**What goes wrong:** Putting `unread` on `GET /api/reports` looks like "rides on the existing 30 second refresh". But `startPolling` returns early on the Past tab, only `map.js` starts it, the Activity page loads no `map.js`, and Phase 4 pins `app.js` at two `fetch(` calls. The count would freeze on Past and never update on Activity.
**How to avoid:** A separate gated endpoint and a new script reading the same `data-poll-interval-ms` value, mounted on every page with the header. "Rides on the 30 second refresh" is then met by the same interval, not the same request. Flag this wording to the owner for confirmation.
**Warning signs:** The count updates on Active and stops on Past.

### Pitfall 2: Duplicate and missed rows from concurrent polls
**What goes wrong:** Two tabs poll together and both insert. Or the cap blocks and the cursor moves anyway, so the change is never announced.
**How to avoid:** Pattern 2. When the cap blocks, do not advance the cursor. Test with two concurrent refreshes against a disposable database and assert one row.

### Pitfall 3: Updates about the reader's own action
**What goes wrong:** A reporter taps Mark resolved and the bell says the report was resolved. A voter's second confirm from another spot flips the report to Live and the bell announces it. A cursor set only at first sight covers just the first poll.
**Fixes:** (a) write the actor's cursor inside `CastVote` from the post vote state it already computes; or (b) rule 3 above, comparing the account's own latest vote time with `adopted_at`. Recommended: (b), because it needs no write path hook and the vote rows are already in the batch. It will also swallow another person's change that lands in the same 30 seconds, which is acceptable and should be documented. `[ASSUMED]`

### Pitfall 4: "Within 1 hour of expiring" promising too much
**What goes wrong:** Wording like "confirm it to keep it alive" is false. A report fades at the `expires_at` it was given and a confirmation does not move it (backlog 999.12). It also must not fire after expiry or on a retracted or hidden report.
**How to avoid:** Emit only while `ViewOf` says active and before `expires_at`. Words say "fades in about an hour" and nothing about keeping it alive. Store `fading_for` as the announced expiry so 999.12 can re-arm it later.

### Pitfall 5: Stored text goes stale or leaks
**What goes wrong:** An update row that froze "3 confirmed" is wrong an hour later. A description excerpt leaks an address or phone number. A place name or distance in the text, with the reader's known position, locates the report.
**How to avoid:** Pattern 5. Add a Go test that every server written string in `updatescopy.go` has no em or en dash (the existing dash guards scan templates and targeted JS only, and generated swagger docs already carry long dashes, backlog 999.8) and no description, coordinate or account value.

### Pitfall 6: Dispute spam as a notification weapon
**What goes wrong:** Two colluding accounts at different spots can Hide a report and flip it back. Each flip could tell the poster and every follower.
**How to avoid:** The cursor design collapses flip flops (announce only when the net state differs from the last announced one), the cap allows one per report per hour per recipient, and a total per recipient per hour ceiling with a roll up row bounds fan in from many followed reports. Hidden is also the one state a poster cannot do anything about, so the words must say what it means and that more confirmations can restore it, using the existing trust sentences. The 24 per day worst case per report per recipient is the stated cost. `[ASSUMED]`

### Pitfall 7: A farmed Reliable account is a fan out lever
**What goes wrong:** Phase 3 D-03 prices the tag at extra verified accounts plus a claimed location. A farmed Reliable account can self declare critical or Rescue needed and, because those bypass the gate, reach every opted in reader nearby immediately with zero confirmations. Non critical reports still need two independent confirmations, so the critical path is the real exposure.
**How to avoid:** The cap per reporter per recipient per hour (NOTIF-05) is mandatory, not optional. Also (a) alert text carries the unconfirmed fact from the trust object ("Not confirmed yet", owner question 11), never a verified sounding word; (b) add a per reporter ceiling across all recipients per hour so one account cannot fan out repeatedly; (c) record that TRUSTX-03 burst detection is not blocking for an in app only bell but is a hard dependency before push or email reuse this rule (ROADMAP scope note 2, TRUST-MODEL.md "Hand offs").

### Pitfall 8: The Reliable filter silently drops real Reliable reporters
**What goes wrong:** `Nearby` loads history for at most 200 reporter accounts, nearest first; beyond that the tag reads none. In a dense 50 km read, a Reliable-only filter then drops reports from reporters who are in fact Reliable.
**How to avoid:** Document it; on a filtered read, state in the filter line that the list may be incomplete when the read was capped, or raise the cap for filtered reads. Also remember the set is likely empty until Phase 5 demo accounts exist (most people show New reporter, D-13), so the empty state needs words that explain what the filter keeps. `[ASSUMED]`

### Pitfall 9: Phase 4's held and removed reports
**What goes wrong:** Phase 3.2 lands before Phase 4, so no held or removed state exists to test against. A later Phase 4 could then notify about a held report.
**How to avoid:** Put the "may notify" decision in one named predicate over `Resolve` and `ViewOf` (for example `MayNotifyAboutReport(vis, expiresAt, now) bool`). Phase 4's withheld wrapper wraps that one function and `TestWithheldInNoView` covers it. Render rows for a report that has become unlisted as "no longer available" (04-CONTEXT: "Phase 3.2 may show Removed after review as an update").

### Pitfall 10: Polling and the host that sleeps
**What goes wrong:** Alerts only exist while a page is open. A report that is posted and expires between two polls, or while the host sleeps, is never alerted. A user returning after hours finds updates stamped "now" for events that happened earlier.
**How to avoid:** Say it in the product copy ("You hear about reports while Pinalert is open"). Stamp rows with detection time and word them as the current state. Re check on `pageshow` and `visibilitychange` so a woken phone catches up at once.

### Pitfall 11: Unread badge and screen readers
**What goes wrong:** An `aria-live` region on a count that changes on poll re-announces every 30 seconds (Phase 3 forbids it on the trust block for the same reason).
**How to avoid:** No `aria-live` on the count. Put the number in the button's accessible name ("Updates, 3 unread") and update it quietly. A short text status only when the panel opens.

### The one gate predicate for anything that may notify
```go
// MayNotifyAboutReport is the only place that says a report may be announced.
// It asks the resolver's output, never the report's own severity, so the
// provisional gate cannot be bypassed by a second copy of the critical rule.
func MayNotifyAboutReport(vis Visibility, expiresAt, now time.Time) bool {
	return vis == VisibilityLive && ViewOf(vis, expiresAt, now) == FeedViewActive
}
```

### Deriving the recipient set for the per reporter cap without storing the link

-- name: AlertsFromReporterInWindow :one
SELECT COUNT(*)::bigint
FROM updates u
JOIN reports r ON r.id = u.report_id
JOIN sessions s ON s.session_id = r.session_id
WHERE u.account_id = sqlc.arg(recipient_id)
  AND u.kind = sqlc.arg(kind)
  AND s.account_id = sqlc.arg(reporter_id)
  AND u.created_at > sqlc.arg(window_start)::timestamptz;
