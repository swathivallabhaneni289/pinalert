# Phase 3.2 Plan 05: Viewer follow and mute state on the feed Summary

Every report on the Nearby feed and on a report link answer now carries `viewer_follows` (the reader posted it or holds any vote row on it) and `viewer_muted` (the reader turned updates off), for that reader only, with no added query.

## What was built

- `ViewerFollows` in `internal/service/follow.go`: same rule as plan 01's `FollowedOpenReports` (posted, or any vote row of any kind and value), computed from the vote rows the read already holds. Viewer 0 is always false.
- `ReportView.ViewerFollows` and `ViewerMuted` in feed.go. Nearby fills follows from the vote rows and `isOwn` (computed once), and muted from `ex.ViewerMuted` of the one extras read.
- `loadReadContext` gained a `viewerAccountID` parameter used only for the extras read. Focus passes the reader and sets `view.ViewerMuted` from it; `baseView` sets `ViewerFollows`. History and RecentHistoryCounts still pass 0.
- Wire: `viewer_follows` and `viewer_muted` always present JSON booleans, mapped in the one mapper `reportViewToResponse` (the report link path already used it, so no other change was needed).
- Tests: `TestViewerFollows`, `TestNearbyCarriesViewerFollowAndMute`, `TestFocusCarriesViewerMute`, `TestHistoryKeepsViewerStateFalse`, `TestFeedReportWireViewerStateKeys`, and the e2e `TestViewerStateOnTheWire` (A posts, B confirms and has a `report_mutes` row, C reads: A true/false, B true/true, C false/false, on the feed and the focus report, with Cache-Control no-store and no other key containing "flag").

## Deviations from Plan

None in behavior. One interpretation: the plan says History views keep both fields false while `buildFinishedView` (shared with Focus) goes through `baseView`, which now sets follows. History therefore clears `ViewerFollows` after building each finished view, so the Past tab is false for both fields even for a reader who closed the report. Focus on a finished report keeps follows as computed.
