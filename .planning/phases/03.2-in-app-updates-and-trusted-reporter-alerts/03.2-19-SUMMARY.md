# Phase 03.2 Plan 19: The Reliable note counts toward the hour gap Summary

A Reliable reporter note now seeds the reader's cursor in the same SQL statement that writes the note, so a reader who votes on that report afterwards cannot get a second row ("Reached Live" and the like) inside the hour (D-12, closes W3).

## The gap

`refreshReliableAlerts` wrote the note through `InsertReliableAlert` and never touched `update_cursors`. When the reader then voted on that report, Refresh started following it with a silent baseline whose `last_update_at` was NULL, so when two other people confirmed it within the hour `DecideUpdate` saw an open gap and wrote a second row about the same report.

## What was built

- **InsertReliableAlert** (internal/store/queries/updates.sql): the insert is now the `ins` CTE with `RETURNING id, account_id, report_id`; a second CTE `seed` inserts into `update_cursors` from `ins` with `last_state = state`, `adopted_at = now`, `last_update_at = now`, `fading_for` left NULL, `ON CONFLICT (account_id, report_id) DO NOTHING`; the outer `SELECT id FROM ins` keeps the return shape (pgx.ErrNoRows when nothing was written). Because the seed reads only from `ins`, a duplicate note or a reader over the hourly ceiling seeds nothing. `sqlc generate` (v1.31.1) changed only internal/store/sqlc/updates.sql.go: `InsertReliableAlertParams` gained `State string`.
- **Caller** (internal/service/updatesalerts.go): passes `State: string(v.Visibility)`, the view's resolver answer, the same string Refresh stores. Only Live and Provisional reach this call (`MayNotifyAboutReport` for `UpdateReliableNearby` needs an active view), and both are valid under the `update_cursors_state_valid` CHECK. The `UpdatesQuerier` method signature did not change, so no fake had to follow; the doc comments on `refreshReliableAlerts`, `InsertReliableAlert` and the interface method say the note counts toward the one per report per hour gap (D-12) and that Phase 3.3 kind 3 reuses this step.
- **PruneUpdates comment** in updates.sql (and the generated copy): "the 7 day window", as `UpdatesRetention = HistoryWindow` (7 days) keeps.

Why the seed is harmless: cursors are read only by `UpdateCursorsForReports` for followed reports in Refresh, pruned per account by expiry, dropped by `UnmuteReport` and by account deletion; `AdoptCursorState` keeps `last_update_at`. A seeded cursor on a report the reader does not follow is read by nothing. When the reader votes later the vote is after `adopted_at`, so Refresh adopts the state silently and `last_update_at` (the note's time) holds the gap.

- `TestReliableNoteCountsTowardTheHourGap` (internal/service, real database): Reliable reporter posts a low report, the reader's Refresh writes the note, the reader confirms it (still Provisional, threshold 2), two other people confirm from two cells, the reader's next two Refreshes write no second row. After the hour (note time plus `UpdateReportGap` plus a minute) the normal rule applies again: `DecideUpdate` sees Provisional to Live while the reader follows the report and writes one `reached_live` row, pinned in the test with a comment, so the report then has the note and that one row.
