## Phase Goal

**As a** person near an ongoing incident, **I want to** confirm or dispute another user's report **so that** reports lacking independent nearby corroboration lose visibility while well-corroborated ones stay trusted — and as a reporter or nearby confirmer, I want to mark a report resolved once it's no longer true, so the feed reflects what's actually happening right now.

<objective>
"As a person near an ongoing incident, I want to confirm or dispute another user's report so that reports lacking independent nearby corroboration lose visibility while well-corroborated ones stay trusted — and as a reporter or nearby confirmer, I want to mark a report resolved once it's no longer true, so the feed reflects what's actually happening right now."

**This plan is one slice of that story: the read side — where the votes 02-03a/b made castable
finally change what a person actually sees.**

Up to now a vote is recorded and answered, but the feed it was cast on has never heard of it: a
report disputed into oblivion still sits at the top of the list, and a report the reporter just
marked resolved is still on the map. This plan closes that loop. `GET /api/reports` — the one
endpoint Phase 1 built to serve **both** the map and the list — starts loading the current votes
for the page it is about to return, building a tally per report, asking `service.Resolve` for the
answer, and filtering on it. Nothing user-clickable lands here; 02-05 is the first user-clickable
increment, and this plan exists so that click has something true to render.

The decisions this plan implements, each cited by ID:

- **D-12** — a **Retracted** report is removed from the live feed and map *immediately*, with no
  grace period and no lingering strikethrough state. It is therefore filtered out of **both** the
  default response and the `?show_disputed=true` response: `show_disputed` reveals disputed
  reports, not resolved ones. A retracted report's only remaining surface is the reporter's own
  Activity history, which 02-07 builds against its own store query for exactly this reason.
- **D-10** — a **Hidden** report is removed from the default feed and map for every viewer, but
  stays browsable behind a "Show disputed" filter on the same page, backed by the same
  resolver-computed query. This plan ships the server half of that toggle: the
  **`?show_disputed=true`** query parameter on the existing route. No new route, no new page.
- **D-11** — that same parameter reveals Hidden **pins on the map**, not just rows in the list. In
  this codebase that requires no extra work and no second code path, and the reason is worth
  stating plainly because it is also TRUST-02's whole claim: `internal/api/handlers/reports.go`'s
  own doc comment records that `GET /api/reports` is the one endpoint serving both surfaces —
  "there is no separate map-only or list-only route." Feed/map identity is therefore **structural**
  here, not a convention two call sites must remember to keep in sync.
- **D-08** — Hidden is fully reversible because visibility is recomputed live from current tallies
  on every read. This plan is where "on every read" stops being a design statement: every response
  calls `Resolve` fresh. There is no cached status column to go stale and no unhide path to write.
- **D-03** — the reporter cannot vote on their own report. 02-03a enforces that server-side and
  02-03b returns 403 for it. This plan supplies the read-side signal the client needs so a
  non-actionable button never renders in the first place: a per-report **`is_own_report`** flag,
  plus **`your_vote`** so 02-05 can show which way the viewer already voted. Both are courtesies
  layered on the enforced control, never a replacement for it.

Purpose: TRUST-02 requires a report's visibility state to be *identical everywhere it is shown*.
02-01 made that possible by writing exactly one function. This plan is where the claim is either
kept or quietly broken — a read path that filters in SQL, caches a status column, or re-derives the
answer in a handler would satisfy every test written so far and still violate the requirement.
That is threat **T-02-04**, and this plan is where it is realised or prevented.

Output: a batched `ReporterAccountsForReports` store query; `internal/service/feed.go` (the
`ReportView` shape, the listability predicate and the viewer's-own-vote lookup); an extended
`ReportService.Nearby`; the `?show_disputed` parameter and the four new response fields on
`GET /api/reports`; a regenerated OpenAPI spec; and end-to-end proof over a real router and a real
Postgres.

   dispute rung. There is no critical Hidden report to assert about. The equivalent assertion that

2. `NearbyReports` is **not** modified to carry the reporter account. The obvious shape — a

The query is `-- name: ReporterAccountsForReports :many`. It selects two things: `r.id` aliased as
`report_id`, and `s.account_id` aliased as `reporter_account_id`. It reads
`FROM reports r LEFT JOIN sessions s ON r.session_id = s.session_id` and filters
`WHERE r.id = ANY(sqlc.arg(report_ids)::bigint[])`, matching `CurrentVotesForReports`' batched-ids
idiom rather than inventing a second one.

Five points the rationale comment above it must make, because each is a place a later reader would
otherwise "correct" it.

(a) **Why it exists at all.** `service.BuildVoteTally(rows, reportID, reporterAccountID)` needs
each report's reporter account to route the reporter's own resolution vote into `ReporterResolved`
and to exclude the reporter's rows from the independent counts. Passing `nil` there on the read
path would mean `ReporterResolved` never fires on a read, and a report whose reporter marked it
resolved would keep appearing in the live feed — a direct D-12/D-13 failure. The same value also
decides the response's `is_own_report` flag (D-03).

(b) **Why it is batched rather than per report.** The feed returns a whole page. One call with the
page's ids costs one round trip; a per-report lookup would be an N+1 — the exact shape
`CurrentVotesForReports` was designed as a batch to avoid.

(c) **Why it is a separate query instead of a join added to `NearbyReports`.** `NearbyReports` is
pinned byte-for-byte by a drift const and its plan is asserted by an `EXPLAIN`-based index test.
Leaving it untouched keeps FOUND-03's proven bounding-box/Haversine query exactly as Phase 1
shipped it, and — the load-bearing part — makes it *self-evident* that the feed query gained no
visibility or vote predicate of its own (`.planning/research/ARCHITECTURE.md` Anti-Pattern 1,
threat T-02-04). Filtering by visibility happens in Go, over `Resolve`'s output, never in SQL.

(d) **Why `LEFT JOIN` and not `INNER JOIN`.** `reports.session_id` carries no foreign key and
`sessions.account_id` is nullable — both deliberate, both documented in migration `00002`. A report
submitted before Phase 1.1 made login mandatory, and any report seeded by
`internal/testutil/seed.go` (which inserts a literal `session_id` with no matching `sessions` row),
therefore has no account-bound session. An INNER JOIN would drop those reports from this result
entirely, and the caller could not distinguish "no reporter account" from "report not in the
batch." With the LEFT JOIN every requested-and-existing report comes back, carrying a NULL
`reporter_account_id`: nobody matches it, `is_own_report` is false for every viewer, and the
report stays in the feed exactly as it does today. Note also that `sessions.session_id` is the
table's PRIMARY KEY, so the join matches at most one row and can never duplicate a report.

(e) **Why the join stops at `sessions`.** `sessions.account_id` IS `accounts.id` by foreign key, so
a third join through `accounts` could only re-confirm a row the constraint already guarantees.
Omitted on purpose, matching `ReportVoteContext`'s own reasoning.
