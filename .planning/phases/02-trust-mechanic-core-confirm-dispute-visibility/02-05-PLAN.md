## Phase Goal

**As a** person near an ongoing incident, **I want to** confirm or dispute another user's report **so that** reports lacking independent nearby corroboration lose visibility while well-corroborated ones stay trusted — and as a reporter or nearby confirmer, I want to mark a report resolved once it's no longer true, so the feed reflects what's actually happening right now.

<objective>
"As a person near an ongoing incident, I want to confirm or dispute another user's report so that reports lacking independent nearby corroboration lose visibility while well-corroborated ones stay trusted — and as a reporter or nearby confirmer, I want to mark a report resolved once it's no longer true, so the feed reflects what's actually happening right now."

**This plan is the first user-clickable increment of that story.** Four plans have built a
resolver, a vote log, four routes and a read path that agrees with them — and so far not one
person can do anything they could not do before Phase 2 started. After this plan a real visitor
opens the feed, taps **Confirm** on someone else's report, and the trust mechanic this whole
product exists for actually runs end to end from a finger on a screen.

The decisions this plan implements, each cited by ID:

- **D-01** — the Confirm/Dispute controls appear on **both** the feed row and the map pin popup.
  Not two implementations: `web/static/js/votes.js` owns one `createVoteBlock`/`updateVoteBlock`
  pair, and `feed.js` and `map.js` each call it. `02-UI-SPEC.md` is explicit that the two surfaces
  ship identical markup and classes precisely so one script handles both; this plan is where that
  becomes structural rather than aspirational.
- **D-02** — a viewer can change their vote. Tapping the other button re-POSTs, and the active
  state that comes back is whatever `your_vote` the feed reports afterward. Re-tapping the button
  that already reflects the standing vote re-sends it and produces no visible change, which
  `02-UI-SPEC.md`'s interaction contract step 5 records as harmless: 02-02's append-only log
  absorbs a duplicate row and the `DISTINCT ON` read still collapses to one current vote.
- **D-04** — **no optimistic update.** Tapping disables every button in that block; nothing about
  the button state changes until the POST has returned. The new state is then applied from a fresh
  `GET /api/reports`, not from anything this client inferred. 02-04's own artifact note sets the
  rule for the sibling case — "a freshly submitted report deliberately carries no synthesised
  visibility: 02-05 refetches the feed after a submit rather than guessing" — and this plan applies
  the identical principle after a vote.
- **D-17** — the voter's location is captured through the browser's native geolocation prompt
  **once per browser session** and cached. `02-CONTEXT.md` leaves the storage mechanism to
  planning; this plan picks `sessionStorage`, because its lifetime *is* the browser session D-17
  names, it needs no expiry bookkeeping, and it dies with the tab rather than persisting a person's
  coordinates across visits.
- **D-18** — a denied prompt **blocks the vote**. No request is constructed, no request is sent,
  and the row shows the Copywriting Contract's exact sentence, which is deliberately worded to
  offer no workaround because there is none.

**The named risk of this plan, stated up front.** `02-PATTERNS.md` flagged it and
`02-RESEARCH.md`'s own code example opens with it: `modal.js`'s `initLocation()` and `map.js`'s
`centerOnVisitor()` both handle a denied geolocation prompt by quietly continuing with a
configured default centre. That is **correct** for those flows — report submission during an
emergency must never dead-end on a permission dialog. Voting has the exact opposite requirement,
and the two call sites sit three files away from the one this plan creates. An executor who
copy-pastes the denial branch ships a client that votes from a hard-coded city centre, which
silently destroys the "distinct geohash cell" half of the independence predicate that is this
product's entire Core Value. Task 1 therefore ships an automated contract test whose only job is
to prove that branch is absent, and its `<action>` names the forbidden shapes explicitly.

**How a frontend plan carries TRUST-03.** TRUST-03 says a vote counts toward the independence
threshold only if it comes from a distinct account *and* a distinct geohash cell. 02-03a computes
the cell and 02-03b proves the gate over HTTP — but both of them compute that cell from whatever
coordinates arrive in the request body. This plan is what makes those coordinates mean something:
D-17 captures a real device position from the browser's own geolocation API rather than a typed
number or an IP guess, and D-18 refuses to send a vote at all when no such position exists. Without
this plan the server's independence predicate is arithmetic over unverified input. With it, every
counted vote is location-backed by construction, which is the requirement's actual claim.

**Two places `02-UI-SPEC.md` contradicts itself, resolved here so neither reads as a deviation.**

1. *When do the buttons disable?* The Interaction contract resolves location in step 2 and disables
   in step 3 — which would leave the buttons live across a slow native permission prompt, a real
   double-submit window. The Color section instead enumerates the disabled treatment as applying to
   "in-flight / reporter viewing own report / **awaiting GPS**". This plan takes the Color section's
   reading: **disable on tap**, covering awaiting-location and in-flight as one state, then
   re-enable immediately on denial exactly as step 2 requires, and on any non-200.
2. *Does the Confirm/Dispute label change while in flight?* Interaction step 3 says the tapped
   button's label "changes to a submitting state", but the Copywriting Contract supplies an
   in-flight string for **Mark resolved** ("Marking…") and for **Reopen** ("Reopening…") and
   deliberately none for Confirm or Dispute — for which it states the opposite rule outright: the
   label "never changes between states … keeping the button width stable in a tight row." Inventing
   a "Confirming…" string would be new copy the contract does not sanction. This plan therefore
   changes no label: in-flight is the disabled treatment the Color section already specifies, plus
   `aria-busy="true"` on the container so the state is announced rather than merely painted.

Purpose: TRUST-01's requirement is that a user can confirm or dispute another user's report. Until
a person can tap something, that is an API. This plan is where it becomes a feature.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| device to browser | The geolocation prompt is the only source of the voter's coordinates. Everything downstream of it in this plan is transport; nothing here can make an untrustworthy position trustworthy, which is why D-18's refusal-to-proceed matters more than any validation this layer could add. |
| browser to API | This plan authors one request shape — `{latitude, longitude}` to one of four allowlisted paths. The server re-derives the cell, the account and the visibility from its own sources; nothing this client sends is trusted for any of them. |
| server response to DOM | The server's error messages are rendered to the reader. They are server-authored, but the sink discipline (`Pinalert.setText`, never a markup parser) is about the sink, not the author — T-01-03's rule holds unchanged across this new data path. |

**This plan adds no security control.** Its whole job at the trust boundary is to add no *bypass*.
The two threats it touches were mitigated and proven server-side in 02-03a and 02-03b; the rows
below record what this layer contributes (defence in depth and, in one case, nothing at all by
design) and what it must not be mistaken for.
