## Gap closure round 2, plan 1 of 4

This plan closes one `status: failed` gap from `02-UAT.md` (severity `minor`, Test 10): the map
basemap does not follow the app's Light/Dark theme. Diagnosis:
`.planning/debug/map-theme-not-applied.md`, root cause CONFIRMED.

It is one of four mutually parallel plans in this round (`02-11`, `02-12`, `02-13`, `02-14`). The
four share zero files, so all run in wave 9 together.

<objective>
**The chrome changed theme. The map did not.**

Plan `02-10` shipped a three-state System/Light/Dark control that writes `data-theme` on the
document root, and every one of the app's own surfaces follows it. The basemap does not, because
neither map module has ever known the theme exists.

The debug session found this is not one omission but two, in two separate files, and that the second
one is easy to miss:

1. `web/static/js/map.js`'s `init()` builds the primary map with the hardcoded literal
   `https://tiles.openfreemap.org/styles/liberty`, plus a light-only OpenStreetMap raster fallback.
2. `web/static/js/modal.js`'s `initLocation()` independently builds the report-submission modal's
   pin-drop map with a byte-identical hardcoded literal and the same light-only fallback. That file's
   own comment records the duplication as this codebase's deliberate convention, not a copy-paste
   slip. A fix touching only `map.js` therefore ships a report modal whose map is still light in dark
   mode: the same UAT failure, one screen deeper.

It is also confirmed **not** a timing problem. `theme.js` is a non-deferred head script (build-gated
by `TestThemeScriptLoadsBeforeFirstPaintOnEveryFullPage`) and applies the attribute before body
parsing starts; both map modules load deferred at the end of the body. The attribute is stable and
synchronously readable by the time either map is constructed. What is missing is purely integration
code.

**Three decisions, made here rather than passed to the executor:**

- **Observe the DOM, do not emit an event.** `theme.js` stays byte-identical. It runs on the login
  gate and the verify-outcome page where no map module exists, and
  `TestThemeModuleHasNoAppShellDependency` fails the build if its source ever names the app shell.
  A `MutationObserver` on `document.documentElement` filtered to `data-theme` needs zero change
  there, which sidesteps that contract instead of threading a needle through it.
- **Re-resolve the mode on every notification, never cache it.** Switching to System *removes* the
  attribute rather than setting a value, so a mode cached at construction time goes stale the moment
  a reader returns to following the OS.
- **The WebGL-less raster fallback stays light in dark mode, accepted deliberately.** OpenFreeMap
  publishes no free dark *raster* tileset; the dark style is vector only. Introducing a different
  raster vendor to serve one degraded code path would add an unevaluated host that receives visitor
  viewport coordinates, which is exactly what `TestBasemapBranchesPointAtCorrectHosts` exists to
  prevent. The mismatch is recorded in a code comment and in the SUMMARY, not silently dropped.

**Output:** both map surfaces resolve their basemap from the live theme at construction, both
re-style on a later switch, both no-op safely when their renderer is not up yet, and the host
allowlist test is rewritten to permit exactly two reviewed style URLs instead of one.
</objective>
