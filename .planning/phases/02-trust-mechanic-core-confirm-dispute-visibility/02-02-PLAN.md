## Phase Goal

**As a** person near an ongoing incident, **I want to** confirm or dispute another user's report **so that** reports lacking independent nearby corroboration lose visibility while well-corroborated ones stay trusted — and as a reporter or nearby confirmer, I want to mark a report resolved once it's no longer true, so the feed reflects what's actually happening right now.

<objective>
**As a** person near an ongoing incident, **I want to** confirm or dispute another user's report **so that** reports lacking independent nearby corroboration lose visibility while well-corroborated ones stay trusted — and as a reporter or nearby confirmer, I want to mark a report resolved once it's no longer true, so the feed reflects what's actually happening right now.

**This plan is one slice of that story: the durable append-only storage layer underneath it.**

A vote is durably appended to a log that has no shared mutable counter to race on. N concurrent
casts from N distinct accounts on one report all land (the TRUST-09 proof). The current effective
vote per (report, account, kind) reads back as the latest row, so **D-02** — "a user can change
their vote after casting it" — is satisfied by appending a new row and letting the read collapse
the history, never by overwriting the old row. Content votes (confirm/dispute) and resolution
votes (resolve/reopen) are separate `kind` values that never interfere with each other's "current"
read, which is what keeps "is this report still true" and "is this resolved" as two independently
tracked signals per **D-02** and D-16.

**MVP framing (why this plan produces no clickable increment).** Phase 2 is one vertical slice —
"a user can confirm, dispute and resolve reports, and see the trust state that results" — and
`02-PLAN-OUTLINE.md` pins the first user-clickable increment at plan 02-05. This plan and 02-01 are
the two deliberately parallel, non-overlapping wave-1 steps through that single slice. Neither is a
"build the schema" / "build the service" layer task: each ends at a provable, independently
testable guarantee (here, TRUST-09's concurrency property proven against a real Postgres), not at
"the foundation is laid." That framing was reviewed and approved in the outline before this plan
was written.

Purpose: TRUST-09's concurrency guarantee is a Core Value requirement — "confirmed by N nearby"
is worthless if concurrent confirmations silently vanish. This plan makes that class of bug
structurally impossible (no shared mutable counter exists to race on) rather than merely guarded
by a lock, and proves it with a test that fails against the rejected upsert design.

Output: migration `00004_create_votes.sql`, query file `internal/store/queries/votes.sql`, the
sqlc-regenerated Go layer, and `internal/store/votes_test.go`.

Scope boundary: store layer only. No HTTP endpoint, no `VotingService`, no geohash computation, no
reporter-self-vote check, no visibility resolution. The HTTP request/response half of TRUST-01 and
every service-layer concern belong to 02-03.
</objective>
