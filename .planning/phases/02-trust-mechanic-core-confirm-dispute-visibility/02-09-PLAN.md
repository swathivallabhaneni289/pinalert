## Gap closure round 1, plan 2 of 3

This plan closes **two `status: failed` gaps** from `02-UAT.md` — one `severity: major` (Test 3,
stale feed after Reopen) and one `severity: minor` (Test 2, the disputed filter resetting on
reload). It is one of three mutually-parallel gap-closure plans: `02-08`, `02-09` (this one) and
`02-10` share **zero** files, so all three run in wave 8 together.

<objective>
**Two ways the feed forgets things it should not.**

**Gap A — stale feed after a Back navigation (major).** The UAT reporter tapped Reopen on the
Activity page, navigated back to the feed, and saw the pre-reopen state until a manual reload —
contradicting 02-07's "no page reload" requirement. `handlers.Page` already sets
`Cache-Control: no-store` on the main document (DEC-Q), which per spec makes Chromium and Firefox
exclude the page from the back-forward cache entirely. **Safari's WebKit page cache does not
reliably honour that header for bfcache eligibility**, so a Safari Back can restore a frozen DOM
snapshot without re-running any JavaScript. Nothing refetches, so the feed shows what it showed
before the vote. The standard, portable fix is not to fight for bfcache exclusion — it is to make
the restore correct: listen for `pageshow`, and when the event reports the page was restored from
the cache, refetch.

The same investigation found a second, smaller hole worth closing in the same breath: **the feed
endpoint itself sets no `Cache-Control` at all.** Only static assets carry one (`router.go`'s
`staticFileServer`). A `fetch()` of an uncached-but-cacheable JSON response is eligible for
heuristic caching, so even a page that *does* re-run its JavaScript can be handed a stale body. One
header on one handler removes that possibility. Set it **in the feed handler**, not in `writeJSON`
— that helper is shared by the auth link-request route, report submission and all four vote routes,
and blanket-applying a cache directive to write endpoints is a different decision that nobody made.

**Gap B — the disputed filter resets on reload (minor, and a deliberate scope reversal).** This is
**not a pre-existing bug.** `02-UI-SPEC.md`'s "Show disputed filter (D-10, D-11)" section specifies
a plain native checkbox with no persistence, and Phase 2 shipped exactly that; the phase's own
human-check listed "the checkbox does not persist checked across a reload" as *expected* behaviour,
and the UAT confirmed it working as specified. **The user changed their mind during the UAT session
on 2026-09-17**: refreshing while reading the disputed view drops them out of it, and they want the
view to survive. This plan implements that reversal and records it as a dated amendment on the spec
itself, following the same convention `02-CONTEXT.md`'s D-16 uses for its own amendment — so a
future reader who finds the original wording does not "restore" the non-persisting behaviour as a
regression fix.

The mechanism is a **URL query parameter**, not `localStorage`, for four reasons worth stating
because they are the reason this is a two-line-feeling change rather than a new storage surface:
the filter is *view state*, so it should be shareable and bookmarkable and should not leak into a
later visit where the viewer never asked for a disputed view; the parameter name is already defined
by the API (`show_disputed`), so the page and the server keep one vocabulary instead of two; a URL
survives both a reload and a back-forward restore with no extra machinery; and `localStorage` throws
in some privacy modes, which would need a try/catch this does not.

**Output:** a feed that is correct after a Back navigation on every browser, an endpoint that cannot
be heuristically cached, and a filter that remembers what the reader asked for.
</objective>
