<objective>
**"If no one disputed it, why am I seeing it in the disputed area?"**

The user has now asked for this twice, five days apart. Today, ticking "Show disputed reports" does
not switch the view: it widens it. A report posted seconds ago with zero votes resolves to
Provisional, Provisional is returned unconditionally, and so the freshly posted report sits in the
"disputed" list alongside the actually-disputed ones with nothing distinguishing why each is there.

The diagnosis corrected the obvious guess. The union is **not** in the HTTP handler and **not** in
SQL. It is in `internal/service/feed.go`'s `Visibility.ListableInFeed(includeDisputed bool)`, a
four-case switch in which `VisibilityLive` and `VisibilityProvisional` return `true` unconditionally
and only `VisibilityHidden` consults the flag. `report.go`'s `Nearby()` calls it once per report at
its single production call site, and that is the whole of the visibility filtering for
`GET /api/reports`.

**This is deliberate, documented, tested behaviour as of today's code, not an accidental wiring
slip.** The additive reading is asserted in four places: the function's own doc comment, the phase's
`02-RESEARCH.md` data-flow diagram, and two named test suites whose failure messages spell it out
("the toggle adds Hidden reports, never removes Provisional ones"; "the toggle should add reports,
not replace the view"). Any honest fix therefore rewrites those assertions rather than leaving them
to fail.

**What the diagnosis also established, and what makes this safe to change:** D-10 and D-11's actual
locked text in `02-CONTEXT.md` require only that Hidden reports be *reachable* through the toggle.
Neither says Live and Provisional must remain visible alongside them. The additive reading was
introduced one layer *below* the locked decision, in `02-RESEARCH.md`'s diagram and in this
function's implementation and tests. Making the filter exclusive therefore contradicts no locked
decision, only an interpretation, and the user has approved reversing that interpretation twice.

**One pre-existing consequence, recorded so it is not mistaken for a new regression.** D-06's
critical-bypass rung sits above the dispute rung in `Resolve()`, so a critical or rescue-needed
report stays Live no matter how many people dispute it. Once the disputed view is a true partition,
such a report will never appear there, even when heavily disputed. That is existing behaviour
becoming more visible, not something this fix introduces.

**Output:** a four-line switch that partitions instead of unions, three artefacts that document the
partition instead of the union, a regenerated OpenAPI spec, and a backlog entry that can be closed.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client query parameter to server-side filter | Unchanged in shape. A boolean parsed from the query string selects which of two server-computed views is returned. This plan changes which reports each view contains, not who may ask or what is trusted |
