## Gap closure round 1, plan 1 of 3

This plan closes **two `status: failed` gaps** from `02-UAT.md` (Test 3, both `severity: major`).
It is one of three mutually-parallel gap-closure plans: `02-08` (this one), `02-09` and `02-10`

<objective>
**The inline destructive confirmation D-15 specified never actually replaced anything, and in the
map popup its prompt was invisible.** Both failures are in one file — `web/static/css/trust.css` —
and both are the same class of bug this repository has now hit five times: a CSS rule that looks
correct in isolation but loses a cascade contest it was never checked against.

**Gap A — the button row is not replaced (D-15).** `votes.js`'s `openResolveConfirm` sets
`hidden = true` on the three primary buttons, which is correct and needs no change. The browser's
native `[hidden] { display: none }` rule is **user-agent origin**, and an author-origin `display`
declaration at *equal specificity* beats it. `trust.css`'s own header block (the comment beginning
"[hidden] specificity fix") states that **every** `display` rule in the file therefore carries
`:not([hidden])` — and the base vote-button rule, the very first rule after that comment, does not.
So the three buttons keep rendering next to the confirmation on both surfaces, which is what the
UAT reported as buttons that "look too big / doubled up".

**Gap B — the confirmation heading is illegible in the map popup.** `02-UAT.md` recorded this gap
as INCONCLUSIVE from static analysis and asked for live DevTools inspection. **That is no longer
necessary — the diagnosis is complete, and the UAT's own investigation missed it because it audited
only `color` declarations and never asked what background the text sits on.** The chain, every link
verified against a primary source during planning:

1. Leaflet 1.9.4 ships `.leaflet-popup-content-wrapper, .leaflet-popup-tip { background: white;
   color: #333; ... }` — confirmed by fetching the pinned stylesheet the template actually links.
2. This repository has **zero** rules matching `leaflet-popup` or `map-popup` in any of its five
   stylesheets — confirmed by grep. Nothing has ever overridden that vendor pair.
3. Therefore **the map popup is a white box in dark mode**, in both Phase 1 and Phase 2.
4. `.resolve-confirm p` sets `color: var(--color-text)`, which in dark mode is `#F3F4F6` — near-white
   text on Leaflet's white wrapper. Invisible.
5. This explains the **discriminating** observation the UAT could not account for: the sibling
   buttons render at full contrast because the base vote-button rule declares
   `background: var(--color-bg)` and therefore **paints its own dark surface**, while
   `.resolve-confirm` declares only a border. Phase 1's popup text (`.map-popup__meta`,
   `.map-popup__description`) has no app `color` rule at all, inherits Leaflet's `#333`, and is
   legible on white — which is why Phase 1's UAT passed and nobody noticed the white box.

**A falsifiable prediction, recorded so the fix can be checked against reality rather than against
itself: this bug does not reproduce in light mode.** In light mode `--color-text` is `#1A1D21` on
Leaflet's white, roughly 16:1. Every screenshot in the UAT session was dark mode (the session's own
note says so). If the reporter ever reproduces the washed-out heading in *light* mode, this
diagnosis is wrong and the fix must be reopened.

**Output:** a `trust.css` whose guard discipline is finally complete, a Leaflet popup that belongs
to this app's theme rather than to Leaflet's 2010 defaults, and three regression gates that fail
the build if any of it is undone.
</objective>
