## Gap closure round 1, plan 3 of 3

This plan closes **two `status: failed` gaps** from `02-UAT.md`, both `severity: minor` (Test 3's
navigation complaint and Test 2's requested theme control). It is one of three mutually-parallel
gap-closure plans: `02-08`, `02-09` and `02-10` (this one) share **zero** files, so all three run in
wave 8 together.

**Requirements note, flagged rather than papered over.** The `requirements` field lists `IDENT-03`,
which covers the Activity page the back link is added to. **The theme toggle has no backing
requirement ID in `.planning/REQUIREMENTS.md`** — it is a net-new feature requested live during the
2026-09-17 UAT session, and no v1 requirement in that file covers appearance or display
preferences. The developer should decide whether to add one (e.g. under a new UX heading) or to
accept it as a UAT-originated enhancement tracked only through this plan and `02-UAT.md`.

<objective>
**Two things a reader could not do: get back, and see the app in the other theme.**

**Gap A — the Activity page is a dead end (minor).** `web/templates/profile.html.tmpl` renders the
account header, the email row and the activity list, and nothing else. There is no link back to the
map or the feed; the browser's own Back button is the only way out. The shared header cannot host
the link: `auth.css`'s own comment records **DEC-S** — the header deliberately carries no left-slot
content of any kind, no bar background and no logo slot, because it is a fixed-position overlay on
top of a full-viewport map. So the link belongs in the page body, as the first thing inside the
Activity page's own `<main>`.

**Gap B — there is no way to choose a theme (minor, new feature).** The app has always had a
complete dark palette, but only the OS-level `prefers-color-scheme` reaches it. The UAT reporter
asked for an in-app switch so light mode can actually be used and verified without changing system
settings — and, separately, noted that every screenshot of the whole session was dark mode, meaning
**light-mode rendering of this phase's work has never been looked at at all.** A toggle is the
cheapest way to make that reviewable.

The good news, and the reason this is a small plan: `main.css` already ships
`:root[data-theme="dark"]` and `:root[data-theme="light"]` blocks, fully populated and deliberately
specificity-ordered to beat the `prefers-color-scheme` media block regardless of source order. Its
own header comment says they exist "so a future theme toggle needs no restructuring." **That
prediction holds — no token is moved and no override block is edited.** What is missing is a control
and something to set the attribute.

Three design decisions worth stating up front, because each is the opposite of an obvious
alternative:

- **Three states, not two.** System → Light → Dark → System. A two-state toggle would permanently
  strand the reader on an explicit choice with no way back to following the OS, which is the state
  the app ships in and the one most people want on a phone that switches at dusk.
- **`localStorage`, not a URL parameter** — the mirror image of the call the sibling plan `02-09`
  makes for the disputed filter, and for the mirror-image reason. A theme is a *preference*: it
  should persist across visits and must not be carried in a shareable link. A filter is *view
  state*: it should be shareable and must not silently persist. Stated here so the two decisions
  read as one consistent rule rather than as an inconsistency.
- **A classic script in the document head, not a deferred module.** A deferred script runs after
  the document is parsed, so the page paints in the wrong palette first and then snaps — the flash
  every naive theme toggle ships with. A non-deferred head script runs while `<head>` is still
  parsing, when `document.documentElement` already exists and nothing has painted.

**Output:** an Activity page you can leave, a theme you can choose from inside the app on every page
that has a menu, a preference that is honoured on every page the app serves, and a set of gates that
make a future fifth page unable to ship without it.
</objective>

| browser storage → root attribute | New in this plan: a value that survives across visits and that a reader (or anything with script access to the origin) can write is read back and reflected into an attribute on the document root, which selects a CSS block |
