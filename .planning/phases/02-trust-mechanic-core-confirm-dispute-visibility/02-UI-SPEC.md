# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Source of truth for base tokens:** `web/static/css/main.css` (already shipped, Phase 1) and `.planning/phases/01-foundation-report-map/01-UI-SPEC.md` (the approved contract that produced it). This document does **not** redeclare Phase 1's tokens — it extends them with the new components, states, and copy Phase 2's confirm/dispute/resolve/reopen mechanic needs, and calls out every place it reuses an existing class or pattern versus introducing a new one.

**Scope note:** Phase 1's theme reference image (`.planning/phases/01-foundation-report-map/assets/01-theme-reference.png`) already mocked "Confirmed by N nearby" and "Unconfirmed · expires soon." The literal weighted "N nearby" count is Phase 3 (TRUST-05) — this phase does not display a number, only the boolean-gated visibility state (Provisional/Hidden/Live/Retracted) and the interaction to change it. Where this spec needs placeholder copy that implies a count, it deliberately avoids one (see Copywriting Contract).

## Design System

| Property | Value |
|----------|-------|
| Tool | none — no shadcn, no component framework. Same Go `html/template` + vanilla JS + hand-written CSS stack as Phase 1, no npm build step. The shadcn initialization gate does not apply: this is not a React/Next.js/Vite project (confirmed: no `components.json`, no `package.json` in the repo). |
| Preset | not applicable |
| Component library | none — new components (vote buttons, visibility tags, the "Show disputed" filter, inline resolve-confirmation) are hand-built HTML/CSS/vanilla JS, following the exact patterns already established in `feed.js`/`map.js`/`main.css` |
| Icon library | none new. Confirm/Dispute/Mark Resolved/Reopen/Show Disputed are **text-label buttons, no icon glyphs** — deliberate, not an oversight: Phase 1's Lucide icon set is reserved for the 9 report categories (`.icon-glyph--*`); adding new icon assets for 4 more actions would grow the self-hosted SVG set for marginal gain on already-legible short labels, and keeps the compact feed-row/popup layout (see "Vote controls layout" below) from getting more crowded on narrow screens. |
| Font | Unchanged — system UI stack (`-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif`), inherited from `main.css`. |

## Spacing Scale

Reuses Phase 1's declared scale exactly — no new token, no exception:

| Token | Value | Usage (Phase 2 additions) |
|-------|-------|------|
| xs | 4px | Gap between a vote button's label and its pressed-state indicator; visibility-tag internal padding (vertical) |
| sm | 8px | Gap between vote-control buttons in a row; visibility-tag internal padding (horizontal); gap between the "Show disputed" toggle and the report list |
| md | 16px | Vote-controls block's top margin from the row's meta line; inline resolve-confirmation block padding |
| lg | 24px | (unchanged from Phase 1 — section padding) |

**Touch targets:** every vote/resolve/reopen button and the "Show disputed" toggle control are minimum 44×44px (WCAG 2.5.5), same floor as Phase 1's FAB/category-tile/slider-thumb — not an exception, a continuation of the existing rule. Because feed rows are dense, buttons meet the 44px floor via `min-height: 44px` with tight horizontal padding (`--space-sm`) rather than Phase 1's `.btn` default padding (`--space-sm --space-lg`), which would overflow three buttons on a narrow feed row.

Exceptions: none.

## Color

Reuses Phase 1's full token set (`--color-bg`, `--color-surface`, `--color-border`, `--color-text`, `--color-text-muted`, `--color-focus-ring`, the three severity hues + tints, `--color-age-stale`). **No new hex value or CSS variable is introduced by this phase.** Every new component below is built by composing existing tokens in a new way — declared explicitly here so the checker can verify no raw hex sneaks in during implementation.

### Vote button color states

| Element | State | Composition | Rationale |
|---------|-------|-------------|-----------|
| `.vote-btn--confirm` | default (no vote cast) | border `--color-border`, text `--color-text`, bg `--color-bg` | Matches Phase 1's neutral `.btn` — no accent until a vote is actually cast |
| `.vote-btn--confirm` | active (viewer's current vote = confirm) | border + text `--color-severity-low`, bg `--color-severity-low-bg` | Reuses the existing green hue's established meaning (low severity / "this checks out") rather than inventing a 5th color — extends, not violates, Phase 1's "accent reserved for severity signaling" rule (see "Accent reserved for" below) |
| `.vote-btn--dispute` | default | border `--color-border`, text `--color-text`, bg `--color-bg` | Same neutral baseline |
| `.vote-btn--dispute` | active (viewer's current vote = dispute) | border + text `--color-severity-critical`, bg `--color-severity-critical-bg` | Reuses the existing red/critical hue's established meaning ("something is wrong here") |
| `.vote-btn--resolve` | default | bg `--color-text`, text `--color-bg` (inverted neutral) | Matches Phase 1's "neutral, non-severity" treatment already used for the FAB and primary submit button — Mark Resolved is a primary-weight action, not a severity signal, so it does **not** borrow a severity hue |
| `.vote-btn--reopen` | default | border `--color-border`, text `--color-text`, bg `--color-bg` | Same neutral baseline as unvoted confirm/dispute — reopening is a corrective, not alarming, action |
| any vote button | disabled (in-flight / reporter viewing own report / awaiting GPS) | existing `--color-text-muted` text, `--color-border` border, `--color-surface` bg (matches Phase 1's disabled-submit-button precedent) | Consistent "unavailable" treatment already implied by `.btn` but never explicitly tokenized in Phase 1 — declared here for Phase 2's four new disableable buttons |

### Visibility state color

| State | Composition | Applies to |
|-------|-------------|------------|
| Provisional | `.report-row`/pin badge gets the **same desaturation mix Phase 1's `.age-aging` already computes** (`color-mix(in srgb, var(--severity-base) 50%, var(--color-age-stale) 50%)`), regardless of the report's actual age stage — this is D-09's literal instruction to reuse the expiry-fade pattern. See "Visibility class precedence" below for how this composes with the existing `.age-*` classes without a conflicting override. | `.report-row`, map pin badge |
| Hidden | Badge fill becomes fully transparent with a `1px solid var(--color-border)` outline ring (replacing the solid severity fill entirely — not a further desaturation step, a distinct "outline" treatment per D-11's explicit wording); glyph color `--color-text-muted`; row left-border becomes `--color-border` (neutral, not severity-colored); row background tint removed (`background: transparent`, not `--severity-tint`) | `.report-row--hidden`, map pin badge (only rendered when "Show disputed" is on) |
| Live | No new treatment — full-saturation severity color exactly as Phase 1 already renders it | `.report-row`, map pin badge |
| Retracted | Never rendered in the feed/map (D-12 — removed immediately). Where it appears (the Activity/profile page, see "Activity Page Extension" below), it uses the same **Hidden outline treatment** (transparent fill + border outline + muted glyph) — visually "this is not currently active" reads consistently whether the reason is dispute or resolution, while the text label distinguishes *why* | `.profile-report-list` row (Activity page) |

**Accent reserved for** (Phase 1's list, extended by this phase — do not add anything beyond this explicit set):
- Everything already listed in `01-UI-SPEC.md` (category icon-badge fill, report-row left-border/tint, severity slider, map pin fill, age-ramp target)
- **New:** the active/pressed state of `.vote-btn--confirm` (green) and `.vote-btn--dispute` (red) — reusing the existing severity hues' established valence (low=reassuring, critical=alarming), not a new color meaning

**Explicitly NOT used for:** `.vote-btn--resolve`, `.vote-btn--reopen`, the "Show disputed" toggle, or any visibility-tag chip. These stay neutral (`--color-text`/`--color-bg`/`--color-border`/`--color-text-muted`) — consistent with Phase 1's "not a heavily-branded consumer look" direction and this phase's own discipline of not inventing new hues.

### Destructive

| Role | Value | Usage |
|------|-------|-------|
| Destructive | `--color-severity-critical` (reused, unchanged) | The inline "Mark this resolved?" confirmation step's affirm button only (see Copywriting Contract) — Mark Resolved removes a report from everyone's live feed, which is the highest-consequence action this phase introduces, so it gets the same destructive treatment Phase 1 already reserved for the discard-draft confirmation |

## Visibility class precedence (CSS cascade contract)

Executor must declare rules in this exact source order in `main.css` or a new `trust.css` (planner's call which file) so precedence resolves correctly — this mirrors the existing `.sev-*` → `.age-*` cascade comment already in `main.css`:

1. `.sev-*` (existing) — sets `--severity-current` to the base hue
2. `.age-*` (existing) — overrides `--severity-current` toward `--color-age-stale` by real elapsed-time stage
3. `.vis-provisional` (**new**, declared after `.age-*`) — unconditionally sets `--severity-current` to the aging mix and `--badge-glyph-fg: var(--color-text)`, **regardless of what stage `.age-*` computed** — a Provisional report always reads as "not yet trusted" even if it is only minutes old. This is a deliberate simplification (trust-state visually dominates age-state for Provisional reports) rather than a `max()` blend of both signals, which would need a second custom property and complicate the exact contract `.age-aging`/`.age-stale` already define.
4. `.vis-hidden` (**new**, declared after `.vis-provisional`) — overrides to the fully transparent/outline treatment described above, ignoring both `--severity-current` and any age stage entirely (Hidden is never shown to a default viewer, so there is no age-based nuance worth preserving once it is shown via the toggle).

A report is never both `.vis-provisional` and `.vis-hidden` at once (a single report has exactly one visibility state per the resolver's contract), so this is a documentation-of-precedence exercise for future-proofing (e.g. an author accidentally leaving both classes on a stale DOM node during a live-poll update), not an expected runtime conflict.

## Vote controls layout

### Feed row extension (`report-row`, extends `feed.js`'s existing `createRow`)

Existing structure (unchanged):
```html
<li class="report-row sev-{level} age-{stage}" data-report-id="{id}">
  <span class="icon-badge icon-badge--sm"><span class="icon-glyph icon-glyph--{cat}"></span></span>
  <div class="report-row__body">
    <p class="report-row__title">{description}</p>
    <p class="report-row__meta">{category} · {relative-time}</p>
  </div>
</li>
```

New Phase 2 additions to `.report-row__body` (appended after `.report-row__meta`, same element, no restructuring of the existing two children above):

```html
<div class="report-row__body">
  <p class="report-row__title">...</p>
  <p class="report-row__meta">...</p>

  <!-- NEW: visibility tag — rendered ONLY for provisional/hidden reports, absent entirely for live reports (no empty chip, no "Confirmed" chip — Phase 3's job) -->
  <span class="visibility-tag visibility-tag--provisional">Unconfirmed</span>
  <!-- or, only ever visible when "Show disputed" is on: -->
  <span class="visibility-tag visibility-tag--hidden">Disputed</span>

  <!-- NEW: vote controls row -->
  <div class="vote-controls" data-report-id="{id}">
    <button type="button" class="vote-btn vote-btn--confirm" data-action="confirm">Confirm</button>
    <button type="button" class="vote-btn vote-btn--dispute" data-action="dispute">Dispute</button>
    <button type="button" class="vote-btn vote-btn--resolve" data-action="resolve">Mark resolved</button>
  </div>
  <p class="vote-error" role="alert" hidden></p>
</div>
```

- **Reporter viewing their own report (D-03):** `.vote-btn--confirm` and `.vote-btn--dispute` are **not rendered at all** (removed from the DOM, not merely `disabled` — cleaner on a row already tight for space, and avoids a non-actionable button reading as a bug). `.vote-btn--resolve` **is** rendered (D-13's reporter-instant path).
- **Non-reporter viewing someone else's report:** all three buttons render. Tapping `.vote-btn--resolve` here is the confirmer-proposal path (D-13/D-14), not instant — see "Mark Resolved interaction" below for how the UI distinguishes the two without a separate button.
- **Retracted reports never reach this template at all** (D-12 — excluded server-side from the feed query), so no reopen button exists in `.vote-controls`. Reopen lives only on the Activity page (see below).

### Map popup extension (`map-popup`, extends `map.js`'s existing `buildPopupContent`)

Existing structure (unchanged):
```html
<div class="map-popup">
  <p class="map-popup__meta">{category} · {severity} · {relative-time}</p>
  <p class="map-popup__description">{description}</p>
</div>
```

New Phase 2 additions (same visibility-tag + vote-controls block, appended after `.map-popup__description`, identical markup/classes to the feed row's block so the same CSS and the same `votes.js` event-delegation code handles both surfaces — per D-01's "both surfaces, not restricted to one"):

```html
<div class="map-popup">
  <p class="map-popup__meta">...</p>
  <p class="map-popup__description">...</p>
  <span class="visibility-tag visibility-tag--provisional">Unconfirmed</span>
  <div class="vote-controls" data-report-id="{id}">
    <button type="button" class="vote-btn vote-btn--confirm" data-action="confirm">Confirm</button>
    <button type="button" class="vote-btn vote-btn--dispute" data-action="dispute">Dispute</button>
    <button type="button" class="vote-btn vote-btn--resolve" data-action="resolve">Mark resolved</button>
  </div>
  <p class="vote-error" role="alert" hidden></p>
</div>
```

Leaflet popups have a fixed max-width and no native reflow guarantee for interactive content, so `.vote-controls` inside `.map-popup` must wrap onto a second line on narrow popups (`flex-wrap: wrap`) rather than force a horizontal scrollbar — the only popup-specific CSS override this phase needs.

### Hidden pin styling (map, D-11)

When "Show disputed" is on, Hidden pins render with the transparent/outline badge treatment from the Color section above, at the same size (`icon-badge--pin`, 44×44px) as any other pin — distinct fill, identical geometry, so it doesn't look broken or half-loaded, just visibly "not currently trusted."

## Interaction contract

### Casting/changing a vote (D-01, D-02, D-04)

1. Tap `Confirm` or `Dispute` (from either surface — feed row or map popup; both call the same `votes.js` function).
2. `votes.js` resolves the voter's location: cached `sessionStorage` value if present (D-17), otherwise triggers the browser's native geolocation prompt **at this point** (first vote of the session) — no custom priming screen first, since the prompt is already user-action-triggered (satisfies the "request after user action" best practice `01-RESEARCH.md`'s State of the Art table cites).
   - **Granted:** proceed to step 3.
   - **Denied/unsupported (D-18):** the tapped button re-enables immediately, no request is ever sent, and `.vote-error` (on that same row/popup) becomes visible with the copy in "GPS denial copy" below. This is a **hard stop**, not a fallback center — do not reuse `modal.js`'s `initLocation()`/`showLocationDenied()` pattern, which intentionally falls back to a default location for report *submission*; voting has the opposite requirement.
3. The tapped button's label changes to a submitting state and **all three** vote-controls buttons on that row/popup disable (D-04 — no optimistic update, and no user can double-submit a second action while the first is in flight).
4. POST fires; on success, the response's fresh `visibility` (and the caller's own new vote state) drives a full re-render of that row/popup's badge classes, visibility tag, and button active-states — exactly as if the row had just been fetched fresh from the feed endpoint. On failure, buttons re-enable and `.vote-error` shows the generic failure copy.
5. **Re-tapping the button that already reflects the viewer's current vote** re-sends the same vote (harmless — the append-only log absorbs a duplicate row) and produces no visible change; tapping the *other* button changes the active state per D-02.

### Mark Resolved interaction (D-13, D-14, D-15)

Because a single "Mark resolved" button serves two different mechanics depending on who taps it (reporter = instant, confirmer = threshold-gated) and because this is explicitly the higher-consequence action in this phase, it gets one extra confirmation step **inline on the same surface** (D-15 — never a separate view):

1. Tap `Mark resolved`.
2. The button is replaced **in place** by a two-button inline confirmation (same pattern as the existing report-submission modal's discard-confirm block in `modal.css`, adapted to an inline row instead of a modal):
   ```html
   <div class="resolve-confirm">
     <p>Mark this report resolved?</p>
     <button type="button" class="vote-btn vote-btn--confirm-resolve">Yes, mark resolved</button>
     <button type="button" class="vote-btn vote-btn--cancel-resolve">Cancel</button>
   </div>
   ```
   `.vote-btn--confirm-resolve` uses the Destructive color (`--color-severity-critical` bg/text-inverted) per the Destructive row above; `.vote-btn--cancel-resolve` is neutral outline.
3. Tapping "Yes, mark resolved" follows the same GPS-then-POST-then-wait flow as any other vote (steps 2-4 above, reusing the `resolve` action).
4. **Server response drives the outcome copy** (see Copywriting Contract) — the UI does not guess whether the resolve action actually flipped the report to Retracted or only recorded one of several needed independent votes; it reflects whatever `visibility`/`reason` the server returns.
   - If the response visibility is `retracted`: the report is removed from the feed/map immediately (D-12) with a toast confirming it.
   - If the response visibility is unchanged (still `live`/`provisional`, reason `awaiting_second_independent_confirmation`-equivalent for the resolve path): the row stays, the inline confirmation collapses back to the normal three-button state, and a toast acknowledges the vote was recorded without claiming the report is resolved yet.
5. Tapping "Cancel" collapses the inline confirmation back to the normal three-button row with no request sent.

### Reopen interaction (D-16) — Activity page only

Because Retracted reports are removed from the feed/map immediately (D-12) and never reappear there, `Reopen` has no home on the feed row or map popup template — it is added to the existing Activity section on the profile page (`profile.html.tmpl`), which already lists the account's own submitted reports and (per `IDENT-03`) is the natural place their confirm/dispute/resolve voting history surfaces too. Extends the existing placeholder text ("Confirm and dispute activity will appear here once voting launches.") rather than adding a new page.

```html
<li class="report-row report-row--hidden" data-report-id="{id}">
  <span class="icon-badge icon-badge--sm vis-hidden"><span class="icon-glyph icon-glyph--{cat}"></span></span>
  <div class="report-row__body">
    <p class="report-row__title">{description}</p>
    <p class="report-row__meta">{category} · {relative-time}</p>
    <span class="visibility-tag visibility-tag--hidden">Resolved</span>
    <button type="button" class="vote-btn vote-btn--reopen" data-action="reopen" data-report-id="{id}">Reopen · not actually resolved</button>
  </div>
</li>
```

Tapping `Reopen · not actually resolved` follows the identical GPS-then-POST-then-wait flow (D-04) as any other vote. **Confirmed 2026-09-15 (amended D-16, see `02-CONTEXT.md`):** the reporter gets an instant, threshold-free reopen, symmetric with D-13's instant resolve. Because this Activity-page button only ever appears on the viewing account's *own* submitted reports (the page lists "the account's own submitted reports," never anyone else's), every tap of this specific button is by definition the reporter's own action — so in practice it always succeeds instantly, and the toast is always "Report reopened." The "reopen vote recorded, pending agreement" toast copy (below) is retained for API-consistency with `castVote`'s generic outcome handling (a non-reporter *could* call the same endpoint directly, outside any UI this phase ships) but is not reachable through this button.

### "Show disputed" filter (D-10, D-11)

Added to the feed pane's toolbar, immediately above `#report-list` (same page, same view, per D-10 — not a new route):

```html
<label class="filter-toggle">
  <input type="checkbox" id="show-disputed-toggle">
  Show disputed reports
</label>
```

- Native checkbox (not a custom-styled switch) — deliberate, matches this project's existing preference for native form controls (`<select>` for shelter capacity, native `<input type="range">` for severity) over hand-rolled ARIA widgets, minimizing new accessibility surface for a portfolio-scale feature.
- Checking it adds `?show_disputed=true` to the existing feed fetch (both the list AND the map query — one shared toggle, one shared query param, per D-11) and causes Hidden reports/pins to appear with the outline treatment described above; unchecking removes them again. No page reload — same `feed.js` polling/refetch mechanism Phase 1 already uses.
- **Empty state when toggled on with nothing to show:** reuses the existing `.empty-state` component with new copy (see Copywriting Contract) — do not silently show nothing with no explanation.

**Amendment history (added 2026-09-17, plan 02-09 — locked, not open):** the scoping above — a plain native checkbox with no persistence — was deliberate and shipped exactly as specified; Phase 2's own human-check listed "the checkbox does not persist checked across a reload" as *expected* behaviour, and `02-UAT.md` Test 2 confirmed it working as specified. The user reversed this during that same Test 2 UAT walkthrough: refreshing while reading the disputed view dropped them out of it, and they asked for the view to survive a reload instead. Plan `02-09` implements that reversal via a **URL query parameter** (`show_disputed`, the exact same name the API already parses) rather than `localStorage`, because the filter is view state — shareable, bookmarkable, and something a later visit must never silently inherit from an earlier one — not a persisted preference. This decision is **locked, not open**: a future reader who finds the original "does not persist" wording above must not restore the ephemeral behaviour as a regression fix — the current, correct behaviour is that the checkbox and the address bar stay in step across a reload and a back-forward-cache restore alike.

## GPS denial copy (D-18 — the phase's highest-risk copy-paste trap)

This copy is deliberately different in tone from Phase 1's non-blocking location notice (`"Location access is off — drag the map to your area, or tap the map to drop a pin."`) — that copy explicitly offers a workaround because submission must never block on GPS. Voting has no workaround by design (D-18), so the copy must not imply one exists.

| Trigger | Copy |
|---------|------|
| Geolocation denied or unsupported, any vote action | "Voting needs your location, so nearby confirmations can be verified as independent. Turn on location access for this site and try again." |
| Vote POST fails for any other reason (network/server error) | "Couldn't record your vote. Check your connection and try again." |
