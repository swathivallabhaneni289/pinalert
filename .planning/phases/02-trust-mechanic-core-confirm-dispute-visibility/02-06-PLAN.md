## Phase Goal

**As a** person near an ongoing incident, **I want to** confirm or dispute another user's report **so that** reports lacking independent nearby corroboration lose visibility while well-corroborated ones stay trusted — and as a reporter or nearby confirmer, I want to mark a report resolved once it's no longer true, so the feed reflects what's actually happening right now.

<objective>
"As a person near an ongoing incident, I want to confirm or dispute another user's report so that reports lacking independent nearby corroboration lose visibility while well-corroborated ones stay trusted — and as a reporter or nearby confirmer, I want to mark a report resolved once it's no longer true, so the feed reflects what's actually happening right now."

**This plan is the half of that story where the consequence becomes visible.** 02-01 through 02-04
made a report's visibility real and 02-05 made the vote castable — but a person looking at the feed
right now cannot tell a provisional report from a trusted one, and a report the neighbourhood
disputed into Hidden simply vanishes with no way to look at it. The trust state exists; it is not
legible. After this plan a reader can see, without opening DevTools or reading Go, that a report is
not yet corroborated, and can deliberately go look at what the neighbourhood pushed out of view.

The decisions this plan implements, each cited by ID:

- **D-09** — a **Provisional** report gets **both** treatments, never one alone: the dimmed/
  desaturated look **and** an explicit text label. D-09's own wording pins the dimming to Phase 1's
  expiry-fade pattern (`01-CONTEXT.md` **D-17**: desaturation toward gray, *not* opacity), "so 'not
  yet trusted' reads consistently with 'going stale'". This plan takes that literally: `.vis-provisional`
  declares the exact `color-mix` value `.age-aging` already computes, so the two states are the
  same pixels by construction rather than by a designer matching them twice. The label is
  `02-UI-SPEC.md`'s Copywriting Contract string, "Unconfirmed", verbatim.
- **D-10** — **Hidden** reports leave the default feed and map for every viewer but stay browsable
  behind a **"Show disputed" toggle on the existing feed** — same page, same resolver-backed query,
  no new route and no separate disputed page. 02-04 shipped the server half (`?show_disputed=true`);
  this plan ships the control that sets it and the outline treatment the revealed rows wear.
- **D-11** — that **same** toggle also reveals Hidden **pins on the map**, styled distinctly, so
  feed and map keep showing identical resolver state (TRUST-02). In this client that requires no
  map-specific code at all, and the reason is the whole point rather than a convenience:
  `app.js`'s own file comment records that it owns the one `GET /api/reports` call and that
  "nothing else in the client fetches reports". One flag changes one URL, one array changes, and
  both subscribers re-render. There is no place for the two surfaces to disagree, because there is
  no second query to get wrong.

Purpose: **TRUST-04** says a non-critical report *displays as* "provisional" until a second
independent confirmation arrives. Everything before this plan satisfies the computing half of that
sentence; this is the plan where "displays as" becomes true. **TRUST-02** says the visibility state
is identical everywhere it is shown — 02-04 made that structural on the server, and this plan is
where the client either preserves it or quietly breaks it by filtering, caching or re-deriving on
one surface.

Output: `web/static/js/visibility.js` (the tag builder, the state-class applier and the closed
label/reason maps), the `.vis-provisional` / `.vis-hidden` cascade rules and the `.visibility-tag`
chip in `web/static/css/trust.css`, the "Show disputed reports" toggle and the disputed empty state
in `index.html.tmpl`, the `show_disputed` query-string flag on the shared store's one fetch, both
surfaces mounting the same tag, and eight new contract tests in `web/votes_contract_test.go`.

**One deliberate resolution of an ambiguity in the brief, recorded rather than silently chosen.**
"When the toggle is on and no disputed reports exist nearby, render the empty-state copy rather than
a blank list." In this codebase `.empty-state` means *shown instead of the list* — `#feed-empty`
appears only when `reports.length === 0`, with `#report-list` hidden, and main.css gives it
`padding: var(--space-2xl)` with centred text. `02-UI-SPEC.md` says to reuse that component, so this
plan inherits its semantics: `#disputed-empty` **replaces** `#feed-empty` inside the existing
zero-reports branch, selected on the store's `showDisputed` flag. It is never stacked above a
populated list, which would put a full-height centred block between the toggle and the rows it is
describing. The consequence is explicit: with the toggle on and nothing nearby at all, the reader
sees "No disputed reports nearby" rather than "No reports near you yet" — unchecking the box
restores the general message immediately, and the checked box sitting directly above it is the
context that makes the narrower message the right one.

**Two prior traps this plan is walking straight back into, and the gates that catch them.**

1. **The `[hidden]` specificity trap, this repo's third encounter.** An author-origin `display`
   declaration beats the user agent's `[hidden] { display: none }` at equal specificity. It shipped a
   permanently-open modal backdrop in Phase 1 (a live UAT blocker, fixed by 01-08), threatened the
   account menu in Phase 1.1, and 02-05 shipped `TestVoteBlockHiddenGuard` because it threatened the
   vote block. This plan adds two more JS-toggled elements and needs **both** guard forms, for two
   different reasons — see Task 1 and Task 3. Each gets its own gate with a vacuity check.
2. **A class name typed into a consumer.** 02-05's `TestBothSurfacesMountTheSameVoteBlock` exists
   because a class literal appearing in `feed.js` or `map.js` is the first step of a second
   implementation. The same gate is extended to this plan's three new class literals and the two
   response fields they are built from.

**On the MVP-mode "failing end-to-end test first" rule.** Unchanged from 02-05's statement of it:
this repo has no build step and no JavaScript test runner, and the established substitute is the
`package web` contract tests, which read the *shipped, embedded* asset out of `StaticFS`/`TemplatesFS`
