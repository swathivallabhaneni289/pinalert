## Gap closure round 2, plan 3 of 4

This plan closes **two `status: failed` gaps** from `02-UAT.md`, both `severity: major`: the
Provisional dimming nobody can see (Test 5) and the Mark Resolved button that stays visible beside
its own confirmation (Test 6). They share `web/static/css/trust.css` and its contract test, which is
why they ship together rather than as two plans.

Diagnoses: `.planning/debug/provisional-dimming-not-perceptible.md` (root cause CONFIRMED, a design
strength gap rather than a code defect) and `.planning/debug/resolve-button-not-hidden.md`
(**INVESTIGATION INCONCLUSIVE**, which shapes what this plan is allowed to claim).

It is one of four mutually parallel plans in this round (`02-11`, `02-12`, `02-13`, `02-14`). The
four share zero files, so all run in wave 9 together.

<objective>
**"I don't see the faded look but I definitely see the unconfirmed chip."**

Half of D-09 works. The "Unconfirmed" chip is visible and correct on both surfaces. The desaturation
that is supposed to accompany it is not perceivable at all.

The diagnosis is unusually clean and unusually uncomfortable: **nothing is broken.**
`applyVisibilityClass` reaches the right element on both surfaces (`feed.js` on the row ancestor,
`map.js` on the pin's badge), the cascade order is right, no later stylesheet contests it. The
treatment is applied exactly as designed. The design is just too weak to see.

`.vis-provisional` mixes the severity colour 50/50 toward the stale-grey token, the exact same ratio
as the intermediate `.age-aging` stage, copied character for character on purpose. Measured against
this app's own contrast machinery, that yields roughly 1.9 to 2.0 to one in dark mode and about 1.5
to one in light mode, against roughly 4.3 to one for the same app's strongest existing desaturation
step. And unlike the age ramp, which a reader learns by watching one report's own border drift over
its lifetime, a Provisional report has no adjacent reference to compare against. A shift that subtle,
with nothing to compare it to, reads as "the same colour".

**Why no test caught it.** The only guard on this value asserts `.vis-provisional` stays string-equal
to `.age-aging`. That would pass unchanged even if both were independently discovered to be
invisible: it checks the two values against each other, never either against the undimmed baseline.
Closing that coverage gap is a first-class deliverable here, not a nicety, which is why this plan
writes the failing test **before** touching the CSS.

**Three decisions, made here rather than passed to the executor:**

- **The ratio is 20 percent severity to 80 percent stale.** Verified against the shipped token tables
  before this plan was written. It lifts the non-critical severities (Low and Medium, the only ones
  that can ever be Provisional, since D-06 keeps critical reports Live) from about 1.9 to about 3.0
  in dark mode, and drops the badge's colourfulness to roughly one fifth of the undimmed value in
  **both** themes. Note the direction carefully: `color-mix(in srgb, var(--severity-base) 20%,
  var(--color-age-stale) 80%)`. Writing 80 percent on the severity stop produces a *less* dimmed
  Provisional that would still sail past a naive percentage check, which is exactly why the gate
  below asserts measured colour, not a number in the source.
- **Colourfulness, not luminance, is the primary assertion.** Light mode's stale token is a near-white
  grey, so mixing toward it raises luminance while the severity colour is mid-dark: the light-mode
  luminance gap physically cannot reach 3 to 1 with the tokens this app ships, even at a 100 percent
  mix. Chroma loss, by contrast, is theme-symmetric and is literally what "desaturated" means. The
  gate asserts both, with an honest, separately-stated floor for each and a comment explaining the
  asymmetry rather than quietly picking whichever number passed.
- **The row's background wash becomes `var(--color-surface)`.** This is the feed-row-only confound the
  diagnosis identified: `.vis-provisional` dims the border and badge but leaves `--severity-tint` at
  full strength, so the row keeps a saturated severity-coloured background while its border fades.
  `transparent` is not available here, because that is precisely `.vis-hidden`'s treatment and
  collapsing the two would regress a Hidden behaviour UAT Test 2 confirmed correct. `--color-surface`
  is an existing neutral token, already permitted by the custom-property allowlist, and leaves
  Provisional and Hidden distinguishable.

**The second gap, and the honest limits on it.** The Mark Resolved button was investigated hard: full
static reads, cross-file greps, git history, and empirical headless reproductions in both Chromium
and WebKit, first isolated and then with the real feed-row DOM ancestry and a simulated background
poll landing mid-confirmation. In every run, in both engines, all three buttons hid correctly. **No
cause was found.** One genuine but inert asymmetry was: `.vote-btn--resolve` is the only rule in the
Mark Resolved block without the hidden-attribute guard every sibling carries, and its declared
colours are exactly the light-background, near-black-text signature the user described. This plan
applies that one guard, because a rule silently diverging from its own file's documented discipline
should not stay that way, and **claims nothing about having fixed the symptom.** The acceptance
criterion is the code state; the symptom retest and the decisive live-inspection instruction live in
the human check.

**Output:** a Provisional state a person can actually see, a test that fails if it is ever weakened
again, and one guard restored to consistency with its neighbours.
</objective>
