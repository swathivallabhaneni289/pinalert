## Gap closure round 2, plan 4 of 4

This plan closes the **mechanical half** of one `status: failed` gap from `02-UAT.md` (severity
`major`, raised during Test 8): the app reads as unpolished. Diagnosis:
`.planning/debug/ui-visual-polish.md`, root cause CONFIRMED as a design-consistency gap with several
independent drivers.

**Most of that gap is deliberately NOT in this plan.** See the scope section below: the broad items
are routed to `/gsd-ui-phase`, on the debug session's own recommendation, and listing them as deferred
here rather than omitting them silently is part of this plan's job.

It is one of four mutually parallel plans in this round (`02-11`, `02-12`, `02-13`, `02-14`). The
four share zero files, so all run in wave 9 together.

<objective>
**Two rules the product currently breaks, and a list of the ones this plan will not try to fix.**

`site-design-rules.md` is a hard constraint list the user wrote during this UAT round, after calling
the current buttons and backgrounds amateurish. A full seven-rule sweep of the live code found
exactly two live violations and cleanly cleared the other five (no gradients, no emoji icons, no fake
metrics, no scroll-triggered spectacle; the only three animations in the whole app are an ambient
login-page rotation, a loading pulse and a 200ms toast entry, all restrained).

The two that are live:

1. **Long dash characters in copy a reader actually sees**, in page titles, body sentences, an error
   message in the browser, a server-side rate-limit message, and the disclaimer in the verification
   email the product sends to real people. The debug session found nine occurrences across eight
   files. **The planner found a tenth while verifying this plan against the source:**
   `internal/api/handlers/auth.go` carries a third, independent copy of the rate-limit sentence, in
   addition to the ones in the rate-limiter package and the client script. Ten occurrences, nine
   files. Recording the discrepancy so a reader comparing this plan against the debug note does not
   read the extra file as unexplained scope creep.

2. **Two pill-shaped controls**: the list/map view toggle and the toast, both at a fully rounded
   radius. Three other things in the codebase carry that same radius and are correctly out of scope,
   because the rule is about pill-shaped buttons: the severity slider's two track pseudo-elements are
   a slider, and the circular icon controls are circles.

**Why the rest of the gap is not here.** The debug session's own recommendation, which this plan
follows, is that the large items are contract-level design work and belong in a `UI-SPEC`, not in a
gap-closure code fix. The structural root cause it identified is that `02-UI-SPEC.md` never mentions
hover, transition, motion or radius anywhere, so of roughly eleven button-family selectors built
against it, exactly one has any interaction feedback at all. Fixing that means designing a motion
system, a radius and shadow and duration token scale, and a surface-elevation treatment, then applying
them consistently. Doing that inside a gap-closure plan would mean inventing an unreviewed design
under a fix's cover, which is the opposite of what the user asked for when they asked for research
first.

**Deferred to `/gsd-ui-phase`, listed so nothing is lost:**

- A hover, active and transition motion system across the whole button family, generalising the one
  working precedent (the Activity page's back control, 150ms ease with its own reduced-motion
  override) rather than inventing a second pattern.
- A radius, shadow and transition-duration token scale alongside the existing spacing and colour
  tokens. The 8px chosen here is an interim value that matches two existing controls; the UI phase may
  re-tokenise it.
- A background and surface-elevation treatment, including whether the report modal's panel and the
  primary buttons should sit on the surface tone rather than the page background.
- The theme control's redesign from a wordy text label to an icon, using the existing masked-SVG icon
  system. The research the user asked for has been delivered; the redesign itself needs a contract.
- The Reopen button's wording, once the user confirms it is a control they meant, through the
  project's existing Copywriting Contract.
- An explicit ruling on the login gate's page heading, recording a considered "not hero text" rather
  than an unstated assumption.

**Output:** ten sentences that read in plain punctuation, two controls that are no longer pills, one
standing gate so the dash cleanup cannot erode, and a written deferral list.
</objective>

<database_protocol>
Two of this plan's three tasks touch Go packages with database-backed tests in them
(`internal/api/handlers`), and one touches packages whose own tests are pure
(`internal/mailer`, `internal/ratelimit`).

`internal/testutil.NewTestDB` **truncates the target database at the start of every test**. The user's
own development server uses a database named `pinalert_test` and holds manual-testing data in it.
**Never point `DATABASE_URL` at `pinalert_test`, and never rely on whatever `DATABASE_URL` happens to
be set in the shell.**

Where a database is genuinely needed, use a disposable one, created and dropped around the run.
`NewTestDB` applies the embedded migrations itself through goose, so a bare empty database is enough.
Always pass the single-worker flag, for the reason the Makefile's own `test` target documents:
packages share one database and each truncates at start, so concurrent packages delete each other's
in-flight rows.

`internal/mailer`, `internal/ratelimit` and `package web` need no database at all. Leave the variable
unset for those: `NewTestDB` skips rather than fails when it is absent.
</database_protocol>
