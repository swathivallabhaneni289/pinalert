## Phase Goal

**As a** person near an ongoing incident, **I want to** confirm or dispute another user's report **so that** reports lacking independent nearby corroboration lose visibility while well-corroborated ones stay trusted — and as a reporter or nearby confirmer, I want to mark a report resolved once it's no longer true, so the feed reflects what's actually happening right now.

"As a person near an ongoing incident, I want to confirm or dispute another user's report so that reports lacking independent nearby corroboration lose visibility while well-corroborated ones stay trusted — and as a reporter or nearby confirmer, I want to mark a report resolved once it's no longer true, so the feed reflects what's actually happening right now."

**This plan closes that story's second half, and the phase.** 02-01 through 02-04 made a report's
visibility real; 02-05 made a vote castable; 02-06 made the resulting state legible. All four
already carry the resolve and reopen machinery end to end — `Resolve()` already computes
`VisibilityRetracted`, `CastVote` already accepts `VoteKindResolution`, all four routes are already
mounted, and `castVote(reportId, 'resolve')` already works from the browser. **Not one line of
voting logic is written here.** What is missing is a surface: nobody can reach any of it, and a
report that is over stays in the feed forever.

The decisions this plan implements, each cited by ID:

- **D-13** — the **reporter can mark their own report resolved instantly**, while **any nearby
  confirmer can also propose "resolved"** and only takes effect once enough **independent**
  confirmers agree. Both halves are already true server-side and neither is re-implemented here:
  a reporter's resolve vote sets `ReporterResolved`, which `isRetracted()` treats as sufficient
  alone; a non-reporter's only adds to `ResolveCells`, which needs `IndependentAgreementThreshold`.
  One button serves both people. The **difference between them is invisible in the markup and
  visible only in the server's answer** — which is precisely why the outcome copy is chosen from
  the response rather than from who is looking.
- **D-15** — "Mark Resolved" sits at **the same surface as Confirm/Dispute**: the feed row and the
  map pin popup, inside the `.vote-controls` container 02-05 shipped, not tucked into a
  detail-only view. Because it is the one higher-consequence action this phase introduces, it gets
  one inline destructive confirmation step **on that same surface** — never a separate view.
- **D-12** — a **Retracted** report leaves the live feed and map **immediately**, with no
  grace-period or strikethrough state. 02-04 already enforces this server-side, so this plan hides
  nothing client-side: a refetch simply stops returning the report. D-12's own parenthetical is
  what this plan owes: *"They remain visible in the reporter/confirmer's own Activity history."*
  That history page is currently the only place a resolved report still exists, and it renders no
  trust state at all.
- **D-16 (amended 2026-09-15)** — a Retracted report **can be reopened**, via a **dedicated
  "Reopen / not actually resolved" action** kept distinct from ordinary confirm/dispute votes on the
  report's content. **The reporter's reopen of their own report is instant and threshold-free,
  symmetric with D-13's instant resolve**; a non-reporter's reopen still needs the same
  independent-agreement threshold as D-14. Both halves are enforced server-side by 02-03a's amended
  `CastVote` and 02-01's `Resolve`; neither is re-implemented here. Two facts about this plan's
  surface follow, and they are the whole reason the Reopen path is **simpler** than the resolve
  path rather than more complex: the Activity page lists **only the viewing account's own submitted
  reports**, so every tap of this button is by definition the reporter's own action; and a
  reporter's reopen always succeeds immediately. So the Reopen button has **one** outcome and its
  toast is the fixed reopen-succeeded string — no branch on visibility, no branch on reason, and
  still no branch on identity, because there is no identity question left to ask. The row's own chip
  and state class are still rebuilt from the response's visibility (see Task 3); it is only the
  toast that is fixed.

**Pre-empting the one thing a phase review will misread.** A fixed success toast looks like exactly
the client-guesses-the-outcome anti-pattern this plan argues against everywhere else. It is not,
and the exception is narrow and checkable: this button renders only on rows the viewer submitted,
and 02-03a's amended `CastVote` guarantees a reporter's reopen un-retracts the report however the
retraction arose. The resolve path, which genuinely has two outcomes, still reads its copy from the
response — and so does the reopen path's *row* update.

**Three corrections to inherited assumptions, recorded rather than silently applied.**

1. **No new store query is created, and its absence is intentional.** `02-PLAN-OUTLINE.md` and
