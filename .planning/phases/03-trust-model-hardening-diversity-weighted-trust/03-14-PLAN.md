## Phase Goal

**As a** person reading the feed during an emergency, **I want to** see how many different nearby people confirmed or disputed each report, and whether it is still current and its reporter reliable, **so that** a few accounts cannot make a weak report look well corroborated.

This plan is the S3 and S4 convergence step of the outline's MVP framing: the still current signal (03-08) and the reporter signal (03-10, loaded on every read path by 03-12) reach the wire. The browser block built in 03-13 (wave 5) already renders each signal the server sends and nothing for an absent one, so after Task 1 a reader of the real feed sees the still current word and the reporter tag side by side (TRUST-07 criterion 2), with no further UI change.

<objective>
The feed and every vote response expose the still current and reporter signals in the pinned wire shape, equal between the two and documented in OpenAPI, so the block shows both signals side by side on real data (D-08, D-21, TRUST-07 criterion 2).

Purpose: TRUST-07 is one requirement, "two signals side by side". The service already computes both signals on all three read paths; until this plan the handler mapper drops them. D-08 fixes the wire form (band or tag, facts, integer 0 to 100 score, null where there is no rating) and D-21 fixes that the feed and the vote response carry one object built one way.

Output:
- Task 1: `CurrencyResponse`, `ReporterResponse` and their mapping in `internal/api/handlers/trust.go`, the regenerated OpenAPI docs, the extended swagger drift guard (V-30) and the extended wire key list, so every 03-07 e2e test now checks both signals too.
- Task 2: the two pinned end to end proofs on a real Postgres: `TestFeedSignalsMatchCastVoteSignals` (V-29 signals part) and `TestReporterSignalFromSeededHistory`.
</objective>
