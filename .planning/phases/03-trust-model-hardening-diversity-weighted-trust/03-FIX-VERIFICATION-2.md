## WR-01 (commit 0fdbc1e): DEFECTS FOUND

Skeptic verdicts: defect, defect

### WR-01-V1 [medium] web/static/js/app.js:189-191 and 244-257 (lastAppliedSeq moves only at line 239), reaching web/static/js/feed.js:239, web/static/js/map.js:378, web/static/js/votes.js:591 and 1161
A 30 s poll P (seq n) is in flight and the server read its rows before the vote was written. The voter's POST returns 200 and the refetch R (seq n+1) gets a 5xx or a reset. R takes the catch path: it is not stale, sets status error and resolves, so votes.js:1161 shows the saved but not refreshed sentence and patches your_vote in the store. P then lands with 200. isStale() is false because n is not below lastAppliedSeq (a failure never advances it), so P replaces state.reports wholesale with pre vote rows and sets status ok. updateRow calls updateVoteBlock (feed.js:239, map.js:378), which clears the sentence (votes.js:591) and rewrites aria-pressed and counters from P. The recorded vote looks unrecorded, with live buttons and no warning, until the next good poll (up to 30 s). On a resolve, a report the server just retracted reappears the same way. This is WR-01 scenario 2 returning through the failed refetch path. Round 1's mySeq !== fetchSeq dropped P here, so relaxing to lastAppliedSeq reopened it. Server side a repeat Confirm is append only and latest wins, so the harm is display truth, not a double count. Remedy: let a refetch that follows a write (votes.js:1153 and submitReport) raise a floor sequence whether it succeeds or fails, and have isStale also drop responses below that floor. Polls would not raise it, so the slow link freeze (V2) stays closed.
