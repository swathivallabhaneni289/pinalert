## WR-01 (commit ec31071): DEFECTS FOUND

Skeptic verdicts: defect, defect

### WR-01-V1 [medium] web/static/js/app.js:202-204 with web/static/js/votes.js:1069-1075
A dropped stale response still resolves fetchReports() as success, and callers treat resolution as 'the store is fresh'. Reader taps Confirm, the POST returns, votes.js:1069 starts refetch R. Before R returns, another fetch P starts (30 s poll tick, a second vote's refetch, Retry, or a Show disputed toggle). R returns first, app.js:202 returns without writing, yet votes.js:1070-1075 releases the busy block and restores focus while state.reports still holds the pre-vote your_vote and counters. The row looks as if the vote was not recorded, with live buttons, until P lands (one round trip, longer on a slow link). If P fails, app.js:210-216 sets error and R's valid post-vote rows are lost until the next good poll (up to 30 s). Before the fix R applied first in this interleaving, so this window is new. Same shape in submitReport (app.js:255-259). Remedy: apply any response newer than the last applied sequence, or make a dropped call return the newest in-flight promise.

### WR-01-V2 [medium] web/static/js/app.js:166 (guard), 202 and 211 (both returns), 226 (poll timer)
Staleness is judged by the newest request started, not the newest response applied. The poll fires every 30 s with no in flight check and fetch has no timeout. If response latency exceeds the poll interval (congested network, or packets blackholed so a failure takes minutes to arrive), every response lands after a newer request has started, so the success path and the failure path both return without writing. A first load stays on the skeleton indefinitely. After a load, rows freeze and no error banner or Retry ever appears. Before the fix those slow responses still rendered or raised the error.

### WR-01-V3 [medium] web/static/js/app.js:202 with web/static/js/votes.js:1069 and 1074 (comment at 1062 states the invariant)
A dropped response still fulfills the fetchReports promise. The reader taps Confirm, the POST returns, and the post vote refetch starts (seq n). A 30 s poll tick, or a second vote's refetch, starts seq n+1 before it lands. The refetch is dropped, its promise resolves, and votes.js releases the busy block and runs focusAfterVote while the DOM still shows the pre vote aria-pressed and counts, the exact window the comment at 1062 forbids, until the newer fetch lands. If that newer fetch fails or hangs, the recorded vote is never shown, because the good answer was discarded.

Skeptic notes: Both named scenarios are closed: app.js:205 is the only writer of state.reports, app.js:193 is the only report fetch, and the geocode search already has its own guard. Residuals come from the drop semantics and from WR-08 interplay. No contract test pins the guard, so it could be removed silently. | Guard closes both review scenarios. Static contract counts still hold (two fetch calls, one show_disputed). No server or trust math effect. Better rule: keep lastAppliedSeq, drop a response only when mySeq is below it, keep the flag check; this fixes issues 1 and 2. No test pins the guard.

## WR-03 (commit 2e00f1c): DEFECTS FOUND

Skeptic verdicts: defect, defect

### WR-03-V1 [medium] web/static/js/votes.js:998-1003 (with 264 and 652-653)
The refresh callback ignores the coordinates getVoterLocation resolves with and recomputes the mark from the sessionStorage cache. requestPosition (line 264, WR-07, which landed before this fix) caches only fixes with accuracy of 300 m or better. A voter refused at 1.4 km has an accurate fix cached, walks indoors to 300 m and taps Confirm. The fresh fix has about 400 m accuracy, resolves but is not stored. applyDistanceHint re-reads the 1.4 km fix (under 120 s old), the button stays marked, nothing is sent, and every further tap repeats this until the old fix passes 120 s. The same happens when setItem throws. This is the WR-03 lockout, and it blocks a vote that WR-07 says a coarse fix may make.

### WR-03-V2 [medium] web/static/js/votes.js:998-1004 (with 264 and 652)
The success callback of getVoterLocation({ fresh: true }) ignores the coordinates it receives, and applyDistanceHint re-reads the session cache via peekVoterLocation. Since WR-07 (ca9776e), a fix with accuracy over 300 m is never cached. A voter who walked from 1.4 km to 300 m, last had a good fix cached under 120 s ago, and is now indoors with a valid fix of accuracy 400 m taps Confirm. The fresh fix is discarded, the old 1.4 km fix re-marks the button, and nothing is sent. Every further tap spends up to 8 s of high accuracy GPS with no feedback. The lock lasts until 120 s after the last good cached fix, not forever. Reproduced in a Node sandbox of the real votes.js: accuracy 20 sends confirm, accuracy 400 sends nothing and stays aria-disabled. If the mark has aged out but not yet been cleared by a poll, the same tap takes a second GPS fix inside castVote (two 8 s waits). The normal vote path would have sent the coarse fix and let the server judge. TRUST-MODEL.md:406 says the voter is not locked out. Fix direction: recompute the mark from the resolved coordinates and pass them to the vote.

Skeptic notes: Main path closes: a good fix is cached, the mark recomputes, the vote follows. Gaps are coarse or failed fixes, where the hint still vetoes the tap. The contract test only checks source strings, so it cannot catch this. Fix direction: compute the mark from the resolved coordinates, or fail open and let the server decide. | The server path is untouched, so no new way to game the trust math or the 1 km rule. The contract test only matches strings, so I checked behavior by running the real votes.js in a Node sandbox with a fake DOM (no files, server or database). No test exercises the coarse fix or busy block cases.
