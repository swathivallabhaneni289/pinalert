### SK2-01 (warning): a timed out confirm that the server finished reloaded to a blank card

**Commit:** 0c66cb6d
**Files:**
- internal/store/queries/auth_codes.sql (+ generated internal/store/sqlc/auth_codes.sql.go)
- internal/service/credentials.go
- internal/service/credentials_signin.go
- internal/api/handlers/auth.go
- web/templates/login_gate.html.tmpl
- web/static/js/auth.js
- tests: internal/api/handlers/login_gate_spent_e2e_test.go (new), internal/service/credentials_spent_db_test.go (new), internal/service/credentials_test.go, internal/api/handlers/auth_e2e_test.go, web/auth_flow_test.mjs

**What the skeptic missed:** after a confirm, `spend` deleted every code row of the address, the spent row included. So the reloaded page found no row at all, not a used one. Nothing tied to the old session id was left to read.

**What changed:**
- **The spent row is kept.**
  - The confirm now deletes every other row of the address through the new `DeleteOtherAuthCodesForEmail`, and keeps the one it spent. W9 still holds: a code pending in another browser can no longer be used.
  - Account delete keeps `DeleteAuthCodesForEmail`, which removes every row.
  - The prune removes the kept row a day after the spend.
- **A marker only the confirm writes.**
  - `ConsumeAuthCode` sets `expires_at` to the same `now()` as `used_at`, and clears the password hash typed at Create account.
  - A row retired because its email did not go out keeps its later expiry, so it is never read as spent.
- **`CredentialService.SpentCode` and the `LoginState.SpentCode` method.**
  - They read only this session's newest code row inside the resume window.
  - They are true only for a row that is a delivery of code (an account_exists or no_account row can never be confirmed), was counted at least once, and has that equal pair.
  - They never ask whether the address has an account, so a known and an unknown address behave alike.
- **LoginGate.**
  - The new branch runs only after the live code check, and only when no done word applies, so a done word always wins. It comes before the switch notice.
  - After Create account, it opens Sign in with `signin-status` reading "Account created. Sign in to continue."
  - After Forgot password, it reads "Password set. Sign in to continue.", the existing sentence and auth.js's PASSWORD_SET_MESSAGE.
  - The address goes into the hidden code screen's `#code-email` as page text only. No new done word, no redirect, no URL, no attribute.
- **Template.** `signin-status` draws `SignInStatus` and is hidden when it is empty.
- **auth.js.**
  - On a Sign in start whose `#code-email` holds text, it copies that text into the Sign in email field as a value and focuses the password, as `finishReset` does.
  - It posts nothing, reloads nothing and navigates nowhere, so nothing can loop.

**Tests:**
- `TestLoginGateSpentCode` (DB, real router). A copy of the browser's cookie confirms the code and its answer is thrown away, which is what a lost answer leaves behind. It checks:
  - after Create account: Sign in, the created line, the address once and only as `#code-email` text;
  - the same page again draws the same, with no redirect;
  - the person then signs in with the chosen password;
  - after Forgot password: the reset line;
  - a wrong code and an account_exists row keep the code screen;
  - `?done=all-devices` wins over a spent code;
  - a fresh browser sees neither line.
  - The create and reset cases failed before the fix.
- `TestSpentCodeOnDatabase` (DB). It checks:
  - no row, a live row and a wrong guess are not spent;
  - a confirmed sign up and a confirmed reset are spent, with purpose and address;
  - the fresh session and a stranger see nothing;
  - only the spent row of the address is left, with no hash, and the other browser's pending row is gone;
  - a replay is ErrWrongCode, and Resend is ErrWrongCode;
  - rows retired after a failed send are neither spent nor live;
  - nothing is spent once the resume window has passed.
  - It did not compile before the fix (no SpentCode).
- Node case "SK2-01: the page drawn for a spent code fills the Sign in email from the page text". It checks both lines, the filled field, the password focus, no request, reload or navigation, and that the next Sign in posts the address. A plain Sign in page fills nothing. It failed before the fix.
- Amended with dated notes:
  - `TestConfirmSignUpCreatesAccountAndRotates` (the fake order pin now names `DeleteOtherAuthCodesForEmail`, and one used row with no hash is left);
  - `TestConfirmResetSetsPasswordAndEndsSessions`;
  - `TestConfirmCodeSecondUseRefused` (one used row with no hash is left, and the replay is still refused).
- `TestAuthJSPanelContract` stays green: no new id or data attribute.

**Status:** fixed, requires human verification.

### SK2-03 (info): on a weak but "online" connection the reload can land on the browser's error page

**File:** web/static/js/auth.js (askServerAgain)
**Reason:** not small. A probe GET of `/login` runs LoginGate, and its switch notice branch can replace the session cookie. That would orphan this browser's code rows just before the reload. A probe with no side effects needs a new route. The code screen still comes back on the next good load while the code is live, and after SK2-01 a spent code is shown too.
