## Blocker

### SK-01 (blocker): CR-S03 does nothing in the default deploy. Without CLIENT_IP_HEADER the reset reserve can still be spent by "no account" notes

**Files:** `internal/api/handlers/authlimits.go:241-250` (MailSender), `internal/mailer/ceiling.go:151` (`sender != ""` skips the share), `README.md:43` (the header is "optional"), `cmd/server/main.go:334-336` (unset only logs a WARNING).

**What goes wrong:** when the header is not set, MailSender returns "" for every request that has a valid cookie, and a send with sender "" has no share limit. The script below spends the whole reserve:
1. GET /login once per batch to get a fresh valid cookie. That gives a fresh device bucket, and there is no network bucket without the header.
2. POST /api/auth/reset with a made up address each time. Each new address dodges the per address cooldown.

A drip of about 1.5 sends a minute keeps the 10 minute window full. Within about an hour it has spent the 70 other class sends and then all 20 kept reset slots. After that a real person's Forgot password gets 503 for the rest of the UTC day, which is exactly the original CR-S03 failure. TestMailCeilingPacesBurst sends one burst and then waits 11 minutes, so it never sees a drip. TestMailReserveSurvivesOneNetwork sets the header. TRUST-MODEL T-07.1-09 accepts this gap, but the README still calls the header optional, so the default configuration is the unprotected one and the "fixed" status overstates the fix.

A separate problem: the counts live in memory, and on the free host the server sleeps after 15 idle minutes, which wipes them. That turns the 90 cap into "until the provider's 100", and from then on the provider refuses every email, the reset class included, whatever the header.

**Fix:**
- Either make CLIENT_IP_HEADER required when ENV=production (log.Fatal, as SESSION_SECRET already does) and change README:43 to say so, or reclassify CR-S03 as "partial, T-07.1-09 accepted" in the FIX report and ROADMAP so the owner decides with the facts.
- Count the day's sends from the database or the provider instead of memory, or at least record the restart wipe in TRUST-MODEL.

**Proving test:** an e2e test with no header. It sends 70 sign ups and 20 "no account" resets, each from a new cookie and spaced 40 s apart on the service clock, then makes a real reset from a fresh browser. It fails today (503) and should answer 200 once the fix is in.

## Warnings

### SK-02 (warning): a busy hasher now counts toward the per address lock, so a real person can be locked out without typing a wrong password

**File:** `internal/service/credentials_signin.go:211` (reserveTry runs before the hash), `:227` (ErrHasherBusy returns with the try kept).

**What goes wrong:** before the fix (f63d5fdb, line 194), ErrBusy returned without recording a failure. Now every try is counted before Verify, and a busy answer keeps it. There are 3 hash slots and a 3 s slot wait. During an emergency rush, or under a script that fetches fresh valid cookies (IN-S05 is only partly closed), Verify returns ErrHasherBusy. The person with the right password sees "Something went wrong. Try again." and presses again. On the 6th press the address is locked for 5 minutes, then 10, and so on. The Cancel of the device and network buckets on 503 does not undo the database count. TestSignInHashBusy pins this behaviour as intended, but it is a regression against the core rule that the lock punishes wrong guesses only.

**Fix:** on ErrHasherBusy, give the try back with a guarded statement of the same shape as RefundAuthEmailSend: `UPDATE auth_throttles SET failures = failures - 1, locked_until = <the value before this try> WHERE scope = $1 AND key_hash = $2 AND last_failure_at = <this try's now>`. ReserveSignInTry would have to return its last_failure_at, plus the previous locked_until or enough to recompute it. This is identical for every address, so it is no oracle. The burst bound still holds, because no password was checked.

**Proving test:** a DB test with a hasher that always returns ErrHasherBusy. Make 6 tries, swap in a real hasher, then sign in with the right password: it should sign in, and the throttle row should be gone or show 0 failures. Today the last step returns SignInLockedError.

### SK-03 (warning): the WR-B01 10 s browser limit is shorter than the server's deliberate 75 s window for sending handlers, so a slow success is shown as "offline"

**Files:** `web/static/js/auth.js:34` (REQUEST_TIMEOUT_MS = 10000), `:242-261` (postJSON aborts and resolves status 0), `internal/api/handlers/credentials.go:43-45` (authWriteWindow = 75 s, because the Resend client may take a minute).

**What goes wrong:**
- **Email me a code, Forgot password, Resend:** the mail provider takes 12 s. The server issues the row, claims the 45 s per address cooldown and sends the code, but the page shows "You're offline" and stays on the entry panel. A second press inside 45 s gets the cooldown 429. A press after 45 s mails a second code, and the code in the first email then fails as wrong. The code screen comes back only after a manual reload, through LiveCode.
- **Code submit and Set new password:** ConfirmReset hashes the new password, with up to 3 s of slot wait, inside the request. On a slow network the answer can arrive after 10 s. The server has already spent the code, set the password and ended the sessions, but the page shows offline, and the next press answers "That code is wrong", because the row is used. The person believes the reset failed. ConfirmSignUp works the same way: the code is consumed and the account bound, and the retry says the code is wrong.

**Fix:** use a limit above 75 s for the three sending calls (or no client limit there), and on status 0 from any credential POST reload GET /login, so the server's LiveCode or SignedIn decides the screen rather than showing "offline" over a state the server already changed.

**Proving test:** in web/auth_flow_test.mjs, a fetch for /api/auth/sign-up that answers 200 after 15 s on the harness clock should open the code screen, not the offline line. A code submit whose answer comes after 11 s should reload, or show the server's state, rather than leave "offline" and then "wrong code".

### SK-04 (warning): WR-B02 is only half closed. On a reloaded code screen the "full" Resend wait is the leftover, so the next Resend reopens at once

**Files:** `web/static/js/auth.js:136` (`fullResendSeconds = numberAttr('data-resend-cooldown-seconds') || numberAttr('data-resend-seconds')`), `:777` and `openCode` (`startResendWait(fullResendSeconds)`), `web/templates/login_gate.html.tmpl:29-30` (no data-resend-cooldown-seconds), `internal/api/handlers/auth.go` (LoginGate sets ResendSeconds to `live.ResendSecondsLeft` on a live code).

**What goes wrong:** the person reloads, or comes back from Mail, 50 s after the send. The page draws data-resend-seconds="0", so fullResendSeconds is 0. They press Resend, and it succeeds: startResendWait(0) shows Resend as ready straight away with no countdown. Change email followed by a new "Email me a code" does the same. The next press is a refused 429, which only then draws a wait (c13c941f). A reload 30 s after the send gives a 15 s "full" wait instead of 45. The browser fixer flagged exactly this hand-off. The server fixer wrote "No template attribute was added", so the gap shipped.

**Fix:** add `ResendCooldownSeconds` (from `cfg.Login.ResendCooldown()`) to loginGateViewModel and draw `data-resend-cooldown-seconds="{{.ResendCooldownSeconds}}"` on the card. The script already reads it.

**Proving test:** a Go contract test that LoginGate with a live code 30 s old draws data-resend-cooldown-seconds="45". Then a node case: load the code screen with data-resend-seconds="0" and the cooldown attribute 45, answer Resend with 200, and Resend should stay off for 45 s.

### SK-05 (warning): the two new confirm transactions take their locks in opposite orders, so they can deadlock

**File:** `internal/service/credentials_signin.go:152-156` (ConfirmSignUp: `spend` first, which consumes its own code row and then DELETEs every code row of the address, then `LockAccountForPassword ... FOR UPDATE`), `:360-363` (ConfirmReset: `SetAccountPasswordNewEpoch` takes the account row first, then `spend`). The sessions and auth_throttles steps also run in opposite orders: ConfirmSignUp ends sessions and then clears the throttle; ConfirmReset clears the throttle and then ends sessions.

**What goes wrong:**
- A legacy account, one with no password made by the old link, has a sign up code in one browser and a reset code in another, and both are submitted together. Tx A (sign up) holds both code rows through the DELETE and waits for the account row. Tx B (reset) holds the account row and waits on its own code row in ConsumeAuthCode. Postgres aborts one with 40P01, and that person gets a 500.
- Two browsers confirming two sign up codes for one new address at the same instant also deadlock: each consumes its own row, then each DELETE waits on the other's row.

Before the fix these were autocommit statements and could not deadlock. The cases are rare, and the rollback leaves the code usable, so the harm is a spurious 500 on the security path.

**Fix:** take one lock first in both transactions, for example `SELECT pg_advisory_xact_lock(hashtextextended(<throttle key of the address>, 0))` before `spend` in both. That also covers the brand new account path, where no account row exists yet to lock. Alternatively, run the account lock before spend in ConfirmSignUp and the throttle clear in the same position in both.

**Proving test:** a DB test that holds ConfirmSignUp inside its transaction after spend (with a hook querier) while ConfirmReset runs for the same legacy address. Both should finish with one success and one ErrWrongCode, never a 40P01 error.

### SK-06 (warning): with CLIENT_IP_HEADER set, the per sender share charges a whole CGNAT carrier address 3 kept slots a day

**File:** `internal/mailer/ceiling.go:148-157`, `internal/api/handlers/authlimits.go:241-250`.

**What goes wrong:** the share applies whenever `otherFull` is true. That is not rare: it holds whenever 10 sends happened in the last 10 minutes, or the day's 70 other class sends are spent. During a real flood, which is this product's use case, both are true for most of the day. A Jio or Airtel CGNAT IPv4 address is then one sender, so after any 3 resets from that address (real people, or one attacker on the same carrier gateway), every further Forgot password from the thousands of phones behind it is refused with 503 for the rest of the UTC day. The FIX report's claim that "a busy carrier address is never refused on a normal day" does not hold on an emergency day. This is the CGNAT collateral damage the project's access model rules out.

**Fix:** have the share apply only to the day reserve (`c.count >= PerDay-ResetReserve`), not to window pacing, and scale it for IPv4 (for example key IPv4 senders to the address plus the device id, or raise the IPv4 share). Otherwise, record the trade-off explicitly in TRUST-MODEL beside the CGNAT rule for the owner.

**Proving test:** a mailer unit test. Fill the window with 10 sign up sends, then send 6 resets from sender "net:49.36.1.1", one a minute. They should all be admitted while the day reserve is untouched. Today the 4th is refused.

## Checked and found clean

- **CR-S01 burst bound:** the upsert's DO UPDATE takes the row lock and rechecks `locked_until` on the latest row version under READ COMMITTED, so a parallel burst gets exactly free_failures + 1 checks. Only a good sign in (after a bind that succeeded), ConfirmReset and ConfirmSignUp clear the row, and an attacker cannot reach any of those without the password or the inbox. The lock schedule is unchanged. When a lock ends, the right password's try sets a new lock and then clears it, and the sign in succeeds. The second refusal of reserveTry answers a positive wait.
- **CR-S02 epoch:**
  - Migration Up defaults both columns to 0, so every existing password session stays signed in. TestMigration00016 covers Down to 15 and back.
  - The FOR SHARE bind waits for the reset's row lock and rechecks the epoch after it, so a sign in that read the old epoch binds nothing.
  - Sessions bound before a reset are both revoked and off epoch.
  - A normal sign in binds at the epoch it read, and a new account binds at 0.
  - The rehash cannot overwrite a newer password.
  - The gate's cost is one predicate on the join that already exists.
  - No production path still calls the unchecked BindSessionAccount; only test helpers insert sessions directly.
  - Down is semantically safe, because the sessions a reset ended stay revoked.
- **CR-S03:** the class pairs and the sender key never depend on the typed address, and SignUp hashes, claims and refunds alike on every branch, so I found no existence oracle in the ceiling, the IN-S01 refund or RetireAuthCode. The state sits under one mutex, and the day rollover resets count and shares.
- **WR-S01:** Minted is set for an absent, malformed or wrongly signed cookie. Every /api/auth route goes through the middleware (no skip prefix matches), and Cancel gives back all three tokens. The switch notice shows once: the new id is unbound, so EndedByPasswordSwitch answers false next time, and nothing loops.
- **WR-T04:** LoginFormFallback never touches r.Body, r.Form or the query. The logger logs method and path only, no global middleware parses the form, and the four card forms are method="post".
- **WR-B03:** `seq` drops every stale answer, a retry carries its own `mine`, judge resets retries, and cancel bumps seq. Settings re-judges on open, and Continue and Save look only at `available` (or `yours` at sign up).
- **WR-B05:** map.js init calls centerOnVisitor, and so startMode, at DOMContentLoaded with no early return before it. The 5 s cap only skips a load without writing the key, so the next load asks again. A location already refused counts as not asking.
- **WR-B06 and IN-B06:** every skip path goes through endFlow and postDone, and a throwing showModal calls forgetAsked and then postDone. forgetAsked only removes an id the same call added, because canAsk and canInstallAsk refuse when it is already listed. installed-ask.js `forget` mirrors this.
- **Templates:**
  - The focus ring is `--color-text` in both themes, at offset 2px over the glass. Black and white backdrops are the extremes for a fixed ring colour over 65 percent glass, so the fixer's 4.99 to 1 floor bounds the globe, and the three solid fallbacks use the same surface and background tokens.
  - The 420 px globe block is only `--g`, placed after the phone block.
  - The Policy lines are true: the home area is name plus a precision 5 cell, usernames are screened through OpenAI, Resend sends the emails, and the code lifetime is 10 minutes.
