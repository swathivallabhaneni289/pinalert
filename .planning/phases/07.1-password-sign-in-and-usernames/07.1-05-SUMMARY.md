# Phase 7.1 Plan 05: CredentialService Summary

The server side of Create account, the typed 6 digit code, Sign in, Resend and Forgot password, over the storage of plan 01, the hasher and codes of plan 02 and the auth emails of plan 03. AuthService, auth.go and profile.go are untouched.

## What was built

- **credentials.go**: the shell and the sending side. `SignUp`, `RequestReset` and `ResendCode` follow one order: normalise the address, check the password (SignUp), take the per address send claim (`ClaimAuthEmailSend`, a refused claim reads `GetAuthEmailSendWindow` to choose `ErrTooManyCodes` or `ErrRateLimited`), hash the NFKC password (SignUp), pick the delivery, `IssueAuthCode`, prune stale code and throttle rows, send exactly one email. Every branch returns nil. A full daily ceiling is `ErrMailUnavailable`, a full hash queue is `ErrBusy`.
- **credentials_signin.go**: `ConfirmSignUp`, `SignIn`, `ConfirmReset` and the reads for the sign in page. Typed codes are stripped of U+0020 and U+00A0 and must then be 6 ASCII digits (else `ErrWrongCode` with no bump). A try is counted by `BumpAuthCodeAttempt` before the keyed hash compare, and a row whose delivery is not `code` can never be confirmed. After a consume, every code row of the address is deleted (W9). `rotate` reads `GetSessionBinding` of the request's id, and when it is bound to a different account deletes its push subscriptions and revokes it (W8) before binding a fresh id from `newID`; zero rows from the guarded bind is an error. SignIn checks the throttle before any lookup or hashing, verifies unknown addresses and password-less accounts against `DummyHash` (W3), records failures, clears the throttle on success, rehashes best effort when the parameters moved, and maps `ErrHasherBusy` to `ErrBusy` without recording a failure.
- **Tests**: 26 named tests from the plan plus `TestSignUpHashBusy`, `TestSignUpPrunesStaleRows` and `TestSignedInAndEndedByPasswordSwitch`, on a stateful fake querier, a recording hasher wrapper and a movable clock. `TestCredentialFlowOnDatabase` walks sign up, wrong code, sign in on a second browser, six wrong sign ins and a locked seventh, Forgot password (sessions revoked, throttle cleared, old password refused, new one works) and a legacy account that keeps its id.

## Notes for later plans

- **Handler mapping (plan 07)**: `ValidationError` field `email` or `password` is 400; `ErrWrongCredentials` is 400 with field `credentials` and `WrongCredentialsMessage`; `ErrWrongCode` is 400 with `WrongCodeMessage`; `ErrRateLimited` and `ErrTooManyCodes` are 429 (the hour sentence is `TooManyCodesMessage`); `SignInLockedError` is 429 with `SignInLockedMessage(e.Wait)`; `ErrMailUnavailable` and `ErrBusy` are 503. A handler that sends a code email must respect the 10 s `WriteTimeout` itself (extend the deadline with `http.NewResponseController` like the cron door, or bound the send).
- **Keys**: `cmd/server/main.go` must pass `WithCodeKey(auth.DeriveKey(secret, auth.CodeKeyLabel))` and `WithThrottleKey(auth.DeriveKey(secret, auth.ThrottleKeyLabel))`, and `WithHasher(auth.NewHasher(auth.DefaultParams))` is the default. Without keys a random key is drawn per process, so codes die on restart. The e2e harness (plan 08) passes `auth.TestParams()` through `WithHasher`.
- **Limits**: `DefaultCredentialLimits.SendCooldown` is `ResendCooldown` (45 s). Anything that signs up and then asks for a reset on the same address in seconds (e2e helpers) must set `SendCooldown` low through `WithCredentialLimits`, as `TestCredentialFlowOnDatabase` does.
- **Clock**: the database compares codes against its own `now()` (bump, consume), so a fixed fake service clock only works with the fake querier; DB tests must use the real clock.
- **Delete my account (plans 06, 07)**: `ThrottleKey(email)` normalises the address itself, then clears `auth_throttles` with scope `sign_in`.
- **Sign in page (plan 11)**: `LiveCode` returns an expired but unconsumed row with `SecondsLeft` 0 so the page can say "The code has expired. Get a new one."; a consumed row, a deleted row or one older than the resume window is false. `SignedIn` is true only for a live session of an account with a password.
- **Reset and browser**: `ConfirmReset` reads the browser's newest row; if the newest row is a sign up row it answers `ErrWrongCode`. The page shows one code screen at a time, so this matches.
