## Fixed

### WR-B01: the sign in card's requests had no time limit

**What changed.** `postJSON` in auth.js now has the same limit as `request()` in welcome.js:
- an AbortController where the browser has one;
- a 10 s timer that covers the body read too.

A request WebKit leaves unsettled resolves as status 0. Its button then:
- loses `aria-busy` and gets its resting label back;
- shows the offline line;
- posts again on a second press.

The limit covers Email me a code, Sign in, the code submit, Forgot password and Resend.

**Test.** Three WR-B01 cases in `web/auth_flow_test.mjs`:
- a fetch that never settles;
- a body that never arrives;
- the code submit and Resend.

Each also checks that no timer is left once an answer is in.

**Commit.** 4a897f38

### WR-B02 (browser half): Resend wait and code expiry on wall clock deadlines

**What changed.** auth.js keeps two deadlines from `Date.now`, `resendAt` and `expiresAt`. They are set:
- at page load, from `data-resend-seconds` and `data-code-seconds-left`, read as integer seconds left, clamped at 0, as the contract says;
- after each send.

Each tick redraws from the clock. `visibilitychange` (when visible) and `pageshow` catch both clocks up at once. A trip to Mail or a reload therefore never shows a stale wait, and the expiry never stalls.

If the server still draws the full 45, the page shows 45 as before and counts it on the clock.

The full wait after a send comes from:
1. `data-resend-cooldown-seconds`, when the page draws it;
2. otherwise, the load value of `data-resend-seconds`. On an entry panel this is the full wait, because there is no code out.

**Test.** Four WR-B02 cases in `web/auth_flow_test.mjs`:
- a minute in Mail and then one tick;
- `visibilitychange` and `pageshow` past the wait and past the lifetime;
- a reload with 12 s and 300 s left, and one with 0 left;
- the full wait after a send, on an entry page and on a reloaded code screen.

The harness gained three things:
- a sandbox `Date` on its clock;
- `sleep(ms)`, which moves the clock with the timers paused, as iOS does;
- the page listeners.

**Commit.** eef48176

**For the orchestrator.** One gap the script cannot close alone. A code screen reloaded with less than the full wait left has no full cooldown on the page. After the next send, the wait shown is the load value, which is too short; the server then refuses the early Resend with its own 429 sentence. To close it:
- the server fixer adds `ResendCooldownSeconds` to the login view model;
- the templates fixer draws `data-resend-cooldown-seconds` on `#login-form-panel`.

The script already reads that attribute. Entry panels should keep drawing `data-resend-seconds` as the full wait.

### WR-B05: the installed app's ask and the location question could open together

**What changed.**

position.js records whether the browser's own location question is shown on this page load. `askingThisLoad()` answers:
- null until the first `startMode` of the load decides;
- true for `ask`, unless location is already refused, which shows no question;
- false for `silent` and `reuse`.

installed-ask.js runs before position.js and map.js, which are deferred later in the page. So after `deviceState` answers `ready`, it looks for that answer every 100 ms for at most 5 s. It skips and writes no key when:
- the question is asked on this load;
- no answer comes;
- the module throws.

The next Nearby load then asks. It does not rely on `navigator.permissions` on iPhone. position.js's own fallback (`unknown`) counts as asking.

**Test.**
- `web/installed_ask_test.mjs`: six WR-B05 cases. They cover the decision arriving before and after `deviceState`, with skip and open; the 5 s cap; no module; and a throwing module. The harness gained a position fake and fake timers.
- `web/position_test.mjs`: one case covering every `startMode` branch.

**Commit.** 6001c206

**Still to check:** the first installed load after sign in, in the iPhone simulator.

### WR-B06: the sign up alerts pop-up asked again on a device that was already asked or on

**What changed.** `canAsk` in welcome.js now returns false in two cases:
- this account is already in `pinalert.alertsAsked`;
- this device already has alerts on for this account. This is read from notify.js's exported intent flag: the account id under `PinalertNotify.INTENT_KEY`, which a successful turn-on sets.

Nothing is requested or awaited before the pop-up. When the pop-up is skipped, `endFlow` records the flow as done at once, so every path still finishes sign up.

**Deviation from the review's fix.** The review suggested awaiting `PinalertNotify.deviceState(pushKey)`. TestWelcomeAlertsScript, which is not mine to amend, bans `deviceState` and `Notification.` in welcome.js ("never asks the device state (a request)"). The intent flag is the request-free signal notify.js already exports.

Limitation: an account asked in Phase 3.3, before the list existed, that answered Not now is asked once more, and is then on the list. If the owner of that pin wants the stricter server check, the pin must be amended first.

**Test.** `web/welcome_alerts_test.mjs`, four WR-B06 cases:
- an account in the list, as JSON and as a single id;
- the intent flag set for this account, with no `deviceState` call;
- the flag set for another account, and an unreadable store;
- a failed first-run-done retry.

One earlier sub-case is amended with a dated note: an account already in the list is no longer asked. TestWelcomeStep3And4Privacy is amended with a dated note: a fifth `localStorage` use, which only reads the intent flag. It is pinned, with no write.

**Commit.** 05b91792

### IN-B03: answers were not tied to the code screen that sent them

**What changed.** auth.js keeps a generation number that `showPanel` bumps (every choice, Change email, Forgot password, a new code screen). Each submit and Resend notes it when sending. A late answer from an older screen only frees its button. It never:
- switches the card;
- writes a line;
- restarts the clocks;
- counts a refused code against the new one.

A sign in, or a confirmed account, that succeeded still goes on, because the browser is signed in.

**Test.** Four IN-B03 cases in `web/auth_flow_test.mjs`.

### IN-B04: folding moved the caret, and a pasted "@" name lost its last letter

**What changed.** username-check.js:
- When the fold rewrites the value while the person is in the input, the caret goes back where it was, less what the fold dropped in front of it.
- A paste handler handles the pasted text in this order:
  1. drops the spaces round it and its leading @;
  2. puts it at the caret;
  3. folds the whole value and cuts it to the field's `maxlength`;
  4. judges it.
- An empty paste is left to the browser.

**Test.** Two IN-B04 cases in `web/username_check_test.mjs`, including "@Ravi.Kumar_12345678" (21 characters), which keeps all 19 letters.
