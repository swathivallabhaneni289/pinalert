## Summary

The link flow is small and well isolated, but its test seams are everywhere. About 272 call sites in the e2e suites reach the account system through three helpers (`verifySession`, `newVerifiedClient`, `gateVerifySession`) and one fake (`recordingMailer`), so the single most important planning fact is: **replace those helpers in place, with the same signatures, in Wave 0** and almost nothing else in the 20+ e2e files has to change. The production design is: a new `CredentialService` (leave `AuthService`, which also owns the Activity page reads and has about 45 constructor call sites, alone), argon2id passwords in PHC strings, a 6 digit code generated with `crypto/rand` and stored as a keyed HMAC in a new `auth_codes` table that is **bound to the requesting session id** (so the typed code screen needs no email in any URL or form field, satisfying D-05 by construction), a fresh session id on every successful sign in, and DB persisted counters for the per account limits because the in memory limiters (`PerIP`, `PerKey`) forget everything when the free host sleeps.

Two product level collisions need the planner's attention. First, "required" step 4 collides with five existing clear paths (`PATCH /api/me/profile` with `{"home_area":null}` or `{"display_name":""}`, the Settings "Remove home area" button, six e2e tests that clear through that PATCH). Second, `service.CheckText` runs the gibberish prefilter, which needs two words of two letters, so it would reject almost every real username; the flag note precedent `service.ScreenAbuse` is the right call. Phase 4 built the stateless reusable text check but its held state (`moderation_checks`, `reports.moderation_state`, the worker) is tied to `report_id`; this phase needs only a two value `username_screen` column and Phase 8 builds the re-check and the held display.

This phase also unblocks the iPhone installed-app check that Phase 3.3 held back (03.3-RESEARCH R1): a typed code and a password work inside a Home Screen app, an emailed link did not. Nothing in the trust model changes; email alias normalisation and disposable email blocking stay out of scope as `docs/TRUST-MODEL.md` already records.

**Primary recommendation:** Build a new `CredentialService` + `auth_codes` + `auth_throttles` + `accounts.password_hash/username` migration (next free migration number at execution time), keep every existing signature that tests construct, replace the four e2e helpers first, revoke the sessions of password-less accounts in the migration so the one time fill in always rides a real sign in, and gate everything behind one shared "onboarding complete" predicate used by the gate, `/welcome` and `first-run-done`.

### Pattern 1: Session bound code, email stays server side (D-05 by construction)

**What:** `auth_codes.session_id` holds the requesting browser's session id. The code screen posts only `{code}`; the server finds the single active row for `(session_id, purpose)`. The email lives in the row.
**When to use:** sign up code and reset code. **Why it also helps security:** a code can only be redeemed from the session that asked for it, so an attacker who triggers a reset for a victim's address cannot use the victim's code, and a victim who is tricked into typing a code somewhere else changes nothing.
**Cost:** the code must be typed in the same browser that asked for it (the typed screen invites exactly that). The old link flow allowed cross device completion; the typed code does not need it.

### Pattern 2: Increment first, then compare (atomic try budget)

```sql
-- Source: reuses the ConsumeToken atomic UPDATE pattern in internal/store/queries/magic_link_tokens.sql
-- name: BumpAuthCodeAttempt :one
UPDATE auth_codes
SET attempts = attempts + 1
WHERE id = (SELECT id FROM auth_codes
            WHERE session_id = sqlc.arg(session_id) AND purpose = sqlc.arg(purpose) AND used_at IS NULL
            ORDER BY id DESC LIMIT 1)
  AND used_at IS NULL AND expires_at > now() AND attempts < sqlc.arg(max_attempts)
RETURNING id, email, code_hash, password_hash, attempts;
-- pgx.ErrNoRows = no live row or the budget is spent: one message for wrong, expired, used, spent.

-- name: ConsumeAuthCode :execrows
UPDATE auth_codes SET used_at = now() WHERE id = sqlc.arg(id) AND used_at IS NULL AND expires_at > now();
-- 1 row = this request won; 0 = a parallel submit already did.
```
Every guess, including the correct one, costs an attempt before the Go side compares, so parallel guessing cannot beat the budget.

### Pattern 4: Public POST group

```go
// Source: go doc net/http.CrossOriginProtection (go1.26.4); push.go decodePushBody for the content type rule
cop := http.NewCrossOriginProtection() // zero value valid; missing Origin and Sec-Fetch-Site pass (non browser clients, Go tests)
r.With(cop.Handler, ratelimit.requireJSON).Post("/api/auth/sign-in", handlers.SignIn(creds, deps.Session, ...))
```
`cop.Handler` has the `func(http.Handler) http.Handler` shape chi expects. A cross site HTML form can neither set `application/json` nor pass the `Sec-Fetch-Site` check, which closes login CSRF (an attacker forcing the victim's browser into the attacker's account).

### Anti-Patterns to Avoid

- **Email in any URL, form field echo or `history.replaceState`.** Today `LoginGate` parses `?sent=<email>` and `auth.js` writes it back with `replaceState`; both are the exact D-05 leak and both must go.
- **Keying a per IP limiter on `RemoteAddr` behind a proxy.** Without `CLIENT_IP_HEADER` every visitor shares the proxy's address and one abuser locks out everyone. The Phase 4 backstop is therefore on only when the header is set; copy that rule. (The current `request-link` `PerIP` limiter breaks it; see Pitfall 9.)
- **Reusing `service.CheckText` for a Username.** The gibberish prefilter rejects single tokens. Use `ScreenAbuse`.
- **Hashing with plain SHA-256 a value that has 10^6 possibilities.** The code needs a keyed HMAC (or it is recoverable from a leaked table in milliseconds).
- **One predicate in the gate and another in `/welcome`.** Produces a redirect loop for legacy accounts (Pitfall 3).

## Recommended Design

### 1. Password hashing

- **argon2id**, `m=19456` KiB, `t=2`, `p=1`, 16 byte random salt, 32 byte key (OWASP's primary minimum; the equal alternative `m=12288, t=3` is the fallback if the host's memory is tight). [CITED: cheatsheetseries.owasp.org Password Storage Cheat Sheet]
- Store the **PHC string** `$argon2id$v=19$m=19456,t=2,p=1$<b64 salt>$<b64 key>` (RawStdEncoding). `argon2` in `x/crypto` has no encoder, so write the encode/parse (about 60 lines) and test it. Cap parsed `m` (say 256 MiB) and `t` before hashing so a corrupted row cannot become a memory bomb. Compare with `subtle.ConstantTimeCompare`. Return `needsRehash` when stored params differ from current, so the parameters can be raised later at sign in.
- **Concurrency cap:** a semaphore of 3 around every hash and verify (19 MiB each, so about 60 MiB peak on a 512 MB host `[ASSUMED host size]`); a request waits on its context, never queues unbounded.
- **Constant work for unknown emails:** verify against a dummy PHC hash generated once at start up with the same params.
- **Tests stay fast:** `auth.NewHasher(auth.Params{...})`; `auth.TestParams()` is `t=1, m=64 KiB` (0.08 ms measured). `CredentialService` takes `WithHasher(h)`; production default is `auth.DefaultParams`. The e2e harness is the only place that passes `TestParams`. A unit test must pin that `DefaultParams` meets the OWASP floor so nobody ships test params.
- **Password policy:** NFKC normalise, then count runes. **Minimum 15, maximum 128** (cap request body at 4 KB). NIST SP 800-63B-4 says verifiers SHALL require 15 characters for a password used as the only factor, SHOULD accept at least 64, SHALL NOT impose composition rules, and SHALL block commonly used or compromised values; 8 is allowed only when the password is part of multi factor authentication, which this is not. [CITED: pages.nist.gov/800-63-4/sp800-63b/authenticators] The 15 is a **D-11 number for the owner viewing**; the fallback the owner may pick is a lower minimum, at the cost of leaving the cited standard. Copy on the form: "At least 15 characters. A few words in a row is fine." Block: the email address or its local part, the words "pinalert" and "password", one character repeated, and a short embedded list of known leaked passwords of 15+ characters `[ASSUMED sizing: a few hundred lines]`.
- No pepper (OWASP: defence in depth, not required; changing it forces resets). [CITED: OWASP]

### 2. The typed 6 digit code

| Property | Proposal (D-11) | Basis |
|----------|-----------------|-------|
| Generation | `rand.Int(rand.Reader, big.NewInt(1_000_000))`, zero padded `%06d` | uniform, CSPRNG |
| Storage | `HMAC-SHA256(key, "pinalert/auth-code/v1|" + purpose + "|" + email + "|" + code)` hex; key is derived from `SESSION_SECRET` (separate label, never the raw secret) and injected via `CredentialService` option | a bare SHA-256 of 10^6 values falls to brute force offline at once |
| Lifetime | 10 minutes | email delay headroom; the old link was 5 |
| Tries | 5 per code, atomic increment first (Pattern 2) | 5 / 10^6 per code |
| Active codes | one per `(session_id, purpose)`; issuing a new one marks the old used | the budget does not multiply by resending |
| Single use | `ConsumeAuthCode` atomic | double submit safe |
| Resend | per address 45 s (`ClaimEmailCooldown`, kept) and at most 5 codes per address per hour (count `auth_codes.created_at`) | 5 sends x 5 tries = 25 guesses per hour per address |
| Same screen, known email | sign up always answers 200 with the same body and does the same steps (claim cooldown, hash the password, one email send). Known with a password: no code row, the email says an account exists and points to Sign in and Forgot password. Known without a password (legacy): treated as new, the code lets them set one | D-02; OWASP: uniform answer and uniform timing [CITED: Forgot Password Cheat Sheet] |
| Reset | known: code email; unknown: a short "there is no Pinalert account for this address, create one" email, so all four request kinds send exactly one email | uniform |
| After reset | set password, `LogOutAllDevices` (revokes every session and deletes push subscriptions), clear that address's throttle, do **not** auto sign in; the screen goes to Sign in with the address kept in memory | OWASP: do not log in automatically, end other sessions |
| Email content | code only, no URL, no link, plain text part included; subject "Your Pinalert code". For `account_exists` and `no_account` no code | D-01 "no link anywhere" |
| Field attributes | code: `autocomplete="one-time-code" inputmode="numeric" maxlength="6"`; email `autocomplete="email"` (or `username`); sign in password `current-password`; new password `new-password` | password managers and iOS autofill; works inside an installed Home Screen app because nothing navigates away |

Residual timing difference between "known with password" and the other branches is one INSERT (about 1 ms). Sending synchronously keeps a mailer failure visible to the person (a failed send still consumes the cooldown, the existing rule); asynchronous sending was rejected because a lost email would be silent.

### 3. Limits (IDENT-04, D-02), all numbers for the owner viewing

Why the in memory limiters are not enough: `PerIP` and `PerKey` live in process memory ("A restart or a free host sleep forgets every bucket", `perkey.go`), so a per account guessing budget kept there resets whenever the host sleeps. The existing precedent for a restart-proof limiter is `ClaimEmailCooldown`, a DB row.

| Scope | Store | Proposal | Notes |
|-------|-------|----------|-------|
| Wrong password per account (and per unknown address, same code path) | `auth_throttles(scope, key_hash)` DB | 5 free failures, then a wait of 5 min doubling each further failure to a 60 min cap; counter forgets after 30 min with no failure or after a success or a reset | key = HMAC of the normalised email so unknown addresses behave identically and no probe address is stored in the clear; a locked attempt is refused before hashing and does not extend the lock; message "Too many tries. Wait N minutes, or reset your password." identical for known and unknown |
| Wrong password per device | `PerKey` keyed by the signed session id (every visitor has one) | burst 8, one more per 60 s, refunded on success via `Decision.Cancel` | a normal person on a shared carrier address is isolated from everyone else; a script that drops cookies is the IP bucket's job |
| Network backstop for failures | `PerKey` keyed by client IP (IPv6 by /64), **only when `CLIENT_IP_HEADER` is set** | burst 300, one more per 2 s | Phase 4 rule (100 accounts behind one address, WR-S02); success refunds |
| Code sends per device | `PerKey` by session id | burst 5, one more per 60 s | replaces the per IP `request-link` limiter |
| Code sends per address | DB | 45 s cooldown + 5 per hour | the hourly count is a `COUNT(*)` on `auth_codes` |
| Code sends network backstop | `PerKey` by IP, header only | burst 60, one more per 10 s | |
| Code tries | DB per code (5) + device `PerKey` | burst 10, one more per 30 s, failures only | |
| Global send ceiling | in memory decorator in `cmd/server/main.go` only | 90 emails per day | Resend free plan is 100 per day and 3,000 per month [CITED: resend.com/docs/knowledge-base/resend-sending-limits]; the provider enforces the true limit, this keeps one attacker from burning the day's quota. It lives in `main.go`, so no test needs to know about it |
| Username check | `PerKey` per account | burst 10, one more per second | debounced typing at about 300 ms; no provider call |
| Username save | `PerKey` per account + `username_changed_at` | burst 5, one more per 10 s; one change per 7 days after the first | public identifier, so renaming is slowed |

A locked account can always be recovered through the reset code, which clears the throttle, so an attacker who deliberately fails cannot permanently lock a victim out. The honest cost is that a determined attacker can keep a victim waiting up to an hour at a time; the doubling schedule and the always open reset keep that bounded.

Wiring: `Deps.AuthLimits` (new, zero value resolves to defaults, exactly the `RateLimits`/`resolveRateLimits` pattern), constants in the `cmd/server/main.go` block, mirror in `api`. Tests never need to open buckets because each test client has its own cookie jar (so its own device bucket) and distinct emails.

### 4. Sessions, CSRF, enumeration

- **Rotation:** Pattern 3. Cookie set before any body write (`SetCookie` is the one writer). The old pre login id is left unbound.
- **CSRF:** `http.CrossOriginProtection` plus `mime.ParseMediaType == application/json` on every new public POST (today's `RequestLink` checks neither). Authenticated routes keep relying on SameSite=Lax (DEC-L); the gated `PATCH /api/me/profile` and `first-run-done` need nothing new.
- **Responses:** `Cache-Control: no-store` on every auth response; sign up and reset requests return the identical body for every branch; wrong credentials return **400** with field `credentials` and the exact sentence "Email or password is wrong." (not 401: `requireVerifiedAccount` uses 401 with field `auth` to mean "no verified session", and `TestAccessGateExemptRoutes` treats 401 as a gate failure). 429 uses the shared envelope with field `email`, the same shape as `internal/ratelimit` so the limiter that tripped is not revealed.
- **Logging:** no email, code or password in any log line (precedent WR-S03: error messages carry no address); the request logger already drops query strings and bodies. The dev `logMailer` printing the code is the same accepted dev only risk as today's printed link (AR-28) and is already fatal outside `ENV=development`.

### 5. Username

| Rule (D-11 proposal) | Detail |
|----------------------|--------|
| Characters | ASCII letters, digits, underscore, full stop. Typed capitals are folded to lowercase on write; stored and shown lowercase |
| Length | 3 to 20 |
| Shape | must contain at least one letter; no leading or trailing full stop; no two full stops in a row |
| Storage | `accounts.username TEXT NULL`, `CHECK (username IS NULL OR username ~ '^[a-z0-9_.]{3,20}$')`, plain `UNIQUE (username)` (NULLs do not collide). ## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Password KDF | your own iterated hash | `argon2.IDKey` | Memory hard, reviewed |
| Random code | `math/rand`, time seeded digits | `crypto/rand` + `big.Int` | Guessable otherwise |
| Code hash | bare SHA-256 | HMAC-SHA256 with a server key | 10^6 space |
| Atomic try budget | read then write in Go | one `UPDATE ... RETURNING` | TOCTOU under parallel guesses |
| Token bucket | counters in a map | `ratelimit.PerKey` (and a DB row for the per account budget) | Existing, tested, has refunds |
| CSRF defence | a token system | `http.CrossOriginProtection` + strict JSON | Stdlib, no state, no template churn |
| Email parsing | a regex | `net/mail` via `normalizeEmail` | Existing |
| Text abuse screen | a word list | `service.ScreenAbuse` | Phase 4 |
| Session revocation on reset | a new revoke query | `SessionService.LogOutAllDevices` | Revokes sessions and deletes push subscriptions |
| Cookie setting | a second cookie writer | `session.Manager.SetCookie` | One writer keeps Path/Secure/SameSite identical (T-01-85) |
| Fast tests with real KDF | skipping hashing | `auth.TestParams()` through `WithHasher` | Real code path, 0.08 ms |

**Key insight:** every hard piece here already exists in this repo in a better tested form (atomic UPDATE, keyed limiter with refund, revocation, text screener, cookie writer). The new code is glue plus one PHC encoder.

## Common Pitfalls

### Pitfall 1: Username fails the gibberish rule
**What goes wrong:** `CheckText` -> `IsGibberish` needs 2 words of 2 letters; "asha" and "ravi123" are rejected as keyboard mashing. **Avoid:** `ScreenAbuse` (precedent plan 04-31). **Warning sign:** a live-check or save test with a one word name returns the report-style gibberish sentence.

### Pitfall 2: "Required" collides with the clear paths
See section 6. **Warning signs:** six e2e tests fail on `{"home_area":null}`; the Settings page offers "Remove home area" while the gate bounces the person to step 4.

### Pitfall 3: Redirect loop for legacy accounts
`onboarded()` (api) and the 303 in `WelcomePage` (handlers) are two copies today. If only one learns the new fields, `/` redirects to `/welcome` which redirects to `/`. **Avoid:** the single `service.OnboardingDone`; add a test that walks `/` -> `/welcome` -> complete -> `/` for an account with terms and first run done but no username.

### Pitfall 4: Legacy accounts are two cases, and live cookies never sign in again
See section 6, Option X. **Warning sign:** the owner's own dev account is still signed in after migrate and nothing asks for a password.

### Pitfall 5: Test blast radius (do Wave 0 first)
272 `newVerifiedClient` calls, `verifySession`, `gateVerifySession`, `requestLink`, `getVerify`, `recordingMailer` (10 files), 13 test tweaks that set `d.RequestLinkRateLimit`, about 45 `NewAuthService` call sites, welcome skip clicks. **Avoid:** (a) a new `CredentialService` and a new `Deps.Credentials` instead of widening `AuthService`; keep `NewAuthService(q, m, baseURL, opts...)` compiling until a final cleanup plan, even though its link half is dead; (b) replace the helpers in place with identical signatures; (c) drop the per IP request-link limiter and delete the 13 tweak lines mechanically in the cleanup plan (compiler-guided), or keep the field as a no-op until then. A `Deps{}` literal that omits `Credentials` (such as `swagger_test.go`) must still build and serve non auth routes: the handlers guard a nil service.

### Pitfall 6: Login CSRF
Public POSTs get no protection from SameSite=Lax. **Avoid:** Pattern 4. **Test:** a request with `Sec-Fetch-Site: cross-site` gets 403; `Content-Type: text/plain` gets 415; the Go test client (no such headers) passes.

### Pitfall 7: Enumeration through behaviour
Different status, body, timing or limiter message per branch. **Avoid:** identical bodies and status for all sign up and reset branches, dummy hash for unknown sign in, the same throttle path for unknown addresses, the same 429 envelope. **Test:** byte compare responses for a known and an unknown address on all four requests and the sign in failure.

### Pitfall 8: Codes in the wrong place
Bare SHA-256, in memory try counters, the email carried in the URL. **Avoid:** HMAC, DB counters, session bound row (Patterns 1 and 2).

### Pitfall 9: The existing per IP limiter is wrong behind a proxy
`PerIP.Middleware` falls back to the TCP peer when no header is configured, which on a proxied host is every visitor's shared address (and burst 5 / 60 s is hostile to CGNAT). The Phase 4 backstop already learned this (on only with `CLIENT_IP_HEADER`). Follow that rule for every new IP bucket and confirm the header with the README canary check on the real host.

### Pitfall 10: Fixation and shared phones
Reusing the pre login id, or leaving the replaced session's push subscriptions live. **Avoid:** Pattern 3 and the `DeleteForSession` call.

### Pitfall 11: Policy and terms
`legal_body.html.tmpl` says only report descriptions go to OpenAI (line 96) and "What Pinalert keeps" lists the email only (lines 119 to 126). Add the password hash (never the password), the public username, the name and the home area name; say usernames go to the moderation service. Any Policy edit must move the "Last updated" date and `service.CurrentTermsVersion` together (`TestTermsVersionFollowsPolicyDate`), which sends everyone through the terms step again. That is acceptable here because every legacy account is routed through the flow anyway, but Phase 5 also edits the Policy (its own plan, GIBS acknowledgement); the later phase must re-use the date it finds, and both must bump.

### Pitfall 12: Account deletion misses new data
Clear `password_hash`, free `username`, delete `auth_codes` for the account's address and its throttle row; update `testutil.Truncate` for `auth_codes` and `auth_throttles` (and remove `magic_link_tokens`) or tests leak rows across packages (they share one database, `-p 1`).

### Pitfall 13: Email leaks through the page address or referrer
`?sent=` echo and `replaceState` are removed; no new screen has a URL that varies by person. Phase 5 sets `Referrer-Policy: same-origin` on `LoginGate`; do not remove it.

### Pitfall 14: Memory on a small host
19 MiB per concurrent argon2 run. Semaphore of 3; if the host reports out-of-memory kills, switch to `m=12288, t=3` (equal strength per OWASP) before anything else.

### Pitfall 15: Two goose concerns
The migration needs a `-- +goose Down` that reverses everything it adds (the data revoke cannot be reversed; say so in a comment). Dropping `magic_link_tokens` in a later plan is its own migration with a Down that recreates it.

### Pitfall 16: `LoginGate` ordering
Handle `?low=` before the signed in redirect (section 7).

### Pitfall 17: Swagger drift
`TestSwaggerSpecCoversRoutes` reads `docs/swagger.json`; regenerate with `make swag` after annotating the new handlers. Seven handler comments and the router's `@description` still say "magic-link flow" (auth.go, geocode.go, reports.go x3, votes.go, router.go); update the wording so the regenerated spec stops describing a link.

### Pitfall 18: `TestAccessGateExemptRoutes` fails on 3xx and 401
Wrong credentials as 401 would fail it; `GET /auth/verify` as a 303 would too. Use 400 for wrong credentials and a separate test for the retired link.

### Pitfall 19: Resend limits and sandbox sender
Free: 100 per day, 3,000 per month. A test of the real mailer path needs the owner's verified domain. Dev uses the log mailer that prints the code.

### Pitfall 20: Password manager and iOS installed app
Wrong `autocomplete` values make managers offer the wrong action; the code field needs `one-time-code`. Panels swap in place so the standalone app never navigates out of scope.

### PHC encode and verify (the only hand written crypto glue)
```go
// Source: golang.org/x/crypto/argon2 (pkg.go.dev); PHC string format; verified timings in this document
func (h *Hasher) Hash(password string) (string, error) {
	salt := make([]byte, 16)
	if _, err := rand.Read(salt); err != nil {
		return "", err
	}
	key := argon2.IDKey([]byte(password), salt, h.p.Time, h.p.MemoryKiB, h.p.Threads, 32)
	return fmt.Sprintf("$argon2id$v=%d$m=%d,t=%d,p=%d$%s$%s", argon2.Version,
		h.p.MemoryKiB, h.p.Time, h.p.Threads,
		base64.RawStdEncoding.EncodeToString(salt), base64.RawStdEncoding.EncodeToString(key)), nil
}
// Verify: strings.Split(encoded, "$") must give 6 parts (first empty); parse m,t,p with Sscanf; reject m > cap;
// recompute with the stored params; subtle.ConstantTimeCompare; needsRehash = stored params != h.p.
```

// Source: this design; mirrors profile.go cleanText style (rune based checks)
func NormalizeUsername(raw string) (string, bool) {
	s := strings.ToLower(strings.TrimSpace(raw))
	return s, usernameShape.MatchString(s) && hasLetter(s) && !strings.Contains(s, "..") &&
		!strings.HasPrefix(s, ".") && !strings.HasSuffix(s, ".")
}
func Reserved(s string) bool {
	folded := foldDigits(strings.NewReplacer("_", "", ".", "").Replace(s))
	if _, ok := exactOnly[folded]; ok { return true }
	for _, tok := range splitWords(s) { if _, ok := exactOnly[foldDigits(tok)]; ok { return true } }
	for _, w := range blockedWords { if strings.HasPrefix(folded, w) || hasWordToken(s, w) { return true } }
	return false
}

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Online password guessing | Spoofing | per account DB throttle, per device bucket, IP backstop, 15 character minimum, blocklist |
| Credential stuffing across accounts | Spoofing | IP backstop (header gated), per device bucket, lock message identical for unknown addresses |
| Account enumeration (status, body, timing, limiter text) | Information disclosure | uniform responses, dummy hash, same envelope |
| Code guessing | Spoofing | 5 tries atomic, 10 minute life, session bound, HMAC at rest, hourly code cap |
| Login CSRF / forced sign in | Tampering | `CrossOriginProtection` + strict JSON |
| Session fixation | Spoofing | new id on sign in |
| Email bombing a third party | Denial of service | 45 s cooldown, 5 per hour per address, per device bucket, daily ceiling |
| Quota burn on the mail provider | Denial of service | daily ceiling decorator |
| Memory exhaustion by hashing | Denial of service | semaphore + body caps + capped parsed params |
| Referrer leak of the email | Information disclosure | no email in any URL; `Referrer-Policy: same-origin` (Phase 5) |
| Offensive or impersonating username | Repudiation / Spoofing | reserved list, `ScreenAbuse`, 7 day rename gap, moderator Remove later |

| Shared phone keeps previous person's alerts | Information disclosure | delete the replaced session's push subscriptions |
