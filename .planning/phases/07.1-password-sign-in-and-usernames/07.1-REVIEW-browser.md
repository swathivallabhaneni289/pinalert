## Warnings

### WR-B01: The sign in card's requests have no time limit, so a stuck request locks its button until a reload

**File:** `web/static/js/auth.js:228-242` (postJSON), `534-540`, `557-562`, `584-589`, `607-615`, `652-657`

**Issue:** `postJSON` calls `fetch` with no AbortController and no timer. Every submit first sets `aria-busy` (`setBusy`), and the guard at the top of each submit (`if (isBusy(...)) return;`) refuses any new press until the promise settles. Resend is guarded the same way by `state.resendBusy`.

If WebKit leaves a request unsettled, the button keeps its busy label ("Sending…", "Signing in…" or "Checking…") forever and cannot be pressed again. The rest of the app already guards against exactly this: `request()` in `welcome.js:365-412` and `settings.js:250-297` bounds the whole request and the body read, and its comment says why ("so a request WebKit leaves unsettled still ends").

**Scenario:**
1. On an iPhone, the person taps **Email me a code** and switches straight to Mail to wait for the code.
2. iOS suspends the tab mid-request, and the request never settles.
3. They come back and the button still reads "Sending…".
4. Pressing it does nothing (`isBusy`), and nothing says what went wrong. Only a reload gets them out.

The same can happen to Sign in, the code submit and Resend.

**Fix:** give `postJSON` the same bound as `request()`: an AbortController and a 10 s timer that covers `res.json()` too, resolving to `{ ok: false, status: 0, body: {} }`. That status already maps to the offline sentence through `messageFor`.

**Test:** in `auth_flow_test.mjs`, a fetch that never settles, then advance the fake clock 10 s. Expect the button to lose `aria-busy` and get back its resting label, the offline line in the panel's error line, and a second press to post again.

**Status:** Verified in code. That WebKit leaves the request unsettled is Unverified here, but the repo's own comments record it. Sure: medium high.

### WR-B02: The resend wait and the code expiry count timer ticks, not real time, and a reload restarts the full wait

**File:** `web/static/js/auth.js:401-422` (startResendWait), `436-449` (startExpiry), `748`; `internal/api/handlers/auth.go:155`

**Issue:** both clocks decrement a counter once per `setInterval` tick (`state.resendLeft -= 1`, `left -= 1`). Nothing reads `Date.now()`, and there is no `visibilitychange` or `pageshow` handler (grep confirms).

- iOS suspends JavaScript while Safari is in the background, and desktop Chrome throttles hidden tabs to one tick a minute after five minutes. Both clocks therefore stop while the person is away and pick up where they stopped.
- On a reload, the server renders `data-resend-seconds` as the constant cooldown (`auth.go:155`), not the time left. `startResendWait` (`auth.js:748`) then restarts the full 45 s.

UI-SPEC Surface 3 names this exact path ("A phone person leaves the browser to read their mail") and says the wait "starts when the panel first shows and after every send".

**Scenario:**
1. The person asks for a code and goes to Mail 5 seconds later.
2. The mail has not arrived after a minute, so they come back to press Resend.
3. The button reads "Resend in 40s" and does nothing, although the server would accept a resend.
4. If iOS reloaded the tab instead, it reads "Resend in 45s".

The expiry notice "The code has expired. Get a new one." comes late in the same way. On a desktop tab hidden for more than 5 minutes it can come many minutes after the code really expired.

**Fix:**
1. Keep two deadlines, `resendAt` and `expiresAt`, from `Date.now()`.
2. On each tick, and on `visibilitychange` and `pageshow`, recompute the seconds left from them.
3. Have the server render the cooldown that is left (the same way it renders `CodeSecondsLeft`) and use that on load.

**Test:**
- Open the code panel, move a fake `Date.now` 60 s ahead, fire one tick. Expect "Resend code" with no `aria-disabled`.
- Fire `visibilitychange` with the clock moved past the lifetime. Expect the expiry line.

**Status:** Verified in code. That iOS pauses the clocks is platform behaviour, not checked in the simulator. Sure: high.

### WR-B03: A refused or stuck username check stays refused until the person edits the name, and step 4 then blames them

**File:** `web/static/js/username-check.js:136-163`; `web/static/js/welcome.js:1623-1626`; `web/static/js/settings.js:520-527`

**Issue:**
- `ask()` treats any answer that is not 200 as `failed` (`res.status !== 200` gives `null`). The 429 from the per account allowance (burst 10, then one a second: `internal/api/router.go:353`) therefore shows "Couldn't check that username. Try again."
- The server's sentence and its Retry-After are dropped, and nothing asks again. The only way to run the check again is the input event (`judge`), so the person has to change the name and change it back.
- The request also has no time limit, so a check WebKit leaves unsettled stays on "Checking…" for good.

In both cases `isGood()` is false. Continue (step 4) or Save username (Settings) stays off.

On step 4, a press on Continue then goes to `focusFirstMissing` and writes "Add your username, name and home area." (`welcome.js:1623-1626`). That sentence is wrong when the name is typed and only the check failed.

**Scenario:**
1. In Settings, a person opens the Username window a few times (each opening spends one check on the stored name, `settings.js:402`).
2. They then type a new name slowly on a phone, pausing more than 300 ms between letters, so each pause sends a check.
3. The burst runs out, and the last check, for the final value, gets 429.
4. The line says "Couldn't check that username. Try again.", Save stays off, and there is nothing to press.

On step 4 the same 429 leaves Continue off, and pressing it tells the person to add a username they have already typed.

**Fix:**
1. In `ask()`, on a 429 read `Retry-After` (or `retry_after_seconds` in the body, default 1 s). Show the server's sentence, or the warn look with "Checking…", and set one timer that re-runs the check if `seq` has not moved.
2. Bound the request with an AbortController (10 s) so a stuck check ends as `failed`.
3. In `finishStep4`, when the username check state is `failed` or `checking`, call `usernameCheck.refresh()` instead of writing "Add your username, name and home area.".

**Test:**
- In `username_check_test.mjs`, reply 429 with `Retry-After: 1` for the last value, advance the injected timer 1 s, and expect a second request for the same value. A good answer must then make `isGood()` true.
- In `welcome_flow_test.mjs`, a failed check and a Continue press must send a new check and must not write MESSAGE_ADD_ALL.

**Status:** Verified in code. Sure: high that the path exists; medium on how often a real person hits it.

### WR-B04: The Reliable tick box in the installed app's ask is unstyled: no 44px target and the small native box (known item 1, confirmed)

**File:** `web/templates/installed_alerts_ask.html.tmpl:15`; `web/static/css/welcome.css:607-624`; `web/templates/index.html.tmpl:9-21`

**Issue:** the box's label uses `.welcome-ask__check`. Its rules (`display: flex`, `min-height: var(--touch-target-min)`, the gap, the margin, the text colour) are scoped to `#welcome-alerts-ask .welcome-ask__check`. The 20px size of the box itself is scoped to `#welcome-alerts-reliable`. Both live in `welcome.css`, which Nearby does not link.

On Nearby the label is therefore an inline line, with the browser's own small checkbox and no 44px target. It sits flush against the buttons, with no 16px margin. The 13c SUMMARY ("Not verified") already saw this and left it.

**Scenario:** on an iPhone, in the installed app, the ask opens on Nearby. The tick box is about 13px, its line is shorter than a finger, and the Not now and Allow row sits right under it. A miss lands on Not now or Allow, against the owner's rule that the ask looks like the sign up pop-up.

**Fix:** move both rules to a stylesheet Nearby links (`auth.css`, beside `.logout-confirm`), scoped to `.logout-confirm .welcome-ask__check` and `.logout-confirm .welcome-ask__check input[type="checkbox"]`. Delete the `#welcome-alerts-ask` copies so there is one rule.

**Test:** a contract test that `index.html.tmpl` links a stylesheet holding a `.welcome-ask__check` rule with `min-height: var(--touch-target-min)`. Then a look in the iPhone simulator.

**Status:** Verified in the CSS and templates. Sure: high.

### WR-B05: On the first Nearby load inside the installed app, the alerts ask and the location question can open together

**File:** `web/static/js/installed-ask.js:276-292`; `web/static/js/map.js:455-481`; `web/static/js/position.js:203-215`

**Issue:**
- `installed-ask.js` skips when another box is open, but `pageLocked` (`86-90`) sees only `dialog[open]` and `data-modal-open`. It cannot see a system prompt.
- An app on the Home Screen has its own storage, separate from Safari's. On its first Nearby load the location marker that `position.js` keeps per account (`askedBefore`) is empty, so `startMode` answers `ask` and `map.js` calls `getCurrentPosition` at load, which shows the system location question.
- Meanwhile `deviceState` answers `ready` without any network when notification permission is not granted (`notify.js` `inspect`). The alerts dialog therefore opens on the same load, at the same moment.

**Scenario:**
1. The person follows the install box and opens Pinalert from the Home Screen.
2. They sign in, and Nearby loads.
3. The iPhone shows "Allow Pinalert to use your location?" over the alerts box "Get alerts for critical reports near Benz Circle?".
4. Answering Allow on the box then brings the notification question straight after.

That is two boxes stacked and three questions in a row, on the first screen. It goes against D-18 ("only when no other pop-up is open") and the owner's rule that boxes behave like one normal system alert.

**Fix:** in `start()`, also skip (without writing the key) while the location question is being asked on this load. For example, have `PinalertPosition.startMode` expose an "asking now" flag, or wait for the map's first fix or fail before the final `pageLocked` check. On a load that skipped, the next Nearby load asks.

**Test:**
- In `installed_ask_test.mjs`: with a fake position module reporting a question in progress, `run()` resolves `skipped` and writes no key.
- Then a check in the iPhone simulator of the first installed load after sign in.

**Status:** Unverified. Traced in code; whether an installed iPhone web app asks for location again (rather than inheriting Safari's answer) needs the simulator. Sure: medium.

### WR-B06: The sign up alerts pop-up asks again on a device that already has alerts on, and ignores the list it writes

**File:** `web/static/js/welcome.js:1205-1228` (canAsk), `1278-1288` (openAsk), `1419-1431`

**Issue:**
- `canAsk` opens the pop-up whenever `baseState()` is `maybe` or `ready`. `maybe` includes a device that is already on. `canAsk` never reads `pinalert.alertsAsked`, although `openAsk` writes it.
- Phase 7.1 sends many accounts back through step 4: every account made with the old link (the username is missing), and every account that re-agrees to changed terms (`data-after-terms-step=4`). Each of these reaches `endFlow`, and on a laptop or Android phone where alerts are already on, the pop-up asks "Get alerts for critical reports near …?" again.
- `installed-ask.js` has the opposite rule: it reads the list and checks `deviceState` before it opens.

**Scenario:**
1. A person turned alerts on in Phase 3.3 on their laptop.
2. After the password switch they set a password, and the fill in shows step 4.
3. They press Continue, and the alerts pop-up opens again for a device that is on.
4. The next Policy update does the same.

That is against D-18 (ask once per device and account) and the owner's "few, never piled up" rule.

**Fix:** in `canAsk`, return false when the account is in `alertsAskedList()`. Before `openAsk`, also await `PinalertNotify.deviceState(pushKey)` and skip on `on`, which covers accounts asked before 7.1 wrote the list. Awaiting before the box opens is allowed; only `enable` must come straight from the Allow tap.

**Test:** in `welcome_alerts_test.mjs`:
- With `pinalert.alertsAsked` holding the account, Continue goes straight to first-run-done and the pop-up stays closed.
- With `deviceState` answering `on`, the same.

**Status:** Verified in code. Sure: medium high. It is partly a design gap: the plan only made the list one way.

### IN-B01: An installed account whose device is already on sends one status request on every Nearby load (known item 2, confirmed)

**File:** `web/static/js/installed-ask.js:271-292`

The key is written only when the dialog opens. When `deviceState` answers `on`, the run returns `skipped` and writes nothing. Every later Nearby load then repeats the `getSubscription` call and the POST to the push status route.

There is a rarer second effect. Suppose the person later turns the device off in Settings. The next Nearby load finds `ready` and asks, right after they chose off. Getting there needs the first loads to have skipped (another box open) and the device turned on elsewhere, so it is rare.

**Fix:** write the key when the state is `on` too.

**Test:** `deviceState` answering `on` writes the account into the list, and a second run makes no `deviceState` call.

Verified. Sure: high.

### IN-B03: Answers are not tied to the code screen that sent them

**File:** `web/static/js/auth.js:604-636`, `651-672`, `675-686`

Change email (`changeEmail`) stops the clocks but does not forget requests still out.

- A Resend answer that lands after Change email, and after a new Email me a code, runs `startResendWait`, `startExpiry` and the "A new code is on its way." line on the new screen. A refused one writes its sentence ("Too many codes for this email…") under the new address.
- A code answer that lands late is counted by `refuseCode` against the new code's five tries, and takes focus.
- A Create account answer that lands after the person chose the Sign in tab switches the card to the code screen under them.

Every case needs a press within one request's time, so this is rare.

**Fix:** a `generation` counter bumped by `openCode`, `changeEmail` and `showPanel`. Each `.then` drops an answer from an older generation.

Verified. Sure: high that it exists; low impact.

### IN-B04: Folding while typing moves the cursor, and a pasted "@" name loses its last letter

**File:** `web/static/js/username-check.js:167-173`; `welcome.html.tmpl:180`, `settings.html.tmpl` (Username input, `maxlength="20"`)

- `judge` writes `input.value = folded` whenever the fold changes the text. Setting `value` puts the caret at the end, so a capital typed in the middle of a name sends the cursor to the end.
- `maxlength="20"` cuts a paste before the fold runs, so pasting "@ravi.kumar_12345678" (21 characters) keeps 19 letters of the name. `auth.js` handles the same problem for the code field with a paste handler (`onCodePaste`).

**Fix:** save and restore `selectionStart` and `selectionEnd` around the write. Add a paste handler that folds first and then cuts to 20.

Verified in code; the caret jump is Unverified in a browser. Sure: medium.

### IN-B05: The Settings username check keeps working while the window is shut

**File:** `web/static/js/settings.js:395-404`, `433-448`

`closeWindow` does not cancel the check's pending timer, so a check due when the window closes is still sent. Every opening also runs `refresh()` on the stored name, which spends one check of the account's allowance just to say "This is your username now.". Both feed WR-B03.

**Fix:** add a `cancel()` to the controller and call it from `closeWindow`. Skip the request when the value equals the stored name in settings mode, and show `yours` locally.

Verified.

### IN-B06: The asked keys are written before showModal, so a box that fails to open still counts as asked

**File:** `web/static/js/welcome.js:1278-1288`, `1446-1457`; `web/static/js/installed-ask.js:289-291`

Both scripts add the account to the list before `showModal()`, which is the documented choice so that a closed tab is not asked again.

If `showModal` throws (the dialog is not connected, or it is already open without being modal), the account is still marked as asked. In `installed-ask.js` the four listeners are also attached to a box that never opened.

There is also an asymmetry, which the 13c SUMMARY records as deliberate: junk in `pinalert.alertsAsked` blocks the installed ask for good, while `welcome.js` replaces it.

**Fix:** take the id back out of the list in the catch.

Rare. Verified.

## Checked and clean

- **Markup sinks:** none in the six scripts. There is no `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `DOMParser` or `eval`. Server sentences, place names and the email are all written with `textContent`.
- **Navigation:** `goNext` (`auth.js:276-279`) navigates only to `/` or `/low`, whatever the server sends. Nothing writes the email to the address, storage or history.
- **Double submit:**
  - `auth.js`: `isBusy` on every submit, `isOff` on the code button (Enter included), and `resendBusy`.
  - `welcome.js`: `finishing`, `askBusy` and `installBusy`.
  - `settings.js`: `savingUsername`, `savingName` and `savingHome`.
  - `installed-ask.js`: `busy` and `finished`.
- **Five tries:** the fifth refusal locks the button and clears the field. Focus goes to Resend, or to the title while Resend waits. A good resend unlocks it. A limit or a password refusal does not count.
- **aria-invalid:** it is added and removed symmetrically, and the rule line in `aria-describedby` is kept (`markInvalid`). `clearAllErrors` on every panel change clears every mark.
- **Two dialogs in sign up:** the alerts pop-up needs `maybe` or `ready` and the install box needs `needs-install`, so they never open together. A Mac Dock app gets neither: `isMacDockApp` in `canAsk`, and `isAppleMobile` in `installed-ask.js`.
- **Close paths in sign up:**
  - Not now, Escape and a refused or failed enable all reach `postDone`.
  - A failed `showModal` posts done at once.
  - A step change under an open, unanswered box closes it without answering, as documented.
- **Settings:**
  - An empty Name is refused with "Your name can't be empty." and no request (`settings.js:597-600`).
  - Save home area with nothing picked says "Choose a home area." with no request (`915-918`).
  - The removed `settings-home-remove` and `settings-home-alerts-note` ids are referenced by no script, so `alertsReady` in `settings-alerts.js` still holds.
- **Live check races:** each judgement, save refusal and refresh bumps `seq`. An answer for an older value is dropped, and Continue and Save go off at the keystroke, before any answer. No stale answer can switch them on.
