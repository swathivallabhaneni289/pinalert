## Findings

### SK3-01 (info): the prune removes a kept row only when someone later sends a code

**File:** `internal/service/credentials.go:557` (the only caller of `PruneAuthCodes`), and the claim at `internal/store/queries/auth_codes.sql:86` ("The prune removes it a day after the spend")
**Scenario:** someone confirms a sign up on a quiet deploy, and nobody anywhere starts Create account or Forgot password afterwards. The prune runs only inside `issueAndSend`, so the kept row, which holds the address and no hash, stays past the day the comment promises, until the next send on the whole site. Unconfirmed rows already behaved this way, and Delete my account still removes the row at once, so this is not a new leak. The comment and the round 3 report state the retention more firmly than the code does.
**Fix:** reword the comment to say "removed by the prune on the first code send a day or more after the spend". Or also call `PruneAuthCodes` from `SpentCode`/`LiveCode`, or from the existing expiry sweep ticker, so retention does not depend on traffic.

### SK3-02 (info): after a reset that was answered in time, the reset line and the address stay on /login for up to an hour

**File:** `internal/service/credentials_signin.go:362` (ConfirmReset does not rotate the session id), `internal/service/credentials_signin.go:547-561` (SpentCode), `internal/api/handlers/auth.go:258`
**Scenario:** a person resets their password on a shared phone, the answer arrives, and they leave without signing in. ConfirmReset keeps the browser's session id, so for the rest of the 1 hour resume window (counted from the send) every load of /login on that browser opens Sign in with "Password set. Sign in to continue." and the address filled in the field. Before round 3 the row was deleted at the confirm, so a reload showed a blank card. The next person on that browser sees the address. This stays inside one browser: the same id already shows the address on the code screen for an unconfirmed code during the same hour (LiveCode), and no other browser can read it. Sign up is not affected, because a confirm that was answered rotates the cookie away from the kept row.
**Fix:** either accept it and write the hour into the UI-SPEC notes, or narrow `SpentCode` to a short time after the spend. Since `expires_at` now equals `used_at`, `row.UsedAt.Time.After(now.Add(-s.limits.CodeTTL))` (or a few minutes) is enough, and the lost answer case still works.

### SK3-03 (info): "Account created." also shows when the confirm only set a password on an account that already existed

**File:** `internal/api/handlers/auth.go:143` and `:304`, `internal/service/credentials_signin.go:186` (the existing account branch of ConfirmSignUp)
**Scenario:** someone with an account from the old emailed link (no password yet) follows the switch notice, chooses Create account, confirms, and loses the answer. The reloaded page says "Account created. Sign in to continue." even though their account and its reports already existed. The wording is slightly wrong. Nothing breaks.
**Fix:** none needed for correctness. If the owner wants it exact, add a constant such as "Password set. Sign in to continue." for this branch. That needs a marker on the kept row, for example leaving `delivery` alone and recording the branch somewhere, so the simpler choice is to leave the wording as it is and let the owner decide in the copy pass.

## Checked and clean

- **A used row can never be confirmed again:**
  - `BumpAuthCodeAttempt` picks only `used_at IS NULL` rows, and `ConsumeAuthCode` also requires `used_at IS NULL AND expires_at > now()`, which the kept row (expires_at = used_at) fails twice over.
  - `ConfirmReset` refuses because its newest row is used.
  - `ResendCode` refuses because the row is used (credentials.go:409).
  - `LiveCode` returns false for a used row.
  - The `IssueAuthCode` retire CTE touches only unused rows, so it never rewrites the kept row.
  - The attempt counter is never reached.
  - There is at most one unused row per session and purpose, so no older unused row can sit behind the kept row.
- **W9 still holds:** `DeleteOtherAuthCodesForEmail` removes every other row of the address, a pending code in another browser included, inside the same transaction and under the same advisory lock order.
- **The spent marker:** the equal `used_at`/`expires_at` pair is written only by `ConsumeAuthCode`. Both use the transaction's now(). `RetireAuthCode` and the retire CTE set used_at alone, against an expiry that the Go clock set CodeTTL later. A rollback after the spend leaves nothing kept.
- **No enumeration oracle:**
  - `SpentCode` reads only `GetLatestAuthCode` for this session id and never the account table.
  - An existing address on sign up (account_exists) and an unknown address on reset (no_account) can never be spent, because `proveCode` refuses any delivery other than code. Spending a row takes the real code from the mailbox, so an attacker without the mailbox gets the same code screen in both cases.
- **The address does not leak to another browser:**
  - It is keyed by the signed session cookie.
  - It is rendered once, as escaped page text in the hidden `#code-email`, and auth.js copies it with `textContent` into `.value`.
  - It never goes into a URL, an attribute or a redirect.
  - `TestLoginGateSpentCode` checks that a fresh browser sees neither line.
- **Revoked sessions:** the session middleware keeps a verified but revoked id (cookie.go resolveID), so the old link case, where LogOutAllDevices revokes the browser's own session, still finds its kept row.
- **Delete my account:** `DeleteAuthCodesForEmail` (accountdelete.go:168) still deletes every row of the address, the kept one included. The code row's email is the same normalised value the account was created from.
- **The prune:** `expires_at < cutoff` matches the kept row once a day has passed since the spend (with the condition in SK3-01).
- **Nothing loops:**
  - LoginGate's new branch redirects nowhere and sets no cookie.
  - The auth.js start branch posts nothing, does not reload and does not navigate.
  - `askServerAgain` runs only on a submit that timed out.
- **"Account created. Sign in to continue." appears only after a real sign up confirm in this browser:**
  - It needs this session's newest row to be a signup row of delivery code that was attempted and spent. A done word overrides it, a live code takes precedence, and an answered sign up rotates the cookie away from the row.
  - The stale line is cleared by the generic status clear (auth.js:205).
- **Other round 3 changes:** the SK2-02 comment now matches the reserve and refund queries. The SK2-05 Policy line is plain text with no sink.
