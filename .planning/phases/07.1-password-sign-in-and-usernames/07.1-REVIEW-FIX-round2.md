### SK-02: a busy hasher counted toward the per address lock

**Commit:** 6bbb5ba1
**Files:**
- internal/store/queries/auth_throttles.sql (+ generated)
- internal/service/credentials.go
- internal/service/credentials_signin.go
- internal/service/credentials_test.go
- internal/service/credentials_db_test.go
- internal/api/handlers/credentials_security_e2e_test.go
- docs/TRUST-MODEL.md

**What changed:**
- `ReserveSignInTry` also returns `last_failure_at`.
- A new guarded `RefundSignInTry` sets `failures = failures - 1` and `locked_until = NULL`. It acts only while the row still holds the reserved try: the same `failures`, the same `last_failure_at`, and `failures > 0`. So it never undoes a later try.
- Clearing the lock restores the state before the try, for two reasons. The reserve only updates a row whose lock had ended or never existed. And the kept `last_failure_at` leaves the forget rule reading the same.
- SignIn calls the give back on `ErrHasherBusy`, best effort, and always answers ErrBusy. Every address takes the same statement, so the give back reveals nothing. The burst bound of CR-S01 holds, because no password was checked.

**Tests:**
- `TestSignInBusyGivesTryBack` (DB):
  - six busy tries for a known and for an unknown address leave 0 failures on both;
  - a wrong password then counts 1;
  - the right password signs in.
  - Before the fix: 6 failures each, then the 5 minute lock.
- `TestEnumerationBusyHasherIdentical` (handler comparison): six busy 503 answers for a known and an unknown address match under compareAuthAnswers. The next wrong password is the plain 400 for both, never the lock. Before the fix it was a 429 for both.
- `TestSignInHashBusy` is amended with a dated note: one try counted, one given back, no bind.
- The plan 09 compareAuthAnswers suite stays green.

**Status:** fixed, requires human verification.

### SK-03: the 10 s browser limit was shorter than the server's 75 s write window

**Commit:** ff60116a
**Files:** web/static/js/auth.js, web/auth_flow_test.mjs

**What changed:**
- `postJSON` takes a limit. A request that runs out of time carries `timedOut`.

- When a code submit (Create account or Set new password) times out, `askServerAgain` calls `window.location.reload()`. The server's LiveCode or SignedIn then draws the right screen, instead of the card showing offline and a retry saying the code is wrong.
- The reload names no path, so navigation still goes only to / or /low through `goNext`.
- The offline line stays in two cases:
  - a fetch that was refused at once (the phone never sent it);
  - a timed out submit while `navigator.onLine` is false, because a reload would show the browser's own error page.

**Tests:** four SK-03 cases in web/auth_flow_test.mjs.

- A send still ends at 80 s, and the two limits are pinned.
- A code submit with no answer in 10 s reloads, in create and reset mode.
- A refused fetch, and a timed out submit while offline, keep the offline line and do not reload.

The first three cases failed before the fix. Two WR-B01 cases are amended with dated notes: Create account and Resend now end at 80 s, and the code submit reloads.

**Status:** fixed.

### SK-05: the two confirm transactions could deadlock

**Commit:** c3b74e6a
**Files:**
- internal/store/queries/auth_codes.sql (+ generated)
- internal/service/credentials.go
- internal/service/credentials_signin.go
- internal/service/credentials_test.go
- internal/service/credentials_lock_db_test.go (new)

**What changed:**
- A new `LockCredentialAddress` query: `pg_advisory_xact_lock(71, hashtext(address_key))`. The key is the keyed throttle hash of the normalised address, and the class 71 keeps these keys apart from any other advisory lock.
- It is the first statement of both the ConfirmSignUp and the ConfirmReset transactions. Two confirms for one address now run one after the other, and the second gets ErrWrongCode.
- The lock also covers a brand new account, which has no row yet to lock.
- The unit fake records the call.

**Test:** `TestConfirmLockOrder` (DB). It holds one transaction at a querier hook and waits until `pg_locks` shows the other one waiting, then releases it.
- A legacy account: the reset is held after `SetAccountPasswordNewEpoch` while the sign up confirm runs.
- Two browsers confirm two sign up codes for one new address: the first is held after `ConsumeAuthCode`.

Before the fix, both cases ended in `40P01 deadlock detected`. After it, each gives one success and one ErrWrongCode. The test ran 5 times in a row without a failure.

Note on the skeptic's suggested reproduction: holding the sign up after spend does not deadlock today, because the reset's `proveCode` waits outside its transaction and simply gets ErrWrongCode. The reset has to be held inside its transaction instead.

**Status:** fixed, requires human verification.

### SK-07 (info): a refused bind had already revoked the browser's other account session

**Commit:** 34e644e2
**Files:** internal/service/credentials_signin.go, internal/service/credentials_db_test.go, internal/service/credentials_test.go

**What changed:**
- `rotate` reads the binding, binds the fresh id at the epoch, and returns `errBindRefused` with nothing else touched when the bind is refused.
- Only after a good bind does it delete the replaced session's push subscriptions and revoke it.
- In SignIn, which runs outside a transaction, a revoke that fails after a good bind returns the error. It leaves a bound id that no cookie carries, which nobody can use.

The fix is small and safe, so it was made.

**Tests:**
- `TestRefusedBindKeepsOtherAccountSession` (DB):
  - the sign in is held in Verify;
  - a reset moves the epoch;
  - the answer is ErrWrongCredentials;
  - the browser's previous account session stays signed in, with its push subscription.
  - Before the fix it was signed out with 0 subscriptions.
- `TestConfirmSignUpCleansReplacedSessionPush` is amended with a dated note. Its order pin is now: bind, then push subscriptions, then revoke.

**Status:** fixed.
