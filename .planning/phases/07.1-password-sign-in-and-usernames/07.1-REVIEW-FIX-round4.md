`CredentialService.SpentCode` now counts a spent code only for `spentCodeMemory` (10 minutes) after the spend, read from the row's `used_at`, not for the whole 1 hour resume window. ### SK3-03 (info): "Account created." showed when the confirm only set a password

**Commit:** c5d34b56
**Files:** internal/store/queries/auth_codes.sql (+ generated internal/store/sqlc/auth_codes.sql.go), internal/service/credentials.go, internal/service/credentials_signin.go, tests: internal/service/credentials_spent_db_test.go, internal/service/credentials_test.go (fake), internal/api/handlers/login_gate_spent_e2e_test.go

The skeptic expected a marker to need a new column. None is needed: in the branch where `ConfirmSignUp` finds an existing account (the old emailed link, or an account that gained a password meanwhile), it now calls `MarkAuthCodePasswordSet` on the row it just spent, inside the same transaction. That sets the kept row's purpose to `reset` (allowed by the table constraints; the row holds no hash). `SpentCode` then returns the reset purpose and the page shows the existing "Password set. Sign in to continue." line. So the choice comes from the confirm's own branch and this browser's own code row; the sign in page still never reads the account table, so nothing tells an outsider whether an account existed, and only a person with the real code ever reaches the spent state. A brand new address still reads "Account created."

**Tests (both failed before the fix):**
- `TestSpentCodeNamesPasswordSetOnExistingAccount` (DB): an old link account gives the password set purpose, one kept row with no hash; a new address gives the signup purpose.
- `TestLoginGateSpentCode`, new subtest "password set on an account from the old link says password set" (real router): the page shows the reset line, never the created line, once-only address as page text, and the person can then sign in.

**Status:** fixed, requires human verification (a purpose value written by the confirm; nothing else reads the purpose of a used row).
