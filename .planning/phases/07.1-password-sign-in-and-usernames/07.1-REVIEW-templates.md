## Critical Issues

### CR-T01: No focus indicator on any sign in card field (sure: high, measured)

**File:** `web/static/css/auth.css:100-102`, with `.login-field` at `:77-87`. The fields are in `web/templates/login_gate.html.tmpl:44, 49, 66, 71, 88, 94, 116`.

**Issue:** `.login-field input:focus { outline: none; }` has specificity (0,2,1). That beats the global `:focus-visible` ring in `main.css:301` at (0,1,0). Nothing puts a ring anywhere else: there is no `.login-field:focus-within` rule in any stylesheet, and the field's border does not change on focus.

Approved sketch 010 draws the ring at `index.html:146` (`.login-field:focus-within { outline: 2px solid var(--color-focus-ring); outline-offset: 2px; }`), and the build dropped it. The Username field in chrome.css got the same pattern correctly (`.username-field:focus-within`, measured 2px solid).

Measured in Chromium and WebKit at every size and in both themes: after Tab into `#create-email`, the input's computed `outline-style` is `none`, the `.login-field` wrapper's `outline-style` is `none`, and its border colour is the unfocused muted grey. Tabbing reaches the email, password, code, new password and forgot email fields with no visible change except the caret. That fails WCAG 2.4.7 on the one page everyone must pass, and it departs from the approved sketch.

Phase 5's single email field had the same gap. Phase 7.1 copied the field look onto every card input and its own sketch fixed it, so the defect belongs to this phase.

**Fix:** in auth.css, next to `.login-field input:focus`:
```css
.login-field:focus-within {
  outline: 2px solid var(--color-focus-ring);
  outline-offset: 2px;
}
```
The Show button inside the field keeps its own `:focus-visible` ring. With this rule, the ring would draw around the whole field while Show has focus too, which is acceptable and matches the sketch.

**Test:** a contract test that `auth.css` holds `.login-field:focus-within` with `outline: 2px solid var(--color-focus-ring)`. Add the browser probe I ran: Tab to `#create-email` and assert that the computed `outline-style` of `.login-field` is `solid`.

### WR-T04: The four card forms post to a route that does not exist (sure: high, measured)

**File:** `web/templates/login_gate.html.tmpl:40, 61, 83, 111` (`method="post" action="/login"`); `internal/api/router.go:621` registers only `r.Get("/login", ...)`; the script loads deferred at `login_gate.html.tmpl:135`

**Issue:** D-10 made every panel a real POST form, so that Enter without the script never puts an email in the address. That part holds. But nothing answers the POST: `curl -X POST /login` returns 405 with an empty body.

The primary buttons are `type="submit"`. On a slow phone network (this app's emergency case), the page can draw, and the person can type and tap Email me a code or Sign in, before `auth.js` has downloaded. They land on a blank 405 page, and their typed email and password are gone. Nothing leaks, but the sign in fails silently.

**Fix (choose one):**

- Add `r.Post("/login", ...)` that answers 303 to `/login` and reads no body. The page comes back and the script is then loaded.
- Answer the POST with the card itself, plus one status line: "Something went wrong. Try again."

This is a handlers change, so pass it to the handlers reviewer.

**Test:** a router test that `POST /login` with a form body answers 303 to `/login`, never 405, and never echoes the email.

### WR-T05: The install box hides its only button on a narrow or zoomed iPhone (sure: high on the measurement, medium on how often it happens)

**File:** `web/templates/welcome.html.tmpl:237-245`; `web/static/css/device-guide.css:25-37`; the box cap is `web/static/css/auth.css:680-697`

**Issue:** The box opens for any iPhone or iPad Safari tab: `baseState()` in `web/static/js/notify.js:105-107` returns needs-install for any Apple mobile that is not installed, whatever the iOS version. Measured in WebKit with welcome's stylesheets:

| Viewport | Content height | Visible box height | Not now bottom edge | Result |
|---|---|---|---|---|
| 326x476: an iPhone SE 2 or 3 Safari tab (375x548) with page zoom at 115 percent, which reflows to a narrower CSS viewport | 567px | 442px (box ends at 460) | 560px | hidden |
| 320x568 | 590px | 534px | 583px | hidden |
| 375x548 | 511px | 511px | 505px | fits, with about 5px of slack |
| 390x664 | | | 551px | fits |

Once the content is taller than the box, the three wrapped steps and the 40px tiles push Not now out of view. The person has to scroll inside a dialog that gives no sign it scrolls to find the one way out, and an iPhone has no Escape key. Safari page zoom or a slightly larger text setting on a common iPhone SE is enough. The 375x548 case has about 5px to spare, so a small text bump tips it over.

The owner's rule is a box like a normal system alert, and the phone first rule says to judge at 320. The UI-SPEC 10a line "the steps wrap inside the box and nothing scrolls sideways" is met, but the button is not on screen.

**Fix:** let the box body scroll while the actions row stays visible. One way is a two row grid on `#welcome-install-ask .logout-confirm__body`, with the steps scrolling and the actions fixed. Another is to tighten the guide inside the pop-up only: 32px tiles and `--space-sm` row padding under `.logout-confirm__body > .device-guide__steps`. Measure again at 326x476 and 320x568.

**Test:** a browser probe at 326x476, 320x568 and 375x548: after `showModal`, the bottom of `#welcome-install-later` is at or above the dialog's visible bottom and the viewport height.

### WR-T06: The card title draws a focus ring that the UI-SPEC says it must not (sure: high, measured)

**File:** `web/templates/login_gate.html.tmpl:32` (`h1#login-title tabindex="-1"`); `web/static/css/auth.css:37-44`

**Issue:** UI-SPEC 1c says focus moves to the title "(`tabindex="-1"`, no outline drawn, as the first-time flow does)", and sketch 010 has `.login-card h1:focus { outline: none; }` at line 136. The build has no such rule. Measured in Chromium and WebKit: fill Create account, press Enter, and the code panel opens with `#login-title` focused and showing a 2px solid ring, because `:focus-visible` matches after a keyboard action. The same happens on every swap that focuses the title (code, reset, too many tries with Resend waiting). The first-time flow (`.welcome__title:focus`) and the Log out box (`.logout-confirm__title:focus`) both suppress it, so the card is the odd one out.

**Fix:**
```css
.login-card h1:focus { outline: none; }
```
This is safe because the title is not a Tab stop.

**Test:** a contract test that auth.css holds `.login-card h1:focus` with `outline: none`, mirroring the existing `.logout-confirm__title:focus` pin.
