### Owner design rules (binding, quoted)

- No purple or heavy gradients; no pill shaped buttons (modest radius rounded rectangles are fine); no fake numbers or testimonials; no hero text or tagline block; no emoji used as icons (SVG or plain text); no em dashes or en dashes anywhere a user can read, which includes the four emails; no scroll triggered animation (short, restrained hover, press, focus and state transitions only).
- Actions are real buttons with 44px touch targets and are never underlined text links.
- Confirm boxes behave like a normal system alert: reuse `.logout-confirm` (no button outlined on open, only its buttons close it, the page behind stays still). This phase draws no new confirm box.
- No explanatory hint text under simple options. Plain everyday words; the owner dislikes long text. Where a line below exists, it is a rule the person needs or an answer to "why is nothing happening", and it is named in the copy table.
- Same features and words on phone and laptop; only arrangement differs. Phone first: judge at 320, 360 and 390 px, then the laptop.
- One way to close each window (the X). Each thing lives in one place.
- A chosen option looks chosen (soft fill), never a black outline.
- No faded text (no opacity under 1 on text). Muted text is never put on `--color-surface` or a tint (4.34 to 1 fails); the sign in card is `--color-surface`, so every line on it takes `--color-text`.
- No buzzes: no string here uses the words buzz, vibrate, sound, ring, silent, quiet or hear.
- The reference pictures the owner pasted are reproduced as drawn; conflicts are listed, not silently adapted.

## Surface 3: The code screen (panel `auth-panel-code`)

One panel, two modes: **create** (after Create account) and **reset** (after Forgot password). The email is held in memory and in the server session row (Pattern 1 of the research), never in the address bar, a form field echo, `replaceState` or any link.

| Part | Create mode | Reset mode |
|------|-------------|------------|
| Title | Check your email | Reset your password |
| Lead (Body 16px, `--color-text`) | We emailed {email}. Type the 6 digit code from that email. | same |
| Field 1 | label **6 digit code** | same |
| Field 2 | none | label **New password** with `lock.svg`, Show/Hide, rule line "At least 8 characters.", `autocomplete="new-password"` |
| Primary button | **Create account** | **Set new password** |
| Secondary buttons | **Resend code**, **Change email** | same |

`{email}` is plain text inside the lead, `textContent` only, `overflow-wrap: anywhere` so a long address never widens the card. The sentence is the same whether or not the address has an account (the email itself says which, Emails section).

**The code field.** One real input, `id="code-input"`, never six boxes, so paste and the keyboard's one time code suggestion work: `type="text"`, `inputmode="numeric"`, `pattern="[0-9]*"`, `autocomplete="one-time-code"`, `maxlength="6"`, `enterkeyhint="done"`, `required`, `autocapitalize="none"`, `autocorrect="off"`, `spellcheck="false"`, leading `shield-check.svg` icon in the built `.login-field`. Digits are Display 24px/600 with letter spacing `0.25em`. Non digits typed or pasted are dropped as typed; a pasted `482 913` becomes `482913`. The six digit code is not submitted automatically; the person presses the primary button or Enter.

**Resend code.** An outlined `.btn`, full width, 44px.

| State | What it shows |
|-------|---------------|
| Waiting | label **Resend in 45s**, counting down each second; the button carries `aria-disabled="true"` (not `disabled`, so it keeps full contrast `--color-text` and stays focusable) and pressing it does nothing. The countdown is not a live region (no chatter); it announces once when it becomes ready |
| Ready | label **Resend code** |
| Sending | **Sending…**, `aria-busy="true"` |
| Sent | back to Waiting, and `code-status` (`role="status"`) says **A new code is on its way.** |
| Refused | the refusal sentence appears in **`code-error` inside this panel** (sketch 009: a refused Resend must be seen), as a `.inline-error` directly above the primary button. Sentences are in Copywriting. The pinned sentence "Too many requests. Try again in a minute." appears exactly once in `auth.js` |

The 45 second wait starts when the panel first shows and after every send. The wait length comes from the page (`data-resend-seconds`), never typed in the script.

**Change email.** An outlined `.btn` with a 20px `arrow-left.svg` at its left, label **Change email**, full width, 44px. It returns to the panel the person came from (Create account, or Forgot password) with the email field filled in and focused. In create mode the typed password stays in its field. Nothing is sent. The old code stays valid until it expires or is replaced (a new request replaces it), which is the server's rule.

**Expiry and tries (what the server can and cannot say).** The server gives one refusal for a wrong, expired, used or spent code (it cannot tell which), so the screen does not invent more messages from the server.

| State | Trigger | What the person sees |
|-------|---------|----------------------|
| Wrong or no longer works | the server refuses the code | `code-error`: **That code is wrong or has expired.** The field keeps its digits selected and focused |
| Expired (client notice) | a timer started when the panel showed, using the lifetime the page carries (`data-code-ttl-seconds`, 10 minutes) | `code-status` (`role="status"`): **The code has expired. Get a new one.** The primary button stays pressable, a press still asks the server |
| Too many tries (client count) | five refusals on this panel for the same code | `code-error`: **Too many wrong tries. Get a new code.** The primary button gets `aria-disabled="true"`, the field is cleared, focus moves to **Resend code** (if it is Waiting, to the title). A successful resend resets the count and the button |
| Locked by the server meanwhile | the server refuses before the client counted five | the same wrong or expired sentence; the client never claims a tries figure it does not have |

**Come back to the code screen.** A phone person leaves the browser to read their mail; iOS may reload the page or drop the tab. When `/login` loads and the session has a live code row, the server renders this panel directly (mode, `{email}` as page text, the seconds left on the code), so nothing is lost. If the plan cannot do this read, the fallback is the entry panel with the same email prefilled, and the person asks again. This is a dependency for the planner, see Hand Off.

**Success.** Create mode: the account exists and the person is signed in on a fresh session id, the card is replaced by navigation to `/`, and the gate sends them into the first-time flow (Surface 7). Reset mode: the card swaps to the Sign in panel with the email kept and the password field focused, and `signin-status` (`role="status"`) reads **Password set. Sign in to continue.** (No automatic sign in after a reset, and every other session of the account ends; research Design 2.)

## Interaction and Accessibility

- **Focus order on the page:** title (not a stop), the two choices (one tab stop, arrows move), the panel's fields in reading order, the primary button, the secondary buttons, then the row under the card (Try the demo, Low data view, Disclaimer, Policy, see 1e), and last the globe credit (built). - **Live regions:** `*-error` lines are `role="alert"`, `*-status` lines and the username line are `role="status"`. The resend countdown is not live. Nothing announces on every keystroke; the username line announces after the debounce.
- **State is never colour alone:** the chosen choice has weight and fill; the username states have an icon and a sentence; the off Continue and Save have the same off look plus their sentence on press.

- **Text size and narrow screens:** no horizontal scroll at 320 px or 200 percent text; the card grows, nothing is cut. The two choice labels never wrap (nowrap, with the 320px padding change in Spacing).

- **No email in any URL:** no `?sent=`, no `location.search`, no `replaceState` with an address, no `Location` header with an address, no link in any email. A contract test and an e2e assertion pin it.
- **Markup sinks:** all server text goes in with `textContent` (the repo's `TestNoMarkupSinksAnywhere`).

## Defaults to confirm at the viewing session

Nothing was asked. Each line is built as written unless the owner vetoes it when looking at the finished screens. Numbers are in plain words.

**Orchestrator defaults**

1. **Password minimum 8 characters, at most 128.** A password on the common list is refused; there are no rules about capitals, digits or symbols. A Show/Hide control and the password manager attributes are in. The stricter option is NIST SP 800-63B-4's **15 characters** when a password is the only sign in factor (research recommended it). Eight was chosen because the owner asked for an easy sign up. The blocklist research sized for 15 character passwords must now cover common 8 to 14 character passwords (planner note).
2. **Option X for old accounts.** The change ends the sessions of every account with no password. They come back through Create account with the same email (one code, then signed in, then the fill in). The alternative, Option Y, keeps their sessions and sends them to a set a password step with no code; it needs two more signed in routes and lets a stolen cookie set a password that outlives revocation.
3. **Name and Home area can be changed but not emptied.** Settings loses Remove home area; empty saves are refused with a sentence. The alternative keeps the old API clears and lets the gate send the person back to step 4.
4. **Every number the research proposes**, in plain words:
   - A code has 6 digits and works for **10 minutes**, once.
   - A person has **5 tries** per code; asking for a new code replaces the old one.
   - **Resend** is possible every **45 seconds**, and at most **5 codes per email address per hour**.
   - A code can only be used in the **same browser** that asked for it.
   - Wrong passwords: **5 free wrong tries per account**, then a wait of **5 minutes**, doubling with each further wrong try up to **60 minutes**; the count is forgotten after **30 minutes** without a wrong try or after a successful sign in or reset. A reset also clears the wait. The message is the same for an address with no account.
   - Per device: about **8 quick sign in tries**, then one more every **minute**. Per network address: a much looser limit (300), switched on only when the host passes the real address.
   - Code requests per device: **5 quick**, then one more per **minute**.
   - The whole site stops sending mail at **90 emails a day** (the free plan's limit is 100).
   - Username check: **10 quick**, then one per **second**. Username save: **5 quick**, then one per **10 seconds**; a name can be changed **once every 7 days** after the first.
   - Username: **3 to 20 characters**; letters, numbers, underscores, full stops; at least one letter; no full stop at the start, the end, or twice in a row; stored in lowercase. Reserved words: police, ndma, ndrf, sdma, sdrf, govt, government, official, pinalert, moderator, administrator, emergency, fire, ambulance (kept even with look alike digits, and as a start or a whole word between separators), and exact only: imd, gov, mod, admin, help, support, 100, 112.
   - Sign in stays valid for the cookie's existing **1 year**.

**Placement and look**

5. The **default choice** is Create account, so a new person lands on it; returning people press Sign in. The alternative is Sign in first, or remembering the last choice on the device.
6. The card title is **Pinalert**, with the two choices directly under it. The alternative is a title that follows the choice (Create account, Sign in).
