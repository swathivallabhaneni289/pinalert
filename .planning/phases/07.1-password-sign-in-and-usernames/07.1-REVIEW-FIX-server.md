## Fixed Issues

### CR-S01: The per address sign in lock is check then act

**Commit:** ac0c134f
**Files:** internal/store/queries/auth_throttles.sql (+ generated), internal/service/credentials.go, internal/service/credentials_signin.go, internal/service/credentials_test.go, internal/service/credentials_db_test.go, docs/TRUST-MODEL.md
**What changed:** a new `ReserveSignInTry` query is `RecordAuthFailure`'s upsert with one more guard on the DO UPDATE (`locked_until IS NULL OR locked_until <= now`). SignIn calls it before the account lookup and the password check, for every address. No row back means locked: the row is read once more for the wait, and when the lock has meanwhile ended the reserve is tried once more (never a negative wait). A wrong password writes nothing more. A good password binds the fresh session first and then clears the row, so a refused bind never clears a lock. The lock schedule is unchanged (the 6th try sets the 5 minute lock, the 7th is refused). A busy hasher keeps the counted try, the same for every address.
**Tests:** `TestSignInLockCountsBeforeVerify` (20 parallel wrong tries against a hasher that blocks in Verify: at most 6 checks, at least 14 locked; was 20 and 0) and `TestSignInGoodPasswordClearsCount` (5 wrong then right, twice: the row is gone each time). `TestEnumerationLockIdentical` and `TestLimitsLockScheduleReachesCap` pass unchanged. The unit fake was renamed to ReserveSignInTry; `TestSignInHashBusy` now pins that a busy try stays counted and binds nothing.
**Status:** fixed, requires human verification.

### CR-S02: A password reset does not reliably end the sessions of the old password

**Commit:** 517ce94b (this one change also closes WR-S02 and IN-S07)
**Files:** internal/store/migrations/00016_add_password_epoch.sql, internal/store/queries/accounts.sql, internal/store/queries/sessions.sql (+ generated), internal/service/credentials.go, internal/service/credentials_signin.go, cmd/server/main.go, internal/api/gate_test.go, internal/api/handlers/auth_helpers_e2e_test.go, internal/api/handlers/reports_e2e_test.go, the service tests, internal/store/migration_00016_test.go, README.md, docs/TRUST-MODEL.md
**What changed:**
- Migration 00016 adds `accounts.password_epoch` and `sessions.password_epoch`, both `BIGINT NOT NULL DEFAULT 0` with a `>= 0` check. Both start at 0, so every session of an account that already has a password stays signed in. Down drops both columns.
- `GetAccountBySessionID` (the access gate, the moderator gate and SignedIn all read it) now also requires `sessions.password_epoch = accounts.password_epoch`.
- The sign in bind is the new `BindSessionAccountAtEpoch`: `INSERT ... SELECT ... FROM accounts a WHERE epoch = the epoch read before the check FOR SHARE OF a ON CONFLICT ...`, with the same never-move and never-revive guard. The syntax was checked on Postgres first. A refused bind answers the one wrong credentials answer. The rehash writes through `SetAccountPasswordIfEpoch`, so it can never overwrite a password set meanwhile.
- ConfirmReset and ConfirmSignUp write through one transaction (`WithCredentialTx`, `PgxCredentialTx`; wired in main.go and in the gate and handler e2e harnesses). ConfirmReset sets the password with a new epoch first (`SetAccountPasswordNewEpoch`, which takes the account row lock), then spends the code, clears the throttle and ends every session and phone alert device. ConfirmSignUp spends the code and locks the account (`LockAccountForPassword`, FOR UPDATE). For an account that already existed (made with the old link, or one that gained a password meanwhile) it sets the password with a new epoch and ends every session and device. For a brand new account it sets the password without moving the epoch. Then it clears the throttle and binds, all in the same transaction.
- Without a runner (only the unit fakes) the steps run on the service's querier as before.
- README and TRUST-MODEL name 00016 in the owner's migrate step.
**Tests:** `TestResetEndsSignInInFlight` (a sign in held in Verify with the old password, a reset run to completion, then released: no live session; was live), `TestConfirmResetIsAtomic` (ending the sessions fails: the password and epoch are unchanged, the old session stays as it was, and the same code works afterwards; was spent and changed), `TestMigration00016` (DownTo 15, an account with a password and a live session, Up: still signed in; moving the epoch signs it out and leaves another account alone). The unit tests of the legacy branch now pin the new epoch and the revoke.
**Status:** fixed, requires human verification.

### CR-S03: One client can spend the whole day's email budget

**Commits:** 5f80d418 (fix), 2d0f7414 (README paragraph)
**Files:** internal/mailer/ceiling.go, internal/mailer/ceiling_test.go, internal/api/handlers/authlimits.go, internal/api/handlers/credentials.go, cmd/server/main.go, cmd/server/main_test.go, internal/api/handlers/credentials_security_e2e_test.go, docs/TRUST-MODEL.md, README.md
**What changed:** `mailer.NewSendCeiling(next, CeilingLimits, now)` replaces the plain daily ceiling in main.go. `NewDailyCeiling` is now that ceiling with no pacing and no share, so its tests are unchanged. The numbers live in the main.go constants, mirrored in `mailer.DefaultCeilingLimits` and pinned by `TestCeilingLimitsMatchTheMailerDefaults`:
- **Day:** 90 sends, 20 kept for the reset class.
- **Pacing:** at most 15 in any 10 minutes, 5 of them kept for the reset class.
- **Sender share:** a reset class send that the other class would have been refused takes a kept slot. One sender may take at most 3 kept slots a UTC day.

The sender key (`AuthGate.MailSender`) is set in the context by the three sending handlers, with `extendWriteDeadline` unchanged. It is the client network (IPv4 address or IPv6 /64) when `CLIENT_IP_HEADER` is set, one shared key for requests without a valid cookie, and none otherwise. Classes are still decided in pairs: reset code with the no account note, sign up code with the account exists note. Neither the classes nor the key ever depend on the typed address, so the counters move the same way for an existing and an unknown address. As the review explained, the reserve cannot tell a reset code from a no account note without becoming an oracle. TRUST-MODEL therefore states the residual gaps as T-07.1-09 accepted: several networks working together, a fresh cookie farm with no header, and an IPv6 holder of many /64s. Its "cannot stop a real person" sentence is replaced with the numbers. No per peer bucket was brought back (CGNAT), and the reset device and network buckets the review offered as options were not added, because the per sender share bites only while the reserve is in use, so a busy carrier address is never refused on a normal day.
**Tests:**
- `TestMailCeilingPacesBurst`: 70 sign ups and 20 resets from fresh browsers in one minute, then a real reset 11 minutes later answers 200 with its code. It was 503.
- `TestMailReserveSurvivesOneNetwork`: with the header set, one network sends 70 sign ups and 20 no account resets, 2 minutes apart, then a real reset from another network answers 200. It was 503.
- `TestEnumerationCeilingWindowIdentical` (hard rule 1, both pairs at the window edge) and `TestEnumerationCeilingShareIdentical` (hard rule 1, at the share edge): each sends the boundary request and the one after it, for a known and an unknown address in two fresh runs, and compares them with compareAuthAnswers.
- `TestMailerCeilingPacesPerWindow` and `TestMailerCeilingSenderShare`.
**Status:** fixed, requires human verification (the numbers are mine, not the owner's; see the note for the orchestrator).

### WR-B02 (server half) with IN-S02: the page clocks

**Commit:** a436c9c2
**Files:** internal/service/credentials_signin.go, internal/api/handlers/auth.go, internal/service/credentials_test.go, internal/api/handlers/login_gate_e2e_test.go
**What changed:** `LiveCode` also returns `ResendSecondsLeft`, the integer seconds left of the resend cooldown since the stored send, rounded up and clamped at 0. The send time is the stored expiry minus the code lifetime: both are on the service clock, while `created_at` is the database's. LoginGate follows the orchestrator's contract:
- **Live code:** `data-resend-seconds` and `data-code-seconds-left` are the seconds left, clamped at 0.
- **No live code:** `data-resend-seconds` stays the full resend cooldown, which the browser counts from after the first send, and `data-code-ttl-seconds` stays the code lifetime. Entry panels never get 0 from this change.

Both numbers now come from the CredentialService (`LoginState` gains `CodeTTL` and `ResendCooldown`), not from `DefaultCredentialLimits` (IN-S02). No template attribute was added or changed.
**Tests:** `TestLoginGateClockAttributes` covers both branches. With custom limits the entry panel shows 50 and 420. 30 seconds after a send (service clock moved) the page shows 20 and 390. After the cooldown it shows 0. `TestLiveCode/resend_seconds_left_follow_the_stored_send` checks 45, then 25 (rounded up), then 0.
**Note for the orchestrator:** in the e2e harnesses, whose cooldown is 1 ms, the entry panel now renders `data-resend-seconds="0"` and "Resend in 0s", because the page reads the service's own number. Production renders 45.
**Status:** fixed.

### IN-S01: Create account claims the send before hashing

**Commit:** 0eb3b6fa
**Files:** internal/service/credentials.go, internal/store/queries/auth_codes.sql, internal/store/queries/email_cooldowns.sql (+ generated), the service tests
**What changed:** the claim stays before the hash, so a refused claim still costs no hash, as plan 05 pinned. When the hasher is busy, the claim is given back with `RefundAuthEmailSend`. That is a guarded update: it changes the row only while its last claim is still the one being refunded, so it can never undo a later claim. When a Create account or Forgot password email does not go out, `RetireAuthCode` marks the row used, on every branch alike, so a reload does not show a code screen for an unsent email. The email might not go out because the ceiling refused it, which pacing now makes more common, or because the provider failed. Resend keeps its row, so a person already on the code screen can press Resend again.
**Tests:** `TestSignUpBusyKeepsClaim` (the retry right after a busy hasher goes through and the hourly count holds 1; it was ErrRateLimited), `TestSignUpBusyRefundsClaimOnDatabase` (the same on real Postgres with the 45 second cooldown; a third request is still refused), `TestFailedSendRetiresRow` (four branches, two failure kinds; the row was live).
**Status:** fixed.

## Recorded, not fixed

### IN-S03: A username save and a name or home area save are not one write

**File:** internal/service/profile.go:484-519
**Reason:** a real fix needs a transaction seam on AccountService, which is built in router.go from `deps.Sessions` with no transaction runner. That is a wider change than a cheap Info fix, and the failure direction is benign: the username is saved and a 500 asks for a retry.

### IN-S04: Signing in again on a browser bound to the same account leaves the old session live

**File:** internal/service/credentials_signin.go (rotate)
**Reason:** revoking the old same-account session would silently stop that browser's phone alerts, because push subscriptions are bound to the session id and the new session has none. Moving the subscriptions is a product and Phase 3.3 decision. Log out of all devices, and now a reset, still end such a copy.

### IN-S05: The three hash slots are a shared resource any script can fill

**File:** internal/auth/password.go, internal/api/handlers/authlimits.go
**Reason:** partly closed by WR-S01. Sign in now has its own shared cookieless bucket, so a junk cookie script is held to 10 then one a minute. A script that fetches a fresh cookie before each try is still bounded only by the per address lock (now exact, CR-S01) and the network bucket with `CLIENT_IP_HEADER`. Closing that without the header needs a per peer bucket, which the project's CGNAT rule declines.

### IN-S06: The typed address stays on the sign in page for an hour

**File:** internal/service/credentials_signin.go (LiveCode), internal/api/handlers/auth.go
**Reason:** hiding or masking the address after expiry changes the browser's expired code screen, which reads the address from the page text. That contract belongs to the browser and template fixers and the owner's viewing, so a server-only change would break it.
