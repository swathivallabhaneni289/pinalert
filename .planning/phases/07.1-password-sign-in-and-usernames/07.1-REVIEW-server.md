## Critical Issues

### CR-S01: The per address sign in lock is check then act, so parallel guesses all run before the lock is written

**File:** `internal/service/credentials_signin.go:171-209` (read `GetAuthThrottle`, then `Verify`, then `recordFailure`), `internal/store/queries/auth_throttles.sql:1-6` (a plain SELECT), `internal/api/handlers/authlimits.go:179-192`

**Issue:** `SignIn` reads the throttle row with a plain SELECT, refuses only if `locked_until` is in the future, then runs the argon2 verify (a 3 slot queue with a 3 second wait), and only after the verify writes the failure with `RecordAuthFailure`. Nothing reserves the try before the verify, unlike the typed code path, where `BumpAuthCodeAttempt` counts first. So every request that reads the row before the sixth failure is recorded goes on to a full password check.

The handler buckets do not close the gap. The device bucket is keyed on the session id, and a script that drops cookies, or sends any invalid `pinalert_session` value, gets a fresh id and a fresh bucket on every request (see WR-S01). The network bucket is off without `CLIENT_IP_HEADER`, and with it allows a burst of 300 from one address.

Failure scenario (verified in code, not run): an attacker sends 200 sign in requests for one address at once, each with a junk cookie. All 200 read "not locked". The hasher admits about `3 slots x (3 s wait + hash time) / hash time` of them before the rest get `ErrBusy`; at about 50 ms a hash that is roughly 180 real password checks. Then the row records about 180 failures and locks for the 60 minute cap. When the lock ends, the attacker repeats. The address gets about 180 guesses an hour instead of the documented 5 free tries and then 5, 10, 20, 40, 60 minute locks. The 460 entry common list is the only other guard, and the minimum is 8 characters (D-13). This defeats the control TRUST-MODEL.md names as "the real guard against guessing one account from many browsers" and that T-07.1-03 relies on when it accepts the cookieless gap. The same burst also fills all three hash slots, so every real sign in and Create account on the server gets 503 for its length (IN-S05).

Sure: high. The order of the four calls is unambiguous.

**Fix:** count the try before the verify in one guarded statement, as the code path does, and clear it on success. For example, a `ReserveSignInTry :one` that upserts like `RecordAuthFailure` but only `WHERE t.locked_until IS NULL OR t.locked_until <= now`, returns no row when locked, and computes the lock from the new count. `SignIn` calls it instead of `GetAuthThrottle`; no row means `SignInLockedError` (read the row once more for the wait); a good password then calls `ClearAuthThrottle` as it does now. A parallel burst then gets exactly `FreeFailures` checks before the lock, because the row lock serialises the upserts.

```go
// credentials_signin.go, replacing the GetAuthThrottle read and the later recordFailure
row, err := s.q.ReserveSignInTry(ctx, sqlcgen.ReserveSignInTryParams{ /* same params as RecordAuthFailure */ })
if errors.Is(err, pgx.ErrNoRows) {
    return SignInResult{}, s.lockedError(ctx, key) // reads locked_until for the wait
}
// ... Verify; on success ClearAuthThrottle; on failure nothing more to write
```

**Test that proves it:** a database test in `credentials_db_test.go` with a wrapped hasher whose `Verify` blocks on a channel. Start 20 goroutines calling `SignIn` with a wrong password for one address, each with its own session id, wait until all have returned from the throttle read (or for a short fixed time), release the channel, and assert the wrapped hasher saw at most `FreeFailures + 1` Verify calls and the rest got `SignInLockedError`. Today it sees 20.

### CR-S02: A password reset does not reliably end the sessions of the old password

**File:** `internal/service/credentials_signin.go:182-221` (SignIn reads the hash, verifies, then binds in `rotate`), `:264-280` (ConfirmReset: `setPassword`, `clearThrottle`, then `LogOutAllDevices`, three separate statements), `:143-148` (ConfirmSignUp logs out before it sets the password), `internal/store/queries/sessions.sql:21-26` (`BindSessionAccount` checks nothing about the password)

**Issue:** two defects in one promise. TRUST-MODEL.md says "A reset ends every session of the account, on every device", and `TestResetEndsEverySession` checks it only for sessions that already exist.

1. Race with a sign in in flight. `SignIn` reads `password_hash` at line 182, spends tens to hundreds of milliseconds in argon2, then `rotate` binds a fresh session at line 345. `ConfirmReset` runs `SetAccountPassword` and then `RevokeAccountSessions` (`revoked_at IS NULL`). A sign in that read the old hash before the reset and binds after the revoke leaves a brand new live session made with the old password. A good sign in refunds its device token and clears the throttle, so an attacker who has the old password can sign in in a tight loop at no cost. Then nearly every reset lands while one of the attacker's sign ins is in flight. Reset after a compromise is exactly when this happens. `ConfirmSignUp`'s "race between two Create account requests" branch has the same window, made wider by running `LogOutAllDevices` before `setPassword`: a sign in with the old password can complete entirely between the two.
2. Not atomic. The code is spent (line 268) before `setPassword`, and `LogOutAllDevices` runs last. If the revoke fails (a database blip), the handler answers 500, the new password is stored, the old sessions stay live, and the spent code cannot be retried. The person sees "Something went wrong" and has no signal that the attacker is still in.

Sure: high for the race (verified in code, timing dependent), high for the ordering.

**Fix:** make the bind conditional on the password not having been replaced since the sign in read it, and set and revoke in one transaction that locks the account row. Do not compare the hash itself: a rehash after a cost change rewrites `password_hash` without the password changing, so two good sign ins at once would refuse each other, and the rehash write is best effort. Instead add a `password_epoch` (or `password_set_at`) column that only `ConfirmReset` and `ConfirmSignUp` move. `GetAccountForSignIn` returns it, and the bind checks it.

```sql
-- name: BindSessionAccountIfEpoch :execrows
-- A sketch: check on Postgres that the locking clause is accepted in this
-- position; if not, take the lock with a SELECT ... FOR SHARE in the same
-- transaction first.
INSERT INTO sessions (session_id, account_id)
SELECT sqlc.arg(session_id), a.id FROM accounts a
WHERE a.id = sqlc.arg(account_id) AND a.deleted_at IS NULL
  AND a.password_epoch = sqlc.arg(read_epoch)::bigint
FOR SHARE OF a
ON CONFLICT (session_id) DO NOTHING;
```

`ConfirmReset` and the ConfirmSignUp "already has a password" branch bump the epoch, set the password and run `RevokeAccountSessions` (and the push delete) in one transaction, password first. The row lock makes a concurrent bind either finish before the reset (then the revoke, a new statement under READ COMMITTED inside the same transaction, sees and revokes it) or wait and then find the epoch moved (0 rows, answered as `ErrWrongCredentials`). Spend the code inside the same transaction, so a failure leaves the code usable.

**Test that proves it:** a database test with a hasher whose `Verify` blocks on a channel: start `SignIn` with the right old password, let it reach Verify, run `ConfirmReset` to completion, release the channel, and assert either an error from `SignIn` or that the returned session id is revoked (or not bound). Today it returns a live session. A second fake querier test makes `RevokeAccountSessions` fail and asserts the code row is still usable and the password unchanged.

### CR-S03: One client can spend the whole day's email budget, the reset reserve included, in about 90 requests

**File:** `internal/mailer/ceiling.go:47-72`, `cmd/server/main.go` (constants `authDailyEmailCeiling = 90`, `authResetEmailReserve = 20`, `codeSendIPBurst = 60`, `codeSendIPEvery = 10s`), `internal/api/handlers/authlimits.go:130-135` and `:197-217`, `internal/service/credentials.go:297-337`

**Issue:** the daily ceiling is one in-memory counter for the whole server. The only per sender limits in front of it are the device bucket (bypassed with a junk cookie, WR-S01), the cookieless bucket (bypassed the same way), the network bucket (off without `CLIENT_IP_HEADER`) and the per address claim (5 an hour per address, which does nothing against many addresses). The Phase 1.1 per IP limiter on the TCP peer (DEC-I) was removed in this phase, so without the header there is no per client limit at all on the three sending routes. And the reset reserve counts `KindNoAccount` as a reset email, so Forgot password for unknown addresses spends the reserve too.

Failure scenario (verified in code, not run): a script sends 70 Create account requests for 70 made-up addresses, then 20 Forgot password requests for 20 more, each with a junk cookie. Every request passes every bucket, every per address claim is new, and each sends one email (to addresses that bounce, which also hurts the Resend sender's standing). Counter reaches 90. For the rest of the UTC day every Create account and every Forgot password on the server answers 503 "Something went wrong. Try again.". An account is needed to use Pinalert at all (D-03), so nobody new can join, and nobody locked out (the targeted lockout TRUST-MODEL.md accepts, because "the owner of the address gets back in through Forgot password") can recover. With `CLIENT_IP_HEADER` set, the network bucket (60, then one per 10 s) still lets one address do it in about 5 minutes. TRUST-MODEL.md's line "an attacker spending the rest on Create account cannot stop a real person getting back in" holds only if the attacker never calls Forgot password.

Sure: high on the mechanics; the severity rests on D-03 making sign up the only way in.

**Fix:** the counter must keep moving the same way for every branch, so the ceiling boundary never tells whether an account exists. Skipping the informational emails (`KindAccountExists`, `KindNoAccount`) near the ceiling without counting them would bring enumeration back: an attacker who fills the counter to one below the limit and then sends Create account for a target, then one more for a fresh address, reads 503 or 200 and learns whether the target has an account. The `TestEnumeration*` tests compare one response at a time and would not catch such a probe. So the fix is on the per sender side:
- Pace the ceiling: also cap sends per 10 minutes (for example 15), so a burst cannot drain a day, and a real person retries a few minutes later instead of the next day.
- Fix the cookieless bucket (WR-S01). With no header, put back a loose per peer bucket on the three sending routes (the DEC-I limiter this phase removed), or record T-07.1-09 as accepted with these numbers in TRUST-MODEL.md and correct its reset reserve sentence.
- Consider a tighter per device and per network budget on `/api/auth/reset` than on sign up, since it is the recovery path.

**Test that proves it:** a handler e2e test with `CLIENT_IP_HEADER` unset: 70 sign ups and then 20 resets for distinct addresses, each sent with `Cookie: pinalert_session=x`, then one Forgot password for a real account from a normal jar a minute later. Assert that the last answer is 200 and that the mailer saw its reset code. Today it is 503. Any fix must also pass a boundary probe test: fill the counter to one below the limit, send Create account for a known and for an unknown address in two runs, and assert the answers to the next request are identical.

## Warnings

### WR-S01: The cookieless bucket checks that a cookie is present, not that it is valid; scripts skip it and real people land in it

**File:** `internal/api/handlers/authlimits.go:130-135` (`arrivedWithoutCookie`), `:197-217`, `internal/session/cookie.go:147-157`, `internal/api/handlers/auth.go:213-223` (LoginGate's switch notice clears the cookie)

**Issue:** `arrivedWithoutCookie` returns false for any request that carries a `pinalert_session` cookie, valid or not. The session middleware gives a request with a bad signature a fresh id. So `Cookie: pinalert_session=x` gets a new device bucket on every request and never touches the shared cookieless bucket. The comment ("it cannot dodge the device bucket by getting a fresh id each time") and the main.go block say the opposite. A GET of `/login` before each POST gives a valid fresh cookie with the same effect.

The reverse case also exists. When LoginGate shows the "Pinalert now uses passwords" notice, it calls `ClearCookie`. `/static/*`, the PWA paths and the globe tiles skip the session middleware, so nothing gives the browser a new cookie before its Create account POST. That POST arrives with no cookie, and the person lands in the one global bucket (10, then one a minute) shared by every cookieless sender on the server. On the day the migration runs, every legacy person who follows the notice shares those 10 sends.

Sure: high (verified in code).

**Fix:** have the session middleware record in the context that it had to mint the id (absent, malformed or bad signature), and key the shared bucket on that flag, not on cookie presence. Optionally apply the same shared bucket to sign in. On the switch notice, call `SetCookie(w, NewID())` instead of `ClearCookie`, so the next POST carries a real cookie. This closes only the junk cookie path: a script that GETs `/login` first still gets a valid fresh id and a fresh device bucket, which only the pacing in CR-S03 bounds.

**Test that proves it:** in `authlimits_test.go`, send `CodeSendNoCookie.Burst + 1` code sends each with a junk cookie and a distinct address, and assert the last is 429. Today all pass. In `passwordless_session_e2e_test.go`, follow the notice and then POST sign up from the same jar after the shared bucket is drained by another client, and assert 200.

### WR-S02: Create account on a legacy account leaves its live sessions in place, so one that never typed a code becomes signed in

**File:** `internal/service/credentials_signin.go:143-148`, `internal/api/gate.go:90`, `internal/store/migrations/00014_add_passwords_and_usernames.sql:127-129`

**Issue:** `ConfirmSignUp` calls `LogOutAllDevices` only when the account already has a password. For an account made with the old link, which has none, it sets the password and keeps every session still bound to it. The gate's only test for these sessions is `has_password` (W1). The moment `setPassword` lands, any live session bound to that account passes the gate. The migration revoked only the sessions that existed when it ran. W1 exists because the old binary can still bind a new one from an emailed link in the deploy gap, and D-14 says the fill in must "always ride a real sign in through a typed code". Such a session skips both. The holder did click a link sent to the same address, so the person at risk is the account owner whose link was opened elsewhere (a shared or forwarded mailbox, a mail scanner that follows links). That is why this is a Warning and not Critical.

Sure: high on the code path; the precondition is the deploy gap.

**Fix:** when the account existed before `InsertAccount` (look it up first, or compare the id), end its sessions as `ConfirmReset` does, inside the same transaction as the password write (see CR-S02).

**Test that proves it:** a legacy account with no password and a live, unrevoked session S bound with `BindSessionAccount` after the migration. Create account and confirm the code from another jar, then GET a gated page with S. Want 302 to `/login` (or 401 on `/api/`). Today it is let in.

### WR-S03: The reserved username rule misses the shape most official handles take, a place before the word

**File:** `internal/service/username.go:115-217`

**Issue:** a blocked word matches only as the start of the whole name or as a token between `_` and `.`. A word at the end or in the middle with no separator passes. Every one of these is available today: `hydcitypolice` (the real Hyderabad City Police handle), `cyberabadpolice`, `vijayawadapolice`, `apsdma` and `tnsdma` (real state disaster authority handles), `indiandrf`, `apgovt`, `realpinalert`, `theofficial`, `siteadmin`, `admin2`, `imdhyderabad`. The app is built around Vijayawada, so `vijayawadapolice` posting "road closed" next to real reports is the impersonation T-07.1-16 is meant to stop ("Names that look official are refused", UI-SPEC). The rule matches plan 04's wording, so this is a gap in the rule more than in the code. It is a Warning because Phase 8 shows these names next to reports.

Sure: high that these pass (verified by tracing `UsernameReserved`). Whether to widen the rule is the owner's call at the viewing.

**Fix:** match the long, unambiguous blocked words anywhere in the folded name without separators (`police`, `ndma`, `ndrf`, `sdma`, `sdrf`, `govt`, `government`, `official`, `pinalert`, `moderator`, `administrator`), and keep start or token matching only for words that occur inside ordinary words (`fire`, `emergency`, `ambulance`, and the exact list). Accept the few false positives (`policeman`).

```go
for _, w := range reservedAnywhereWords { // police, ndma, ndrf, sdma, sdrf, govt, government, official, pinalert, moderator, administrator
    if strings.Contains(whole, w) { return true }
}
```

**Test that proves it:** extend `username_test.go`'s table with `hydcitypolice`, `apsdma`, `vijayawadapolice`, `realpinalert`, `indiandrf` as reserved, and keep `imdone`, `modest`, `helpful`, `firefly_fan` as their current verdicts.

## Info

### IN-S01: Create account claims the send before hashing, so a busy hasher or a failed send burns the cooldown and an hourly send

**File:** `internal/service/credentials.go:297-303`, `:475-511`

`claimSend` commits before `Hash`, so an `ErrBusy` 503 still uses up the 45 second cooldown and one of the 5 hourly sends. The person's immediate retry gets "Too many requests". When the Resend call fails after `IssueAuthCode`, the row stays live, and a reload of `/login` shows the code screen as if a code had been sent. Fix: hash before the claim (the hash is the same work on every branch, so enumeration is unchanged), and on a send failure mark the row used. Test: a fake hasher that returns `ErrHasherBusy` once, then a retry within 45 s succeeds.

### IN-S02: The sign in page reads the default limits, not the service's

**File:** `internal/api/handlers/auth.go:154-155`

`CodeTTLSeconds` and `ResendSeconds` come from `service.DefaultCredentialLimits`, while the service enforces `s.limits`, so a `WithCredentialLimits` change makes the page count down the wrong numbers. `CredentialService` already exposes `CodeTTL()` and `ResendCooldown()`; add them to `LoginState` and read them there.

### IN-S03: A username save and a name or home area save in one request are not one write

**File:** `internal/service/profile.go:484-519`

The username is written first and the name and home area after, in separate statements. If the second write fails, the username is saved and the person sees a 500. The comment says nothing is half applied, which is true only in the other direction. Fix: run both in one transaction, or say so in the comment.

### IN-S04: Signing in again on a browser bound to the same account leaves the old session live

**File:** `internal/service/credentials_signin.go:326-343`

`rotate` revokes the old session only when it is bound to a different account. Bound to the same account, it stays live after the browser's cookie is replaced, so a copy of the old cookie keeps working until Log out of all devices. Revoke it in that case too; nothing is lost, because authorship stays on `sessions.account_id`.

### IN-S05: The three hash slots are a shared resource that any unauthenticated script can fill

**File:** `internal/auth/password.go:51-58`, `internal/api/handlers/authlimits.go:179-192`

Sign in has no cookieless bucket, and the device bucket is skipped with a junk cookie, so a steady stream of wrong sign ins keeps all three slots busy. Every real sign in, Create account and reset then waits 3 s and gets 503. T-07.1-03 accepts that guesses are bounded by the hashing cost; it does not record that the cost falls on everyone else. The fix for WR-S01, extended to sign in, bounds it.

### IN-S06: The typed address stays on the sign in page of that browser for an hour

**File:** `internal/service/credentials_signin.go:360-381`, `internal/api/handlers/auth.go:201-212`

`LiveCode` returns any unused row inside the one hour resume window, expired included, so anyone who opens `/login` on a shared phone within the hour sees the address the last person typed. Consider limiting the address to rows not yet expired, or showing it masked after expiry.

### IN-S07: ConfirmSignUp spends the code before it creates the account

**File:** `internal/service/credentials_signin.go:130-154`

A database error after `spend` (in `InsertAccount`, `setPassword`, `clearThrottle` or `rotate`) answers 500 with the code already used, so the person must ask for a new one. `ConfirmReset` already orders its soft failures before the spend. Running the steps in one transaction (CR-S02) fixes this too.

## Checked and clean

- **The 10 second write limit:** the three handlers that send mail (`SignUp`, `ResendCode`, `RequestReset`) call `extendWriteDeadline` after the body and the buckets and before the service. No other handler in the diff sends mail. The other three do at most two hashes, each with a 3 s slot wait, well under 10 s.
- **Enumeration:** every Create account branch takes the same claim, the same hash and one row, and sends one email in the same ceiling class. `KindNoAccount` and `KindCodeReset` share the reset class, so a ceiling refusal never depends on whether an account exists. Sign in verifies the dummy hash for an unknown address and for an account with no password, and the lock is keyed on an HMAC of every address, known or not. Resend recomputes the delivery and obeys the same claim.
- **Codes:** `crypto/rand` with `rand.Int`, an HMAC bound to purpose and address, stored as a hash. `BumpAuthCodeAttempt` counts before the compare in one guarded UPDATE, `ConsumeAuthCode` is single use with an affected rows check, rows are bound to the session that asked, an `account_exists` or `no_account` row can never be confirmed, and a confirm deletes every other row of the address.
- **Session fixation and binding:** `rotate` always binds a freshly drawn id and never the request's. A session bound to another account has its push rows deleted and is revoked. `BindSessionAccount` never moves a bound row or revives a revoked one.
- **Cross site POST:** all six routes sit behind `http.CrossOriginProtection` and a strict `application/json` check with a 4 KB cap and no unknown fields.
- **Gates:** both `requireVerifiedAccount` and `requireModerator` treat `has_password = false` as signed out. `OnboardingDone` is the one predicate for the gate, `/welcome` and first-run-done, so a legacy account cannot loop, and first-run-done answers 409 with the field `profile` when a field is missing.
- **Usernames:** the shape rule equals the database CHECK, letters are ASCII only, `SetAccountUsername` enforces the 7 day gap in SQL as well as in Go, a lost uniqueness race (SQLSTATE 23505) maps to the taken sentence, a rejected screen is refused and an unjudged one saved as pending (D-16), and the live check never calls the screener.
- **Delete my account:** inside the transaction it deletes the cooldown, the code rows of the real address and the throttle row (the keyer is wired in `router.go:600-606`), and the scrub clears the password hash and frees the username.
- **Migrations:** 00014 Up adds the columns, constraints, tables and index, and revokes every live session of an account with no password. Down reverses the schema and states that the revoke cannot be undone. 00015 drops the link table, and its Down recreates the table as 00002 made it.
- **Logs:** no handler or service logs an address, a password or a code. The development log mailer prints the code and is refused outside `ENV=development`. Resend errors are reduced to a kind and a status.
- **Phase 5:** the session skip set (the PWA paths, the globe tiles, `/demo`, `/static`, the refresh POST) was already in place at the base and is unchanged. The six auth routes are outside the gate and inside the session middleware. The retired `/auth/verify` is a constant 303 that checks nothing.
