## Findings

### SK2-01 (warning): a timed out confirm that the server finished reloads to a blank entry card

**File:** `web/static/js/auth.js:335-350` (askServerAgain), `web/static/js/auth.js:731-746` (submitCode),
with `internal/service/credentials_signin.go:512-514` (LiveCode) and `internal/api/handlers/auth.go:222-238`
(LoginGate)

The SK-03 comment says that after a timed out code submit the server "draws the right screen". It
does not when the confirm committed:

- **Create account.** ConfirmSignUp commits the account, the password and a bind of a fresh session
  id. The fresh id only reaches the browser in the Set-Cookie of the answer the script aborted at 10 s.
  After the reload the browser still carries its old, unbound id. LiveCode sees `used_at` set and
  reports no live code, so the page shows the default Create account panel. The person is not signed
  in and nothing says the account exists. If they type Create account again they get the "account
  exists" email, which reads like an error.
- **Forgot password.** ConfirmReset commits the new password and logs every device out. After the
  reload the page shows the Create account panel with no "Password set. Sign in to continue." line,
  and the email is gone from the card. A person who then types the old password spends tries toward
  the per address lock.

If the server did not commit, the reload is fine: the live code brings the code screen back and the
person retypes the code (and the new password for a reset). Nothing loops, because a reload only
follows a submit the person made.

**Fix:** have LoginGate tell a code this session spent within ResumeWindow from no code at all. For
example, LiveCode (or a sibling) returns `spent=true, purpose` when the latest row has `used_at` set.
For a reset, render the Sign in panel with the email filled and the existing `PASSWORD_SET_MESSAGE`
line. For a sign up, render the Sign in panel with the email filled and a line saying the account is
ready to sign in with the password just chosen. Add an `auth_flow_test.mjs` case for a timed out
submit plus a handler test for the spent row render.

### SK2-02 (info): the refund keeps earlier failures in memory longer than the comment says

**File:** `internal/store/queries/auth_throttles.sql:116-133` (RefundSignInTry)

The comment says "the forget rule also reads the same". It does not: the reserve moved
`last_failure_at` from the old value L to this try's time, and the refund keeps the new time. So a
row that had `failures=4, last_failure_at` 29 minutes ago comes out of a busy answer with
`failures=4` remembered for 30 more minutes, where before it was forgotten one minute later. This only
makes things stricter. It never gives a guesser an extra check: a busy answer comes before any slot
is taken (`internal/auth/password.go:130-142`), and a later try changes `failures` and
`last_failure_at`, so the guard never undoes a try that was checked. Known and unknown addresses take
the same statement.

**Fix:** correct the comment to say the forget window restarts from the busy try, or return the old
`last_failure_at` and `locked_until` from the reserve (a CTE reading the old row) and restore them in
the refund.

### SK2-03 (info): on a weak but "online" connection the reload can land on the browser error page

**File:** `web/static/js/auth.js:341-348`

`navigator.onLine` is true on a captive portal or a 2G link that times out. Then `location.reload()`
fails and Safari shows its own "cannot open the page" screen in place of the card, which is the
outcome the offline check was meant to avoid. The typed code is lost, though the code screen comes
back on the next good load while the code is live.

**Fix:** before reloading, make a short GET to a small no-store endpoint (or to `/login` with a 5 s
limit). Reload only if it answers. If it does not, keep the offline line.

### SK2-04 (info): the 5 s margin between the 80 s client limit and the 75 s server window

**File:** `web/static/js/auth.js:39`, `internal/api/handlers/credentials.go:43-45, 159-163`

The client's clock starts before the request body is uploaded. The server's 75 s window starts in
`extendWriteDeadline`, after the body is read and the buckets have passed. On a slow uplink those
steps can take more than 5 s, and then the client gives up while the server can still answer. In
practice the server's own work is bounded near 64 s (a 60 s mail client, a 3 s slot wait and one
hash), so this is unlikely.

**Fix:** none needed. Optionally use 90 s for SEND_TIMEOUT_MS and say in the comment that the client
clock starts earlier than the server's.

### SK2-05 (info): one stored item is still not on the Policy list, and another line gives the wrong purpose

**File:** `web/templates/legal_body.html.tmpl:155-166`, `web/static/js/official-banner.js:275`

The three keys SK-09 added are real and described correctly: `pinalert.pushIntent` holds one account
number, `pinalert.changesAsked` holds a list of account numbers, and `pinalert.locationAsked.<account>`
is set to `'1'`. But `sessionStorage` key `pinalert.nearbyCentre` stores
`{account, lat, lon, savedAt}` for the official alerts nearby view. The only position line says
"so voting doesn't ask again", which does not describe this item.

**Fix:** add one line, for example "Your position and account number for a short time during a
visit, so official alerts near you load without asking again."

## Checked and clean

- **SK-01:** `clientIPHeaderFor` refuses an empty header only when `ENV` is not `development`. The README
  dev steps export `ENV=development`. No test starts the server binary, and `.github/workflows/ci.yml`
  only builds, vets and runs `go test`/`node --test`, so CI is unaffected. The README checklist
  explains how to run the canary before the first non development start (an echo service on the same
  host), and the header name check still applies everywhere.
- **SK-02:** the refund is guarded on the exact `failures` and `last_failure_at` the reserve returned,
  and on `failures > 0`. A parallel or later try changes both, so the refund never undoes a checked
  try. ErrHasherBusy is returned before a slot is taken, so a busy answer never checked a password and
  cannot be used for free guesses. Clearing `locked_until` restores the state before the try, because
  the reserve only updates an unlocked or expired row. A refund that fails or is cancelled keeps the
  try, which is the safe direction. Known and unknown addresses run the same statements and get the
  same ErrBusy.
- **SK-03:** a reload only follows a submit the person made and is skipped when the card has moved
  on (the generation check comes first), so it cannot loop. The 80 s limit applies only to the three
  sending calls.
- **SK-04:** `ResendCooldownSeconds` is copied before the live code branch overwrites `ResendSeconds`
  (auth.go:179 against :237). The script prefers it, and a page without the attribute falls back to
  the old value.
- **SK-05:** `pg_advisory_xact_lock(71, hashtext(ThrottleKey(email)))` is the first statement inside
  `inTx` in both ConfirmSignUp and ConfirmReset. The code bump in `proveCode` runs on autocommit before
  the transaction, so it holds no row lock. The key is a keyed hash of the normalised address taken
  from the code row in both paths, so it is stable for one address. A hashtext collision only makes
  two addresses wait for each other. `TestConfirmLockOrder` passed on the scratch database.
- **SK-06:** both the share check and the `shares[sender]++` are gated on `dayReserveInUse`, and the
  window's kept slots still go to the reset class. One sender can now take the whole window reserve,
  but the day reserve and its 3 per sender share still protect the 20 day slots.
- **SK-07:** the bind runs before the push delete and the revoke. A refused bind leaves the old
  session and its alerts alone. Inside ConfirmSignUp it all rolls back together. In SignIn a revoke
  that fails after a good bind leaves a bound id that no cookie carries.
- **SK-09:** see SK2-05. The three named keys match the code.
