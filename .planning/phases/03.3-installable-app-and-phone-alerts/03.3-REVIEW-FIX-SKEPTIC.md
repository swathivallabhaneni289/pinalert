## Warnings

### WR-01: S-01 docs now say every note except Reliable needs Live, which the code does not do

**Files:** `docs/TRUST-MODEL.md:549`, `docs/PUSH.md:80`

**Issue:** The wording is new in this diff. The sentences contradict each other and the code.

TRUST-MODEL.md says:
- "So every note except the Reliable one needs a Live report".
- Two sentences later: the now disputed and was marked resolved notes "are sent only while the resolver still gives Hidden or Retracted".

PUSH.md says:
- "because every phone note except the Reliable reporter one needs a Live report".
- The same bullet ends: "now disputed needs the feed to have hidden it".

What the code does:
- `eventStillHolds` (pushworker.go:493-498) sends `hidden` only while Hidden and `resolved` only while Retracted, so neither of those notes is ever about a Live report.
- The paragraph also says each note "is decided twice, once when it is queued", and it now lists `UpdateFading` among the predicate's kinds. But `changesFor` (pushdispatch.go:609-629) queues changed rows with no predicate. The fading check happens only at send time.

**Scenario:** A reader of the trust model doc, the portfolio's core write-up, is told that a non-Live report never produces a phone note. The worker then sends "now disputed" for a report that was Provisional and was hidden by disputes, so it was never Live. `TestTrustModelDocMatchesCode` passes because it does not parse this sentence.

**Smallest fix:** In both files, scope the sentence:
- "every note about a report still in the feed, except the Reliable one, needs a Live report", or
- "every note that announces a report rather than its leaving the feed".

In TRUST-MODEL.md, also say that a change note's predicate runs at send time only.

A note for the owner, not a finding: whether a "now disputed" note about a never-Live report fits D-07 is a product question. That behaviour existed before this diff.

### WR-02: after a key rotation the switch still reads On, and the new PUSH.md rotation sentence does not cover it

**Files:**
- `docs/PUSH.md:33` (commit d65c096)
- `web/static/js/notify.js:310-313` (`inspect`) and `notify.js:463-470` (`reconcile`)

**Issue:**
- B-02 added the key check only on the `ready` branch.
- Right after a rotation the server row still exists. 403 counts as a device failure, but `countFailure` deletes only when the last success is more than 7 days old (`PushDeviceStaleAfter`, pushworker.go:86, 774).
- So `inspect` gets `registered: true` and returns `{state: 'on'}`, and `reconcile` returns `'on'` before `sameKey` runs.

The old PUSH.md text ("turn On this device off and on again") was right for this case. The new text ("Turning On this device on again replaces the old browser subscription") is not, because the switch already reads On. The browser fixer flagged the off then on case in its report, but the doc edit dropped it.

**Scenario:**
1. The operator rotates the keys.
2. A person who received an alert yesterday opens Settings and sees On this device switched on.
3. Every send to that device fails with 403, and the row survives for at least 7 days.
4. Following the docs, there is nothing to turn on.

**Smallest fix:** Pick one.
- Docs only: restore "If the switch still shows on, turn it off and on again; if it shows off, turning it on replaces the old subscription."
- Code: in `inspect`, when `sub` exists and `!sameKey(sub, key)`, skip the status call and return `{state: 'ready', sub: sub, known: true}`. The switch then reads off, and one tap runs `enable`, which drops the old-key subscription.

### WR-03: S-05 still cancels a send in transit at SIGTERM, so a duplicate can still follow a redeploy

**Files:** `internal/service/pushworker.go:606` with `cmd/server/main.go:451-461`

**Issue:**
- `fanOut` builds `sendCtx` from the run context, which `serveUntilDone` cancels first on a signal.
- A request already on the wire is aborted. It is classed as a transport failure and rescheduled on the WithoutCancel write context.
- If the push service had already accepted it, the row is sent again after the restart. That is the duplicate S-05 described, with the window moved from "after the 201" to "before the 201 is read".
- `shutdownGrace` is sized for "one fan out (service.PushSendTimeout), then its marks", which this code never lets finish. The fixer listed this as a residual.

**Scenario:**
1. A Render redeploy sends SIGTERM 200 ms after the worker POSTs a Critical alert to Apple.
2. Apple delivers it, but the cancel aborts the read of the 201.
3. The row is retried after the new instance starts, and the iPhone shows the alert twice.

**Smallest fix:** In `fanOut`, use `sendCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), PushSendTimeout)`. The worker loop already stops claiming on `ctx.Done()`, and the 25 s grace covers the 10 s send plus the 10 s marks.

## Info

### IN-01: a second Ctrl-C is swallowed during the shutdown grace

**File:** `cmd/server/main.go:429-430`

**Issue:** `stopSignals` runs only when main returns. Until then `signal.NotifyContext` keeps catching SIGINT, so a developer's second Ctrl-C does nothing for up to 25 s. The wait is bounded, so this is a convenience issue only.

**Fix:** Call `stopSignals()` right after `runCtx` is done, for example in a small goroutine `go func() { <-runCtx.Done(); stopSignals() }()`. A second signal then gets the default behaviour back.
