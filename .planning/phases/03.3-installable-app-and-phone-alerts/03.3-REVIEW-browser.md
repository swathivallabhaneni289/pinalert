## B-01: The renewed subscription is registered for whoever is signed in, skipping the shared device rule

- **Severity:** medium
- **File:** `web/static/js/sw.js:122-139` (the POST at 130-135)
- **Defect:** on `pushsubscriptionchange` the worker subscribes again and POSTs the new subscription to `/api/me/push/subscription` under whatever session cookie the browser holds, with no check that the old endpoint belonged to that account and no intent check (a worker cannot read `localStorage`), so it bypasses the account check that `notify.js:22-25` and 03.3-06-SUMMARY deviation 1 promise.
- **Failure scenario:**
  1. Account A turns On this device on in Firefox (the browser that fires `pushsubscriptionchange` with an `oldSubscription`).
  2. A uses plain Log out (`account-menu.js:232`, a form post) or Log out of all devices (`settings-alerts.js:498-519`). The server deletes A's row (03.3-10), but nothing on the client unsubscribes, so the browser subscription stays (recorded as intended in 03.3-10-SUMMARY, used here only as the precondition).
  3. Account B signs in on the same browser and never touches On this device.
  4. The push service expires or resets the subscription and `pushsubscriptionchange` fires.
  5. The worker subscribes again and POSTs under B's cookie. The upsert (`internal/store/queries/push.sql:21-24`) stores the new endpoint for B.
  - **Wrong result:** B now receives Critical and Changes notifications on a device B never turned on, and B's Settings shows On this device as on (the status check confirms the endpoint for B). B's alert titles appear on the lock screen of A's phone. The same path silently re-enrols A after A logged out, and re-registers a subscription left behind by a failed enable (400 or 503) that the person saw as off.
- **Smallest fix (browser only):** in the handler, ask the server first whether the old endpoint is this account's, and re-register only then. The Settings reconcile still covers the remaining cases through its intent check.

```js
self.addEventListener('pushsubscriptionchange', function (event) {
  var old = event.oldSubscription;
  if (!old || !old.endpoint || !old.options || !old.options.applicationServerKey) return;
  function postJSON(url, body) {
    return self.fetch(url, {
      method: 'POST',
      credentials: 'same-origin',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(body)
    });
  }
  event.waitUntil(
    postJSON('/api/me/push/status', { endpoint: old.endpoint }).then(function (res) {
      return res.ok ? res.json() : null;
    }).then(function (answer) {
      if (!answer || answer.registered !== true) return null;
      return self.registration.pushManager.subscribe({
        userVisibleOnly: true,
        applicationServerKey: old.options.applicationServerKey
      }).then(function (sub) {
        return postJSON(SUBSCRIPTION_URL, sub);
      });
    }).catch(function () {})
  );
});
```

The test `web/pwa_sw_test.mjs:244` needs a status answer added to its fetch stub.

## B-02: After a server key change, Allow alerts and the device switch fail for good, and reconcile shows a dead device as on

- **Severity:** low (needs the operator to change the key pair, which docs/PUSH.md:33 discourages but describes)
- **File:** `web/static/js/notify.js:358-362` (enable) and `notify.js:419-429` (reconcile)
- **Defect:** `enable` calls `pushManager.subscribe` with the current key without first removing an existing subscription made with a different `applicationServerKey`, and `reconcile` re-posts that old key subscription without comparing keys.
- **Failure scenario:**
  1. Account A turned On this device on with key pair K1.
  2. The operator changes to K2. Every send to A's device is answered 403. After 5 such answers and no success for 7 days, the push worker deletes the row (`internal/service/pushworker.go:78-86`, `679`).
  3. Case one, the same account: A opens Settings. `inspect` finds the K1 subscription, the server says not registered, the intent matches, and `reconcile` posts it again. The switch shows on, yet every send fails with 403 until the row is deleted again, and the cycle repeats on each Settings visit.
  4. Case two, another account on that browser (step 5 of the welcome flow, or Settings): the switch shows off. Allow alerts or the switch calls `enable`, which calls `subscribe` with K2 while the K1 subscription exists. Chrome and Firefox reject this with InvalidStateError, so the person sees "Couldn't turn alerts on. Try again." (welcome) or "Couldn't turn this on. Try again." (Settings) on every tap. The off then on recovery that PUSH.md:33 describes is not reachable, because the switch is already off.
- **Smallest fix:** in `enable`, after the registration is ready, read `getSubscription()`. If it exists and its `options.applicationServerKey` bytes differ from `keyBytes(key)`, `unsubscribe()` it before `subscribe`. In `reconcile`, skip the re-post (return `ready`) when the stored subscription's key differs from the page key.

```js
return readyRegistration().then(function (registration) {
  var want = keyBytes(key);
  return registration.pushManager.getSubscription().then(function (old) {
    if (old && !sameKey(old.options && old.options.applicationServerKey, want)) {
      return old.unsubscribe();
    }
  }).then(function () {
    return registration.pushManager.subscribe({ userVisibleOnly: true, applicationServerKey: want });
  });
})
```

where `sameKey` compares the two byte arrays.
