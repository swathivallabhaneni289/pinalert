# Phase 3.3 templates, CSS and icons review

Nothing here breaks the page or a product rule. The four defects below are small, and one of them (T-01) matters for the iPhone-only install guide. `go test ./web/ -short -count=1` passes. I judged layout from the CSS and markup only. No server, browser or database was used.

## What was checked and held up

- Copy: every string in the step 5 template, the guide partial and the Notifications box matches the UI-SPEC copy table word for word (P33-C2 to C7, C11 to C16, N1). A scan of the templates for buzz, vibrate, sound, ring, silent, quiet and hear found no user-visible hit. No "of 4" is left anywhere. No dash appears in any new string.
- Hidden elements: every `display` rule on something that carries `hidden` is guarded.
  - `.place-row:not([hidden])` in places.css:56
  - `.welcome__alerts-part:not([hidden])`
  - `.device-guide__step:not([hidden])`
  - `.welcome__actions .btn[hidden]`, which beats `.btn` inline-flex
  - `.inline-error:not([hidden])` in chrome.css
  - `.welcome__lead` and `.welcome__card-body` set no display, so the attribute works on them.
- Owner rule: `.welcome__title:focus { outline: none }` is kept (welcome.css:~170). Step 5 uses `tabindex="-1"` and the same h1 pattern as steps 1 to 4.
- app_head: the theme-color values #FFFFFF and #0B0D10 equal `--color-bg` light and dark (main.css:124, 170, 207). Every template that has a `<head>` includes `app_head` (check_inbox is a partial that login_gate includes). There is no duplicate icon, manifest or theme-color tag elsewhere.
- Icons: share.svg and square-plus.svg match the Lucide v1.41.0 geometry and the attribute block of bell.svg and chevron-right.svg (viewBox 24, stroke 2, round caps, currentColor). They are raster-free. The masks are literal `url("/static/icons/...")`. Forced-colours handling of mask icons is covered globally by app-bar.css:433.
- Settings order matches Surface 2: On this device, Critical, Changes, Reliable, distance. Each variant pair sits in a never-hidden wrapper, so the box hairline is drawn once per wrapper. The distance row and the Critical and Reliable switches are hidden with no home area, and the "Add a home area first" buttons appear instead.
- Touch targets: `.place-row` has min-height 52, `.welcome__back` 44, `.btn` 48, and the switch row is a whole-row label. The new rows have no fixed height, so long labels wrap at 320 px.
- Guide window: `role="dialog"`, `aria-modal`, `aria-labelledby`, the X as the only control in the body, and no hint text under any option.

## Findings

### T-01 (medium) Install guide steps lose their list semantics in Safari

**File:** `web/static/css/device-guide.css:20-26` with `web/templates/device_guide.html.tmpl:15`

**Defect:** The guide is an `<ol>` styled with `list-style: none`, and Safari with VoiceOver drops list semantics from such a list unless it carries `role="list"`. UI-SPEC "Interaction and Accessibility" requires "a screen reader reads 1 of 3".

**Failure scenario:** This guide shows only on an iPhone or iPad in a Safari tab, that is the exact browser that strips the semantics. At any width, light or dark, with VoiceOver on, step 5 "Install to get alerts" and the Settings guide window read three unrelated paragraphs. There is no "list, 3 items" and no "1 of 3". The ordered-steps cue is lost for the one audience that sees this component. The repo already uses the fix on its other `list-style: none` ordered lists (moderate.html.tmpl:39, 46 and 53).

**Fix:** In device_guide.html.tmpl change `<ol class="device-guide__steps">` to `<ol class="device-guide__steps" role="list">`.

### T-02 (low) Guide lead spacing stacks on the container gap, so it differs by place

**File:** `web/static/css/device-guide.css:9-14` (`.device-guide__lead { margin: 0 0 var(--space-12) }`)

**Defect:** The lead keeps a 12 px bottom margin, but both containers already space their children. Flex margins do not collapse, so the gap is not the contract's 16 px in either place.

**Failure scenario:** At 390 px (and the same at 320 and 1280), on an iPhone in a Safari tab:
- Step 5 `needs-install`: the lead sits in `.welcome__alerts-part`, a flex column with `gap: 16px`. The gap between the lead and the steps box is 16 + 12 = 28 px, against 16 px between every other block in the flow.
- The Settings window: `.app-window__body` has `gap: 8px`, so the gap there is 8 + 12 = 20 px.

The same component is spaced differently in its two places.

**Fix:** Set `margin: 0` on `.device-guide__lead` so the container gap alone spaces it (16 px in the step). Optionally add `.app-window__body > .device-guide__lead { margin-bottom: var(--space-sm) }` to keep the window at 16 px.

### T-03 (low) Blocked and unsupported rows still show the pointer cursor

**File:** `web/static/css/places.css:~58-70` (`.place-row { cursor: pointer }`), reached by `web/templates/settings.html.tmpl:80` and `:86`

**Defect:** The Surface 2a blocked and unsupported rows are "not a control (no chevron, no hover)". They are plain `div.place-row` elements and inherit `cursor: pointer`.

**Failure scenario:** On the laptop (1280 px, either theme), with the browser permission denied, hovering "On this device / Blocked in your browser settings..." shows a hand cursor. It signals a clickable row that does nothing.

**Fix:** Add `.place-row:is(div) { cursor: default }`, or give the two rows a modifier class (for example `place-row--static`) with `cursor: default`. The existing `#settings-radius-row` div has the same cursor, but it holds a working select.

### T-04 (low, check with a real screen reader) The step 5 refusal status line is unhidden and filled in the same moment

**File:** `web/templates/welcome.html.tmpl:194` (`<p ... id="welcome-alerts-status" role="status" hidden>`)

**Defect:** The `role="status"` region is `hidden` (display: none) until the refusal, so the region and its text appear together. Several screen readers, VoiceOver on iOS in particular, do not announce a live region that is created or shown at the same time as its content.

**Failure scenario:** At 390 px on an iPhone with VoiceOver, the person taps Allow alerts and refuses in the browser prompt. The buttons are replaced by Continue, and "Alerts are off on this device." may never be spoken. The person hears nothing about the result. The Settings side avoids this by using the always-present `#notice-live`.

**Fix:** Keep an always-present empty `role="status"` element (visually-hidden or zero-height, not `hidden`) and have `welcome.js` write the sentence into it. Show the visible line separately, or drop `hidden` from the status element and toggle only its text.
