# Phase 3.3 Plan 11: The push worker and the server wiring Summary

**A worker that sends the queued phone alerts only after reading the report, the event, the switches and the mute again, only while it holds the row's lease, with every push service answer handled per device, plus the pokes from posting and voting and the VAPID startup wiring.**

## What was built

- `internal/service/pushworker.go`: `PushWorkerQuerier` (with the `*sqlcgen.Queries` assertion), `PushWorker`, `NewPushWorker`, `Run`, `SweepOnce`, `PushBackoff`, `sendErrorClass`, and the constants of the plan (`PushWorkerInterval` 5 s, `PushClaimBatch` 50, `PushLeaseSeconds` 60, `PushLeaseMargin` 20 s, `PushSendConcurrency` 8, `PushSendTimeout` 10 s, `PushMaxAttempts` 4, `PushBackoffBase` 15 s, `PushBackoffCap` 5 min, `PushDeviceFailureLimit` 5, `PushDeviceStaleAfter` 7 days). A compile time constant fails the build if the lease is shorter than a row's fan out plus its margin.
- `sendRow` order: renew the lease (a lost renewal logs `lease_lost` and ends the row with no read, send or mark); read the report through `loadPushFacts`; stale when under one second of life is left or now is at the row's own expiry; the kind's predicate (`MayNotifyAboutReport` for Critical and Reliable, `Confirmed` plus active for a confirmed update, `eventStillHolds` for a changed row, W4); `PushAccountHome` for the mute and the switch of the row's kind, a confirmed update following the switch of the alert it updates (W5); home area and distance measured exactly as the dispatcher measures them; the hourly cap (not for confirmed updates); the live devices with the host taken from `policy.Check` and never from the stored column (N6); `BuildPushText` words from current facts; one fan out of at most 8 sends under one 10 s context; each answer settled per device; one mark carrying the renewed lease.
- Answers: 2xx marks the device fine; 404 and 410 delete it; 429, 5xx, timeouts, canceled sends, network errors and refused addresses never count against a device and back off by `PushBackoff` (at least the longest Retry-After), never past the row's or the report's expiry and at most 4 attempts; 400, 403 and a policy refusal add one to the failure count; a device is deleted only at the limit and when its last success is missing or over 7 days old (W6). Once one device accepted a row it is sent and the failed devices are not retried for it.
- Words: `sent_unconfirmed` is set exactly when the body says Not confirmed yet. Message: Payload V 1, Kind the row kind, Tag `report-{id}`, URL `/?report={id}`, Topic `r{id}`, Urgency high for Critical only, TTL the report's remaining life up to an hour for Critical and 30 minutes for the rest.
- Logs and the sweep's returned error hold row, account, report and device ids, a status, the host and a class word, nothing else. `sendErrorClass` maps an error to `timeout`, `canceled`, `refused_address`, `policy`, `payload` or `network` and the error value is dropped at once (W3).
- `report.go` and `trust.go`: the `notifier` field, `WithReportChangeNotifier` and `WithVoteChangeNotifier`, and one guarded poke each: after a stored report (just before the success return, so a replay and every refusal return earlier) and right after `InsertVote` succeeds. No decision in `SubmitChecked` or `CastVote` changed.
- `cmd/server/main.go`: `push.LoadConfig(os.Getenv)` at startup (a half set or bad config stops startup with `log.Fatalf`; both unset logs the warning and runs neither goroutine), `Page.PushPublicKey`, the `lateUpdates` adapter, the notifier options added only when push is on (a nil dispatcher is never stored in the interface), and the dispatcher and worker started next to the moderation worker with one shared endpoint policy value.

## Deviations from Plan

1. **[Interpretation] The submit poke uses actor 0.** Task 2's behaviour text says `ReportChanged(new report id, account id)`; the dispatcher's own contract ("the voter, or 0 for a new report") and the wave notes say 0. `TestSubmitPokesNotifier` asserts 0. With the account id the changes branch would run for a brand new report for no reason.
2. **[Rule 2] A confirmed update gets the home area and radius check.** The plan applies step 5 to critical and reliable only, but `BuildPushText` refuses a critical or reliable input with no distance, so a confirmed update needs one; applying the same range check keeps it consistent with the alert it replaces.
3. **[Rule 2] A critical row needs a serious report at send time**, in addition to the shared predicate. The dispatcher never queues otherwise; this only closes an impossible case.
4. **[Rule 2] Post send writes use a shutdown proof context** with a new unexported `pushWriteTimeout` (10 s); the plan lists no such constant.
5. **[Detail] Statuses not in the plan** (401, 413, other 3xx and 4xx) end the row as failed and count nothing; `ErrBadKeys` reads as the `policy` class (counts against the device), and `ErrNoTTL`, `ErrBadTopic`, `ErrBadUrgency` and `ErrPayloadTooLarge` read as `payload` (our fault, not retried, not counted).
6. **[Test placement] The poke tests live in package `service`** (internal) so they can reuse `fakeVotingQuerier`; the submit side uses a tiny fake that embeds a nil `Querier`, so any call outside the three methods `SubmitChecked` uses would panic loudly. No database was needed for the poke tests.
7. **[Verification wording] "Zero `--- SKIP` lines" cannot hold for the whole `internal/service` package** because `TestScreeningFixture` skips by design (pre-existing, outside this plan). It is the only skip.
8. Extra test `TestSendErrorClass` (the closed class words) and `TestWorkerSweep` (sweep order, the claim parameters, stopping between rows, `Run`), beyond the plan's list.
