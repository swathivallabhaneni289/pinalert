# Phase 3.3 Plan 13: Step 5 Alerts of the first-time flow Summary

Step 5 asks for alerts in the app's own words before the browser's prompt, with four device variants, an example notification printed from the Go builder, and first-run-done now sent only from step 5; every pinned test that counted four steps counts five.

## What was built

- **Server** (`internal/api/handlers/welcome.go`): `welcomeSteps` gains "Alerts"; `welcomeViewModel` gains `PushPublicKey` (from `cfg.PushPublicKey`), `HasHomeArea` and `AlertExample` (from `service.AlertExample()`). The page still never learns a position.
- **Template** (`web/templates/welcome.html.tmpl`): every label reads "Step n of 5"; the flow root carries `data-push-key`; `section#welcome-step-5` has the Back control, the title, the ready part (lead, one Critical card with the home area line, `div.welcome__example` as a group named Example notification with the app mark from `/icons/app.svg`, the closing line), the install part (`{{template "device_guide"}}`), the blocked and unsupported sentences, `#welcome-alerts-status` (role status), `#welcome-alerts-error` (role alert) and the three buttons. device-guide.css is linked.
- **Script** (`web/static/js/welcome.js`): `deviceVariant`, `drawAlerts`, `enterAlerts`, `onAllowAlerts`, `onNotNow`, `onAlertsContinue`, plus `alertsDone`, `needAgreement`, `toAlerts`, `onAlertsResult`, `setAlertsBusy`. Step 4's Continue (after the profile save) and Skip call `goTo(5)`; `postDone` has one caller, `alertsDone`. On arrival the base state is read at once and drawn before focus moves to the title (so a screen reader hears "Install to get alerts" on an iPhone tab), then `deviceState(key)` redraws unless the person left, the step is busy, or a refusal is showing.
- **CSS** (`web/static/css/welcome.css`): five even progress stops (20 to 100), `.welcome__alerts-part`, `.welcome__example`, `-mark`, `-tag`, `-title`, `-body`, and `.welcome__actions .btn[hidden]` (see Deviations). The owner rule `.welcome__title:focus { outline: none; }` and its audit29 row are untouched.
- **Noise contract**: `noiseCheckedFiles` gains `static/js/sw.js`, `templates/app_head.html.tmpl`, `templates/welcome.html.tmpl` and `static/js/welcome.js`; all scan clean.

## Deviations from Plan

**1. [Rule 3 - Blocking] welcome_flow_test.mjs amended (not in files_modified)**
- **Found during:** Task 2. The harness page had four step sections, so `goTo(5)` was refused and every case that finished from step 4 failed.
- **Fix:** the harness gains the step 5 ids, "Alerts" in the step names, five entry state arrays, a default fake `PinalertNotify`, and the finishing cases click Not now on step 5 (request indices stay the same). Dated notes added. **Commit:** b85dff3.

**2. [Rule 3 - Blocking] Disagree box ban on a status region re-scoped**
- **Found during:** Task 1. `TestWelcomeStep2ReadsTheSharedText` banned `role="status" hidden>` over the whole page, which step 5's required status line now matches.
- **Fix:** the ban now covers the Disagree box markup only (the box is a group that takes focus), with a dated note. **Commit:** cc90649.

**3. [Rule 1 - Bug] `.btn[hidden]` rule added to welcome.css**
- `.btn` sets `display: inline-flex`, which outranks the native hidden attribute, so Continue (hidden by default) and the buttons hidden in the other variants would have stayed visible. The plan's `:not([hidden])` pattern cannot help a base rule that is always on, so `.welcome__actions .btn[hidden] { display: none; }` was added. **Commit:** cc90649.

**4. Test renamed.** `TestWelcomeFourStepsInOrder` is now `TestWelcomeFiveStepsInOrder` (the plan allowed the existing name or an amended one; the old name would have been false). Nothing else referenced it.

**5. DB verify command widened.** The plan's `-run 'TestWelcome'` misses `TestOnboardingFlowEndToEnd` and `TestExistingAccountSeesFlowOnce`, which hold the "Step n of" pin; I ran `TestWelcome|TestOnboarding|TestExistingAccount|TestHomeCentre` and then the whole `./internal/api/...` and `./web/` packages with `-p 1`.

**6. Server sentence on a 400.** notify.js returns the server's own sentence as `result.message`; step 5 shows it in place of "Couldn't turn alerts on. Try again." when present (tested). All other failures use the UI-SPEC line exactly.

**7. Agreement guard (small addition).** Allow alerts, Not now and Continue send a person who has not agreed back to step 2 without running the prompt or sending anything, the same rule `finish` already applies. Tested.
