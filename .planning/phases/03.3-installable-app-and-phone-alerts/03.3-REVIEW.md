# Phase 3.3 gap fix: Code Review Report

**Reviewed:** 2026-10-28
**Depth:** standard
**Files Reviewed:** 17 (tests read only to judge what they prove)
**Status:** issues_found

## Summary

The server half holds up. The cap order, the Critical exemption, the hidden replay and the Apple
filter do what the gaps ask, and fanOut and settle are untouched. The browser half has two ways to
leave a person stuck behind a modal box that cannot be answered:

- the changes pop-up can open over the report form or the Flag box, which have already made it
  inert;
- neither pop-up has a time limit on the browser's push calls.

The Apple rule is keyed per account rather than per device. The Low data re-measure followed the
procedure in form, but its write-up hides about 82 KB of growth that came from before this range.

### Checked and clean

- `fanOut` and `settle` are not in the diff.
- `heldByHourlyCap` holds at `sent >= PushPerAccountPerHour`, the same `>= 4` as before, so
  there is no off by one. Critical and confirmed update return false.
  `CountAccountPushesInWindow` still lists `critical`, so a sent Critical counts.
  `TestWorkerCriticalNeverHeldButCounted` and the e2e `TestPhoneAlertCapShowsNothingExtra` prove
  that a later Reliable or changed push is then held.
- A confirmed update is neither counted nor held, and never goes to an Apple device.
- `VoteLogForReport` is read only for a changed row whose event is hidden. `TestWorkerReadsVoteLogOnlyForHidden`
  pins this. `AccountPushSentAboutReport` is read only when an Apple device is in the list.
- **The vote log replay in `reportWasConfirmed`:**
  - Ordering by `created_at, id` ascending, with the last row per (account, kind) kept, matches
    the `DISTINCT ON ... created_at DESC, id DESC` of `CurrentVotesForReports`.
  - The reporter's content votes are dropped by `filterVoteRows`.
  - `Resolve` ignores `now`, so replaying with the current time is safe.
  - The `votes` table has no delete path, so the log is complete.
- **The Apple filter:** the Apple check is per device, so in a mixed device list the Google
  device still gets the push. The host comes from `policy.Check`, never from the stored column.
- **The bell row for a hidden report:** it is still written when the push is skipped.
  `pwHiddenRows` in `pushworker_hidden_db_test.go` asserts the `updates` row for both the
  confirmed and the never confirmed report.
- **Endpoints and keys:** none is placed in a URL or a log line.
  - The `apple_repeat` log line carries only row and device ids.
  - `changesAskFor` logs the numeric account id and the error.
  - notify.js sends the endpoint only in a POST body.
- **Escaping of the home area name:** `data-home-area` and the `<h2>` title are html/template
  attribute and text contexts. welcome.js writes the title with `setText`, which is
  `textContent` (welcome.js:225). Search results are not parsed as markup.
- **localStorage:** every access is inside try (notify.js 134 to 158, changes-ask.js 96 and 118).
  A throwing store means no re-register and no pop-up.
- **Log out keeps what the re-register needs:** the client side of Log out is a plain form post.
  There is no `Clear-Site-Data` header and no `removeItem` or `disable()` on that path, so the
  intent flag and the browser subscription survive. The re-register can fire.
- **A different account:** `intentIsSet` compares against `data-account-id`, so it never
  re-registers for a different account.
- **The first real statement of each Allow tap:** in welcome.js:1182 to 1184 and in
  changes-ask.js:213 to 215, `enable(...)` comes first after synchronous guards only.
- **Not now and Escape:** they save nothing in either pop-up.

## Critical Issues

### CR-01: The changes pop-up can open over the report form or the Flag box, inert and impossible to answer

**File:** `web/static/js/changes-ask.js:99` (canOffer), triggered from `web/static/js/report-form.js:1424` and `web/static/js/votes.js:566`

**Issue:** `canOffer` refuses to open only when a native `dialog[open]` exists. The report
form, the Flag box and the reader window are not `<dialog>` elements. They lock the page with
`Pinalert.lockPage` (app.js:1251), which:

- walks from their backdrop up to `body`;
- sets `inert` on every sibling along the way;
- marks the root with `data-modal-open`.

`#changes-ask` is a direct child of `body` (index.html.tmpl:226, low.html.tmpl:113), so the lock
makes it inert. `showModal()` does not clear `inert`.

Concrete path:

1. A person posts a report and closes the form while the post is still out.
2. They open a new report form, so the page is locked and `#changes-ask` is inert.
3. The first post's answer arrives. report-form.js:1424, the `sent.session !== formSession`
   branch, calls `offerChangesAsk()`.

`canOffer` sees no `dialog[open]`, writes `pinalert.changesAsked` and calls `showModal()`. The
result:

- The pop-up is in the top layer, but it is inert, so Not now and Allow cannot be tapped and
  `title.focus()` fails.
- Modality blocks everything else, including the report form.
- On an installed iPhone app (base state `maybe`) there is no Escape key and no back gesture,
  so the person is stuck until they kill the app.

The same happens when a confirm or dispute is saved (votes.js:566) after the person opened the
Flag box while the location fix and the POST were running. It breaks the requirement that the
pop-up never stacks on another box.

**Fix:** treat the custom modals like a native one, before the key is written:

```js
if (document.querySelector('dialog[open]') ||
    document.documentElement.hasAttribute('data-modal-open')) {
  return '';
}
```

Add a test that sets `data-modal-open` on the root and expects no open, no stored key and a
resolved `settled()`.

### CR-02: No time limit on the browser's push calls, so a pop-up can stay busy forever and settled() never resolves

**File:** `web/static/js/notify.js:413-423`, consumed at `web/static/js/changes-ask.js:228` and `web/static/js/welcome.js:1193`

**Issue:** `enable` wraps only `serviceWorker.ready` and the POST in `withTimeout`. Three calls
are awaited bare:

- `pushManager.getSubscription()` (413);
- `existing.unsubscribe()` (415);
- `pushManager.subscribe(...)` (419).

If any of them never settles, nothing ends the wait. Examples:

- a push service the browser cannot reach;
- a browser build with a broken push stack;
- a subscribe stuck behind a service worker update.

The effect in each pop-up:

- **changes-ask.js:** `Promise.resolve(pending).then(save, save).then(finish, finish)` never
  reaches `finish`. The dialog stays modal with both buttons disabled. `onCancel` prevents
  Escape and `onLater` returns while `busy`. `current` never resolves, so `settled()` never
  resolves either. The brief requires that it does, because Phase 9 plan 09-17 waits on it
  before its star box.
- **welcome.js:** the same chain was rebuilt by plan 19 at line 1193, so `postDone` is never
  reached. That contradicts "sign up must always finish, whatever happens".

This wait existed before this diff, but the diff rebuilt both chains and states this guarantee.

**Fix:** keep the permission prompt unbounded, because that wait is the person's own choice.
Bound the three browser calls inside `enable`. Its first synchronous statement stays the
`requestPermission` call:

```js
return withTimeout(Promise.resolve(registration.pushManager.getSubscription())).then(function (existing) {
  if (existing && !sameKey(existing, key)) {
    return withTimeout(Promise.resolve(existing.unsubscribe()));
  }
  return null;
}).then(function () {
  return withTimeout(Promise.resolve(registration.pushManager.subscribe({
    userVisibleOnly: true, applicationServerKey: keyBytes(key)
  })));
})
```

Add tests where `subscribe` returns a promise that never settles. They should expect changes-ask
to close and resolve, and welcome to reach first-run-done, after `REQUEST_TIMEOUT_MS`.

## Warnings

### WR-01: The Apple first push rule is per account, so an Apple device that never got the first push gets nothing about the report

**File:** `internal/service/pushworker.go:503-524`, `internal/store/queries/push.sql:564-575`

**Issue:** `AccountPushSentAboutReport` asks whether any row about the report reached state
`sent` for the account. `settle` marks a row sent when any one device accepted it
(pushworker.go:879). Two cases go wrong:

1. **Transient failure.** An account has a Chrome laptop and an iPhone. A Critical push reaches
   Chrome, but the iPhone gets a 5xx or a timeout. The row is sent and the iPhone is not
   retried; that part predates the diff. Every later push about the report (reached live, now
   disputed, resolved) is now also withheld from the iPhone as `apple_repeat`. The iPhone ends
   with zero notes about a report the rule says it should hear about once.
2. **A device added later.** A person turns on alerts on their Mac Safari after the first push
   went to their Android phone. The Mac never hears about that report.

The gap text says "only the first push about a report is sent" *to that device*. The
implementation's comment admits it is per account and report.

**Fix:** record per device delivery. One option is a `push_report_devices (subscription_id,
report_id)` row written in `settle` for each accepted Apple device; the filter then reads it per
device. A cheaper proxy without a table: skip an Apple device only when its
`push_subscriptions.last_ok_at` is at or after the earliest `sent_at` about this report for the
account. Add a test: the first push is accepted by Google and fails for Apple, then the second
push still reaches Apple.

### WR-02: The load-time re-register can land after Off in Settings and bring the endpoint back

**File:** `web/static/js/notify.js:447-475` (disable), `480-529` (runReconcile and reconnectAtLoad)

**Issue:** `pending` is shared only through `reconcile`. Sequence on the Settings page:

1. `reconnectAtLoad` is between its status answer (`known: true`) and its `POST
   /api/me/push/subscription`.
2. Settings has drawn the switch, and the person taps Off.
3. `disable()` posts `/unsubscribe`, which wins the race. It clears the intent flag and calls
   `subscription.unsubscribe()`.
4. The re-register POST then arrives and the upsert puts the row back.

If `unsubscribe()` failed in the browser (the swallowed rejection at line 466), the endpoint is
still live. The person then keeps getting pushes on a device Settings shows as off.
`enable()` racing the load check is harmless (both upsert), but `disable` is not.

**Fix:** in `disable` (and `enable`, for order), wait on the load check first:

```js
var before = pending !== null ? pending.then(noop, noop) : Promise.resolve();
return before.then(function () { /* existing body */ });
```

`runReconcile` should also re-read `intentIsSet()` just before its POST.

### WR-04: "Once per account per browser" holds only one account id, so a shared phone re-asks

**File:** `web/static/js/changes-ask.js:96, 118`

**Issue:** `pinalert.changesAsked` holds a single id. Account A is asked, then account B on the
same browser is asked and the key becomes B. When A signs back in, A is asked again, and the
same happens on every switch. The test "storage holding another account id opens for this one
and writes this one" pins this behaviour. It breaks the stated rule, on exactly the shared
family phone this product designs for.

**Fix:** store a small JSON array of asked ids, for example capped at 20. Treat a parse failure
as "do not open", to keep the fail-closed stance.

### WR-05: In the sign up pop-up, a failed home area save silently drops Reliable and leaves Critical alerts with nothing to match

**File:** `web/static/js/welcome.js:1138-1151, 1193-1201`

**Issue:** if the PATCH of the home area picked in the pop-up answers 400 or times out:

- `homeName` stays empty, so `wantReliable && homeName !== ''` quietly skips the Reliable save;
- the device was already turned on by `enable`;
- the title the person read said "near {picked place}";
- sign up then finishes with no word.

This is the exact failure the 03.3-UAT gap for test 4 was filed against: Allow delivers nothing
and nothing says why. It now happens on the error path.

**Fix:** keep sign up finishing, but carry the outcome. For example, write the failure to
`sessionStorage` and show one line on the first page: "Your home area was not saved. Add it in
Settings to get alerts." Alternatively, show the profile error line in the pop-up and offer
Allow again. In either case add a test for a 400 on the home save with the tick box ticked.

## Info

### IN-01: Critical pushes now have no per person ceiling at all

**File:** `internal/service/pushworker.go:562-568`

**Issue:** this is the owner's decision. Note the result for the trust model: the only bound
left on Critical lock screen alerts is `PushCriticalReportsPerReporterPerHour` per reporter. N
signed up accounts posting Critical reports near one area can push N times that limit to every
person there in an hour. This is the gaming surface the Core Value warns about.

**Fix:** consider a high backstop for Critical only (for example 12 an hour), or document the
bound in docs/TRUST-MODEL.md.

### IN-02: The automatic re-register trusts a subscription that does not report its key

**File:** `web/static/js/notify.js:193-197`, used at `486`

**Issue:** `sameKey` returns true when `options.applicationServerKey` is missing. The requirement
"the kept subscription used the current key" is therefore not checked on such browsers, and the
check now runs on every page load without a tap. After a key rotation, such a browser
re-registers a dead subscription. The worker then wastes sends on it until the failure count
drops it.

**Fix:** in `runReconcile` only, require a readable key, for example
`asBytes(found.sub.options && found.sub.options.applicationServerKey) !== null`, before
posting. Settings' tap path can keep the lenient rule.

### IN-03: A dialog closed by the browser without the cancel handler leaves changes-ask in a stale state

**File:** `web/static/js/changes-ask.js:240-249`

**Issue:** Chrome's close watcher can close a modal dialog without a cancelable `cancel`. That
happens on a second Escape with no user activation in between, for example Escape twice while
Allow is busy. Nothing listens for `close`, so `finish` runs only when `enable` settles. Combined
with CR-02, `current` stays pending and `offer()` keeps returning that stale promise for the
life of the page.

**Fix:** add `dialog.addEventListener('close', function () { if (!busy && current) { finish(); } })`.
With the CR-02 fix in place this becomes insurance rather than a live path.
