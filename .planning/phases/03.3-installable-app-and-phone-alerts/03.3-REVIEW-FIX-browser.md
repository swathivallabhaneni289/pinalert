# Phase 3.3: Browser scripts review fix

Both findings were confirmed against the code and fixed. Each fix has node cases that fail on the code before the fix and pass after it. Files touched: web/static/js/sw.js, web/static/js/notify.js, web/pwa_sw_test.mjs, web/pwa_client_test.mjs. No server code was changed.

## B-01: fixed

- **Commit:** ea7bcc6 `fix(03.3): B-01 renew a push subscription only for the account that had it`
- **Change:** in `web/static/js/sw.js`, `pushsubscriptionchange` now returns at once when there is no old subscription, no old endpoint or no old key. Otherwise it posts `{endpoint: <old endpoint>}` to `POST /api/me/push/status` (request and answer shape read from `internal/api/handlers/push.go`: body `{endpoint}`, answer `{registered: bool}`). It subscribes again and posts the new subscription to `/api/me/push/subscription` only when the answer is OK and `registered === true`. A not registered answer, an HTTP error, a body that is not JSON and a network failure all post nothing and do not call `subscribe`. The endpoint travels only in JSON bodies and nothing is logged.
- **Tests (web/pwa_sw_test.mjs):**
  - `pushsubscriptionchange asks the server about the old endpoint, then subscribes again and posts the new one when it is registered` (registered renews, and checks the status call comes first with credentials and JSON headers)
  - `pushsubscriptionchange posts nothing when the status answer is not-registered (shared device, B-01)`, and the same for `http-error`, `bad-json` and `network`
  - `pushsubscriptionchange with an old subscription that has no endpoint asks and posts nothing`
  - The unchanged `with no old subscription does nothing` case still passes. The fetch stub of `loadWorker` now answers the status URL (mode set by `opts.status`).
- **Fails before the fix:** yes. Run against the old sw.js, the new cases failed (the old worker posted the subscription without asking, for example 1 !== 0 on the not-registered case).

## B-02: fixed

- **Commit:** 30d8ab2 `fix(03.3): B-02 drop a push subscription made with another server key`
- **Change:** in `web/static/js/notify.js`, new helpers `asBytes` and `sameKey` compare `subscription.options.applicationServerKey` with `keyBytes(key)`. `enable`, after permission is granted and the registration is ready, reads `getSubscription()` and unsubscribes it first when its key is known to differ, then subscribes with the page key. `reconcile` returns the plain state (no re-post) when the stored subscription's key differs. A subscription that reports no key is treated as matching, so browsers that do not expose `options` behave as before. `Notification.requestPermission` is still the first and only call before `enable` returns; the key check runs after the permission answer.
- **Tests (web/pwa_client_test.mjs, the fake `subscribe` now rejects like Chrome and Firefox when a subscription with another key exists):**
  - `enable: drops a browser subscription made with another server key, then subscribes with the page key (B-02)`
  - `enable: a subscription made with the page key, or one that reports no key, is left alone`
  - `enable: a prompt is still the first and only call before it returns, with the key check after it (B-02)`
  - `reconcile: does not re-post a subscription made with another server key (B-02)`
  - `reconcile: re-posts a subscription made with the page key`
- **Fails before the fix:** yes. Against the old notify.js, the first, third and fourth cases failed (3 failures, 32 passing); the other two are guards.

After B-02, `enable` drops the old key subscription itself, so for an account whose switch shows off a single Allow alerts or switch tap now recovers. For a device the server still shows on, off then on remains right. Suggested wording: "If the pair changes, every stored device stops working. Turning On this device on again replaces the old browser subscription with one made with the new key."
