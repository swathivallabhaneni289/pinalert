# Phase 3.3 server review (part 1 of 3)

Scope: the Go server side of phone alerts as on main at 02e877e. No test was run and no database was created: the one trust finding is already pinned as expected behaviour by an existing unit test case, so a run would only repeat it.

## S-01: a Changed "fades in about an hour" push goes out for a Provisional (unconfirmed, non critical) report

- **Severity:** high
- **Where:** internal/service/pushworker.go:492-493 (`case UpdateFading: return f.View == FeedViewActive`), reached from pushworker.go:467-468 (the Changed branch of `stillHolds` never calls `MayNotifyAboutReport`). Upstream: internal/service/updates.go:215-222 (3.2's `DecideUpdate` writes a fading row for any active view), internal/service/history.go:82-89 (`ViewOf` gives `FeedViewActive` for Provisional), internal/store/queries/push.sql `EnqueueChangedFromUpdates` (queues `fading` rows with no visibility rule). The behaviour is pinned as correct by internal/service/pushworker_test.go:617 (`"fading, still active"`, severity low, `wantVis: VisibilityProvisional`, `want: "sent"`), and 03.3-15-SUMMARY deviation 1 changed the docs to match the code instead of the plan.
- **Defect:** the Changed kind's send time check accepts the fading event for any active report, so it bypasses the Provisional gate that D-07 and the comment on `MayNotifyAboutReport` (updates.go: "Every other kind needs Live, so the Provisional gate holds for anything Phase 3.3 adds") require for every non critical, non Reliable push.
- **Failure scenario:** account B has Changes on and a live subscription and confirms a Medium Flood report R that has one confirm cell, so R stays Provisional. Within an hour of R's expiry the 5 minute changes sweep calls `Refresh(B)`; `DecideUpdate` sees `View == FeedViewActive` and writes a `fading` updates row; `EnqueueChangedFromUpdates` queues a `changed` row; the worker loads R (Vis Provisional, View Active), `eventStillHolds(UpdateFading)` returns true and B's lock screen shows "A report you voted on fades in about an hour" / "Flood, Medium. ..." for a report that was never Live. The reporter's own report gets "Your report fades in about an hour" the same way. The other change kinds were checked the same way and hold: `reached_live` requires `ConfirmedByPeople` (pushworker.go:486-487), so it never reaches a lock screen for a Provisional or dispute majority Critical report; `hidden` requires Vis Hidden and `resolved` requires Vis Retracted (pushworker.go:488-491), both are state change announcements listed in UI-SPEC 3b and make no confirmation claim; Withheld returns false for all four.
- **Smallest fix:** route the fading event through the one predicate. Pass `run.now` into `eventStillHolds` and use:

```go
case UpdateFading:
	return MayNotifyAboutReport(UpdateFading, f.Vis, f.ExpiresAt, now)
```

  This requires Live and active, so a Provisional report's fading row is skipped as `not_eligible` and still shows in the bell. Flip pushworker_test.go:617 to `want: "not_eligible"`, add a Live fading case that expects `sent`, and restore the plan 15 sentence in docs/PUSH.md.

## S-02: an upper case `HTTPS:` VAPID subject passes validation but is sent as `mailto:HTTPS://...`

- **Severity:** low
- **Where:** internal/push/config.go:123-128 (`strings.HasPrefix(strings.ToLower(s), "https:")` then `return s, nil` unchanged); the same lower casing in the BASE_URL fallback of `loadSubject`. webpush-go v1.4.0 vapid.go:76-77 checks `strings.HasPrefix(subscriber, "https:")` case sensitively and otherwise prepends `mailto:`.
- **Defect:** startup accepts a subject the library then mangles, so a configuration the loader calls valid produces an invalid VAPID `sub` claim.
- **Failure scenario:** `VAPID_SUBJECT=HTTPS://pinalert.example` (or no subject and `BASE_URL=HTTPS://pinalert.example`). `LoadConfig` returns ok, the server starts with push on, and every send carries the JWT claim `sub: "mailto:HTTPS://pinalert.example"`. A push service that validates `sub` (Apple answers BadJwtToken with 403) refuses every send; the worker judges 403 as a device fault (`judge` returns bump), so after five rows each subscription without a recent success is deleted.
- **Smallest fix:** in `normalizeSubject`, after `url.Parse` succeeds, return `"https:" + s[len("https:"):]` (or `u.String()` with `u.Scheme = "https"`), so the returned subject always starts with lower case `https:`.

## S-03: a failed delete on plain Log out keeps the previous person's alerts flowing to the shared device

- **Severity:** low
- **Where:** internal/api/handlers/auth.go:861-866 (`DeleteForSession` error is logged and the cookie is cleared anyway). Plain Log out does not revoke the session row (internal/session/cookie.go:167-175, DEC-K), so `PushSubscriptionsForAccount`'s `ss.revoked_at IS NULL` join still matches.
- **Defect:** the handler comment says "the session's own revocation path and the send path's live-session join are the backstops", but plain Log out never revokes the session, so neither backstop applies and the subscription stays live with no further cleanup path.
- **Failure scenario:** person A, signed in on a family phone with alerts on, taps Log out while the database is briefly unavailable (pool timeout). `DeleteForSession` fails, the log line is written, the cookie is cleared and A is redirected to /login, believing the phone is clear. A's row in `push_subscriptions` still points at A's live session S_A, so the worker keeps sending A's Critical alerts and "Your report ..." Changed notes (A's home area distance included) to the phone that person B now uses, until B happens to register the same endpoint or A runs Log out of all devices elsewhere.
- **Smallest fix:** when `DeleteForSession` returns an error, answer 500 without clearing the cookie (the person can press Log out again), or revoke the session row on this one failure path; and correct the comment.

## S-04: the recovery sweeps always serve the same fixed slice, so accounts past the 500th and reports past the 50th newest are never recovered

- **Severity:** low
- **Where:** internal/store/queries/push.sql:243-244 (`AccountsWithChangesPush ... ORDER BY a.id LIMIT row_cap`) with `PushChangesSweepAccountCap = 500` (internal/service/pushdispatch.go:82, used at :275); push.sql:266-267 (`RecentReportsForPush ... ORDER BY created_at DESC LIMIT row_cap`) with `PushSweepReportCap = 50` (pushdispatch.go:80, used at :254).
- **Defect:** both caps take the same first rows on every run with no cursor or rotation, so anything beyond the cap is never reached by the sweep, which is the only producer for fading pushes and the only recovery for dropped pokes (`ReportChanged` drops when the 64 slot buffer is full, pushdispatch.go `ReportChanged`).
- **Failure scenario (accounts):** 501 accounts have Changes on and a live device. Account id 501's fading events have no vote poke, so only `ChangesSweepOnce` could queue them, and it never lists account 501: that account never receives a fading push, nor a change push for any row whose vote poke was dropped. **Failure scenario (reports):** during a flood, 80 reports are posted in two hours and the dispatcher, busy with Reliable `Refresh` fan outs, drops some pokes. A Critical report that is now the 60th newest and whose post poke was dropped is never evaluated: its nearby accounts get no Critical alert, and a "Not confirmed yet" note already on a lock screen gets no confirmed update if the confirming vote's poke was the dropped one.
- **Smallest fix:** keep a rotating cursor (for example `WHERE a.id > $after ORDER BY a.id LIMIT` with the last id remembered, wrapping to 0), and for reports order the sweep by `push_report_progress.evaluated_at NULLS FIRST` so the least recently evaluated report is served first.

## S-05: shutdown kills a fan out between the push service's 201 and the mark, so every deploy can repeat sends; the `WithoutCancel` write path never runs

- **Severity:** low
- **Where:** cmd/server/main.go:424-425 (`go pushDispatcher.Run(context.Background())`, `go pushWorker.Run(context.Background())`) and :437 (`srv.ListenAndServe` with no signal handling or `Shutdown`); internal/service/pushworker.go:449-452, whose comment says the writes run "on a context that outlives a shutdown, so a send a push service accepted is still marked".
- **Defect:** nothing ever cancels the workers' context and the process installs no SIGTERM handler, so a host stop terminates the process mid fan out instead of letting `settle` mark the row; the shutdown safety the worker was built for is unreachable.
- **Failure scenario:** a redeploy sends SIGTERM while the worker is in `fanOut` for a Critical row with two devices; the push services have answered 201 and the process exits before `MarkPushSent`. 60 seconds after the new instance starts, `ClaimDuePushes` reclaims the row (its lease lapsed) and sends it again. An iPhone, which does not replace by tag, shows the Critical alert twice, and the account's hourly cap counts it once while two were shown.
- **Smallest fix:** in main, create `ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, os.Interrupt)`, pass `ctx` to both `Run` calls, and on `<-ctx.Done()` call `srv.Shutdown` and wait (a `sync.WaitGroup`, bounded by a few seconds more than `PushSendTimeout`) for the worker goroutine to return, so the in flight row reaches `settle` on its `WithoutCancel` context.

## Checked and not reproduced

- **Lease and marks:** `ClaimDuePushes` uses a MATERIALIZED CTE with `FOR UPDATE SKIP LOCKED`; `ExtendPushLease` and all four marks are conditional on `state = 'queued'` and the exact held `lease_until`; the claim returns the stored timestamptz, so the equality round trips. The 60 s lease minus the 10 s fan out and 20 s margin is enforced at compile time. A lapsed but unclaimed lease is still correctly renewed by its holder. No double send past a held lease was found apart from the documented crash case (S-05).
- **SSRF and endpoint handling:** https only, no user info, port 443 only, IP literals refused, exact host or dot boundary suffix allowlist, 2048 cap; the guarded client refuses loopback, private, link local, multicast, unspecified and CGNAT at dial time after DNS, follows no redirect, has no proxy and a 10 s timeout; the sender re-checks the policy; the worker takes the Apple host from the policy at send time, not from `endpoint_host`. Errors are reduced to class words or SQLSTATE; no endpoint, key, report text, coordinate or email reaches a log line or error string in the reviewed code.
- **Trust paths:** Critical requires Live through `MayNotifyAboutReport(UpdateCriticalNearby)` at queue and send time; Reliable allows Provisional only through `UpdateReliableNearby`; "Not confirmed yet" and "Confirmed by people nearby" both follow `ConfirmedByPeople`, so a dispute majority Critical report never reads as confirmed; the confirmed update is queued only for a sent row whose words said Not confirmed yet and is rechecked at send. Switches, mute, home area and distance are reread at send. UI-SPEC 3b says Changed notes never carry Not confirmed yet, so that is not a finding.
- **Privacy across accounts:** the endpoint upsert moves a device to the newest account and resets its failure count; Log out deletes by session; Log out of all devices revokes and deletes; Delete my account deletes outbox and subscriptions in its transaction; status and unsubscribe act on the caller's own rows only; a signed in browser cannot be bound to a second account (OutcomeConflict), so a session never changes owner under a subscription.
- **Limits and bodies:** per account write and status budgets, `application/json` only (415), 4 KB `MaxBytesReader` (413), unknown fields and trailing data refused, 8 devices per account trimmed oldest first, 4 pushes per account per hour, per reporter caps of 3 Critical and 2 Reliable per hour, 2000 recipients per report.
- **Startup:** both keys unset logs one warning and leaves push off (no notifier, no workers, register answers 503); one key, a malformed key, a mismatched pair or a missing or bad subject stops startup with a message that holds no key value (except the case in S-02, which passes when it should not).
