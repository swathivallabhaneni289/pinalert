### Task 1: internal/api/handlers/push_flow_e2e_test.go

All eight named tests exist and pass on `p33_15_a`, with three consecutive runs stable:

- `TestPhoneAlertCriticalEndToEnd`: reader A (home at the report point) gets one message with Kind critical, Tag `report-{id}`, URL `/?report={id}`, Title "Water rising near Central Market", Body "N km from your home area. Not confirmed yet." (N computed in the test from the stored cell middle and `service.DistanceWords`), Urgency high, TTL above 0 and at most one hour, Topic `r{id}`. A reader 15 km away, the author and a reader who muted the report get none. The recorded pokes are checked (post with actor 0, then each voter). After two confirms from distinct cells A gets a confirmed_update with the same tag and title and the body "Confirmed by people nearby. N km from your home area."; later dispatcher, changes and worker sweeps send nothing.
- `TestPhoneAlertReliableAtPosting`: with `testutil.SeedReliableReporter`, a reader with the Reliable switch on gets one message for the low Provisional report, "From a Reliable reporter. ... Not confirmed yet."; a near reader with the switch off gets none.
- `TestPhoneAlertChangesToMyReport`: the reporter turns Changes on through PATCH /api/me/alerts and gets one "Your report is now confirmed" after two confirmations; the voter whose vote caused the change gets nothing, also after the changes sweep.
- `TestPhoneAlertCapShowsNothingExtra`: five Critical reports from five reporters give four messages, distinct tags, no summary wording, one outbox row skipped with `cap_account_hour`, four sends in total.
- `TestPhoneAlertAppleGetsNoUpdate`: the Apple endpoint gets the first message only, the person's fcm device gets both.
- `TestPhoneAlertStopsAfterLogout`: after POST /auth/logout the device row is gone and a new Critical report goes only to a control reader.
- `TestPhoneAlertPayloadHasNoReporterWords`: the description (phone number, street, landmark), coordinate digits and email fragments appear in no recorded message.
- `TestPhoneAlertAreaNameStaysOffFeedAndBell`: the area name is checked in the database first (so the test cannot pass vacuously) and then absent from the vote answer, GET /api/reports, GET /api/updates and GET /?report={id} for three readers, with no `area_name` field.

How it drives the pipeline: a recording `pwNotifier` is given to the report and voting services and forwards each poke to the real dispatcher. After each HTTP action the test hands every recorded poke to `EvaluateReport` and runs one `PushWorker.SweepOnce`.

## Deviations from Plan

1. **[Doc follows code] The "fades in about an hour" sentence in the plan is not what the code does.** The plan asks PUSH.md to say a fades note about an unconfirmed report shows in the bell but is not sent to the phone. `EnqueueChangedFromUpdates` queues any fading update row, and `eventStillHolds(UpdateFading)` only needs the report to be active (`pushworker_test.go` case "fading, still active" expects `sent` for a Provisional report). So a person who posted or voted on a report and has Changes on does get the fades in about an hour note on the phone, confirmed or not. docs/PUSH.md says that. Plans 09 and 11 are consistent with each other here; it is the plan 15 text and its 3.2 reference that were wrong. Not changed in code (repo rule 7).
2. **[Interpretation] Builder.** The plan names `newTrustE2EServer`; I used `newE2EServerWith` (it has the tweak hook and its signing secret matches `p17raSessionClient`, which `SeedReliableReporter` needs) and wall clocks, not a fixed or offset clock. A clock ahead of the database makes the dispatcher's `next_attempt_at` later than the database `now()` the claim compares against, so nothing would be due.
3. **[Interpretation] Voter in the Changes test.** The earlier voter (v1) gets nothing either: 3.2 takes a silent baseline at a voter's first refresh, which happens at the confirming vote, when the report is already confirmed. The test asserts the confirming voter gets nothing, and only that any message v1 might get is a "A report you voted on" change note.
4. **[Rule 2 in docs] Two sentences in the existing "Reliable reporter alerts" section of TRUST-MODEL.md** said the alert was limited to the bell and that Phase 3.3 "must record that gap or meet it". They would have been false after this plan and were updated (not in the plan's list of amended lines).
5. **[Repo rules over plan text] No scratch server was started, no `p33_15_b` was made and the desktop check was not run.** Repo rule 5 forbids starting a server for a device check; the three device checks are written as owner steps in docs/PUSH.md. The plan's `env -u`/`env -i` verify commands were run as an inline `DATABASE_URL=...` prefix (repo rule 4). The commit trailer is the repo's `Claude Opus 5.5` line.
