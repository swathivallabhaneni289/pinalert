# Phase 01.1 Plan 01: Identity schema, mailer seam, and the login-gate request-link slice Summary

**Full vertical slice for requesting a magic-link verification email: crypto/rand 256-bit tokens hashed with SHA-256 before storage, an injectable Mailer seam (log-only in dev), AuthService.RequestLink wired through a real POST /api/auth/request-link endpoint, and a server-rendered globe login gate whose CSS-masked background animation never blocks the interactive email form.**

## Performance

- **Duration:** ~35 min
- **Completed:** 2026-09-11
- **Tasks:** 3 (all `type="auto"`, `tdd="true"` for Tasks 1-2)
- **Files modified:** 23 (16 created, 7 modified)

## Accomplishments

- `internal/auth` package: 256-bit `crypto/rand` tokens, SHA-256 hex hashing, 5-minute TTL — the raw token is never persisted, only its hash.
- Migration `00002_add_accounts_and_verification.sql`: `accounts`, `magic_link_tokens` tables, nullable `sessions.account_id` (deliberately no FK — see this plan's threat T-01-56/AR-27), and the `(email, created_at DESC)` index plan 01.1-05's cooldown will read.
- `AuthService.RequestLink`: `net/mail`-based validation (no hand-rolled regex), trim+lowercase normalization, insert-before-send ordering so a mailer failure still consumes a future cooldown slot, and an injectable clock (`WithClock`) added now so plan 01.1-05 needs no constructor change later.
- `GET /login` and `POST /api/auth/request-link` live end to end: a visitor can load the globe login gate, submit an email, and a real verification link (hashed before storage) reaches the log-mailer — verified against a real Postgres via `auth_e2e_test.go` and manually against a running server.
- `web/static/css/auth.css`: token-only styling, `@keyframes globe-rotate` respecting `prefers-reduced-motion`, and a CSS-mask-based globe background consistent with `main.css`'s established icon-glyph coloring mechanism.

## Decisions Made

- **`AuthService.RequestLink` now returns `(string, error)`** instead of the plan's bare `error` — the normalized email is returned so `RequestLink`'s HTTP handler echoes exactly what was mailed (trimmed, lowercased) rather than re-deriving or duplicating normalization logic at the handler layer, and so `RequestLinkResponse.Email` in the success JSON body is provably correct rather than an unverified pass-through of client input.
- **`POST /api/auth/request-link` is registered inside chi's `r.Route("/api", ...)` subrouter**, not as a literal top-level sibling path as the plan's wiring section suggested — chi's radix-tree router does not cleanly support a literal path registered directly alongside a wildcard `Route` mount at the same prefix; nesting inside the existing group produces the identical URL (`POST /api/auth/request-link`) and keeps the route reachable with no access-gate middleware, since none exists yet in this phase.
- **`mail.svg`/`circle-alert.svg` exempted via an explicit allowlist** in `web/css_contract_test.go` (`nonCategoryIcons`) rather than relocated out of `web/static/icons/` — UI-SPEC explicitly directs these two Lucide icons to that directory using the "identical pattern to Phase 1's 9 category glyphs," so the fix targets the existing test's documented scope (category-icon drift, not "every file under static/icons/") instead of contradicting two design artifacts (UI-SPEC + this plan's own `files_modified`) to route around it.
- **Check-inbox's "Check again" button uses UI-SPEC's exact Copywriting Contract text**, not the plan action's own paraphrase ("Refresh") — the id (`refresh-inbox`) matches the plan literally; the visible label follows the canonical copy table since no acceptance criterion pinned the paraphrase and the UI-SPEC table is the authoritative source for user-facing strings.
- **Globe background rendered via CSS `mask-image` + `background-color: currentColor`-style coloring**, not an `<img src="...">` as a literal reading of "every stroke `currentColor` so page CSS controls it" might suggest — an `<img>`'s loaded SVG document does not inherit the page's `color` property (this is the exact mechanism `main.css`'s own extensive commentary documents as the cause of a prior dark-mode icon-rendering bug, T-01-13-01), so the mask approach is what actually achieves "page CSS controls it."

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Over-broad category<->icon contract test would have failed the build on the two new auth icons**
- **Found during:** Task 3 (fetching mail.svg/circle-alert.svg per the plan's `<action>`)
- **Issue:** `web/css_contract_test.go`'s `TestCategoryGlyphMaskRulesCoverEveryCategory` walks every file under `static/icons/` and requires each to be claimed by a `.icon-glyph--{category}` mask rule tied to `Pinalert.CATEGORIES`. Adding `mail.svg`/`circle-alert.svg` — both directed to that exact directory by UI-SPEC's Icon library row and this plan's own `files_modified` — would fail that reverse-walk, since neither is a category glyph. The test's own doc comment scopes its purpose to the nine `CATEGORIES` glyphs specifically, so the reverse-walk's blanket claim over the whole directory is broader than its documented intent.
- **Fix:** Added an explicit, auditable `nonCategoryIcons` allowlist (`static/icons/mail.svg`, `static/icons/circle-alert.svg`) checked before the "claimed by a rule" assertion; left every other assertion in the test (forward direction, rule-points-at-a-real-category, base `.icon-glyph` rule shape) untouched. Styled the two new icons under a distinct `.auth-icon--` CSS prefix (not `.icon-glyph--`) specifically so they can never collide with `collectGlyphMaskRules`'s category-rule scan in either direction.
- **Files modified:** `web/css_contract_test.go`
- **Verification:** `go test ./web/... -run TestCategoryGlyphMaskRulesCoverEveryCategory -v` passes; full `go test ./... -p 1` green.
- **Committed in:** `d2db23e` (Task 3 commit)

**2. [Rule 1 - Bug] `AuthService.RequestLink`'s bare `error` return would have forced the handler to duplicate normalization**
- **Found during:** Task 3 (writing `handlers.RequestLink`, whose success response must carry "the normalised email")
- **Issue:** As specified in Task 2, `RequestLink(ctx, rawEmail) error` gives the caller no way to learn the normalized address without re-implementing `normalizeEmail`'s trim/lowercase/parse logic at the handler layer — a second, driftable copy of a security-relevant normalization rule.
- **Fix:** Changed the signature to `RequestLink(ctx, rawEmail) (string, error)`, returning the normalized email on success. Updated all seven call sites in `internal/service/auth_test.go` accordingly (one now also asserts the returned value equals the expected normalized form).
- **Files modified:** `internal/service/auth.go`, `internal/service/auth_test.go`, `internal/api/handlers/auth.go`
- **Verification:** `go test ./internal/service/... ./internal/api/... -v` — all pass, including the new assertion on the returned normalized email.
- **Committed in:** `d2db23e` (Task 3 commit; the Task 2 commit `bf96d6e` still reflects the original bare-`error` signature, which is expected for an atomic per-task commit history)
