## Phase Goal

**As a** visitor, **I want to** verify my email with a magic link before I can report or vote, **so that** every report and vote is tied to an accountable, verified identity.

`01.1-04` closed the gate; everything behind it now belongs to a verified account. This plan gives that account a front door that is present on every page behind the gate: the one place a person can see which address they are signed in under, reach their own history, and hand the device back.

<objective>
Deliver D-12's account menu as a **shared header partial** that every gated page renders: the header icon opens a dropdown showing the verified email address, an "Activity" item that navigates to the profile page, and a "Log out" item that fires immediately.

Purpose: without it there is no route to `/profile` from inside the running app and no way to log out without typing a URL. D-12 also rejected the obvious shortcut — a bare icon-link straight to the profile page — because logging out should not require a page navigation first. That makes the menu the phase's actual entry point, and its open/close, focus and dismissal behaviour load-bearing rather than decorative.
Output: `web/templates/account_header.html.tmpl` (the shared header), its wiring into the app shell, `account-menu.js`, the account email on the shell view model, and three contract tests locking the markup, the behaviour and the panel's hidden state.

Scope boundary and wave order: this plan runs **before** the profile page (`01.1-07`), deliberately. The header partial has to exist on disk before any page references it — `html/template` fails at *execution* time on `{{template "name" .}}` when `name` is not in the parsed set, so a profile page that includes a partial a later wave has not yet written would fail its own acceptance tests for the whole gap. The reverse direction costs nothing: the menu's `/profile` and `/auth/logout` targets are literal path strings in markup, so until `01.1-07` registers those routes they are ordinary dangling links that 404 — this plan's tests never call them. That asymmetry (a dangling link versus a broken template execution) is why the header lands first.
</objective>

<decisions_resolved>
Decision letters are register labels assigned when each decision was first made. They are retained across the 2026-09-11 wave swap that moved the account menu ahead of the profile page, so they do not run alphabetically with plan order: `01.1-07` carries `DEC-K`–`DEC-N` and `DEC-T`.

- **DEC-O — opening the menu requires JavaScript; the logout inside it is still a real form submit.** D-12 moves the logout control into a dropdown, which supersedes the "works with no JavaScript" half of `01.1-07`'s DEC-L. Accepting that is not a quiet downgrade, for two reasons. First, the security property DEC-L actually protects is CSRF resistance, and that comes from the POST plus `SameSite=Lax`, not from the absence of JS — so the menu item stays a `<button type="submit">` inside a real `<form method="post">`, never a `fetch` call, and `T-01-84` carries over untouched. Second, the app shell this menu sits in is already end-to-end JS-dependent: the map, the feed, the submission modal and the store all require it, so a no-JS visitor at `/` sees an empty frame with or without this menu. A `.no-js` CSS reveal or a duplicated `<noscript>` control would buy zero real capability on that page and cost a second copy of the logout form to keep in sync.
- **DEC-P — the email reaches the shell from the request context, not from `PageConfig`.** `PageConfig` is process-wide configuration built once in `cmd/server/main.go`; identity is per-request. The gate from `01.1-04` has already resolved the account, so `Page` reads it from there. The consequence worth planning for: `page_test.go`'s two existing tests build a bare `httptest` request with no gate in front of it, so they must now put an account into the request context themselves — which is why this plan may need to export a context constructor next to `AccountFromContext`. This plan is the first handler outside the gate to need it, so it owns adding it; `01.1-07`'s `Profile` handler then reuses whatever lands here.
- **DEC-Q — the gated app shell gets `Cache-Control: no-store`.** Until this plan the shell contained no personal data, so caching it was harmless. It now renders the account's email address on every response. `01.1-04`'s gate already applies `no-store` to its own redirect; this closes the gap on the one page a person actually leaves open on a shared device. `01.1-07` applies the same header to `/profile`, which carries the address *and* the report history (DEC-T, `T-01-86`).
- **DEC-R — one header file, included by both pages, rather than duplicated markup.** The user's 2026-09-11 decision is "full header everywhere": the account menu must render identically on the app shell and on the profile page. Two hand-maintained copies of a `role="menu"` panel with a focus trap pointed at it is the textbook way to ship an accessibility fix to one page and not the other. So the header lives in its own file, `web/templates/account_header.html.tmpl`, and each page includes it by its parsed template name. No `{{define}}` block is needed: `ParsePageTemplate`'s `template.ParseFS(web.TemplatesFS, "templates/*.tmpl")` glob already names every parsed file's template after its base filename, and `01.1-01` established exactly this pattern when `login_gate.html.tmpl` included `{{template "check_inbox.html.tmpl" .}}`. **The partial's data contract is deliberately one field, `.Email`** — the icons resolve through `mask-image` URLs in CSS rather than through markup, so the partial needs no `AssetVersion`, and a one-field contract is one any gated page's view model can satisfy without inheriting a layout struct. The `<script>` tag for `account-menu.js` stays in each page's own end-of-body script block rather than inside the partial, so it cannot land ahead of the vendor tags in the shell and disturb the script-order contract; both pages are gated on referencing it.
- **DEC-S — the header's left slot is a wordmark linking home, not empty.** D-12 specifies what the menu contains; it does not say what else the header holds, and the header itself is new (Phase 1 shipped none). The user's decision exists to solve a concrete complaint — from the profile page there was "no way back to the app" short of the browser back button — and a menu whose only destinations are the page you are already on and the login gate does not solve it. One anchor to `/` carrying the product name does, it is the conventional home affordance, it needs no view-model field, and on the app shell it is a harmless self-link. Flagged here rather than assumed: this is the one element in the header not enumerated in `01.1-UI-SPEC.md`.
- **DEC-T is recorded in `01.1-07`** (no-store on the profile response), listed here only so the register reads continuously.
</decisions_resolved>
