## Phase Goal

**As a** visitor, **I want to** verify my email with a magic link before I can report or vote, **so that** every report and vote is tied to an accountable, verified identity.

This plan makes that identity visible to the person who owns it: a profile page listing what they have contributed, and the endpoint that hands the device back to someone else.

<objective>
Deliver IDENT-03's profile page — one merged Activity section per D-13 — and D-09's explicit logout endpoint, with the reports listing resolved through the account rather than the session.

Purpose: the account-versus-session distinction is the reason this phase exists. The profile page is the first place it becomes visible, and getting the join right here is what proves the model Phase 2's independence predicate will depend on.
Output: `ReportsByAccount`, `GET /profile`, `POST /auth/logout`, and `profile.html.tmpl`.

Scope boundary: this plan ships the logout *endpoint*, not its on-screen control, and touches no app-shell markup. D-12 makes the header an account menu rather than a bare profile link, and plan `01.1-07` owns `web/templates/index.html.tmpl` and every account-menu control — including the "Log out" button — one wave later.
</objective>

<decisions_resolved>
- **DEC-K — logout clears the cookie and leaves `sessions.account_id` intact.** The next request issues a brand-new session id, so the browser is genuinely logged out. The old session row keeps its binding on purpose: it is what still connects reports submitted from that session to the account, which is exactly what the profile page reads. Unbinding it would silently erase a person's own history from their own profile.
- **DEC-L — logout is a `POST`, not a link.** `SameSite=Lax` does not send the session cookie on a cross-site POST, so a forged logout is not possible; the same is not true of a GET. It needs no confirmation dialog — D-11 makes logout fully recoverable by re-verifying the same address (UI-SPEC "Destructive actions in this phase: none"). **Amended 2026-09-11 for D-12:** the control is a real HTML form submit rather than a `fetch` call, and that is what carries the CSRF property above — but it now lives in the account menu (`01.1-07`), not on this page. This plan registers the route only; see `01.1-07`'s DEC-O for what moving it costs and what it does not.
- **DEC-M — the profile query joins through `sessions.account_id` with a plain inner join.** RESEARCH.md suggested considering a defensive `LEFT JOIN`, but with `WHERE s.account_id = $1` the two are equivalent: an orphaned report has no session row and therefore no account, so it is filtered out either way. No foreign key is relied upon — see `T-01-56` in `01.1-01` for why none was added.
- **DEC-N — D-11's "no account recovery" is surfaced, not hidden.** There is no recovery affordance anywhere in the UI, and the profile page states plainly which address the account is tied to so a person can see what they would need to keep access to.
</decisions_resolved>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| verified session → another account's data | The profile query is the first read scoped to an identity rather than to everyone |
| browser → `POST /auth/logout` | A state-changing request that revokes the caller's own access |
| shared/public device → session cookie | The scenario logout exists for |

## STRIDE Threat Register

Numbering continues the project register; `01.1-05` ended at `T-01-81`, accepted risks at `AR-33`.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-82 | Information Disclosure | Insecure direct object reference — reading another account's reports | high | mitigate | `ReportsByAccount` takes the account id from `AccountFromContext`, resolved server-side by the gate from the signed session cookie. No account, user or report identifier is ever accepted from the query string or body, so there is no parameter to tamper with. `TestProfileListsOwnReportsAcrossSessions` seeds a second account's report and asserts it does not appear |
| T-01-83 | Information Disclosure | Session identifier leaking through the profile payload | medium | mitigate | `ReportsByAccount` selects no session column, continuing Phase 1's T-01-02 control; `TestNearbyReportsExcludesSessionID` remains green alongside it |
| T-01-84 | Tampering | CSRF on logout | low | mitigate | Logout is `POST` only, and `SameSite=Lax` withholds the session cookie from cross-site POST requests, so a forged logout cannot carry an authenticated session. This is the same control Phase 1's AR-02 relied on, and unlike `GET /auth/verify` (see `T-01-61`) it genuinely covers this endpoint because the method is POST |
| T-01-85 | Spoofing | Stale session usable after logout on a shared device | medium | mitigate | `ClearCookie` mirrors every attribute of the issued cookie, so the browser actually drops it; `TestClearCookieMatchesIssuedAttributes` pins the attribute match, which is the failure mode that otherwise ships silently |
| T-01-86 | Information Disclosure | Profile page cached and shown to the next person on a shared device | medium | mitigate | `Cache-Control: no-store` on the logout redirect; the profile page itself sits behind the gate, which already sends `no-store` on its redirect for an unverified session |
| T-01-87 | Repudiation | Permanent loss of account access with no recovery path | low | accept | D-11 makes this an explicit product decision, not an oversight: there is no recovery mechanism in v1, and a lost inbox means starting fresh. Surfaced rather than hidden — the profile page shows the tied address and README states the consequence plainly. Accepted risk **AR-34** |
