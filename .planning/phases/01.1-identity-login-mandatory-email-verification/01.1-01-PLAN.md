## Phase Goal

**As a** visitor, **I want to** verify my email with a magic link before I can report or vote, **so that** every report and vote is tied to an accountable, verified identity.

This plan delivers the first vertical slice of that story: a visitor can reach a login screen, type an email address, and cause a real verification link to be generated and delivered through the mailer seam. Plan `01.1-02` closes the loop by making that link actually log the visitor in.

<objective>
Ship the request-a-magic-link slice end to end — database, token crypto, mailer seam, service, JSON endpoint, and the server-rendered login screen — so a visitor can ask for a verification link and the link genuinely leaves the system.

Purpose: IDENT-02 needs a real delivery path and IDENT-01 needs a token that cannot be forged or replayed. Both are load-bearing for every later plan in this phase.
Output: migration `00002`, `internal/auth`, `internal/mailer`, `AuthService.RequestLink`, `POST /api/auth/request-link`, `GET /login`, and the globe login surface.
</objective>

<decisions_resolved>
Three questions were left open by RESEARCH.md / PATTERNS.md. They are resolved here for the whole phase; later plans inherit these answers rather than re-deciding them.

- **DEC-A — cooldown value (RESEARCH A2, CONTEXT D-03 discretion):** the resend cooldown is **45 seconds**, the midpoint of D-03's 30–60s range. Implemented in plan `01.1-05`; the constant is introduced here as `service.ResendCooldown` so the check-inbox copy and the later limiter share one source of truth.
- **DEC-B — token shape (CONTEXT "Claude's Discretion"):** 32 bytes from `crypto/rand`, `base64.RawURLEncoding` for the emailed value, SHA-256 hex for the stored value, 5-minute TTL (D-02). The raw token is never written to the database and never logged outside the development mailer.
- **DEC-C — no-JavaScript submit is out of scope for the request step:** the request form posts through `web/static/js/auth.js` to the JSON endpoint, matching Phase 1's existing JS-only report submission (`web/static/js/modal.js`). UI-SPEC only requires a non-JS fallback for the post-verification redirect (UI-SPEC item 12), which plan `01.1-02` delivers as a real server-rendered anchor.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /api/auth/request-link` | Untrusted, unauthenticated email string crosses into the server and triggers an outbound email |

## STRIDE Threat Register

Numbering continues Phase 1's project-wide register from `T-01-50` (`01-SECURITY.md` line 60: "Future plans in this project must continue from `T-01-50`"). Accepted risks continue from `AR-26`.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-51 | Spoofing | Magic-link token guessing | high | mitigate | 32 bytes from `crypto/rand` (never `math/rand`), base64url-encoded — 256 bits of entropy makes online guessing infeasible without depending on a rate limiter for the verify path |
| T-01-52 | Information Disclosure | Token material at rest in `magic_link_tokens` | high | mitigate | Only `sha256` hex of the raw token is stored (`auth.HashToken`); a database read never yields a usable link. SHA-256 rather than bcrypt/argon2 because the secret is high-entropy machine-generated, not a human password |
| T-01-53 | Denial of Service | Unbounded request body on `POST /api/auth/request-link` | medium | mitigate | `http.MaxBytesReader` at the same 64 KB cap as `POST /api/reports`, plus `DisallowUnknownFields` so a padded payload is a loud 400 |
| T-01-54 | Denial of Service | Unlimited verification-email sends burning the free-tier quota | high | mitigate | Deferred by design to plan `01.1-05` (IDENT-04): the `magic_link_tokens` row this plan inserts **before** the send is the record that limiter reads, and the `(email, created_at DESC)` index it needs ships in this plan's migration |
| T-01-55 | Information Disclosure | Provider/API detail leaking through error responses | medium | mitigate | Mailer failures are wrapped and logged server-side; the client receives the generic 500 body Phase 1's T-01-15 control already established |
| T-01-56 | Tampering | Orphaned `reports.session_id` with no `sessions` row | low | accept | No FK is added from `reports.session_id` to `sessions.session_id`. `internal/session/cookie.go` lines 106-111 deliberately log-and-continue when `persistSession` fails, so a valid signed cookie can exist with no `sessions` row — a FK would turn that tolerated path into a failed report submission during an emergency. The profile query in plan `01.1-06` uses a plain inner join filtered on `account_id`, which excludes orphans for free. Accepted risk **AR-27** |
| T-01-57 | Information Disclosure | Raw token written to logs by the development mailer | low | accept | `logMailer` prints the full link by design — it is the only way to complete the flow without a provider key. It is selected only when the Resend key is absent, and plan `01.1-03` makes that a fatal error outside `ENV=development`. Accepted risk **AR-28** |
