## Phase Goal

**As a** visitor, **I want to** verify my email with a magic link before I can report or vote, **so that** every report and vote is tied to an accountable, verified identity.

Seven plans shipped that flow. `01.1-VERIFICATION.md` then found that one of its five success criteria — SC4 / IDENT-04, the abuse resistance on the one endpoint that spends real money — does not actually hold. Both of its layers exist and both pass their own unit tests, and both are defeatable. This plan closes that gap and proves it with tests that fail against the code as it stands today.

<objective>
Re-close IDENT-04 (ROADMAP SC4): make the per-IP limiter's key un-forgeable, and make the per-email cooldown atomic.

Purpose: as shipped, `POST /api/auth/request-link` has two independent abuse controls and an attacker can walk through both at once. The per-IP bucket is keyed on a value the caller sets in a request header, so every request can mint a fresh bucket. The per-email cooldown is a `SELECT` followed by a separate `INSERT` with no lock and no unique constraint, so concurrent requests for one address all read "no recent token" before any of them writes. Together that is an unbounded mail bomb aimed at a third party's inbox, funded by this project's free Resend quota — the precise opposite of what SC4 promises.
Output: a header-independent limiter key, an `email_cooldowns` table whose primary key does the serialising, a single-statement atomic claim replacing the read-then-insert, and three adversarial tests that reproduce the attack.
</objective>

<decisions_resolved>

- **DEC-U — do not invent a trusted-proxy allowlist.** `01.1-VERIFICATION.md` frames the header-trusting fix conditionally: chi's `ClientIPFromXFFTrustedProxies` is correct **if** this service is confirmed to sit behind exactly one trusted reverse proxy that overwrites inbound proxy headers. That condition is not met. PROJECT.md names Render and Railway as *candidates*; nothing is deployed, and no CIDR for any proxy in front of this app is known. Writing a placeholder allowlist would encode an unverified assumption as a security control, which is strictly worse than having none. So the client IP is resolved from the TCP peer address instead — `middleware.ClientIPFromRemoteAddr`, the non-deprecated chi function whose own documentation describes exactly this situation ("Use this when this server is directly connected to the public internet with NO reverse proxy in front of it"). A short comment in `router.go` records that a confirmed single trusted proxy would make `ClientIPFromXFFTrustedProxies` the correct upgrade. That upgrade is not built speculatively now.

- **DEC-V — the limiter reads the router's decision, it does not re-derive it.** `middleware.ClientIPFromRemoteAddr` and every other `ClientIPFrom*` function store the resolved address in the request context and deliberately **never mutate `r.RemoteAddr`** — that non-mutation is the whole point of the replacement API. So a limiter that keys on `r.RemoteAddr` alone would silently ignore a future switch to `ClientIPFromXFFTrustedProxies` and would then key every request on the single proxy's own IP, turning a per-IP limiter into a global throttle on the login endpoint. `PerIP.Middleware()` therefore reads `middleware.GetClientIP(r.Context())` first and falls back to the `r.RemoteAddr` host only when no `ClientIPFrom*` middleware is installed. The fallback is what keeps `internal/ratelimit` usable standalone for Phase 4's ROBUST-04 and keeps `01.1-05`'s existing limiter tests green unchanged.

- **DEC-W — a dedicated cooldown table with an atomic upsert-guard, not an advisory lock and not `SELECT ... FOR UPDATE`.** The gap's `missing` list offers three shapes; this is why the third wins.
  - `SELECT ... FOR UPDATE` locks *rows that exist*. The first-ever request for an address has no row to lock, so the very first concurrent burst against a fresh address — the actual attack — races exactly as it does today. Making it correct needs an insert-then-lock dance inside an explicit transaction.
  - A Postgres advisory lock needs a transaction spanning the check and the insert, which means threading a pool or a `WithTx` seam into `AuthService`. `AuthService` holds the narrow `AuthQuerier` interface precisely so `internal/service/auth_test.go` can fake it; adding transaction plumbing would rewrite that already-verified test architecture for no security gain over the alternative.
  - A `PRIMARY KEY` on `email_cooldowns.email` makes Postgres itself serialise concurrent claims: the second `INSERT ... ON CONFLICT (email) DO UPDATE` blocks on the unique index, then re-evaluates its guard against the row the winner just committed. One statement, no transaction, correct at every isolation level. It is also the same idiom `ConsumeToken` already uses and documents in this codebase — "a single atomic conditional UPDATE, never read-then-write" — so the cooldown stops being the one place in `auth.go` that does the thing the file next to it warns against.

- **DEC-X — the cooldown clock moves from `magic_link_tokens.created_at` to `email_cooldowns.last_requested_at`, and it is claimed before the token is minted.** This preserves both halves of `01.1-05`'s DEC-J and tightens one of them. A refused claim performs no insert and no update — its guard fails, so the stored timestamp is untouched and a refusal still cannot extend the window that refused it. A granted claim commits *before* token generation, insert and send, so a send failure, a quota exhaustion, or even a failed token insert still consumes the cooldown. That last case is new and deliberate: the old shape left the cooldown unconsumed if the token insert failed, which was a retry loop waiting to happen.

- **DEC-Y — `middleware.Logger` will now record the TCP peer rather than a header-derived address.** Deliberate and stated rather than discovered later. Behind a future reverse proxy those log lines show the proxy, not the visitor; that is honest — the server genuinely does not know the visitor's address without a proxy it trusts. Not a regression to fix here, and it disappears the moment DEC-U's condition is actually met.

</decisions_resolved>
