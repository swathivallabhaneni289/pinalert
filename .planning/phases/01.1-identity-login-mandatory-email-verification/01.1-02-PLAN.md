## Phase Goal

**As a** visitor, **I want to** verify my email with a magic link before I can report or vote, **so that** every report and vote is tied to an accountable, verified identity.

This plan closes the loop opened by `01.1-01`: the emailed link now actually authenticates the browser that opens it. After this plan a real person can go from a cold browser to a verified identity without any manual database work.

<objective>
Implement `GET /auth/verify` end to end — atomic single-use token consumption, lazy account creation, session→account binding, and all five link-landing outcome screens.

Purpose: IDENT-01's "cannot act until verified" needs a mechanism that actually marks a session verified, and IDENT-05 requires that mechanism to ride on Phase 1's existing cookie rather than replace it.
Output: `accounts`/`sessions` queries, `AuthService.VerifyToken`, the `Verify` handler, and `verify_outcome.html.tmpl`.
</objective>

<decisions_resolved>
- **DEC-D — the fifth link-landing outcome (RESEARCH.md Pitfall 4, an acknowledged UI-SPEC gap):** when a token belonging to one address is opened in a browser whose session is **already** verified as a different account, the server **refuses to re-bind** and shows a distinct outcome screen. Silently switching identities is the exact payload of the attacker-distributes-their-own-link attack. This does not weaken D-07's cross-device support, because that case only ever involves an *unverified* browser. UI-SPEC's four-outcome table is extended by this plan; copy is specified in Task 3.
- **DEC-E — conflict is checked before consumption, not after:** RESEARCH.md's diagram places the conflict check after the atomic consume, which would burn a legitimate owner's single-use token on someone else's browser. This plan checks first and consumes second. The pre-consume reads are used only to select outcome copy; authorisation still rests entirely on the atomic conditional UPDATE.
- **DEC-F — the session id is not rotated on verification.** D-08 and IDENT-05 lock the Phase 1 cookie mechanism as-is; `account_id` is bound onto the existing session row. See threat `T-01-63` for the fixation analysis behind accepting this.
</decisions_resolved>

D-01's choice of a clicked link over a typed code is also why no confirmation step is added here — clicking is the whole interaction.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| email inbox → `GET /auth/verify` | An attacker-chosen URL can be navigated to by any browser, carrying that browser's session cookie |
| `GET /auth/verify` → `sessions.account_id` | The single write that converts an anonymous session into an identity |
| concurrent requests → one token row | Two clicks can race for the same single-use secret |

## STRIDE Threat Register

Numbering continues the project register; `01.1-01` ended at `T-01-57`, accepted risks at `AR-28`.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-58 | Elevation of Privilege | Token replay — reusing a consumed link | high | mitigate | `ConsumeToken` is one conditional UPDATE guarded by `used_at IS NULL AND expires_at > now()`, decided by rows-affected; `TestConsumeTokenIsSingleUse` and `TestConsumeTokenConcurrent` lock it |
| T-01-59 | Elevation of Privilege | TOCTOU race between two simultaneous clicks | high | mitigate | No read-then-write anywhere on the authorisation path; the pre-consume reads select copy only. `TestConsumeTokenConcurrent` asserts exactly one success under Postgres row-level locking |
| T-01-60 | Spoofing / Elevation of Privilege | Attacker distributes their own unclicked link to hijack a verified visitor's identity | high | mitigate | DEC-D conflict check: an already-verified session opening a token for a different account is refused, not re-bound, and the token is not consumed. `TestVerifyAccountConflict` locks it |
| T-01-61 | Tampering | CSRF on the state-mutating `GET /auth/verify` — **re-opens Phase 1's AR-02** | medium | accept | AR-02 was accepted in Phase 1 on the stated grounds that "there is no authenticated action to ride"; this phase creates exactly such an action, so it is re-assessed here rather than inherited. Assessment: `SameSite=Lax` **does** send the session cookie on a top-level GET navigation, so an *unverified* visitor who follows an attacker's link is bound to the attacker's account. The T-01-60 conflict check does **not** cover this case — it only fires when the session is already verified as someone else. The mitigation normally used (binding the token to the requesting session) is unavailable because D-07 locks cross-device verification as intended behaviour, and converting the link to a POST would destroy D-01's click-a-link premise. Residual accepted: the attack is inherent to bare magic links, is single-use, expires in 5 minutes, and yields an account the attacker already controls rather than access to a victim's data. Compensating controls: single-use consumption (T-01-58), 5-minute TTL, the conflict check for verified sessions, and `Cache-Control: no-store` on the outcome page. Accepted risk **AR-29** — revisit if Phase 2 makes an account's vote history valuable enough to be worth planting |
| T-01-62 | Denial of Service | Mail-security scanner prefetching and consuming a link before the visitor clicks | low | accept | Only `GET` is registered for `/auth/verify` and chi does not auto-map HEAD, which removes HEAD-only scanners. A full-GET scanner still consumes the link; the already-used outcome page is the designed graceful-degradation path and D-01 explicitly rules out adding a confirmation click.
