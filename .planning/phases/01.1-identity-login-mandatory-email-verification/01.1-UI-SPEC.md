# Phase 1.1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Provenance note:** This phase introduces no parallel design language. Every token in this
document (spacing, type, base color) is **inherited unchanged from `01-UI-SPEC.md`** (Phase 1's
design contract) and restated here in full so this file validates standalone against the six
checker dimensions without requiring a cross-reference. The only genuinely new visual surface is
the rotating-globe login background (see "Globe Background" under Color) and five new icons (see
"New Icons"). No new CSS custom property is introduced anywhere in this phase — see "Token
Discipline" under States & Interactions.

**Source decisions:** `01.1-CONTEXT.md` D-01 through D-11 (magic link, 5-minute expiry, 30–60s
resend cooldown, login-required-to-view-anything, ambient globe background, long-lived
multi-device sessions, explicit logout, no account recovery).

## Color

Inherited unchanged from Phase 1 — restated in full so this dimension validates standalone.

### Base surfaces & text

| Role | CSS variable | Light | Dark | Usage (this phase) |
|------|-------------|-------|------|----------------------|
| Dominant (60%) | `--color-bg` | `#FFFFFF` | `#0B0D10` | Login gate page background, profile page background |
| Secondary (30%) | `--color-surface` | `#F1F3F4` | `#16181C` | Login card/panel background, profile report-row alternating background |
| Border | `--color-border` | `#E1E4E8` | `#2A2D31` | Login card outline, input borders, profile section dividers, globe wireframe lines |
| Text primary | `--color-text` | `#1A1D21` | `#F3F4F6` | Headings, form labels, primary button fill (inverted role) |
| Text muted | `--color-text-muted` | `#6B7280` | `#9CA3AF` | Helper copy, cooldown countdown text, placeholder text, globe wireframe lines |
| Focus ring | `--color-focus-ring` | `#1A1D21` (2px solid, 2px offset) | `#F3F4F6` (2px solid, 2px offset) | Keyboard focus outline on the email input, submit button, resend button, logout button |

### Accent — this phase has no severity concept

Phase 1's accent role is the severity palette (traffic-light colors reserved for confirm/dispute
trust signaling). **This phase has no severity data and introduces no new accent color.** The
10% accent budget in this phase's UI is spent entirely on one reused token:

| Role | CSS variable | Light | Dark | Usage |
|------|-------------|-------|------|-------|
| Accent (10%) | `--color-severity-critical` (reused, not new) | `#C0392B` | `#E5695C` | Inline error/validation text ONLY — malformed-email message, rate-limit notice, link-expired inline notice on the "check your inbox" screen. Directly matches Phase 1's existing precedent at `modal.css:235` (`#form-error { color: var(--color-severity-critical); }`) — this phase reuses that exact pattern, does not invent a new red. |

**Accent reserved for:** inline error/validation copy only (the row above). Nothing else in this
phase uses accent color.

**Explicitly NOT used for:** the magic-link submit button, resend button, "Refresh" button, "Log
out" button, the globe background, or any link/decorative element. Those use the neutral roles
below, exactly as Phase 1's FAB and "Post report" button do.

### Neutral (non-severity) interactive elements

| Element | Light | Dark |
|---------|-------|------|
| Magic-link submit button, resend button, "Refresh" button, "Log out" button, link-landing "Send new link" / "Continue" buttons | `#1A1D21` bg / `#FFFFFF` text | `#F3F4F6` bg / `#0B0D10` text |
| Login card panel | `--color-surface` bg, `--color-border` 1px outline | same |

High-contrast neutral, inverted-role buttons — identical treatment to Phase 1's FAB/"Post report"
button, per D-10's "not a heavily-branded consumer look."

### Destructive

**None in this phase.** No delete-account flow exists in v1 (D-11: losing email access means
starting fresh, not deleting anything). Logout (D-09) is non-destructive and fully recoverable —
the same email can simply be re-verified — so it needs no confirmation dialog and no destructive
color treatment. It uses the same neutral inverted button style as every other primary action
above.

### Globe Background (the one new decorative surface — palette locked, not left open)

The rotating-globe ambient background (D-06, D-07) is a monochrome wireframe drawn **exclusively**
from three already-declared neutral tokens — no new hue, no blue "ocean" color, no gradient:

| Element | CSS variable |
|---------|-------------|
| Globe meridian/graticule lines | `--color-border` |
| Globe outline / limb | `--color-text-muted` |
| Globe fill (if any solid area is used) | `--color-surface` |

Opacity: dim enough that the login card (`--color-surface` panel + `--color-border` outline) reads
as the clear foreground with full text contrast — treat the globe as a background texture, not a
competing visual element. Do not let the globe cross behind the card at full opacity; reduce its
opacity (e.g. 30–50%) or restrict it to the page margins outside the card, executor's choice, as
long as the card's text/border contrast ratios are unaffected.

**Implementation constraints (prescriptive, not exploratory):**
- **Do NOT** use `three.js`, `globe.gl`, WebGL, or any CDN-hosted animation library. This sits on
  the mandatory login gate for an emergency-reporting app — a heavy asset blocking access to
  flood/hazard info on a degraded connection is a real product defect, not a cosmetic risk (Phase
  4 explicitly ships a low-bandwidth mode later; don't create a heavyweight dependency now that
  contradicts it). It would also inherit Phase 1's WebGL-fallback obligation (MapLibre already
  requires one) for zero product benefit on a decorative background.
- **Implement as:** a single self-hosted SVG (committed under `/static/icons/` or a new
  `/static/img/globe.svg`, budget under 10KB) — e.g. a wireframe sphere built from graticule
  circles/ellipses — animated with a plain CSS `@keyframes` `transform: rotate(...)` (or
  `background-position` shift on a repeating pattern), no JS animation library, no runtime CDN
  fetch.
- **`prefers-reduced-motion: reduce`:** the globe renders as a single static frame, animation
  fully disabled — same precedent as Phase 1's toast/skeleton reduced-motion rules
  (`main.css`/`modal.css`).

## States & Interactions

This phase adds five new screens/states to Phase 1's shell (login gate, check-your-email,
link-landing outcomes ×4 sharing one template, and profile page) plus a global access gate. None
of Phase 1's existing map/feed/modal interaction contracts change — this section covers only what
`01-UI-SPEC.md` doesn't.

### Access gate (D-05 — login required to view anything, not just to act)

1. Any unauthenticated request to any route is served the login gate screen full-bleed, **replacing
   the entire Phase 1 app shell** — no partial page load first.
   **Do NOT** render a dimmed, blurred, or otherwise partially-visible preview of the map/feed
   behind the login wall. D-05 means zero content visibility for an unverified visitor, not
   reduced visibility — a blurred map preview is the instinctive move here and it violates D-05.
2. The globe background renders immediately and continuously (see Color → Globe Background); the
   email input + submit button are interactive from first paint — no sequential "wait for
   animation, then see the form" step, no skip button (there is nothing to skip).
3. The gate replays identically every time login is needed — session expired, explicit logout, new
   device — not only on a visitor's first-ever visit (D-07).

### Requesting the link

4. Submit (valid email) → button shows "Sending…", disabled → on success, the screen transitions
   in place (globe background persists, does not restart or flash) to "Check your inbox".
5. Malformed email → inline error below the field, `--color-severity-critical` text, per Phase 1's
   `#form-error` precedent; button stays idle, no request sent.
6. Rate limit hit (either the per-address or per-IP limiter from IDENT-04) → generic inline error
   (copy above); the resend cooldown timer does **not** start, since no email was actually sent.

### Check your inbox (waiting state)

7. Shows heading/body/resend/refresh per Copywriting Contract above.
8. Resend cooldown (D-03, 30–60s): button disabled, label shows a live per-second countdown
   ("Resend in 45s" → "Resend in 44s" → …) rather than a mysteriously inert disabled button; at 0
   it re-enables and reads "Resend link" again.
9. Link expiry (D-02, 5 minutes from send) is a **separate, independent timer** from the resend
   cooldown — never conflate them in copy or logic. If 5 minutes pass with no verification, an
   inline "This link has expired" notice appears in this same screen; the resend button/cooldown
   continues to operate on its own clock regardless.
10. **Cross-device click (explicit, since this is the classic magic-link failure mode):** this
    stack has no polling/websockets, so the tab that requested the link cannot detect that it was
    clicked elsewhere. Verification only completes on whichever browser/device actually opens the
    link. If the visitor opens the email on a different device/browser than the one showing "Check
    your inbox," this waiting tab has no way to know and stays in this state until manually
    refreshed — this is expected behavior, not a bug to work around.
11. "Refresh" reloads the current page: if this exact browser/device is the one that clicked the
    link (its session cookie is now set), the reload lands the user directly in the verified app
    shell; otherwise it simply re-shows this same waiting state.

### Clicking the emailed link (separate page/route — the actual authentication event)

12. Valid, unexpired, unused token → server sets the verified session cookie (extends Phase 1's
    existing cookie mechanism per D-08/IDENT-05, same 1-year `MaxAge`) → shows the "Email verified"
    success screen → auto-redirects into the app shell after ~1.5s. Provide the "Continue" link as
    a functioning non-JS fallback, not decoration — do not block entry solely on a JS redirect
    firing.
13. Expired / already-used / malformed token → the corresponding outcome screen above, all three
    sharing **one page template** (heading/body swap only) — do not build three separate page
    layouts for this.

### Profile page (IDENT-03)

14. Reachable via a new, minimal persistent header entry point (a small profile icon/link — Phase
    1 shipped no header at all, so this is a genuinely new element; keep it to a single icon-button
    using the `user` glyph, neutral style, top-right, consistent with the FAB's icon-only,
    unobtrusive treatment).
15. Two sections, always both present: "Your reports" (the user's own submitted reports, reusing
    Phase 1's existing `.report-row` list rendering and severity-first ordering rules verbatim —
    no new list component) and "Your activity" (confirm/dispute history).
16. "Your activity" is a **real, always-empty state in this phase** (scope note: Phase 1.1 ships
    before Phase 2, so no confirm/dispute data model exists yet) — show the empty-state copy above,
    worded so it reads as "not launched yet," not "broken." Do not omit the section entirely and do
    not fabricate placeholder data.
17. "Your reports" empty state (new user with nothing submitted) uses the empty-state copy above.
18. "Log out" is a plain neutral button (same inverted style as other primary actions), no
    confirmation dialog — see Copywriting → Destructive actions.

### Token discipline

19. This phase introduces **zero new CSS custom properties**. Every color, spacing, and type value
    above reuses Phase 1's existing `--color-*`, `--space-*`, and `--font-*` variables verbatim. The
    only new static assets are: one committed globe SVG and five new committed icon SVGs (see
    "New Icons"). Do not create a parallel `--color-auth-*`/`--space-auth-*` token set.
