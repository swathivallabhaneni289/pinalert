## User Constraints (from CONTEXT.md)

### Locked Decisions

**Verification mechanism**
- **D-01:** Email verification is a **magic link**, not a typed OTP code — the verification email
  contains a link; clicking it verifies the account. No code to type or mistype.
- **D-02:** The verification link expires after **5 minutes**.
- **D-03:** A new verification email can be requested after a **30-60 second cooldown**.
- **D-04:** No "wrong attempts" concept applies — IDENT-04's rate limiting applies to
  *verification-email send requests* per address and per IP, not to guess attempts.

**Login gate placement**
- **D-05:** Login is required to view **anything** — no anonymous browsing at all.
- **D-06:** The landing screen shows a **rotating globe animation as a continuous ambient
  background** — not a blocking sequential intro. Login form is layered on top, interactive
  immediately.
- **D-07:** The globe-animation background replays every time login is needed (session expired,
  logged out, new device) — not just first-ever visit.

**Session persistence**
- **D-08:** Once verified, login is **long-lived on that device** — reuses Phase 1's existing
  session-cookie mechanism (1-year `MaxAge`, `internal/session/cookie.go`).
- **D-09:** An explicit **"Log out"** action exists and clears the session cookie.
- **D-10:** The same verified account **can be logged in on multiple devices simultaneously** —
  each device gets its own independent session after its own verification.

**Account recovery**
- **D-11:** There is **no account-recovery mechanism** for v1. Losing access to signup email means
  verifying a new email and starting a fresh account.

## Summary

This phase adds passwordless email authentication on top of Phase 1's existing anonymous,
HMAC-signed session cookie — it does not replace that cookie mechanism (D-08/IDENT-05), it gates
what an unverified session is allowed to reach. The standard, industry-verified shape for this is:
a visitor requests a link for an email address; the server mints a high-entropy random token,
stores only its SHA-256 hash with a 5-minute expiry, and emails the raw token via Resend; clicking
the link atomically consumes the token (single UPDATE with `used_at IS NULL AND expires_at > now()`,
checked by rows-affected) and marks the **current browser's session row** verified against an
`accounts` row resolved (created-if-absent) from that email.

The one design decision with outsized leverage for Phase 2 is this: **because D-10 explicitly
allows one verified account to hold many independent device sessions, the account is the identity
Phase 2's independence predicate must dedupe on — not the session.** `reports`/votes stay keyed on
`session_id` per IDENT-05 (no schema change to that column), but `account_id` must be reachable
from every session row via a join, or Phase 2's whole reason for existing (closing the
multi-device gaming gap) silently fails to hold. The profile page (IDENT-03) needs the exact same
join, for the exact same reason — get it right once, in one place.

The other outsized-risk item is Resend's sandbox restriction: **before a custom domain is
verified with Resend, `onboarding@resend.dev` only delivers to the Resend account owner's own
signup email — not to arbitrary visitor addresses.** For a project whose whole audience is
"anyone can verify any real email," this is a genuine launch blocker, not a formatting detail, and
CONTEXT.md does not address it. It is flagged prominently below and in Open Questions.

**Primary recommendation:** Model identity as `accounts` (one row per verified email, created
lazily at successful-verification time) with `sessions.account_id` as a nullable FK set only on
verification; gate all app routes except the auth endpoints and static assets behind a chi
middleware checking `account_id IS NOT NULL`; send mail via `resend-go` v3 behind a small `Mailer`
interface (dev/test get a log-only fake, matching the existing `loadSessionSecret` fail-fast
pattern); rate-limit the send endpoint with a DB-backed per-email cooldown (authoritative, survives
restarts) plus an in-memory per-IP token bucket (secondary, matches `golang.org/x/time/rate`,
already the project's chosen library for this exact class of problem).

### Alternatives Considered

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| `resend-go` (locked by CONTEXT.md/PROJECT.md) | Raw `net/smtp` against a free relay (e.g., Gmail SMTP) | Not evaluated as a real alternative — CONTEXT.md/PROJECT.md already locked Resend for cost, deliverability (DKIM/SPF handled), and dashboard visibility. Listed only for completeness |
| `accounts` table + `sessions.account_id` FK | Store `email`/`verified_at` directly on `sessions`, no separate table | **Rejected.** D-10 (same account, many simultaneous device sessions) cannot be modeled by denormalizing email onto each session row without duplicating and drifting the same email across N rows — a real `accounts` row is the only way one email maps to one identity across many sessions |
| DB-backed per-email cooldown | Purely in-memory per-email limiter (same map+mutex shape as the per-IP limiter) | **Rejected as sole control.** The free-tier host (Render, per PROJECT.md) sleeps and cold-starts, wiping in-memory state; the per-email cooldown exists specifically to protect a scarce, real, cross-restart resource (Resend's 100/day quota), so it must be the DB-backed, restart-surviving check. The per-IP limiter has a weaker consequence if reset by a restart, so in-memory is an acceptable secondary control there |
| SHA-256 hash of the raw token in `magic_link_tokens` | bcrypt/argon2 of the token | **Rejected.** bcrypt/argon2 exist to slow down brute-forcing a *low-entropy* human secret (a password). A 256-bit CSPRNG token has no brute-forceable low-entropy structure — a slow hash only adds attacker-irrelevant latency to every legitimate verify request. SHA-256 (fast, one-way, sufficient) is the correct primitive here, matching the industry pattern surfaced in research (Auth0/Supabase/Clerk-class implementations) |

### System Architecture Diagram

```

   │
   ▼
 GET /  ──────────────► [access-gate middleware] ── unverified? ──► render login-gate template
   │                                                                  (globe bg, email form — SSR,
   │                                                                   no JS required for the gate
   │                                                                   itself)
   │  verified? ──► pass through ──► existing app shell (map/feed, unchanged from Phase 1)
   │
   ▼
 POST /api/auth/request-link  (email in body)
   │
   ├─► net/mail.ParseAddress validation ──fail──► 400 {field, message}
   │
   ├─► per-IP token-bucket check (golang.org/x/time/rate, in-memory) ──fail──► 429 generic message
   │
   ├─► per-email cooldown check (SELECT MAX(created_at) FROM magic_link_tokens WHERE email=$1)
   │     within 30–60s? ──fail──► 429 generic message, NO row inserted, cooldown untouched
   │
   ├─► INSERT magic_link_tokens (token_hash, email, expires_at)   ◄── cooldown clock starts HERE,
   │     (this is the record IDENT-04 is actually protecting —        before the Resend call, so a
   │      it must exist even if the send below fails)                 failing/quota-exhausted send
   │                                                                    still consumes the cooldown
   ├─► Mailer.SendVerificationLink(ctx, email, rawToken) ──fail──► log server-side, generic 500
   │     (resend-go in prod; log-only fake in dev/test — never a live network call in CI)
   │
   └─► 200 → client shows "Check your inbox"

 Visitor clicks emailed link:
 GET /auth/verify?token=...
   │
   ├─► sha256(token) lookup
   ├─► atomic single-use consume:
   │     UPDATE magic_link_tokens
   │     SET used_at = now()
   │     WHERE token_hash = $1 AND used_at IS NULL AND expires_at > now()

   │   (0 rows affected → expired/used/malformed outcome page; exact cause distinguished by a
   │    cheap prior read, not by the atomic update's own result)
   │
   ├─► conflict check: is THIS browser's current session already verified under a DIFFERENT
   │     account than the email just resolved? ──yes──► refuse-to-rebind outcome (see Pitfall
   │     "Fifth link-landing state" below — this is the concrete defense against the
   │     attacker-distributes-their-own-link threat, and it does not break D-07's cross-device
   │     support, because that case only ever hits an UNverified session)
   │
   ├─► resolve accounts row for email: INSERT ... ON CONFLICT (email) DO NOTHING, then SELECT
```

### Pattern 1: Lazily-created accounts, eagerly-issued sessions

**What:** A `sessions` row is created for every visitor immediately (Phase 1's unchanged
behavior). An `accounts` row is created only at the moment a magic link is successfully consumed —
never at "request link" time, never speculatively.
**When to use:** Any time an anonymous-first identity model is retrofitted with an authenticated
layer, and you need to avoid creating orphaned "pending" accounts for emails that never actually
verify (e.g., someone fat-fingers an email they don't own — no permanent row should exist for it).
**Example:**
```sql
-- Source: standard upsert-then-select pattern, cross-checked against magic-link
-- implementation guides [CITED: multiple, see Sources]
-- name: ResolveAccount :one
INSERT INTO accounts (email) VALUES (sqlc.arg(email))
ON CONFLICT (email) DO NOTHING;

-- (sqlc needs the INSERT and the SELECT as two statements, since ON CONFLICT DO
--  NOTHING returns nothing on the conflict path — RETURNING would be empty)
-- name: GetAccountByEmail :one
SELECT id, email, created_at FROM accounts WHERE email = sqlc.arg(email);
```

### Pattern 2: UPSERT the session→account binding, never UPDATE

**What:** The verify handler must bind `account_id` onto the session with
`INSERT ... ON CONFLICT (session_id) DO UPDATE`, not a bare `UPDATE ... WHERE session_id = $1`.
**When to use:** Always, in this codebase specifically — `internal/session/cookie.go`'s
`Middleware` calls `persist` (which does `UpsertSession`) and, on failure, **logs and continues,
still setting the signed cookie** (`cookie.go:106-121`). That means a browser can legitimately hold
a valid signed session cookie with **no corresponding `sessions` row at all** (e.g., a transient DB
hiccup on first visit). A bare `UPDATE` against that session_id silently affects zero rows — the
email sends, the click "succeeds" from the visitor's perspective, but the gate still reads
"unverified" on the very next request, and the token is now consumed. This is a genuine dead-end
bug class unique to this codebase's existing failure-tolerant session design, not a generic magic
link concern.
**Example:**
```sql
-- name: BindSessionAccount :exec
INSERT INTO sessions (session_id, account_id)
VALUES (sqlc.arg(session_id), sqlc.arg(account_id))
ON CONFLICT (session_id) DO UPDATE SET account_id = EXCLUDED.account_id;
```
The access-gate middleware's read side must mirror this defensiveness: **no row found for this
session_id must be treated identically to "unverified,"** never surfaced as a 500.

### Pattern 3: Dedupe on `account_id`, not `session_id` — the whole point of this phase

**What:** Every place that currently reasons about "distinct sessions" for trust/aggregation
purposes must, from this phase forward, resolve to the underlying `account_id` via a join through
`sessions`, not stop at `session_id`.
**When to use:** Two concrete call sites exist right now, and a third is load-bearing for Phase 2:
1. **IDENT-03's profile page** ("Your reports"): a verified account may have submitted reports
   from *several different device sessions* (D-10). Filtering `WHERE reports.session_id = $current`
   would only show reports from *this one device* — silently wrong the moment the same person's
   second device is in play.
2. **Phase 2's TRUST-03** ("distinct session AND distinct geohash cell"): this phase was inserted
   specifically because the user judged raw session-counting gameable via multiple devices from one
   person (see `01.1-CONTEXT.md`'s Phase Boundary). If Phase 2 implements "distinct session" as
   literal `session_id` distinctness without resolving through `account_id`, **the independence
   predicate is exactly as gameable as before this phase existed** — one person on three devices is
   three "independent" votes. State this explicitly in Phase 2's own planning: TRUST-03's
   "distinct session" must mean "distinct `account_id`," with `session_id` retained only as the
   write-path identity column (IDENT-05).
**Example:**
```sql
-- name: ReportsByAccount :many
-- Note: LEFT JOIN, not INNER — see "Existing anonymous data has no account" in Common Pitfalls.
SELECT r.* FROM reports r
JOIN sessions s ON r.session_id = s.session_id
WHERE s.account_id = sqlc.arg(account_id)
ORDER BY r.created_at DESC;
```
**Schema decision required:** migration `00001_create_reports.sql` never added a foreign key from
`reports.session_id` to `sessions.session_id`. Recommend adding it now
(`ALTER TABLE reports ADD CONSTRAINT fk_reports_session FOREIGN KEY (session_id) REFERENCES
sessions(session_id)`), both for referential integrity and so a future `INNER JOIN` here is
provably safe — but until that constraint exists and is confirmed clean against any real data, keep
this specific query as a plain `JOIN` only after confirming zero orphaned `reports.session_id`
values in the target environment, or use `LEFT JOIN` defensively if that confirmation isn't
practical before this phase ships.

### Anti-Patterns to Avoid

- **Denormalizing email onto `sessions` directly (no `accounts` table):** breaks D-10 the moment
  the same person verifies from a second device — you'd either duplicate the email across rows
  (no single identity to dedupe on) or need a separate lookup table anyway, which is just
  `accounts` with extra steps.
- **Rate-limiting only at the "request link" endpoint and treating the "verify" endpoint as safe
  because tokens are unguessable:** true that 256-bit entropy makes brute force infeasible without
  any rate limit — but pair this with actually using the full entropy (see Code Examples), don't
  quietly ship a shorter token "for URL readability."
- **Binding the magic-link token to the *requesting* browser session:** would break D-07's
  explicitly-locked cross-device verification support (open the email on your phone, verify while
  the laptop tab requested it). Do not add this binding even though it would look like a natural
  CSRF-hardening step — the correct mitigation for the cross-user-link-sharing threat this would
  otherwise address is the same-account-conflict check in Pattern above, not session-binding.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Email address syntax validation | Custom regex | `net/mail.ParseAddress` (stdlib) | Avoids a documented ReDoS/false-negative-prone hand-rolled pattern; reject any non-empty `Name` field to keep it a bare-address check |
| Transactional email delivery (SMTP, retries, DKIM/SPF, deliverability) | Raw `net/smtp` against a relay | `resend-go` v3 client | CONTEXT.md/PROJECT.md-locked choice; hand-rolling SMTP delivery/deliverability is exactly the kind of "looks simple, isn't" problem this heuristic exists for |
| Per-IP request throttling | A homemade counter+timestamp map | `golang.org/x/time/rate`'s `Limiter` (token bucket) | Already the project's named standard for this exact class of problem (see CLAUDE.md's Supporting Libraries table) |
| Single-use token consumption under concurrent requests | Read-then-write (`SELECT used_at`, then `UPDATE` if null) | One atomic `UPDATE ... WHERE used_at IS NULL AND expires_at > now()` checked by rows-affected | The read-then-write shape has a TOCTOU race: two concurrent clicks (e.g., a real user plus a mail-scanner prefetch landing at nearly the same instant) could both pass the read check before either writes. A single conditional `UPDATE` is atomic under Postgres's row-level locking — exactly the same reasoning the industry sources converge on |

**Key insight:** every item above already has a battle-tested, narrowly-scoped answer; the actual
engineering work in this phase is the *schema/identity modeling* (accounts vs. sessions,
account-dedupe for Phase 2) — not any of the primitives above.

## Common Pitfalls

### Pitfall 1: Profile page (or Phase 2) filters by `session_id` instead of `account_id`
**What goes wrong:** A verified user's reports/votes from a second device silently don't appear;
Phase 2's independence predicate stays gameable via multiple devices — the exact problem this
phase exists to close.
**Why it happens:** `session_id` is the column every existing query (`reports.sql`) already keys
on — it's the path of least resistance to just keep using it.
**How to avoid:** Always resolve to `account_id` via the `sessions` join (Architecture Patterns,
Pattern 3) for anything IDENT-03 or Phase 2's TRUST-03 touches.
**Warning signs:** A query or requirement description that says "distinct session" without also
saying "→ distinct account."

### Pitfall 2: `UPDATE sessions SET account_id = …` instead of UPSERT
**What goes wrong:** A visitor whose `sessions` row failed to persist on first visit (a real,
already-handled failure path in `cookie.go:106-111`) clicks a valid magic link, the token is
consumed, and nothing happens — no row to update. They see "verified," reload, and the gate still
blocks them. The token is now burned; they must request a new one.
**Why it happens:** `UPDATE` silently no-ops on a missing row; nothing errors, so this ships
invisibly in normal testing (where the sessions row almost always already exists).
**How to avoid:** `INSERT ... ON CONFLICT (session_id) DO UPDATE SET account_id = ...` (Pattern 2).
**Warning signs:** A verify-handler test that never exercises "session row absent at verify time."

### Pitfall 3: Cooldown record inserted only after a successful Resend call
**What goes wrong:** If Resend's call fails — including a 429 once the 100/day free-tier quota is
exhausted — no cooldown row is written, so the client can retry immediately and indefinitely
against the exact scarce resource IDENT-04 exists to protect.
**Why it happens:** It reads naturally as "insert the token row once we know we actually sent
something." UI-SPEC's own copy ("the resend cooldown timer does not start, since no email was
actually sent") reinforces this instinct — but that clause is scoped to the *rate-limit-rejected*
path (item 6 in UI-SPEC's "Requesting the link" section), not to a downstream send failure.
**How to avoid:** Insert the `magic_link_tokens` row (starting the cooldown clock) *before* calling
`Mailer.SendVerificationLink`, not after. A send failure still leaves the cooldown active; a
rate-limit rejection (checked *before* the insert) correctly never touches it — these are two
different points in the request flow and must not be collapsed into one.

### Pitfall 4: Missing fifth link-landing state — same-browser, different-account conflict
**What goes wrong:** UI-SPEC's `01.1-UI-SPEC.md` specs exactly four link-landing outcomes
(verified / expired / already-used / malformed). It does not specify what happens when a token for
`b@example.com` is clicked in a browser whose *current* session is already verified as
`a@example.com`. Silently re-binding the session to the new account is the literal mechanism of an
attacker-distributes-their-own-magic-link attack: get a victim (already verified as themselves) to
click a link the attacker requested, and the victim's browser is now transacting as the attacker's
account.
**Why it happens:** It's the one link-landing branch nobody thinks to ask about, because the
"happy path" (unverified browser clicks its own link) and the intentional cross-device case (D-07,
an *unverified* browser opens a link requested elsewhere) both work fine without this check.
**How to avoid:** This is a genuine **UI-SPEC gap, not an implementation detail** — flag it for the
planner to resolve explicitly (recommend: refuse to re-bind, show a distinct outcome — e.g. "This
link is for a different account. Log out first." — rather than silently switching identities).
This does not conflict with D-07: D-07's cross-device case only ever involves an *unverified*
session; this conflict check only fires when the current session is *already* verified as someone
else.
**Warning signs:** A verify-handler implementation with only four outcome branches.

### Pitfall 5: `testutil.Truncate` doesn't know about the new tables
**What goes wrong:** `internal/testutil/db.go`'s `Truncate` hardcodes
`"TRUNCATE reports, sessions RESTART IDENTITY CASCADE"`. Left unchanged, `accounts` and
`magic_link_tokens` rows accumulate across test runs and leak between packages sharing one Postgres
instance under CI's `-p 1` flag (see `.github/workflows/ci.yml`'s own comment on why `-p 1` is
required at all).
**How to avoid:** Add both new tables to the `TRUNCATE` statement in the same plan that adds the
migration.

### Pitfall 6: `RESEND_API_KEY` unset breaks local dev and CI
**What goes wrong:** Without a fallback, every local `go run`/`go test` invocation and every CI run
either needs a real (rate-limited, quota-metered) Resend key or fails outright.
**How to avoid:** Mirror `cmd/server/main.go`'s existing `loadSessionSecret` shape exactly: fatal
if unset outside `ENV=development`; inside `ENV=development` (and in all Go tests, via constructor
injection of a fake `Mailer`), fall back to a log-only mailer that prints the raw verification link
to stdout instead of calling Resend. CI must never make a live network call to Resend — the
handler/service tests should inject the fake `Mailer`, not the real one, the same way store tests
already inject `testutil.NewTestDB`.

### Pitfall 7: Swagger spec silently goes stale
**What goes wrong:** `internal/api/handlers/reports.go`'s existing swag annotation on
`POST /api/reports` literally states *"no signup or authentication is required."* Once the access
gate ships, that sentence is false, and `TestSwaggerSpecCoversRoutes` (per `01-SECURITY.md`'s
T-01-26 (01-07)) exists specifically to catch route/behavior drift.
**How to avoid:** Update the doc-comment annotations and regenerate (`swag init` /
`make swag`, per the existing `Makefile` target) as an explicit task in this phase's plan, not an
afterthought.

### Pitfall 8: Existing anonymous sessions/reports have no `account_id` and never will, retroactively
**What it means:** Every `sessions`/`reports` row that existed before this phase ships has
`account_id = NULL` and no way to acquire one — there is no migration path from "anonymous
session" to "this was actually person X" after the fact. Pre-existing reports simply never appear
on anyone's profile page. **This is expected, not a bug** — record it as a one-line note rather
than silently discovering it during UAT.

## Common Threat Pattern — worth its own callout (see Security Domain for the formal register)

**An attacker can distribute their own not-yet-clicked magic link to get a victim's browser to
"verify" as the attacker's account.** Because tokens are single-use, this only ever succeeds against
one victim per token, and only within the 5-minute expiry — but it is real, and it is the direct
reason Pitfall 4's conflict check exists. It is fundamentally inherent to any bare magic-link
scheme (this is not specific to this codebase), and the standard mitigation — binding the token to
the requesting session — is explicitly unavailable here because D-07 locks in cross-device
verification as intended behavior. The conflict check (refuse to silently re-bind an
already-verified session to a different account) is the mitigation compatible with D-07.

## Code Examples

### Token generation and hashing
```go
// Source: pattern derived from crypto/rand + crypto/sha256 stdlib docs, cross-checked against
// magic-link implementation guides converging on >=256-bit entropy [CITED: multiple sources, see
// Sources section]. Mirrors internal/session/cookie.go's existing crypto/rand.Read usage, sized up.
const tokenBytes = 32 // 256 bits — same entropy floor the researched implementations converge on

func GenerateToken() (raw string, hash string, err error) {
	buf := make([]byte, tokenBytes)
	if _, err := rand.Read(buf); err != nil { // crypto/rand, never math/rand
		return "", "", err
	}
	raw = base64.RawURLEncoding.EncodeToString(buf) // goes in the emailed URL
	sum := sha256.Sum256([]byte(raw))
	hash = hex.EncodeToString(sum[:]) // goes in the database — raw value never stored
	return raw, hash, nil
}
```

### Atomic single-use token consumption
```sql
-- name: ConsumeToken :one
-- A single conditional UPDATE, not read-then-write — see Don't Hand-Roll's TOCTOU note.
UPDATE magic_link_tokens
SET used_at = now()
WHERE token_hash = sqlc.arg(token_hash)
  AND used_at IS NULL
  AND expires_at > now()
RETURNING email;
-- sqlc's :one returns pgx.ErrNoRows when zero rows match (already-used, expired, or unknown
-- token) — the handler distinguishes *which* by a preceding cheap SELECT for the outcome copy
-- UI-SPEC requires (expired vs. already-used vs. malformed), not by parsing this error.
```

```sql
-- +goose Up (00002_add_accounts_and_verification.sql, illustrative — planner finalizes exact DDL)
```

### Mailer interface (testability seam)
```go
// Source: standard Go dependency-injection shape, matching this codebase's existing
// service.NewReportService(queries) constructor-injection pattern.
type Mailer interface {
	SendVerificationLink(ctx context.Context, email, link string) error

```

## Open Questions

1. **Can a real visitor (not the developer) actually receive the verification email in the
   deployed environment?**
   - What we know: Resend's free tier restricts `onboarding@resend.dev` to delivering only to the
     account owner's own signup address until a custom domain is verified with Resend
     (DNS records added, DKIM/SPF configured).
   - What's unclear: whether a custom domain will be available/verified before this phase is
     demoed to anyone other than the developer. Neither CONTEXT.md nor PROJECT.md addresses domain
     ownership/verification at all.
   - Recommendation: resolve this explicitly before planning treats IDENT-02 as "just call the
     API" — either (a) secure and verify a domain in Resend before this phase's deploy step, or
     (b) explicitly scope v1's demo narrative to acknowledge that only the developer's own email
     can complete the flow until a domain exists, and say so in the plan rather than discovering it
     during UAT.

2. **Should the FK from `reports.session_id` to `sessions.session_id` be added in this phase's
   migration, or deferred?**
   - What we know: it doesn't exist today (migration `00001` never added it); adding it now makes
     Pattern 3's join provably safe as an `INNER JOIN` rather than requiring a defensive
     `LEFT JOIN`.
   - What's unclear: whether any orphaned `reports.session_id` values already exist in whatever
     environment this ships against (unlikely, since nothing ever deletes a `sessions` row, but not
     independently confirmed here).
   - Recommendation: add the constraint; if it fails to apply, that failure itself is the answer
     (orphans exist and need investigation before proceeding) — don't skip the attempt.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes | Magic-link possession-factor auth; 256-bit CSPRNG token, 5-minute expiry, single-use, generic error messages that don't reveal whether an address has an account (already locked in UI-SPEC's copy) |
| V3 Session Management | yes | Existing `internal/session/cookie.go` HMAC-signed cookie, unchanged; new binding is the `sessions.account_id` FK, set only server-side |
| V4 Access Control | yes | chi middleware gate checking `account_id IS NOT NULL`, applied via route grouping so any route outside the group is unprotected *by construction* — matches this codebase's existing explicit-middleware-application style |
| V5 Input Validation | yes | `net/mail.ParseAddress` for email syntax; existing `MaxBytesReader` + `DisallowUnknownFields` pattern from `reports.go` reused for the new request-link endpoint |
| V6 Cryptography | yes | `crypto/rand` for token generation (never `math/rand`), `crypto/sha256` for at-rest storage (never storing the raw token) |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Token brute force | Spoofing | 256-bit entropy makes this infeasible without relying on rate limiting as the primary control (rate limiting is IDENT-04's job for the *send* endpoint, a different resource) |
| Email enumeration (does this address have an account?) | Information Disclosure | Generic response copy regardless of outcome — already locked in UI-SPEC ("does not reveal which limiter tripped or whether the address exists") |
| Attacker distributes their own not-yet-clicked magic link to hijack a victim's session identity | Spoofing / Elevation of Privilege | Same-account-conflict check (Pitfall 4) — refuse to silently re-bind an already-verified session to a different account. This is this phase's own genuinely novel threat, not one lifted from a generic checklist — flag prominently in the authored `<threat_model>` |
| Email security scanners pre-fetching/consuming single-use links before the real user clicks | Denial of Service (self-inflicted, degrades UX not security) | Accept, matching the "already-used token" outcome page as the graceful-degradation path (already designed in UI-SPEC); additionally, only registering the verify route for `GET` (chi does not auto-map `HEAD` to a `GET`-only handler the way `net/http.ServeMux` does) cheaply avoids one class of prefetch (`HEAD`-only scanners) without adding the confirmation-click step D-01 explicitly rules out |
| Verify endpoint is a state-mutating `GET` | Tampering (classic REST objection) | Accepted as industry-standard for magic links; the exploitable variant of this concern is already covered by the same-account-conflict + single-use-token mitigations above, not by making it a POST (which would break "click a link" as the entire point of D-01) |
