## Phase Goal

**As a** visitor, **I want to** verify my email with a magic link before I can report or vote, **so that** every report and vote is tied to an accountable, verified identity.

Slice `01.1-01` proved a link can be generated and handed to the mailer seam. This plan makes that link actually arrive in a real inbox, and writes down the one configuration step that no amount of code can substitute for.

<objective>
Complete IDENT-02: a production Resend-backed `Mailer`, an environment loader that fails fast rather than silently degrading, and the deployment documentation that records the custom-domain requirement standing between this code and a real visitor receiving mail.

Purpose: without this plan, the phase ships a verification flow that only works when someone reads the server log. Without the documentation half, the Resend sandbox restriction gets discovered during UAT instead of before deploy.
Output: `internal/mailer/resend.go`, `internal/mailer/loader.go`, the `resend-go/v3` dependency, and a README email/deployment section.
</objective>

## STRIDE Threat Register

Numbering continues the project register; `01.1-02` ended at `T-01-64`, accepted risks at `AR-31`.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-65 | Information Disclosure | `RESEND_API_KEY` leaking through logs or error responses | high | mitigate | The key is read once in `LoadMailer` and held only inside the client; SDK errors are wrapped with an operation name and never the credential; the client-facing response stays the generic 500 from Phase 1's T-01-15 control |
| T-01-66 | Tampering | Supply chain — `github.com/resend/resend-go/v3` | high | mitigate | Version pinned in `go.mod` with a `go.sum` checksum; the package's legitimacy was established against `proxy.golang.org` plus the vendor's own documentation and recorded in RESEARCH.md's Package Legitimacy Audit with an OK verdict (official Resend organisation repository, active v3 line). Go's module checksum database makes a silent post-publication swap detectable at build time |
| T-01-67 | Spoofing | Sending from an unverified sandbox domain | medium | mitigate | `RESEND_FROM` is configurable so a DNS-verified domain replaces the sandbox sender; Task 2 records domain verification as a required pre-launch step. Residual until the domain is verified: mail is undeliverable to third parties rather than spoofable, so the failure mode is availability, not impersonation |
| T-01-68 | Denial of Service | Silent degradation to the log-only mailer in production | medium | mitigate | `LoadMailer` returns an error when the key is absent outside `ENV=development` and `cmd/server/main.go` turns that into a fatal at startup — a misconfigured deploy fails loudly at boot instead of accepting logins nobody can complete |
| T-01-69 | Information Disclosure | Live credential reaching CI or a test run | medium | mitigate | Every mailer test targets the pure body-builder or the loader with `t.Setenv`; no test constructs a live client, and the `Mailer` interface is what lets service and handler tests inject a fake instead |
</threat_model>
