# Phase 01.1 Plan 06: Shared account header partial — trigger, dropdown menu, and the no-store view model Summary

**One shared `account_header.html.tmpl` partial (D-12) rendering an icon-only account trigger and a `role="menu"` dropdown with the verified email, an Activity link, and a real POST logout form; wired into the app shell with a self-contained `account-menu.js` for open/close/focus-trap/dismissal, and `Cache-Control: no-store` on the now-personally-identifying shell response.**

## Performance

- **Duration:** ~25 min
- **Started:** 2026-09-11T19:37:00+05:30 (approx., wave start)
- **Completed:** 2026-09-11T19:54:28+05:30
- **Tasks:** 2 (both `type="auto"`)
- **Files modified:** 17 (7 created, 10 modified)

## Accomplishments

- `web/templates/account_header.html.tmpl`: the entire header in one file, included by both pages via `html/template`'s base-filename resolution (established by 01.1-01's `check_inbox.html.tmpl` pattern) — an `aria-label="Account menu"` icon-only trigger (`aria-haspopup="menu"`, `aria-expanded="false"`, `aria-controls="account-menu"`) plus a `hidden` `role="menu"` panel holding the verified email as plain text, an `<a role="menuitem" href="/profile">Activity</a>`, and a real `<form method="post" action="/auth/logout"><button type="submit" role="menuitem">Log out</button></form>`. No left-slot content of any kind (DEC-S) — the header holds exactly the trigger and the panel.
- `internal/api/handlers/page.go`: `Email` added to `pageViewModel`, populated per request from the gate's resolved account (DEC-P) — a missing account in context is a log-and-500, not a redirect, since the gate should have made that state impossible. `Cache-Control: no-store` set alongside `Content-Type` (DEC-Q): the shell now renders a personal identifier into every response.
- `internal/account` (new leaf package): `Account`, `WithAccount`, `FromContext` — moved out of `internal/api/gate.go` because the plan's literal design (keep the accessor in `internal/api`, have `internal/api/handlers.Page` call it directly) is a compile-time import cycle: `internal/api` already imports `internal/api/handlers` (router.go, gate.go), so the reverse import is impossible. `internal/api` keeps thin `Account`/`AccountFromContext` re-exports for its own same-package callers.
- `web/static/js/account-menu.js`: a self-contained IIFE with zero dependency on `window.Pinalert` or the other four scripts — click toggles the panel and assigns `aria-expanded` in the same function that changes visibility, Escape closes and returns focus to the trigger, a document-level outside-click listener is bound only while open and torn down on close, and Tab/Shift+Tab reuse `modal.js`'s own focusable-element selector and wrap-around logic rather than a second, independently-drifting trap.
- Contract tests: `TestPageShellRendersAccountMenu`, `TestPageShellEscapesAccountEmail` (T-01-88) in `internal/api/handlers/page_test.go`; `web/account_menu_contract_test.go` (six tests covering the id contract, keyboard handlers, aria-expanded assignment, listener add/remove pairing, no-markup-sink, and no-app-shell-dependency); `TestAccountMenuHiddenGuard` in `web/css_contract_test.go`, verified red when the `:not([hidden])` guard is removed and green when restored.

## Decisions Made

- **`internal/account` as a new leaf package** — see key-decisions above. This is the load-bearing structural fix that lets the rest of the plan's design (DEC-P: email reaches the shell from the request context) actually compile.
- **`.account-menu__item` class instead of an ID-prefixed descendant selector** — see key-decisions above; sidesteps a false positive in `TestAccountMenuHiddenGuard`'s broad substring check without weakening what the guard actually protects.
- **Header is `position: fixed`, top-right** — matches the FAB/view-toggle's existing fixed-positioning convention rather than joining normal document flow, so it doesn't disturb `.app-shell`/`#map`'s self-resolving `100vh`/`100dvh` height contract.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `internal/account` leaf package, replacing the plan's "keep AccountFromContext in internal/api" design**
- **Found during:** Task 1
- **Issue:** The plan's DEC-P explicitly designed `internal/api/handlers.Page` to call `api.AccountFromContext` directly. `internal/api` already imports `internal/api/handlers` (router.go registers `handlers.Page`/`handlers.LoginGate`; gate.go imports `handlers.ErrorResponse`/`handlers.ErrorDetail`), so the reverse import needed to satisfy the plan's literal design is a compile-time import cycle — a blocking, non-optional Go build error, not a stylistic preference.
- **Fix:** Moved `Account`, the context key, `WithAccount`, and `FromContext` into a new dependency-free leaf package `internal/account` (mirrors `internal/session`'s and `internal/ratelimit`'s own single-purpose shape). `internal/api/gate.go` now imports it and stores/reads the account through it; `internal/api` keeps `Account` as a type alias and `AccountFromContext` as a thin re-export for its own same-package callers. `internal/api/handlers/page.go` imports `internal/account` directly.
- **Files modified:** internal/account/account.go (new), internal/api/gate.go, internal/api/handlers/page.go, internal/api/handlers/page_test.go
- **Verification:** `go vet ./...` and the full `go test ./...` suite both green; `gate_test.go`'s four existing HTTP-level tests pass unchanged (they never referenced `api.Account`/`AccountFromContext` directly, only the router's observable HTTP behavior).
- **Committed in:** `3b32b51` (Task 1 commit)

**2. [Rule 3 - Blocking] `user.svg`/`log-out.svg` added to `nonCategoryIcons` in `web/css_contract_test.go`**
- **Found during:** Task 1
- **Issue:** `TestCategoryGlyphMaskRulesCoverEveryCategory` (a pre-existing Phase 1 contract test, not owned by this plan) walks every committed icon file and fails if any icon is unclaimed by a `.icon-glyph--{category}` rule. The two new auth-surface icons (styled via `.auth-icon--*`, not `.icon-glyph--*`, following the same pattern as 01.1-01's `mail.svg`/`circle-alert.svg`/`check-circle.svg`) tripped this on first run — a blocking test failure in Task 1's own verify command, not a pre-existing/out-of-scope failure.
- **Fix:** Added both filenames to the existing `nonCategoryIcons` exemption map, same as the three prior auth-surface icons.
- **Files modified:** web/css_contract_test.go
- **Verification:** `go test ./web/... -count=1` green.
- **Committed in:** `3b32b51` (Task 1 commit)

**3. [Rule 1 - Bug] `.account-menu__item` class instead of an ID-prefixed descendant selector for the menu items**
- **Found during:** Task 2
- **Issue:** The original CSS used `#account-menu a[role="menuitem"], #account-menu button[role="menuitem"] { display: flex; ... }` for the menu item layout. `TestAccountMenuHiddenGuard` (this task's own new test) flags any rule whose selector *contains* `#account-menu` and declares `display` without the `:not([hidden])` guard — a correct broad check for the panel's own toggle rule, but it also caught this descendant selector, even though a descendant element's own `display` property never overrides an ancestor's `[hidden]`-driven `display: none`.
- **Fix:** Renamed the selector to a plain `.account-menu__item` class (added to both the `<a>` and `<button>` elements in the template), which carries no `#account-menu` substring and so is outside the guard test's scope, with identical visual/behavioral output.
- **Files modified:** web/templates/account_header.html.tmpl, web/static/css/auth.css
- **Verification:** `TestAccountMenuHiddenGuard` passes; manually confirmed it goes red when `:not([hidden])` is stripped from the panel's own rule and green when restored.
- **Committed in:** `4686bad` (Task 2 commit)

**4. [Rule 3 - Blocking] Literal string "Pinalert" removed from account-menu.js's doc comment**
- **Found during:** Task 2
- **Issue:** An early draft of the file's header comment explained the no-dependency design using the literal phrase "window.Pinalert." This tripped the plan's own acceptance criterion (`grep -c 'Pinalert' web/static/js/account-menu.js` must return 0) and this task's own `TestAccountMenuJSHasNoAppShellDependency` test — a blocking verification failure, not a behavior change.
- **Fix:** Reworded the comment to say "the app shell's global store" instead of naming `Pinalert` directly; no functional code changed.
- **Files modified:** web/static/js/account-menu.js
- **Verification:** `grep -c 'Pinalert' web/static/js/account-menu.js` returns 0; `TestAccountMenuJSHasNoAppShellDependency` passes.
- **Committed in:** `4686bad` (Task 2 commit)
