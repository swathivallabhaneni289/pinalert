## Phase Goal

**As a** visitor, **I want to** verify my email with a magic link before I can report or vote, **so that** every report and vote is tied to an accountable, verified identity.

`01.1-06` made the identity real and readable at `/profile`. This plan gives it a front door: the one place in the running app where a person can see which address they are signed in under, reach their own history, and hand the device back — without hunting for a page.

<objective>
Deliver D-12's account menu: the app-shell header icon opens a dropdown showing the verified email address, an "Activity" item that navigates to the profile page, and a "Log out" item that fires immediately.

Purpose: after `01.1-06` there is no route to `/profile` from inside the running app and no way to log out without typing a URL. D-12 also rejected the obvious shortcut — a bare icon-link straight to the profile page — because logging out should not require a page navigation first. That makes the menu the phase's actual entry point, and its open/close, focus and dismissal behaviour load-bearing rather than decorative.
Output: the app-shell header, `account-menu.js`, the account email on the shell view model, and two contract tests locking the markup and the behaviour.
</objective>

<decisions_resolved>
- **DEC-O — opening the menu requires JavaScript; the logout inside it is still a real form submit.** D-12 moves the logout control into a dropdown, which supersedes the "works with no JavaScript" half of `01.1-06`'s DEC-L. Accepting that is not a quiet downgrade, for two reasons. First, the security property DEC-L actually protects is CSRF resistance, and that comes from the POST plus `SameSite=Lax`, not from the absence of JS — so the menu item stays a `<button type="submit">` inside a real `<form method="post">`, never a `fetch` call, and `T-01-84` carries over untouched. Second, the app shell this menu sits in is already end-to-end JS-dependent: the map, the feed, the submission modal and the store all require it, so a no-JS visitor at `/` sees an empty frame with or without this menu. A `.no-js` CSS reveal or a duplicated `<noscript>` control would buy zero real capability on that page and cost a second copy of the logout form to keep in sync.
- **DEC-P — the email reaches the shell from the request context, not from `PageConfig`.** `PageConfig` is process-wide configuration built once in `cmd/server/main.go`; identity is per-request. The gate from `01.1-04` has already resolved the account, so `Page` reads it the same way `01.1-06`'s `Profile` handler does. The consequence worth planning for: `page_test.go`'s two existing tests build a bare `httptest` request with no gate in front of it, so they must now put an account into the request context themselves — which is why this plan may need to export a context constructor next to `AccountFromContext`.
- **DEC-Q — the gated app shell gets `Cache-Control: no-store`.** Until this plan the shell contained no personal data, so caching it was harmless. It now renders the account's email address on every response. `01.1-06` already applies `no-store` to the logout redirect and the gate applies it to its own redirect (`T-01-86`); this closes the last gap on the one page a person actually leaves open on a shared device.
</decisions_resolved>
