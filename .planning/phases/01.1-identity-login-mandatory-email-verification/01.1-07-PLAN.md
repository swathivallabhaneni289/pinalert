## Phase Goal

**As a** visitor, **I want to** verify my email with a magic link before I can report or vote, **so that** every report and vote is tied to an accountable, verified identity.

This plan makes that identity visible to the person who owns it: a profile page listing what they have contributed, and the endpoint that hands the device back.

<objective>
Deliver IDENT-03's profile page — one merged Activity section per D-13, under `01.1-06`'s shared header — and D-09's explicit logout endpoint, with the reports listing resolved through the account rather than the session.

Purpose: the account-versus-session distinction is the reason this phase exists. The profile page is the first place it becomes visible, and getting the join right here is what proves the model Phase 2's independence predicate will depend on.
Output: `ReportsByAccount`, `GET /profile`, `POST /auth/logout`, and `profile.html.tmpl`.

Scope boundary and wave order: this plan runs **after** `01.1-06`, which owns the header end to end — the partial file, the account-menu markup, `account-menu.js`, the `user` and `log-out` glyphs, and every header rule in `auth.css`. This page includes that partial; it defines no header of its own and copies none of its markup. The order is deliberate: `html/template` fails at execution time on a `{{template}}` call naming a template that is not in the parsed set, so a profile page written before the partial existed would fail its own acceptance tests for a whole wave. Conversely, the two routes this plan registers were already linked from `01.1-06`'s menu as plain path strings, which simply 404'd until now — a dangling link, not a broken render.
</objective>

<decisions_resolved>
Decision letters are register labels assigned when each decision was first made. They are retained across the 2026-09-11 wave swap that moved the account menu ahead of this plan, so they do not run alphabetically with plan order: `01.1-06` carries `DEC-O`–`DEC-S`.

- **DEC-K — logout clears the cookie and leaves `sessions.account_id` intact.** The next request issues a brand-new session id, so the browser is genuinely logged out. The old session row keeps its binding on purpose: it is what still connects reports submitted from that session to the account, which is exactly what the profile page reads. Unbinding it would silently erase a person's own history from their own profile.
- **DEC-L — logout is a `POST`, not a link.** `SameSite=Lax` does not send the session cookie on a cross-site POST, so a forged logout is not possible; the same is not true of a GET. It needs no confirmation dialog — D-11 makes logout fully recoverable by re-verifying the same address (UI-SPEC "Destructive actions in this phase: none"). **Amended 2026-09-11 for D-12:** the control is a real HTML form submit rather than a `fetch` call, and that is what carries the CSRF property above — but it lives in `01.1-06`'s shared header, not in this page's own markup. This plan registers the route the already-shipped control posts to; see `01.1-06`'s DEC-O for what moving it cost and what it did not.
- **DEC-M — the profile query joins through `sessions.account_id` with a plain inner join.** RESEARCH.md suggested considering a defensive `LEFT JOIN`, but with `WHERE s.account_id = $1` the two are equivalent: an orphaned report has no session row and therefore no account, so it is filtered out either way. No foreign key is relied upon — see `T-01-56` in `01.1-01` for why none was added.
- **DEC-N — D-11's "no account recovery" is surfaced, not hidden.** There is no recovery affordance anywhere in the UI, and `01.1-06`'s header menu states plainly which address the account is tied to, on this page as on every other, so a person can see what they would need to keep access to.
- **DEC-T — `GET /profile` sends `Cache-Control: no-store`, for the same reason DEC-Q gave the app shell one.** This page renders the verified address *and* the account's full report history, which is strictly more sensitive than the shell, and a shared or public device is the exact scenario D-09's logout exists for. The gate already sends `no-store` on its own redirect and `01.1-06` sends it on the shell; leaving the one page that lists a person's whole contribution history in a back-button cache would be the last and worst gap of the three.
</decisions_resolved>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| verified session → another account's data | The profile query is the first read scoped to an identity rather than to everyone |
| browser → `POST /auth/logout` | A state-changing request that revokes the caller's own access |
| shared/public device → session cookie, and → the cached profile page | The scenario logout exists for, and the page that lists the most about a person |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-82 | Information Disclosure | Insecure direct object reference — reading another account's reports | high | mitigate | `ReportsByAccount` takes the account id from `AccountFromContext`, resolved server-side by the gate from the signed session cookie. No account, user or report identifier is ever accepted from the query string or body, so there is no parameter to tamper with. `TestProfileListsOwnReportsAcrossSessions` seeds a second account's report and asserts it does not appear |
| T-01-83 | Information Disclosure | Session identifier leaking through the profile payload | medium | mitigate | `ReportsByAccount` selects no session column, continuing Phase 1's T-01-02 control; `TestNearbyReportsExcludesSessionID` remains green alongside it |
| T-01-84 | Tampering | CSRF on logout | low | mitigate | Logout is `POST` only, and `SameSite=Lax` withholds the session cookie from cross-site POST requests, so a forged logout cannot carry an authenticated session. This is the same control Phase 1's AR-02 relied on, and unlike `GET /auth/verify` (see `T-01-61`) it genuinely covers this endpoint because the method is POST |
| T-01-85 | Spoofing | Stale session usable after logout on a shared device | medium | mitigate | `ClearCookie` mirrors every attribute of the issued cookie, so the browser actually drops it; `TestClearCookieMatchesIssuedAttributes` pins the attribute match, which is the failure mode that otherwise ships silently |

Also applied to the logout redirect. `TestProfileRendersSharedHeader` asserts the header on the profile response rather than leaving it as a claim in a comment |
| T-01-87 | Repudiation | Permanent loss of account access with no recovery path | low | accept | D-11 makes this an explicit product decision, not an oversight: there is no recovery mechanism in v1, and a lost inbox means starting fresh.
