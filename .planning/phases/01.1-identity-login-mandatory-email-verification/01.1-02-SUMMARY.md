# Phase 01.1 Plan 02: GET /auth/verify — atomic single-use consumption, lazy account creation, and the five-outcome landing screen Summary

**AuthService.VerifyToken decides all five magic-link landing outcomes (verified/expired/used/malformed/conflict) on one atomic conditional UPDATE and a session-account upsert, rendered through a single shared `verify_outcome.html.tmpl`; a DEC-D conflict check refuses to silently re-bind an already-verified browser to a different account.**

## Performance

- **Duration:** ~15 min
- **Started:** 2026-09-11T13:08:46Z
- **Completed:** 2026-09-11T13:23:33Z
- **Tasks:** 3 (all `type="auto"`, `tdd="true"` for Tasks 1-2)
- **Files modified:** 16 (4 created, 12 modified)

## Accomplishments

- Data layer: `ConsumeToken` is one conditional `UPDATE ... WHERE used_at IS NULL AND expires_at > now()`, decided by rows-affected — proven single-use under a real goroutine-vs-goroutine concurrency test against Postgres, not just sequentially. `BindSessionAccount` is an upsert, not a bare `UPDATE`, so a session whose row never persisted (Phase 1's documented `cookie.go` log-and-continue path) still ends up correctly bound.
- `AuthService.VerifyToken`: shape-checks the raw token before touching the database, reads the token row only to pick outcome copy, checks for an existing conflicting verified session *before* consuming (so a rightful owner's link survives being opened in the wrong browser), then atomically consumes, lazily resolves the account, and binds — in that exact order, proven by call-order assertions on a fully-programmable fake querier.
- `GET /auth/verify` end to end against real Postgres: request a link, click it, land on "Email verified" with `sessions.account_id` set; re-click sees "already used"; an expired/malformed token gets its own copy; opening a second address's link in an already-verified browser is refused without touching that browser's binding or consuming the second token; and the upsert path is proven by deleting the `sessions` row between request and click.
- One shared `verify_outcome.html.tmpl` covers all five outcomes via heading/body/CTA swap, a 2-second meta-refresh plus a real anchor for the verified outcome (no JS dependency), and `Cache-Control: no-store` since the response reflects an authentication state change.

## Decisions Made

- **`VerifyToken`'s email return value for `OutcomeConflict` is the session's EXISTING verified account, not the clicked token's target address** — this wasn't in the plan's literal text but follows directly from what the UI-SPEC copy needs ("You're signed in as {{.CurrentEmail}}") and from the plan's own reasoning ("the second return value... verified email"): in a conflict, the only address that's actually verified on this browser is the existing one — the token's address was never proven here. See Deviations for how this was caught.
- **check-circle.svg was hand-edited after the `curl` fetch** to match the established icon convention (`width="100%" height="100%"`, `aria-hidden="true"`, `focusable="false"`) that `mail.svg`/`circle-alert.svg` from `01.1-01` already use, rather than left at Lucide's raw `24x24` defaults — consistent with "matching the shape of the icons already committed" from the plan's action text.
- **`check-circle.svg` added to `web/css_contract_test.go`'s `nonCategoryIcons` allowlist**, following the exact pattern `01.1-01` established for `mail.svg`/`circle-alert.svg` — an auth-surface icon under `.auth-icon--`, not a category glyph the reverse-walk contract governs.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `VerifyToken`'s conflict-case return value named the wrong email**
- **Found during:** Task 3 (writing the `Verify` handler's `CurrentEmail` view-model field, whose UI-SPEC copy is "You're signed in as {{.CurrentEmail}}")
- **Issue:** Task 2's initial implementation returned `row.Email` (the clicked token's target address) as the second return value on the `OutcomeConflict` path. The handler needs the browser's *already*-verified address to render the DEC-D copy correctly — returning the token's target address would have shown a visitor "You're signed in as [an address they never verified]," which is both wrong and a minor information-disclosure smell (confirming an unverified address exists as a magic-link target).
- **Fix:** Changed the conflict branch to return `existing.Email` (the session's currently-bound account, read via `GetAccountBySessionID` earlier in the same function) instead of `row.Email`. Updated the doc comment and the corresponding unit test (`TestVerifyTokenConflictRefusesRebind`) to assert on the session's existing address.
- **Files modified:** `internal/service/auth.go`, `internal/service/auth_test.go`
- **Verification:** `go test ./internal/service/... -run TestVerifyToken -v` — all pass, including the corrected assertion; `TestVerifyAccountConflict` in `auth_e2e_test.go` additionally proves the correct address appears in the rendered conflict page against a real router.
- **Committed in:** `44f9117` (Task 3 commit — the Task 2 commit `7a9e3c2` still reflects the original, later-corrected return value, which is expected for an atomic per-task commit history)
