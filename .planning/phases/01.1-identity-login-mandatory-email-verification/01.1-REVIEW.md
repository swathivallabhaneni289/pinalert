# Phase 01.1: Code Review Report

**Reviewed:** 2026-09-12T05:27:00Z
**Depth:** standard
**Files Reviewed:** 58
**Status:** issues_found

## Summary

This phase implements mandatory magic-link email verification, the account-gated access control layer, the per-address resend cooldown, per-IP rate limiting on the request-link endpoint, the shared account header/menu, and the profile page. The implementation is unusually well-documented — nearly every design decision cites a threat ID (T-01-NN) and an accepted-risk entry (AR-NN) in the phase's own planning docs, and the test suite (unit + real-Postgres e2e) is extensive and exercises most of the documented threat model directly.

Given that density of self-documentation, this review cross-checked the code against `.planning/phases/01.1-identity-login-mandatory-email-verification/*.md` rather than treating every attack surface as undiscovered. One class of finding below (IN-01) turned out to be a deliberately accepted, correctly-implemented risk (AR-29) — flagged only for traceability, not as a defect. The remaining findings are either genuinely new (the rate-limiter's IP key is spoofable — the phase's own threat register addressed IP spoofing's *memory* impact but never its *throttle-bypass* impact) or are logic/robustness gaps not covered by any existing threat entry (the resend-cooldown race, the dead branch in `VerifyToken`, token leakage into request logs, and the absence of any server-side session revocation).

The most serious finding (CR-01) is that `internal/api/router.go` wires in chi's `middleware.RealIP`, which the exact pinned version (`go-chi/chi/v5@v5.3.2`, confirmed by reading the vendored source directly) has itself marked `Deprecated` for being "vulnerable to IP spoofing," citing three GHSA advisories, with no trusted-proxy configuration applied on top of it anywhere in this codebase. That single gap defeats DEC-I's per-IP rate limiter outright, and compounds with WR-01 (a genuine TOCTOU race in the per-address resend cooldown) to leave `POST /api/auth/request-link` with no real abuse-resistance against a scripted client sending a burst of requests with a rotating spoofed source-IP header.

## Critical Issues

### CR-01: Rate limiter's IP key is trivially spoofable — chi's `middleware.RealIP` is deprecated for exactly this reason, and no trusted-proxy allowlist is configured

**File:** `internal/api/router.go:105-107,143-148` (also `internal/ratelimit/perip.go:141-163`)
**Issue:** `NewRouter` unconditionally chains `middleware.RealIP` before the per-IP rate limiter that is scoped to `POST /api/auth/request-link` (DEC-I: burst 5, refill 1/60s). `internal/ratelimit/perip.go`'s own doc comment for `Middleware()` states it "reads `r.RemoteAddr`, which chi's `middleware.RealIP` has already normalised upstream in this project's router" — i.e. the limiter's entire security property depends on `RealIP` having resolved a trustworthy client IP.

It has not. Reading the exact pinned module (`go.mod` pins `github.com/go-chi/chi/v5 v5.3.2`; verified directly against `.../go-chi/chi/v5@v5.3.2/middleware/realip.go`), chi's own source says:

```go
// Deprecated: RealIP is vulnerable to IP spoofing — it mutates r.RemoteAddr
// to the leftmost X-Forwarded-For value, or to True-Client-IP / X-Real-IP
// whether or not your infrastructure actually sets them. See
// GHSA-3fxj-6jh8-hvhx, GHSA-rjr7-jggh-pgcp, GHSA-9g5q-2w5x-hmxf.
//
// Use [ClientIPFromHeader], [ClientIPFromXFF], [ClientIPFromXFFTrustedProxies]
// or [ClientIPFromRemoteAddr] and read the IP with [GetClientIP] instead.
```

`realIP()` unconditionally trusts `True-Client-IP`, then `X-Real-IP`, then the leftmost entry of `X-Forwarded-For` — whichever header the caller happens to send, with no allowlist of trusted upstream proxies. Any client can set `X-Forwarded-For: <anything-that-parses-as-an-IP>` on every request and get a fresh token bucket every time, making the per-IP burst-of-5 effectively unlimited from the caller's perspective. Nothing in this codebase configures a trusted-proxy list, and nothing documents an assumption that the deploy platform (Render/Railway per PROJECT.md) strips a client-supplied `X-Forwarded-For` before this middleware ever sees it.

This directly undermines DEC-I, whose whole point is a "secondary, looser" abuse control layered under the per-email cooldown. The phase's own threat register did consider IP spoofing (T-01-80, `01.1-05-PLAN.md:249`) but only assessed the *unbounded-map-growth* consequence (mitigated by the idle-sweep eviction) — the *rate-limit-bypass* consequence of the same spoofing capability was never separately assessed or accepted as a risk.

**Fix:** Stop using the deprecated `RealIP` (or, if the deploy platform is confirmed to sit behind a single trusted reverse proxy that overwrites/strips inbound proxy headers, use chi's replacement with an explicit trusted-proxy allowlist):

```go
// router.go
r.Use(middleware.RealIPHeader("X-Forwarded-For")) // or:
// trusted, _ := middleware.NewTrustedProxies([]string{"<render/railway proxy CIDR>"})
// r.Use(middleware.ClientIPFromXFFTrustedProxies(trusted))
```

or, if there is no verified single trusted proxy in front of this service, drop `RealIP` entirely and key the limiter on the raw `r.RemoteAddr` (the actual TCP peer), accepting that this loses accuracy behind any real proxy but at least cannot be forged by the request body/headers a client controls.

## Warnings

### WR-01: Per-address resend cooldown is a TOCTOU race (compounds CR-01 into an effectively unbounded email-bombing vector)

**File:** `internal/service/auth.go:137-145`; `internal/store/migrations/00002_add_accounts_and_verification.sql:9-16` (no `UNIQUE`/serializing constraint on `email`)
**Issue:** `RequestLink`'s cooldown check is a plain `SELECT` (`LatestTokenForEmail`) followed, several lines later and in a separate statement, by an `INSERT` (`InsertMagicLinkToken`) — never inside a transaction with row-level locking, and `magic_link_tokens` has a `UNIQUE` constraint only on `token_hash`, not on `email`. N requests for the same address arriving concurrently can all read "no prior token within 45s" before any of their own inserts commit, so all N proceed to mint a token and send mail — the cooldown is advisory, not atomic, unlike `ConsumeToken` a few lines below it in the same file, which the code's own comments describe as deliberately atomic "never read-then-write" specifically to avoid this exact TOCTOU shape.

Standing alone, this is bounded by the per-IP limiter's burst of 5 (DEC-I) — a nuisance, not a real vulnerability. Combined with CR-01 (the IP key is spoofable), the bound disappears: an attacker can fire an arbitrary number of concurrent `POST /api/auth/request-link` requests for one victim address, each with a different spoofed source-IP header, and each one races the same unserialized cooldown read, email-bombing the victim's inbox and burning Resend send quota with no effective ceiling.

**Fix:** Serialize the check-and-insert, e.g. wrap both in a single transaction using `SELECT ... FOR UPDATE` against a per-email row (would need a dedicated `email_cooldowns` table, since `magic_link_tokens` has no unique key on `email` to lock against), or use a Postgres advisory lock keyed on a hash of the normalized email for the duration of the check-then-insert.

### WR-02: Dead code in `VerifyToken`'s race-recovery branch mis-reports "expired" instead of "already used" for a concurrently-consumed token

**File:** `internal/service/auth.go:211-216,239-248`
**Issue:** `VerifyToken` first checks `row.UsedAt.Valid` (line 211) and returns `OutcomeUsed` immediately if true. Only after that check does it reach the `ConsumeToken` call (line 239); on `pgx.ErrNoRows` from `ConsumeToken`, it re-checks `row.UsedAt.Valid` (line 242) to decide between `OutcomeUsed` and `OutcomeExpired` — but by this point in the function, `row` is provably unchanged since the earlier check, so `row.UsedAt.Valid` is guaranteed `false` here (control flow could only reach line 239 by having already returned at line 212 if it were `true`). The branch at line 242 is therefore unreachable dead code, and every `ConsumeToken`-returns-`ErrNoRows` case — including the exact concurrent-double-click race the atomic `UPDATE ... WHERE used_at IS NULL AND expires_at > now()` was written to detect (per `magic_link_tokens.sql`'s own comment about "a real user plus a mail-scanner prefetch") — is reported to the visitor as `OutcomeExpired` ("This link has expired") even when the true cause was a concurrent consumption ("This link was already used"). Not a security issue (the token is still correctly single-use either way), but a real, provable logic/UX bug.

**Fix:** At the `ConsumeToken` failure branch, decide using the current clock instead of the stale pre-consumption `row`:

```go
email, err := s.q.ConsumeToken(ctx, hash)
if err != nil {
    if errors.Is(err, pgx.ErrNoRows) {
        if row.ExpiresAt.After(s.now()) {
            // Still unexpired as of our read — the only way ConsumeToken
            // could still fail is a concurrent consumer winning the race.
            return OutcomeUsed, "", nil
        }
        return OutcomeExpired, "", nil
    }
    return "", "", fmt.Errorf("service: consuming magic-link token: %w", err)
}
```

### WR-03: Raw magic-link tokens are written to plaintext application logs via chi's request logger

**File:** `internal/api/router.go:108` (`middleware.Logger`); `internal/auth/token.go:1-7`
**Issue:** `token.go`'s package doc comment states the security property this phase depends on: "the raw token... is the secret that gets emailed to the visitor; only its SHA-256 hash is ever written to internal/store's... table... a database read never yields a usable link." That property is undermined by a different sink: `router.go` installs `middleware.Logger` globally, and chi's `DefaultLogFormatter.NewLogEntry` (verified directly in the pinned `chi/v5@v5.3.2` source, `middleware/logger.go:120`) logs `r.RequestURI` verbatim — the full path *and query string* — for every request. `GET /auth/verify?token=<raw-32-byte-secret>` (the only way this token is ever transmitted per `router.go`'s own comment: "GET only, deliberately") therefore has its complete, unhashed, still-valid secret written to stdout on every verification. On the project's intended hosts (Render/Railway, per PROJECT.md), stdout is retained and viewable via the platform's log dashboard well past the token's 5-minute TTL, and by anyone with dashboard access — a materially different (and broader) exposure than "the hash never yields a usable link" implies.

**Fix:** Either move the token out of the query string onto a path segment plus a redact step in a custom log formatter, or (cheaper) install a `middleware.RequestLogger` with a custom `LogFormatter` that strips/redacts the `token` query parameter before it reaches `NewLogEntry`, e.g.:

```go
r.Use(middleware.RequestLogger(&redactingFormatter{}))
// redactingFormatter.NewLogEntry clones r.URL, deletes q.token, and delegates
// to middleware.DefaultLogFormatter with the redacted URI.
```

### WR-04: No server-side session or account revocation exists anywhere in this phase

**File:** `internal/api/handlers/auth.go:429-435` (`Logout`); `internal/session/cookie.go:165-175` (`ClearCookie`)
**Issue:** `Logout` (and `ClearCookie` underneath it) only deletes the *browser's own copy* of the `pinalert_session` cookie. There is no code path anywhere in this phase that invalidates the underlying session id or its `account_id` binding server-side — the `sessions` row is deliberately left intact (DEC-K, correctly, for report-history continuity), and the signed cookie value itself remains cryptographically valid (HMAC verifies) for its full one-year `MaxAge` regardless of whether "logout" was ever clicked. The phase's own threat register (T-01-85) reasons carefully about the browser-side half of this ("does ClearCookie actually make the *browser* drop it") but nowhere addresses the server-side half: if a raw, signed session cookie value is ever exfiltrated by any other means (device left unlocked before a "logout," a MITM on a non-TLS hop, a future XSS, a captured log per WR-03's sibling risk if a session id were ever logged), there is no mechanism — no session table flag, no revocation list, nothing — to invalidate that specific session or force it to re-verify, for up to a year.

**Fix:** At minimum, give `sessions` a `revoked_at` (or reuse a boolean) column that `Logout` sets, and have `requireVerifiedAccount`/the session middleware treat a revoked row the same as a missing one. This is a modest addition given the schema already exists and is already read on every gated request.

## Info

### IN-01: Confirmed — the `GET /auth/verify` forced-verification exposure is a deliberately accepted, correctly-implemented risk (AR-29), not a new finding

**File:** `internal/service/auth.go:197-266`; `internal/api/router.go:120`
**Issue:** On first read, `GET /auth/verify` looks like a textbook "login CSRF": it is a state-changing, unauthenticated `GET` endpoint, `SameSite=Lax` cookies **are** sent on a top-level cross-site `GET` navigation, and an attacker who mints a token for their own address and gets a victim to open it (e.g. via a shared link) will have the victim's fresh/unverified session bound to the attacker's account — the `OutcomeConflict` check (DEC-D/DEC-E) only fires when the visiting session is *already* verified as someone else, which is not the victim's state here.

This is exactly the scenario `.planning/phases/01.1-identity-login-mandatory-email-verification/01.1-02-PLAN.md` (T-01-61) analyzed and accepted as **AR-29**, re-opening Phase 1's AR-02 specifically because this phase "creates exactly such an action." The plan explicitly rules out the two standard mitigations (binding the token to the requesting session breaks D-07's intentional cross-device verification; converting the link to a POST breaks D-01's click-a-link premise) and instead accepts the residual risk on the stated grounds that the attack is single-use, expires in 5 minutes, and only ever yields the victim an account the attacker *already* controls rather than access to the victim's own data.

This review verified all three of the plan's stated compensating controls are actually present in the shipped code: single-use atomic consumption (`ConsumeToken`'s conditional `UPDATE`), the 5-minute TTL (`auth.TokenTTL`), the same-account conflict refusal (`OutcomeConflict`), and `Cache-Control: no-store` on the outcome page (`Verify` handler). No new action is needed beyond what AR-29 already scopes. Recorded here only so this review's traceability is complete and a future reader doesn't have to re-derive the same analysis from scratch.
