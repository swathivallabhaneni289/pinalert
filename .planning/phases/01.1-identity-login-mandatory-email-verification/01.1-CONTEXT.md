# Phase 1.1: Identity & Login — Mandatory Email Verification - Context

**Gathered:** 2026-09-10
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase replaces Phase 1's anonymous, no-signup access model with mandatory email
verification: a visitor cannot view the map/feed, submit a report, or cast a confirm/dispute vote
until they've verified an email address by clicking a link sent to it. Covers IDENT-01 through
IDENT-05. This phase was inserted mid-way through discussing Phase 2 (Trust Mechanic Core) after
the user judged fully anonymous voting too gameable via multiple devices/sessions from one
person — see PROJECT.md's Key Decisions for the full tradeoff record, including why phone OTP was
rejected (no free tier at any real SMS volume; the cheap route needs India DLT sender
registration, a business-entity requirement) in favor of email-only verification.

Phase 2's voting/independence-predicate design depends on this phase: "distinct session" in
Phase 2's TRUST-03 now means "distinct verified account," not "distinct anonymous session."

</domain>

<decisions>
## Implementation Decisions

### Verification mechanism
- **D-01:** Email verification is a **magic link**, not a typed OTP code — the verification email
  contains a link; clicking it verifies the account. No code to type or mistype. (This was a
  late change during discussion: the user first suggested dropping verification checks entirely,
  which would have let anyone claim any email with zero proof of ownership — defeating this
  phase's whole purpose. After that tradeoff was made explicit, the user settled on a magic link
  as the verification mechanism instead of a typed code.)
- **D-02:** The verification link expires after **5 minutes**.
- **D-03:** A new verification email can be requested after a **30-60 second cooldown** — prevents
  spam-clicking "resend" from burning through the free email quota (Resend: 100/day) or looking
  like abuse.
- **D-04:** No "wrong attempts" concept applies (there's no code to guess with a link) — IDENT-04's
  rate limiting instead applies to *verification-email send requests* per address and per IP, not
  to guess attempts.

### Login gate placement
- **D-05:** Login is required to view **anything** — no anonymous browsing at all, not even
  passively looking at the map/feed. This is a deliberate full-accountability choice, made with
  the tradeoff explicitly surfaced (a first-time visitor mid-emergency can't check what's nearby
  without verifying first).
- **D-06:** The landing screen shows a **rotating globe animation as a continuous ambient
  background** — not a blocking sequential intro. The login/verification form is layered on top
  and interactive immediately; there is no separate "wait for animation, then see login" step and
  therefore no skip button is needed (nothing blocks).
- **D-07:** The globe-animation background replays every time login is needed (session expired,
  logged out, new device) — not just on the visitor's very first-ever visit.

### Session persistence
- **D-08:** Once verified, login is **long-lived on that device** — reuses Phase 1's existing
  session-cookie mechanism, which already has a 1-year `MaxAge` (`internal/session/cookie.go:23`,
  `oneYear` constant). No repeated verification on return visits from the same
  device/browser unless cookies are cleared.
- **D-09:** An explicit **"Log out"** action exists and clears the session cookie — useful for
  shared/public devices. **Refined 2026-09-11:** it lives in an account menu (see D-12), not
  buried at the bottom of the full profile page — logging out shouldn't require a page
  navigation first.
- **D-10:** The same verified account **can be logged in on multiple devices simultaneously** —
  each device gets its own independent session after its own verification. Logging in on a new
  device does not invalidate other devices' sessions.

### Account recovery
- **D-11:** There is **no account-recovery mechanism** for v1. If someone loses access to their
  signup email entirely, they simply verify a new email and start a fresh account. The old
  account's report/vote history stays under the old, now-inaccessible account — accepted as a
  reasonable v1 tradeoff given login itself didn't exist before this phase.

### Account menu (added 2026-09-11)
- **D-12:** The header entry point (previously a bare icon-link straight to the profile page) is
  an **account menu** (dropdown/bar) opened from the same header icon, showing: the verified
  email address (display only), an **"Activity"** option that navigates to the profile page, and
  a **"Log out"** action that fires immediately from the menu — no page navigation required to
  log out.
- **D-13:** The profile page's two previously-separate sections ("Your reports" / "Your
  activity") are **merged into one section**, titled "Activity", listing both the account's
  submitted reports and its confirm/dispute voting history together (the latter still ships as
  the real always-empty state from D-09/IDENT-03's original scope — Phase 2 hasn't shipped voting
  yet).

### Claude's Discretion
- Exact verification-link token format/storage (e.g., signed token vs. random ID looked up in a
  short-lived table) — implementation detail, not discussed as user-facing.
- Exact wording/branding of the verification email itself, and exact visual treatment of the
  rotating-globe background (asset choice, animation library/CSS approach) — visual/copy
  implementation detail; the *behavior* (continuous ambient background, not blocking) is locked,
  the *look* is Claude's call within Phase 1's established neutral-utility visual direction (D-10
  from `01-CONTEXT.md`).
- Whether the verification-link rate limit (D-04) is keyed per-address, per-IP, or both, and the
  exact limit numbers beyond the 30-60s resend cooldown already specified — implementation detail
  within the IDENT-04 requirement.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `internal/session/cookie.go`'s `Manager` — the signed-cookie session mechanism is retained
  wholesale; this phase gates it behind verification rather than replacing it.
- `internal/store/migrations/00001_create_reports.sql`'s `sessions` table — existing table to
  extend (add email/verification columns) rather than a new identity table built from scratch.

### Established Patterns
- Server-computed, client-untrusted fields (Phase 1's `T-01-07` pattern: server decides
  `expires_at`/`created_at`/`geohash`, decoder rejects unknown fields) — the same pattern applies
  to verification state: a client can never claim "I'm verified," the server sets that based on a
  successfully-clicked link.
- `MaxBytesReader` + input caps on `POST /api/reports` (Phase 1's `T-01-08`) — the new
  verification-email-request endpoint will need the same shape of DoS-conscious caps (this phase's
  own threat model, to be authored at planning time, should cover it).

### Integration Points
- The existing session `Middleware` (`router.go:70`, mounted ahead of every route) is the natural
  place to add a "is this session verified" check gating access to the rest of the app — Claude's
  discretion on exact implementation, but this is the existing integration point, not a new one.

</code_context>

<specifics>
## Specific Ideas

- **Rotating globe, ambient background, login form on top** — the user's own words: "a globe
  rotating and then a smooth transition of asking them to log in" — clarified over two follow-ups
  to mean a continuous background animation with an already-interactive login form layered on top,
  not a sequential splash-then-form flow. This is a specific visual moment the user has in mind for
  the whole login experience, not just a generic auth page.
- **Magic link over OTP code** — explicitly chosen over a typed passcode after the tradeoff of
  "no verification at all" was surfaced and rejected. The user's reasoning: "let's send a
  verification link... when they click it, that's approved."

</specifics>

<deferred>
## Deferred Ideas

(Account-recovery mechanisms, backup-email support, and any password-based alternative to the
magic link were considered and explicitly deferred/rejected during discussion, not left
ambiguous — see D-11 and D-01 above.)

**Added 2026-09-11, raised while reviewing the planned account menu — both are new capabilities,
not implementation decisions for this phase:**

- **Report-activity notifications.** Notify a reporter when someone confirms/disputes their
  report, so they know "people are talking about this" and can respond. Belongs with Phase 2's
  confirm/dispute mechanic and needs real delivery infrastructure that doesn't exist yet — closely
  related to two items already in `PROJECT.md`'s deferred/stretch list ("Targeted confirm-nudge to
  already-engaged sessions", "Proactive retraction push notification"), both explicitly waiting on
  Web Push/VAPID infrastructure. Revisit alongside that infrastructure, not as part of Phase 1.1
  or Phase 2's core voting mechanic.
- **Comment/discussion thread under each report.** Free-text discussion visible when a report is
  opened (from the feed or the map pin), distinct from confirm/dispute voting (a simple
  agree/disagree signal, not threaded text). This is not currently tracked anywhere in
  `REQUIREMENTS.md` or `PROJECT.md` — it's a genuinely new capability for the whole project, not
  an existing deferred item. Needs its own scoping (moderation surface, abuse vectors on free text
  tied to a real account) before it becomes a phase.
</deferred>
