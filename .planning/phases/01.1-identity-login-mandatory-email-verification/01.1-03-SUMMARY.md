**Resend-backed verification-email delivery via `resend-go/v3`, gated by a `LoadMailer(env)` loader that fails fast outside `ENV=development`, plus README documentation of the sandbox-sender pre-launch domain-verification requirement.**

## Accomplishments
- `internal/mailer/resend.go`: `NewResendMailer(apiKey, from string) Mailer` builds a `resendMailer` wrapping `resend.Client`, sending through `Emails.SendWithContext` with the UI-SPEC-exact subject, body copy, button label, and didn't-request-this disclaimer. The HTML body is built by a pure, network-free `verificationEmailHTML(link string) string` function, kept separate specifically so it is unit-testable without a client or network call.
- `internal/mailer/loader.go`: `LoadMailer(env string) (Mailer, error)` mirrors `loadSessionSecret`'s exact shape — set `RESEND_API_KEY` wins regardless of `ENV`; unset key + `ENV=development` returns the log mailer with a warning; unset key + any other `ENV` (including unset) returns an error naming `RESEND_API_KEY`, never calling `log.Fatal` itself so the package stays testable.
- `cmd/server/main.go`: replaced the direct `mailer.NewLogMailer()` construction from 01.1-01 with `mailer.LoadMailer(env)`, exiting via `log.Fatalf` on error — confirmed live via two boot checks (see Issues Encountered / verification below).
- `go.mod`/`go.sum`: added `github.com/resend/resend-go/v3 v3.17.0`, the exact version pinned and approved in `01.1-RESEARCH.md`'s Package Legitimacy Audit. Re-resolved against `proxy.golang.org` directly during execution — still current, no version drift.
- `README.md`: extended the "Run locally" env block with `RESEND_API_KEY`, `RESEND_FROM`, `BASE_URL`, and `ENV`; added a new "Email delivery (Resend)" section stating the `onboarding@resend.dev` sandbox-sender delivery restriction as an explicit pre-launch checklist (add + DNS-verify a domain, then set `RESEND_FROM`), and noting the free-tier quota alongside plan 01.1-05's cooldown/rate-limit controls.

## Decisions Made
- HTML-escaped the link before embedding it in `verificationEmailHTML`'s anchor `href` and visible text. The plan's action text didn't call this out explicitly, but the link carries a caller-influenced token/query string, so leaving it unescaped would be a Rule 2 (missing critical functionality) gap in an otherwise auto-escaped-by-default project (per CLAUDE.md's `html/template` convention for the rest of the app). Covered by `TestVerificationEmailHTMLEscapesLink`.
- Ran `go mod tidy` after `go get` because the initial `go get` placed `resend-go/v3` under the `// indirect` require block despite being directly imported by `resend.go` — `go mod tidy` corrected the classification. No version change resulted (still `v3.17.0`).

## User Setup Required

**External service configuration is required before real visitors can receive mail** — this plan's own `<user_setup>` block documents it, and README.md's new "Email delivery (Resend)" section now records it as the pre-launch checklist:

1. Obtain a `RESEND_API_KEY` from the Resend Dashboard (API Keys → Create API Key, sending permission sufficient).
2. Add and DNS-verify a custom sending domain (Resend Dashboard → Domains → Add Domain, then add the printed DKIM/SPF records at the DNS registrar) — until this is done, `onboarding@resend.dev` only delivers to the Resend account owner's own signup address, so every other visitor's verification email is silently undeliverable.
3. Set `RESEND_FROM` to an address at the verified domain.

None of this blocks the plan's own automated verification (the log-only mailer covers development/CI), consistent with the plan frontmatter's `autonomous: true`.
