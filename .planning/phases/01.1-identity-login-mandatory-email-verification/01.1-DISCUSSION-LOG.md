## Login gate placement

| Option | Description | Selected |
|--------|-------------|----------|
| Immediately on landing | Map/feed not visible until login completes | (superseded by clarification) |
| Browse freely, gate only on report/vote | View freely, login triggers only on action | |
| Login required just to view anything | No anonymous browsing at all | ✓ |

**User's choice:** Login required to view anything at all. Clarified via free text over two exchanges that the landing experience is a rotating globe animation playing continuously as an ambient background, with the login/verification form already interactive on top from the start — not a sequential "watch intro, then see login" flow. Because nothing is actually blocking, no skip mechanism was needed (an earlier proposed "tap to skip" question became moot once this was clarified).

**Notes:** User's own words: "a globe rotating and then a smooth transition of asking them to log in" and later, when asked about a skip button: "it moves around in the background, and they'll have a login option on that window anyway." The globe-animation background replays every time login is needed (not just the very first visit ever).

## Session persistence ("remember me")

| Option | Description | Selected |
|--------|-------------|----------|
| Long-lived, like Phase 1's cookie | Stays logged in indefinitely on that device | ✓ |
| Expires after a shorter window | Requires re-verification periodically | |

**User's choice:** Long-lived — confirmed this reuses Phase 1's existing session cookie, which already has a 1-year `MaxAge` (`internal/session/cookie.go`).

Follow-up questions in this area:
- **Explicit logout?** Yes, explicit logout available (vs. no logout / only clearing cookies ends a session).
- **Multi-device?** Yes, multiple devices simultaneously — each gets its own independent session (vs. single active session that logs out other devices).

## Email verification mechanism (emerged mid-discussion, not originally a selected area)

This surfaced when the user, while answering the Account Recovery question, initially suggested dropping verification entirely ("just log in with the email ID should be good... there's no need of, like, OTP"). This was flagged clearly as a real risk: without any verification, anyone could type any email address (real or fake) and get an instantly "verified" account, defeating the entire purpose of this phase (closing the vote-stuffing gap that motivated mandatory login in the first place). After that tradeoff was made explicit, the user reconsidered.

| Option | Description | Selected |
|--------|-------------|----------|
| Typed OTP code | 6-digit code entered by the user | (originally assumed, superseded) |
| No verification at all | Just type an email, no proof of ownership | Explicitly considered and rejected after tradeoff was surfaced |
| Magic link | Click a link in the verification email | ✓ |

**User's choice:** Magic link. User's own words: "Maybe let's do the verification. Let's send, like, a verification link or something. And when they click it, that's approved or something like that."

**Notes:** Carries forward the previously-decided 5-minute expiry and 30-60 second resend cooldown (both originally framed around a typed code, but apply equally to a link's validity window and resend throttling). The previously-decided "5 wrong attempts before lockout" no longer applies — there's no code to guess with a link.

## Account recovery

| Option | Description | Selected |
|--------|-------------|----------|
| No recovery — verify a new email, start fresh | Simplest for v1, no continuity of history | ✓ |
| Some recovery mechanism (backup email, etc.) | Preserves history, more to build | |

**User's choice:** No recovery mechanism for v1. Losing access to the signup email means starting over with a new email; old account's history stays under the old, inaccessible account.
