# Phase 01.1 Plan 04: requireVerifiedAccount access gate and the OpenAPI reference it changes Summary

**A single chi `r.Group` wrapping `GET /`, `POST /api/reports` and `GET /api/reports` behind `requireVerifiedAccount` — resolved per request from `sessions.account_id`, fail-closed on any error other than "not verified yet" — closes D-05's door behind the login flow plans 01.1-01 through 01.1-03 built, and the published Swagger spec now says so.**

## Accomplishments

- `internal/api/gate.go`: `requireVerifiedAccount(q *sqlcgen.Queries)` resolves the caller's account from `sessions.account_id` via the signed session cookie only — never from anything the client asserts. A `pgx.ErrNoRows` result (no account bound yet) is unverified, not an error; any other database error is logged and also treated as unverified, so the gate fails closed on an infrastructure fault rather than opening it. An unverified `/api/` request gets a 401 in the same `ErrorResponse` envelope every other error uses; every other unverified request gets a 302 to `/login` with `Cache-Control: no-store`.
- `internal/api/router.go` regrouped so every gated route — `GET /`, `POST /api/reports`, `GET /api/reports` — lives inside one `r.Group` applying the gate, while `/login`, `POST /api/auth/request-link`, `GET /auth/verify`, `/static/*`, and `/swagger/*` stay flat, literal, and exempt. Because chi panics if a wildcard mount is registered twice over overlapping prefixes, `/api/auth/request-link` is registered as a literal path rather than nested inside an `r.Route("/api", ...)` subrouter — the router file's comments record this constraint so a later reader doesn't try to "clean it up" into a nested mount and reintroduce the panic.
- `internal/api/gate_test.go`: four tests driving the real router against a real Postgres — unverified visitors get no app-shell markup and a 401 with no row written; a session verified through the real magic-link flow gets Phase 1's app back unchanged; all five exempt routes stay reachable (table-driven); and a session whose `sessions` row is deleted between verify and request still redirects rather than 500s.
- `internal/api/handlers/reports_e2e_test.go` updated so `TestSubmitThenNearbyReturnsReport` and `TestNearbyResponseOmitsSessionID` verify a session (reusing the 01.1-02 fake-mailer harness from `auth_e2e_test.go`) before driving the now-gated `/api/reports` — neither test lost an assertion; the Set-Cookie check moved to right after verification, where the cookie is actually issued now.
- The published API reference caught up: `reports.go`'s two operations now say a verified session is required and document `@Failure 401`; `router.go`'s API-wide description says the same while keeping the ROBUST-08 emergency-services disclaimer; `GET /auth/verify` carries a comment explaining why it's deliberately absent from the spec; `swagger_test.go`'s drift guard now asserts `/auth/request-link` is documented and both `/reports` operations declare 401. `make swag` regenerated `docs/` and reproduces it byte for byte.

## Decisions Made

- **Flat literal `/api/*` route registration instead of an `r.Route("/api", ...)` subrouter** — see key-decisions above. This is the mechanical reason the plan's literal "put every remaining route inside a r.Group" reads as a single group in the file even though `/api/auth/request-link` and `/api/reports` share a URL prefix.
- **`unverifiedErrorResponse` constructed inline in gate.go** rather than exporting `handlers.writeFieldError` — kept the handlers package's public surface unchanged; `gate.go` already imports `handlers` only for the two exported response types.
- **Set-Cookie assertion relocated, not dropped**, in `reports_e2e_test.go` — see key-decisions above.
- **Swag annotation blocks in `reports.go` reformatted to single-space** (`@Failure 401` instead of column-aligned `@Failure      401`) so the plan's literal `grep -c '@Failure 401'` acceptance check matches; `swag` itself is whitespace-tolerant so this has no effect on the generated spec beyond the intended content changes.

## Deviations from Plan

None — plan executed exactly as written. The router restructuring needed one implementation-detail choice not spelled out in the plan's action text (flat literal routes vs. a nested `/api` subrouter, driven by a real chi `Mount` panic constraint the codebase had already documented in the pre-existing router.go comment); this is recorded above as a design decision rather than a deviation, since it doesn't change any behavior, test, or acceptance criterion the plan specified — it's the mechanism that satisfies "one r.Group" given chi's actual routing rules.
