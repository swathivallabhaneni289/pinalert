## Summary

The phase is mostly a server contract problem with a large front end rewrite behind it. Everything the screens need can be derived from data the code already loads. `CurrentVotesForReports` already returns, per report, account and kind, the latest vote row with `value`, `geohash_cell` and `created_at` (`internal/store/queries/votes.sql`). That is enough to compute when a report was closed and who closed it with a pure function, and no new table or migration is needed. `votes.value` is unconstrained TEXT, so a new resolution value needs no schema change either (`internal/store/migrations/00004_create_votes.sql`).

The pinned `NearbyReports` query stays. Active and Disputed keep using `ReportService.Nearby` with the same query count. Past needs two new bounded reads (expired in the window, and unexpired candidates that may be Retracted), both taking `now` and the window start as parameters so backlog 999.5 (replay) can inject a clock. Visibility, view membership, closure time and outcome are all decided in Go by `Resolve`, `ClassifyOutcome` and one new pure classifier. No vote predicate goes into SQL.

The three places a plan can go badly wrong are: (1) coarsening a finished Rescue report in only one of the four leaking fields (latitude and longitude, `geohash`, `description`, and `distance_km` from the exact SQL Haversine, which a reader can triangulate by moving the search centre); (2) letting live reports fill the history candidate cap, so Past comes back empty during a disaster; and (3) the take back leaking into `ReopenCells` or burning budget on a withdraw with nothing to withdraw. The front end risk is the number of source shape contract tests that pin `app.js`, `feed.js` and `createRow` text, which change deliberately and must be edited in the same plan as the code.

**Primary recommendation:** Build the server contract first as three parallel units (pure view and closure and coarsening functions, the take back vocabulary and `CastVote` change, the history reads and handler parameters) plus a fourth independent unit (reader geocoder lane). Freeze the wire shape in swagger. Then build the screens against it in this order: shared state and CSS lift, rows and Past cards, map tools, take back block and toast action. Edit the pinned tests in the same plan as the code they pin.

## Findings by research question

### 1. History reads (Q1)

**What exists.**
- `ReportService.Nearby` (`internal/service/report.go:534-622`) runs `NearbyReports` (expires_at > now(), bbox then Haversine, nearest first), then `ReporterAccountsForReports`, then `ReporterHistoryReports` (only if accounts), then one `CurrentVotesForReports` over page ids plus history ids, then per report `BuildVoteTally`, `Resolve`, `ListableInFeed`, `BuildTrust`. An empty page returns before any batched read (asserted by `TestNearbyBatchesVoteReadsOnce`, `internal/service/feed_test.go:464`). [VERIFIED]
- `ListableInFeed(includeDisputed bool)` (`internal/service/feed.go:65`) is a fail closed switch. Retracted is listable in neither view. Phase 4 plan 04-01 names this exact method and `TestWithheldInNoView` loops it. **Keep it unchanged** and add the new predicates beside it. [VERIFIED: 04-01-PLAN.md lines 170 and 171]
- Indexes: `idx_reports_lat_lon (latitude, longitude)`, `idx_reports_expires_at (expires_at)`, `idx_reports_geohash`, `idx_reports_session_expires (session_id, expires_at DESC, id DESC)` (migration 00005), `idx_votes_report_account_kind_created (report_id, account_id, kind, created_at DESC, id DESC)` (00004), `idx_votes_account_kind_report_created (account_id, kind, report_id, created_at DESC, id DESC)` (00006). [VERIFIED: internal/store/migrations]

**Recommendation: no migration.** Report lifetime is 8 hours (24 for critical) from creation (`internal/service/report.go:31-32`), so a 7 day window is a scan of `expires_at > now - 7 days` over the existing `idx_reports_expires_at` or the bbox index, bounded by a row cap. Add an EXPLAIN style test only if the planner wants it (model: `TestNearbyReportsUsesIndex`, `internal/store/reports_test.go:66`).

**Candidate sets.** Put two queries in a new `internal/store/queries/history.sql`, never touching `reports.sql` (its drift test `TestNearbyReportsQuerySourceHasExpectedShape` reads that file). Both take `now` and bounds as parameters, never `now()`, so a clock can be injected (backlog 999.5), copying `ReporterHistoryReports` (`internal/store/queries/reliability.sql`, choice (d)).
- `ExpiredReportsInWindow(now, window_start, bbox, row_cap)`: `expires_at <= now AND expires_at > window_start`, bbox, ordered `expires_at DESC, id DESC`, `LIMIT row_cap`. Feeds both groups (a Retracted report that then expired stays Resolved).
- `OpenReportsInArea(now, bbox, row_cap)`: `expires_at > now`, bbox, nearest first, `LIMIT row_cap`. Feeds only the Resolved group (a Retracted report that has not yet expired).

Do **not** use one query ordered by `expires_at DESC` with one cap. Unexpired live reports have the latest expiry, fill the cap first, and in a disaster Past comes back empty. Do **not** add a votes predicate (`EXISTS (... kind = 'resolution' ...)`) to either query. The comments on `NearbyReports` and `ReporterAccountsForReports` forbid a visibility or votes predicate in report reads, and the cost without it equals an Active poll. The prefilter `expires_at > now - 7 days` is a safe superset because `CastVote` step 5 refuses any vote on a report at or past expiry, so `resolved_at < expires_at` always (`internal/service/trust.go:411-414`). [VERIFIED]

A cheaper alternative that adds no SQL is to reuse `NearbyReports` for the unexpired set, because `Nearby` already reads it. Its cost is the database clock (`now()`) instead of an injected one, which blocks replay. Recommend the parameterised query.

**View classifier.** Add a closed string type whose name matches Phase 4's grep, for example `type FeedView string` with `FeedViewActive`, `FeedViewDisputed`, `FeedViewResolved`, `FeedViewPast` and a `FeedViewNone` zero value. One pure function, no context, no store types:

```go
// ViewOf is the one partition (D-03). It fails closed: an unknown visibility is none.
func ViewOf(v Visibility, expiresAt, now time.Time) FeedView {
	switch v {
	case VisibilityRetracted:
		return FeedViewResolved // closed then expired stays Resolved
	case VisibilityLive, VisibilityProvisional, VisibilityHidden:
		if !expiresAt.After(now) {
			return FeedViewPast // a hidden report that expires moves to Past
		}
		if v == VisibilityHidden {
			return FeedViewDisputed
		}
		return FeedViewActive
	default:
		return FeedViewNone
	}
}
```

`TestWithheldInNoView` (04-01) calls every Go view predicate over its whole domain and needs each to be pure with no I/O. Phase 4 wraps this with `ReportMeta.Withheld()`. Do not read moderation state here.

**Closure time and who closed it.** Derive both from the `CurrentVotesForReportsRow` slice already loaded, with a pure `ClosureOf(rows, reportID, reporterAccountID) Closure{ByReporter, ByPeople bool, At time.Time}`.
- `filterVoteRows` (`internal/service/trust.go:150`) already keeps each non reporter standing resolve with its `Cell` and `CreatedAt` (`placeVote`). It does not keep the reporter row's time. Extend `voteBuckets` with `ReporterResolvedAt time.Time`, additive and tally neutral.
- Do not use "the latest resolve row" for the independent case. Closure happens when the second distinct cell stands, not at the latest vote and not at the first. Replay the standing resolution rows (resolve, reopen and the new unresolve value) in `created_at` order, building a `VoteTally` incrementally and calling `isRetracted()` after each row. Record `At` on every false to true flip and return the last recorded `At` if the final state is retracted. That is the start of the current retraction. Write a test with a flip, a reopen and a second close.
- Because every account's row is already the latest per (report, account, kind) (`DISTINCT ON`, `internal/store/queries/votes.sql`), a withdrawn mark simply is not there. This matches "nothing latches" (02-CONTEXT D-08).
- `ByReporter` is true when the reporter's standing row is `resolve`. `ByPeople` is true when `ResolveCells >= IndependentAgreementThreshold`. The phrase is "Resolved by you", "by the poster", "by people nearby", "by the poster and people nearby" or "by you and people nearby". The server writes the phrase (it knows `IsOwnReport`). The browser appends `", " + relativeTime(history.at)`.

**Outcome.** For an expired report that is not Retracted call `ClassifyOutcome(meta, tally, expiresAt, now)` (`internal/service/reliability.go:66`) and map the four values to the UI-SPEC labels: corroborated "Confirmed by N people nearby", contradicted "Disputed", unconfirmed "Expired unconfirmed", neutral "Expired". This is why D-10 holds (a critical report that was out disputed returns contradicted). `ClassifyOutcome` zeroes all four resolution fields before calling `Resolve`, so a take back can never change an outcome or a rating. [VERIFIED: reliability.go:66-87]

Wording note for the planner: the existing server copy says "people at different spots" (`internal/service/trustcopy.go`, A88) while UI-SPEC C16 and D-09 say "people nearby". Put the new history strings in one new file (`historycopy.go`) under the same closed character set and add the file to the plain copy test, rather than editing `trustcopy.go`. The word "place" must stay out (`p30Banned` in `internal/service/trustwording_test.go`).

**Request shape (one list request, one `fetch(`).** Add to `GET /api/reports`:

- Keep `show_disputed` accepted as a deprecated alias (true means `view=disputed`). Return 400 when `view` and `show_disputed` conflict. That keeps `TestShowDisputedRevealsHiddenReports`, `TestShowDisputedRejectsNonBooleanValue` (`internal/api/handlers/feed_visibility_e2e_test.go:121,326`), the `getNearby` helper and the swagger check for `show_disputed` (`internal/api/handlers/swagger_test.go:334`) green.

One string for not found and, in Phase 4, held or removed, so moderation state is not revealed. This avoids a third `fetch(` and a new route.
- Response gains `view` (echo), `recent` (only when view is active, the list is empty and no category is set: `{resolved_24h, expired_24h}`), `cut` for Past (`{resolved: bool, expired: bool}`), and `focus`.

**HIST-04 counts without breaking `TestNearbyBatchesVoteReadsOnce`.** That test asserts an empty page costs zero extra reads. Do not run the count inside `Nearby`. Make it a separate service method (for example `ReportService.RecentHistoryCounts(ctx, lat, lon, radius, now)`) that the handler calls only when `view` is active, `category` is empty and `Nearby` returned zero reports. Past is not polled, the client skips the 30 second poll while Past is selected.

### 4. Place search (Q4)

**Current state.** `geocode.Client.Search` waits on a process wide limiter, 1 request per second, burst 1, with `limiterWaitTimeout` 1.5 s (`internal/geocode/client.go:44-55,174`). `GET /api/geocode` sits behind a per IP limiter, burst 3, one token per 2 s, built once at route registration (`internal/api/router.go:228-240`). The reporter form uses it with the sentence "Search unavailable, try tapping the map instead." (`internal/api/handlers/geocode.go:41`).

**Recommendation (own lane, never in front of a reporter).**
1. Add `Client.SearchReader(ctx, q)`. Normalise the key (trim, lower case, collapse spaces). Check a small bounded TTL cache first (assumed 256 entries, 6 hours, in memory). On a miss, try the same `rate.Limiter` with `Reserve()` or `Allow()` and no wait: if no token is free now, return a busy error. A reader can therefore never queue ahead of a reporter's `Wait`, because a waiting reporter leaves the bucket in debt and `Allow` returns false. Do not change `Search`, so Phase 7's tests stay green.
2. A separate handler and route (for example `GET /api/geocode/place`, flat, inside the gated group) with its own messages: 503 maps to C31 and 429 to C32 in UI-SPEC. The report form sentence is wrong for a reader.
3. Key the reader budget per verified account (the account is in the request context), not per IP. Carrier NAT shares one IP across many phones, the exact collateral damage the project already designed around (CLAUDE.md access model). `ratelimit.NewPerIP` keys by IP, so either add an account keyed sibling or key the existing map with a string built from the account id. Keep a small burst (assumed 3 per 10 s).
4. Minimum 3 and maximum 200 characters stay as `parseGeocodeQuery` (`geocode.go:57-66`). UI-SPEC sets the input `maxlength` equal to the server limit.

**Result shape.** Reuse `GeocodeResult {name, display_name, lat, lon}` (`geocode.go:52-57`). The browser cuts `name` to 32 characters with an ellipsis. The swagger guard forbids Nominatim internal fields (`internal/api/handlers/swagger_test.go`), so add nothing.

**Browser needs.** A new script (not `app.js`, which keeps exactly two `fetch(` calls, not `feed.js` or `activity.js`, which keep zero) with its own `fetch(`. On a pick it calls `Pinalert.setCenter(lat, lon, false)`, sets the place on the store, asks the map to move (a new exported `PinalertMap.moveTo`, because `map` is private in `map.js:25`), then `Pinalert.fetchReports()`. Use an `AbortController` so a stale response never lands. "Back to my location" needs a new `PinalertMap.recenterOnReader()` that reruns the geolocation step (`centerOnVisitor` is private, `map.js:258`).

**Known UAT hazard:** backlog 999.7 (address search ranks worldwide) will make "Velachery" return other countries. A `countrycodes` bias on the reader lane only would help but changes behaviour the owner may want global. Open Question 4.

## Common Pitfalls

### Pitfall 1: coarsening one field and calling it done
**What goes wrong:** latitude and longitude are rounded but `geohash` (p8) or `distance_km` (exact Haversine) still pin the spot. **Why:** four fields carry location. **Avoid:** the single function replaces all four and one test asserts all four on both reads. **Warning sign:** a test that checks only `latitude`.

### Pitfall 2: live reports fill the history cap
**What goes wrong:** one query ordered by `expires_at DESC` returns live reports first and Past is empty in a disaster. **Avoid:** two candidate sets with separate bounds (Q1). **Warning sign:** a Past test that seeds fewer rows than the cap.

### Pitfall 3: the take back counted as a reopen or wasted
**What goes wrong:** reusing `reopen` lifts closed reports, or a withdraw with nothing to withdraw burns budget and replaces a standing reopen. **Avoid:** new neutral value, pre insert check that the latest resolution value is `resolve`, count only in the log. **Warning sign:** `ReopenCells` changes in a take back test.

### Pitfall 4: nested count breaks the pinned empty page test
**What goes wrong:** running the 24 hour counts inside `Nearby` costs reads on an empty page. **Avoid:** a separate method the handler calls. **Warning sign:** `TestNearbyBatchesVoteReadsOnce` "an empty page costs neither batched call" fails.

### Pitfall 5: a pinned JS source test fails for a good reason
**What goes wrong:** a rename silently breaks ten tests that read source text. **Avoid:** edit the pins in the same plan, naming the old and new literals in the SUMMARY. Do not weaken them to pass.

### Pitfall 6: laptop rows pick up phone only colours
**What goes wrong:** lifting `phone.css:328-335` puts `--color-tone-good` on laptop tints or lifting muted rules puts muted on `--color-surface` (4.34 to 1). **Avoid:** lift only the structural rules, keep the tone rules phone only, add the contrast pair tests listed in UI-SPEC.

### Pitfall 7: Past cards invisible to focus helpers
**What goes wrong:** helpers test `classList.contains('report-row')`, so focus falls to the body after a removal. **Avoid:** list every site (Q5) and test focus order.

### Pitfall 8: reader search starves the report form
**What goes wrong:** readers queue on the same `Wait`. **Avoid:** `Allow` only plus cache plus a per account budget (Q4).

### Pitfall 9: the 7 day window versus the expiry clock
**What goes wrong:** a report is in Resolved by `At` but missing from the candidates, or counted in both groups. **Avoid:** de duplicate by id across the two sets, take one `now` per request and pass it to every read and to `Resolve`, `ViewOf`, `ClassifyOutcome`.

### Coarsening (pure) [ASSUMED]
```go
const approxGeohashPrecision = 6 // about 0.6 km by 1.2 km cell, within about 0.7 km of the truth

func CoarsenFinishedRescue(r Report, finished bool, centreLat, centreLon float64) (Report, bool) {
	if !finished || r.Category != CategoryRescueNeeded {
		return r, false
	}
	gh := geohash.EncodeWithPrecision(r.Latitude, r.Longitude, approxGeohashPrecision)
	lat, lon := geohash.DecodeCenter(gh)
	d := haversineKm(centreLat, centreLon, lat, lon)
	r.Latitude, r.Longitude, r.Geohash, r.Description, r.DistanceKm = lat, lon, gh, "", &d
	return r, true
}
```

### Known Threat Patterns

| Pattern | STRIDE | Standard mitigation |
|---------|--------|---------------------|
| Triangulating an exact spot from `distance_km` with moving search centres | Information disclosure | recompute `distance_km` from the coarse point |
| Reading a precise `geohash` or description of a finished Rescue report | Information disclosure | one coarsening function over all four fields, tested on every read path |
| Spoofing the poster to get a free Reopen | Elevation of privilege | reporter identity from `ReportVoteContext`, never the request |
| Withdraw spam to flip a closed report | Tampering | two per account per report, counted from the append only log, only after a standing `resolve` |
| Using `reopen` in place of the take back to lift a closed report | Tampering | separate neutral value, test that it never enters `ReopenCells` |
| Reader searches exhausting the shared geocoder | Denial of service | `Allow` only lane, cache, per account budget |
| Probing report ids by the `report=` parameter | Information disclosure | one answer for not found, withheld and removed; `too_old` reveals only that an id once existed |
| Moderation state revealed through history | Information disclosure | `ViewOf` fails closed; Phase 4 `Withheld()` yields `none` |
