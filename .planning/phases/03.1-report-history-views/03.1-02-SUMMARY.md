# Phase 3.1 Plan 02: The take back of a mistaken Mark resolved Summary

A person who marked a report resolved by mistake can now take that back with a neutral `unresolve` value that drops their resolve, never counts as a reopen and never moves a rating, limited to two per report per account and counted from the append only votes log with no migration.

## What was built

- `internal/store/queries/undos.sql` and generated `internal/store/sqlc/undos.sql.go`: `ResolutionUndoCounts`, one batched query over the existing `votes` table and `idx_votes_account_kind_report_created`. The values and kind are parameters. No other generated file changed.
- `internal/service/takeback.go`: `UndoLimit = 2`, `ErrNothingToTakeBack`, `ErrUndoLimitReached`, `ViewerResolution`, `UndosUsed`, `UndosLeft`, `undoCountParams`.
- `internal/service/trust.go`: `VoteUnresolve` in `VoteValues` (five values) and valid for the resolution kind only; `VotingQuerier.ResolutionUndoCounts`; `CastVoteResult.UndosLeft *int` (nil for content votes); the CastVote branch.
- Fakes updated: `fakeVotingQuerier`, `p05VotingFake`, `bodyVoteFake`.

## CastVote behavior

- `isTakeBack` is its own named predicate: resolution kind with value unresolve. It excuses the missing location check and the 1 km check. `isReporterResolutionVote` is unchanged (acceptance grep prints 1).
- Expired report: refused by step 5 as before, nothing written.
- No standing resolve of the caller: `ErrNothingToTakeBack`, before any write and before the undo count read.
- Two undos used: `ErrUndoLimitReached` for a take back, and for the poster's reopen only. A non poster's reopen is never limited, a resolve is never refused for the limit.
- `UndosLeft` is `UndoLimit - used - 1` after a take back or a poster reopen, `UndoLimit - used` after any other resolution vote, and nil for content votes.
- Ratings: `ClassifyOutcome` already clears every resolution field, and `TestTakeBackLeavesRatingsUnchanged` proves outcomes and `ScoreReliability` are equal with take backs appended.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The take back refusals and the undo count run after the distance step, not before it**
- **Found during:** Task 2, first full run of `TestCastVoteRejectsTooFar`.
- **Issue:** The plan placed steps 5c and 5d between 5b and 6. With that order a resolve or reopen refused for distance made a `ResolutionUndoCounts` read, breaking the existing invariant (`calls = exactly [ReportVoteContext]`) that a vote refused for distance costs only the context read.
- **Fix:** The two steps are named 6b and 6c and sit right after step 6. Behavior for the take back is identical because it skips step 6; the only change is that a non poster's too far resolve or reopen costs one read less. Both still run before any write and before the cell is computed. The CastVote doc comment states why.
- **Files modified:** `internal/service/trust.go`
- **Commit:** 3f915da

**2. [Rule 3 - Blocking] Store test lives in package store_test**
- The plan said "package store"; the existing store tests are `package store_test` and share seeding helpers from `votes_test.go`, so `undos_test.go` is in `store_test` too.

## Accepted risks and notes

- **T-31-09 (accepted):** two simultaneous take backs by the same account can overshoot the limit by one, because the log has no lock by design (T-02-02). Recorded in the CastVote doc comment.
- A take back sent with no coordinates is stored with a geohash cell computed from 0,0, as the reporter's own location free resolve already is. The unresolve value enters no vote bucket, so the cell is never counted.
- A take back does cost one extra `CurrentVotesForReports` read (the pre insert check), only for the take back.
- Plan 08 must map `ErrNothingToTakeBack` and `ErrUndoLimitReached` (both 409 in my proposal) and add the route; plan 15 must document the unresolve value in TRUST-MODEL.md.
