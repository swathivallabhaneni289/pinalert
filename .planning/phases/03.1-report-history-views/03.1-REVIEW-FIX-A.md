## CR-01: a linked report freezes at the first answer

**Commit:** 2d507ec
**Files:** web/static/js/app.js, web/static/js/map.js, web/static/js/feed.js, web/static/js/map-tools.js, web/past_tab_contract_test.go, web/map_follow_contract_test.go, web/review_fix_a_contract_test.go
**Status:** fixed: requires human verification (state machine logic)

What changed:

- app.js: `report=ID` is sent with every list request while the link is held
  (the clear after the first answer is gone). Every applied answer replaces
  `state.focus`: it is set to `null` first and takes `body.focus` only while
  the id that request carried is still the store's id, so an answer sent
  before the link ended cannot bring the pin back. An answer whose focus is
  not `ok` (too old, unavailable) is final and ends the id. New assign only
  `Pinalert.dropFocus()` clears `focusId` and `focus` (no notify, no fetch).
- The link ends on the reader's own changes: `switchTab` (tab strip and See
  past reports), the filter empty Clear filter (feed.js), `onChipPress`,
  `onClearFilter`, `pickResult` and `onBackPress` (map-tools.js).
  `selectTabOnScreen`, the link's own tab choice, keeps it.
- map.js: when the reader closes the linked popup (`openedFocusId`),
  `onPopupClose` calls `endLinkOnClose()`, which drops the link and redraws
  the pins after Leaflet has finished the close (removing a marker inside its
  own popup close would remove the popup twice). If the removed pin held the
  focus that `returnFocusToOpener` gave it, focus goes to the map container.
  A close made by a redraw (`removingPopup`) or by a resize across 900px (new
  `resizeClosing` flag) does not end the link.
- feed.js: `handleFocus` acts once per link instead of once per answer, since
  every answer now carries a new object; otherwise a take back that moves the
  report would pull the reader to another tab.

Pinned literal edited (past_tab_contract_test.go, TestFocusSelectsTabWithoutAddressWrite):

- old: `"focus === handledFocus"`
- new: `"handledFocus !== null"`

The view_strip_contract_test.go literals `if (body && body.focus) {`,
`state.focus = body.focus;` and `state.focusId = null;` are all still present
in that order, so that test was not edited. map_follow_contract_test.go only
had its comment widened to name the one `Pinalert.dropFocus()` call; its
`state.focus =`, `state.focusId` and `setFocusId(` bans on map.js still hold.

Driven: link request carries `report=42`; the first `ok` answer is stored and
the id kept; the take back refetch still carries the id and its answer
replaces the focus (`undos_left` 2 to 1, `view` resolved to active,
`your_resolution` to null); an answer with no focus nulls it; an answer that
lands after `dropFocus` leaves focus null and the next request has no
`report=`; a `too_old` answer is stored for the toast, ends the id, and the
next answer nulls it. `handleFocus` selects the tab on the first answer only
and toasts `too_old` once. `onPopupClose` drops the link and defers the
redraw on the reader's close, moves focus to the map when the removed pin had
it, and keeps the link for a redraw close, a resize close and another report's
popup.

## WR-03: the old tab's rows stay under the new heading

**Commit:** 826a104
**Files:** web/static/js/app.js, web/static/js/feed.js, web/static/css/feed.css, web/review_fix_a_contract_test.go
**Status:** fixed

What changed:

- app.js `markListLoading(on)` sets or removes `data-loading` on
  `.pane--list`. `fetchReports` calls `markListLoading(isBackgroundRefresh &&
  !rowsMatchStore())` as each request starts, and `markListLoading(false)`
  right before `notify()` on an applied answer and on a failure. A stale
  answer changes nothing. Putting the mark in the one list request means every
  path that changes the set is covered (tab press, link tab choice, chips,
  Clear filter, place pick, Back to my location, the back and forward cache
  restore) without each handler having to remember it, and pressing back to
  the rows' own tab removes the mark at once.
- feed.css hides `#report-list`, `#past-groups`, `#feed-count`, the five
  empty blocks and `#feed-error` under the mark (`display: none`, not dimmed,
  so nothing of the old set is readable or reachable by a screen reader) and
  shows `#feed-skeleton` through `.pane--list[data-loading] #feed-skeleton[hidden]`,
  which outranks `#feed-skeleton[hidden]`. Each hide selector carries
  `:not([hidden])`, which keeps TestDisputedEmptyStateHiddenGuard's rule that
  no display rule names `#disputed-empty` bare. No new tokens, no literals.
- The store is never emptied, so `isStale`, `rowsMatchStore` and the
  TestFeedErrorStateKeepsStaleRows literals are unchanged.

No pinned literal edited.

Driven: first load with no rows does not mark; a poll on the same set does
not mark; Active to Past marks while the store keeps both rows, the Past
answer clears it; Past to Disputed marks and pressing back to Past clears it
at once, and the late Disputed answer is dropped; a chip change marks and a
failure clears it and drops the rows of the other set; a place change marks
and its answer clears it.

Note on the UI-SPEC: its state table says a tab press "keeps rows" while
loading (line 571) and line 200 says the skeleton shows "only when no rows are
on screen". This fix replaces that with the skeleton whenever the rows on
screen belong to another set, as the review and the owner's Phase 2 objection
require. Rows of the same set (a poll, a Retry, a vote refetch) still stay on
screen exactly as before.

## WR-04: the Undo toast trusts :hover

**Commit:** 1f55fee
**Files:** web/static/js/app.js, web/review_fix_a_contract_test.go
**Status:** fixed

What changed: `pauseToast(evt)` returns early for a `pointerenter` whose
`pointerType` is not `mouse`, and records a mouse in the new
`toastPointerInside` flag. `resumeToast` clears the flag on `pointerleave`,
reads the flag and the focus instead of `matches(':hover')`, and restarts at 4
seconds only when the timer was paused (`toastTimer === null`), so a lifted
touch neither stops nor shortens the 8 second toast. `showToast` clears the
flag for every new toast, because a toast hidden under the mouse gets no
`pointerleave`. The four `addEventListener` literals pinned by TestToastAction
are unchanged, and `startToastTimer(toastEl, TOAST_RESUME_MS);` still appears
once.

No pinned literal edited.

Driven with fake timers, and a stub whose `matches(':hover')` always answers
true (a sticky hover; the old code never restarts under it): a touch on the
text leaves the toast up at 7.9 s and hidden at 8.1 s; a mouse enter holds it
for 60 s and a leave hides it 4 s later; focus holds it and focus leaving
hides it 4 s later; a plain toast hides at 3 s under the mouse and the next
Undo toast is not held by a stale flag; a mouse leave while focus stays inside
keeps it paused until the focus leaves.

## WR-05: a refused take back keeps the stale Undo

**Commit:** d13c611
**Files:** web/static/js/votes.js, web/review_fix_a_contract_test.go
**Status:** fixed

What changed: a new `answeredByServer(err)` is true for an error the server
sent (postVote gives it a `field`), which covers both 409 refusals, the
expired refusal and any other answered refusal. In `onTakeBackClick`'s failure
branch such an error runs `Pinalert.fetchReports({ afterWrite: true })` first;
then the label is restored, the block released and the refusal line written.
Focus stays on the button when it is still shown, else it follows
`focusAfterTakeBack(origin)` (the row, then the current tab link), because the
refetch usually hides the Undo. `takeBackFromToast`'s failure branch reads the
list again too before it returns the sentence. A transport failure has no
answer to read and only shows the line, as before. The take back ordered pins
in takeback_contract_test.go keep matching, since the new refetch comes after
the success path's.

No pinned literal edited.

Driven: a 409 on the opened report's Undo refetches with `afterWrite`, before
the release and before the refusal line; with the Undo gone after the render,
focus takes the take back route; with it still shown, focus stays on it. A
transport failure does not refetch and shows "Couldn't undo that. Try again.".
A refused toast Undo refetches and returns the server sentence; a toast
transport failure does not refetch.

`recenterOnReader`'s `done` calls `Pinalert.clearPlace()` in the same step as
`Pinalert.setCenter`, when the position or the default area arrives (both the

line, the distance words and the list all still describe the searched area.

Driven (real `recenterOnReader` text, real store, held geolocation answer):
the place and "1.2 km from Kochi" stay while the position is pending, and no
request is sent; when it arrives the place is cleared, the centre is the
