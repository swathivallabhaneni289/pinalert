# Phase 3.1 hand off: what this phase changed under later phases

Written by plan 03.1-15. One bullet per follow up, each naming the file or plan it touches. Nothing here edits a Phase 4, 3.2, 5, 8 or 9 plan file: those plans still say what they said, and the people who plan them read this list first. The trust model side (the take back, the history labels, the finished Rescue blur) is in `docs/TRUST-MODEL.md`, and its drift test `TestTrustModelDocMatchesCode` pins the numbers and names to the code.

How this was written: plans 01 to 10 were merged when this file was written, so their items come from the built code and their SUMMARY files. Plans 11 to 14 (the map tools, the Past cards, the finished pins, the take back screens) and plan 16 (the final gate) were not merged, so their items come from their plans. Check those items against the built code before relying on them.

## Phase 4

- **Flag leaves the row.** The Flag this report control lives in the opened report only, in every view (P4-A7 amended, UI-SPEC departure R9). A compact list row now holds no button and no link inside it, so plan 04-24 must not add Flag to a feed row, and every Phase 4 plan or spec line that puts Flag on each row (P4-A7 in `04-UI-SPEC.md`, the 04-24 plan and its tests) needs that edit before Phase 4 is built. The opened report is the map popup on a laptop and the full screen sheet on a phone.
- **Three pinned web tests were edited here, not run unedited.** Plan 04-13 says `TestShowDisputedUsesOneSharedQueryParam`, `TestFeedErrorStateKeepsStaleRows` and `TestFetchReportsDropsOnlyResponsesOlderThanTheLastApplied` run unedited. Plan 05 edited all three in `web/votes_contract_test.go` because `state.showDisputed` became `state.view`. The first keeps its name and now pins one `'&view='` literal, `setView` and no `show_disputed` in app.js. 04-13 and 04-19 should take their new literals from the 03.1-05 SUMMARY, which holds the old and new text:
  - `TestFeedErrorStateKeepsStaleRows` now pins `rowsFor = { view: sentView, category: sentCategory, lat: sentLat, lon: sentLon };` and `if (!rowsMatchStore()) {` followed by `state.reports = [];`.
  - `TestFetchReportsDropsOnlyResponsesOlderThanTheLastApplied` now pins `return mySeq < lastAppliedSeq || mySeq < writeFloor || sentView !== state.view ||` and the next line `sentCategory !== state.category || sentLat !== state.center.lat || sentLon !== state.center.lon;`.
  - `TestFeedExplainsAnEmptyDisputedResult` was edited too (04-13 lists it as stay green): it now bans `type="checkbox"` in the whole page template and wants `class="view-tabs"` before `id="report-list"`. A Phase 4 checkbox anywhere in `index.html.tmpl` would trip it, so narrow that check to the list pane first.
  - `TestAgeAndFadeUseTheServerClock` was not edited.
- **The moderator row's view word comes from `ViewOf`.** Plan 04-23's `view` field is the `FeedView` word `ViewOf` returns: `past` for Expired, `resolved` for Resolved, `active`, `disputed`, and `none` for anything `ViewOf` does not list (the fail closed `FeedViewNone` is an empty string in Go, so the moderator JSON maps it to the word none). `GET /api/reports?view=resolved` is a read only alias that is answered as `past`, and the echoed `view` is `past`.
- **`TestWithheldInNoView` must also loop `ViewOf`.** `ViewOf(visibility, expiresAt, now)` is pure and takes values only, so Phase 4's test can loop every `Visibility` and every expiry side with no database. `ViewOf` knows nothing about moderation: Phase 4 wraps it with its own withheld check, and a held or removed report appears in no view.
- **Where the Phase 4 strips go.** The "Waiting to send" queue strip and the stale list line sit between the filter line (`p#filter-line`) and the list (`#report-list`), in that order. The tab strip, the status line, the note and the place line are above them and are not touched.
- **The Low data view shows Active only.** It gets no tab strip, no chips and no place search, and The main page never writes `view=active` to its address. A main address with a query string is never redirected to Low data, and `/?report=ID` with no view still works (moderator links). A 04-18 Low data row reads `facts` for its trust block, as TRUST-MODEL.md already says.
- **The popup reserve already clears the map tools.** Plan 11 adds `--map-tools-height` and widens the popup top autopan reserve with it (P4-A4 says to widen if top controls are added), so Phase 4 adds its own term to that reserve and does not replace it.
- **`app.js` still has exactly two `fetch(` calls.** The view, category and report link are parameters of the one list fetch, and the place search lives in its own script, `web/static/js/map-tools.js` (plan 11), which holds one `fetch(` to `/api/geocode/place`. A Phase 4 plan that counts `fetch(` in `app.js` keeps its pin at two, and one that counts them across the web files has to expect the extra one.
- **The take back is a fifth vote route.** `POST /api/reports/{id}/unresolve` (plan 08) sits inside the verified account group beside confirm, dispute, resolve and reopen. Any Phase 4 limit, 429 body, swagger `@Failure 429` list or test that names "the four vote routes" has to name five, and `docs/swagger.json` is the frozen wire shape to build against. Its two refusals are 409 with field `report`: "You have no resolved mark on this report to take back." and "You have used both undos on this report."
- **Rows, the Phase 3 pins (plan 09, UI-SPEC departures R1 to R7).** A phase 4 plan that touches `createRow` or the row CSS meets these changes, named by the older Phase 3 identifiers:
  - A55: the row title clamps at two lines at every width (`TestRowTitleWrapsLongWords` now exempts the shared `#report-list .report-row .report-row__title` head in `feed.css`).
  - A75 and A81: the state word joins the body's flex order and the title gap is `--space-xs`.
  - A5, A22, A78, A79 and A96: no trust toggle, panel, chevron or clock on a row; a row has one plain text trust line (`createTrustLine`).
  - A17, A66 and A35: no vote control, note or error in a row.
  - A94: the distance shows on a laptop row.
  - 01 D-12: the 32 px category badge is gone from laptop rows.
- **Browser harness checks change by design.** The checks T8 and T11.8 vote from a laptop row, as do the others in `test0.js`, `test3.js`, `test4.js`, `test5.js` and `test8.js`. A row holds no vote control now, so the orchestrator moves them to the opened report in `~/code/pinalert-browser-checks` (plan 16, list item 2). Any check that looks for `.trust-block__toggle`, `.vote-controls` or the round badge inside `#report-list` changes too, and the old `#show-disputed-toggle` is now the link `a.view-tab[data-feed-view="disputed"]`.
- **Small gap for 04-13 or 04-24.** `votes.js` `focusAfterRetract` knows only `feed-empty` and `disputed-empty` as empty fallbacks, not `feed-empty-history`, `past-empty` or `filter-empty`. Rows hold no vote control now, so it is harmless, but Phase 4's focus return should add them.

## Phase 3.2

- **The report link works from a link alone.** `/?view=resolved&report=ID` and `/?report=ID` open that report on the map outside the reader's radius and outside the 7 day window. The list read takes `report=ID` and returns a `focus` object with a status (`ok`, `unavailable` or `too_old`) and, for `ok`, the report. A Hidden report that has not expired answers `ok` with the view `disputed`. The id is accepted from the address only as 1 to 18 digits with no leading zero, and it is sent on the first request and then cleared. Updates and their notification links should build `?report=ID` and let `focus` do the rest, and should write copy for `unavailable` and `too_old` (the words are in the UI-SPEC "Empty, Error and Link States").
- **The take back lives in the opened report.** The Activity page gained one thing only, the sentence "You have used both undos on this report." that replaces Reopen when both undos are used. Its voted cards never offer Reopen (`TestProfileVotedRowNeverOffersReopen`), and the six tab Activity page, My votes included, was left alone (D-24).
- **Two new viewer fields are on the wire.** `your_resolution` (null or the viewer's own standing resolution word) and `undos_left` are on `FeedReportResponse`, and `undos_left` is also on every resolve, reopen and unresolve vote response. Phase 3.2's update wording may read them and must not decide the limit itself: the server enforces it.
- **Update wording and a finished Rescue report.** If an update names a report that is finished and is Rescue needed, it reads the blurred report from the same `Focus` read. Do not copy the exact coordinates or description into an update row, a notification or a share link.

## Phase 5

- **New tabs go in the same strip.** Alerts and Following become tabs beside the three tabs of this phase, and the default tab is then renamed Nearby. This phase builds only the three tabs and does not claim any address name for the new ones, so Phase 5 picks them. The closed list of views is `FeedViews` in `internal/service/history.go`, the strict parser is `parseFeedView` in `internal/api/handlers/reports.go` (an unknown word is a 400, never a silent default), and the enum is in the swagger, so a new view changes all three together.
- **Official pins ignore the tab and the chips.** An official pin is not a user report, so it is shown whatever tab is selected and is not filtered by a category chip (D-13). The map label that names the tab (plan 13) should say so when a tab hides user pins only.
- **Demo mode and finished reports.** A seeded finished Rescue report goes through the same blur as a real one, because the blur is applied at read time to every report. The "Hand offs to later phases" list in TRUST-MODEL.md already says demo reports need to sit near the visitor or be exempt from the 1 km rule, and a seeded report that is already closed or expired appears in the Past tab like any other.

## Phases 8 and 9

- **Build the coarsening and the single report read once.** `CoarsenFinishedRescue` and `CoarsePoint` in `internal/service/coarsen.go`, and `ReportService.Focus` in `internal/service/historyread.go`, are the shared pieces. A report page (Phase 8) and a followable profile (Phase 9) read a report through `Focus` or through `buildFinishedView`, and never from a raw row, so a finished Rescue report cannot reach a page with its exact spot or its text.
- **The honest limit travels with it.** The blur stops a finished report handing out the spot. It cannot take back what a reader saw while the report was live (D-23). Phase 8 comments and Phase 9 profile pages must not suggest otherwise, and a followable profile that lists someone's finished Rescue reports applies the same blur.
- **Wire guards.** The swagger name guard (`(?i)cell|account|session|email` and the `session_id` and `reporter_account_id` substring bans) now also covers `handlers.ReportListResponse`. A new response object for a report page has to pass it.

The report form's own search is unchanged. D-14 will look partly broken at UAT until 999.7 lands.

## Owner questions at UAT

Put these to the owner one at a time, in these plain words, each with the answer to recommend. The defaults below stand unless the owner vetoes them.

- **D-10, the Disputed label.** "When people near a serious report said it was wrong and it then faded, the Past tab says Disputed. Is that right, or should it just say Expired?" Recommend Disputed, because the person's reliability rating already counts that report against them and the two should agree.
- **D-11, tapping a Past card.** "Tapping a finished report opens it on the map, and you can only read it, with one exception: the person who marked it resolved by mistake can take that back. Is that what you want?" Recommend yes, because Updates and moderator links open a report by number and need somewhere to land.
- **D-13, what the map shows.** "While Disputed or Past is selected, the map shows only that tab's reports with a small label, and finished pins look different and cannot be voted on. Is that right?" Recommend yes, because yesterday's flooded road must never read as live.
- **D-27, the Activity page and finished Rescue reports.** "On your Activity page, a card for someone else's finished Rescue report that you voted on now shows the blurred spot and no text, like the Past tab. Your own posts stay exact. Is that right?" Recommend yes, because those cards carried the exact spot and the text for as long as the vote existed, which defeated the blur for the people who voted.
