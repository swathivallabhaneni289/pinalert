## Problem 1: the map keeps the old set's pins and label while the list loads

**Commit:** 626f842
**Files:** web/static/css/feed.css, web/static/js/app.js (comment only), web/review_fix_a2_contract_test.go
**Status:** fixed

What changed:

- feed.css, right after fixer A's list rule, a new rule keyed off the same
  mark: `.app-shell:has(> .pane--list[data-loading]) .pane--map .leaflet-marker-pane`
  and `.app-shell:has(> .pane--list[data-loading]) #map-label:not([hidden])`
  get `display: none`. The map pane is a sibling of the list pane, so the
  shell is matched by the marked list pane it holds. phone.css already relies
  on `body:has(...)` for the phone sheet, so this adds no new browser floor.
  A browser without `:has()` drops the rule and shows the map as before.
- Hidden, not dimmed, like fixer A's rows: the old pins also leave the tab
  order and the accessibility tree. No transition, so reduced motion has
  nothing to turn off.
- No second loading flag: no script reads or writes `data-loading` besides
  fixer A's `markListLoading`, and map.js is untouched by this commit. Since
  `markListLoading(false)` runs right before `notify()`, the pins and the label
  come back in the same step in which the map draws the new set (or the
  failure), so no old pin paints under the new label.
- What stays visible: the Leaflet controls (zoom, attribution), the map tools
  (search, chips, Back to my location), the basemap and an open popup. The
  marker pane holds only report pins, including the distant pin a link adds:
  the reader's position is not drawn as a marker anywhere in map.js (the only
  `L.marker` is the report pin in `upsertMarker`), so nothing of the reader's
  is hidden. A grep of every script for `L.marker`, `L.circle`, `L.polygon`,
  `L.geoJSON`, `markerPane` and `addTo(map` finds one other marker, the
  draggable pin of the submit modal (modal.js), which lives on its own map in
  `#modal-map` outside `.pane--map`, so the rule does not reach it.
- app.js: the `markListLoading` comment now says the map follows the mark.

No pinned literal edited. The new rule is a separate block, so fixer A's
test that slices its list rule up to the first `}` is not affected, and
TestMapToolsCSS's `.map-label` lookup matches whole selector parts only.

Driven: a first load with nothing on screen does not mark; Active to Past

## Problem 2: a redraw that closes the linked popup leaves the link open

**Commit:** 52718c4
**Files:** web/static/js/map.js, web/review_fix_a_contract_test.go, web/review_fix_a2_contract_test.go
**Status:** fixed: requires human verification (state machine logic)

What changed: in `onPopupClose` the link end condition drops `!removingPopup`
and keeps `!resizeClosing`, so every close of the linked popup ends the link
except the one a resize across 900px makes. `endLinkOnClose` is unchanged (one
`Pinalert.dropFocus()`, one deferred `redrawAfterLinkEnded`), and the focus
return stays gated on `!removingPopup` and synchronous, with no `setTimeout` in
`onPopupClose`.

Why ending it on every close but a resize is simpler and still correct: a
redraw that keeps the same report never closes its popup. `upsertMarker`
reuses the one marker per id and updates the icon, the position and the card
in place, which leaves the popup open, and a report that moves from the
link's own pin into the list keeps the same marker id. So a redraw closes the
linked popup only through `map.removeLayer`, which means the report has left
the tab or chip the reader is on (a resolve from Active, a take back off
Past, a fade). In that case nothing on screen holds the link any more, and
keeping it would send `report=ID` on every poll and could bring the pin back
with no popup. A resize close is the one close that leaves the report in the
set, so it alone keeps the link. Opening another report's popup closes the
linked one through Leaflet and ended the link before this fix too; that is
unchanged. Closing another report's popup, or a redraw removing another
report's pin, never matches `openedFocusId` and keeps the link.

Calling `dropFocus` from inside `render` is safe: it only assigns, the rest of
the removal loop does not read the focus, and `openFocusOnce` at the end of
`render` returns early on a null focus. The deferred redraw finds the pin
already gone and changes nothing; it runs after feed.js has read
`takeRemovedPopupFocus` in the same notify.

Pinned literal edited (review_fix_a_contract_test.go, TestReviewFixALinkedReportRefreshes):

- old: `"String(id) === openedFocusId && !removingPopup && !resizeClosing"`
- new: `"if (id !== null && String(id) === openedFocusId && !resizeClosing) {"`

The test's comment now says the link ends on every close but a resize's. Its
other pins (one `Pinalert.dropFocus()` in map.js, the deferred redraw, the
resize flag) are unchanged. popup_contract_test.go's `removingPopup` before
`returnFocusToOpener(` order still holds. New test
TestReviewFixA2LinkEndsOnRedrawClose pins the condition, the unchanged focus
return gate, no timer in `onPopupClose`, and the removal flag around
`map.removeLayer` in `render`.

Driven (all passed on the fix; the base map.js failed the 7 checks marked *):

- a link to a distant Active report opens its pin; the refetch after a resolve
  still carries `report=42`; the answer with view `resolved` removes the pin

  pin back with no popup* (on the base code the pin came back closed)
- a linked report open on Past whose take back makes it live: the removal

- a removal while focus was in the linked popup (focus on a laid out control

  listener in the same notify gets `true` from `takeRemovedPopupFocus` before

  redraw cannot clobber the A67 flag
- kept: a redraw of the same report keeps the popup, the link and `report=42`
  on the next poll; the report moving into the list keeps both; a resize
  across 900px closes the popup and keeps the link; closing another report's
  popup and a redraw removing another report's pin keep the link
