# Phase 03.1: Code Review Report

**Reviewed:** 2026-10-15

## Summary

One Critical finding, and it is a client defect, not a server one: a report opened from a link outside the list radius freezes at the state of the first answer, which breaks the take back (and every vote refresh) on exactly the D-11 link path (CR-01). The two areas the phase exists to protect hold up on the server: the finished Rescue blur has no bypass I could find, and the take back cannot touch another person's vote, cannot be counted as a reopen or a confirm, cannot pass the expiry refusal and cannot move a reporter rating. The other defects are edges: a race that makes the documented "overshoot by one" untrue, a silent candidate cap in the Resolved group, and two front end state machine gaps.

Area by area:

1. **Take back (trust.go, takeback.go, undos.sql, handlers/votes.go, votes.js, app.js).** Sound on identity, neutrality, expiry and ratings. The account id comes only from the gate. Step 6b reads the caller's own standing row, so nobody can take back someone else's mark. `filterVoteRows` puts `unresolve` in no bucket for anyone, and sets both reporter flags false for the poster, so it is never a reopen or a confirm. Step 5 (expiry) runs before 6b and 6c. `ClassifyOutcome` clears resolution fields, so no rating moves. The poster's reopen is counted in the same two (`spendsBudget`). Findings: CR-01 (stale focus object breaks take back from a link), WR-01 (race), WR-04 (toast timer), WR-05 (no refetch on refusal), IN-06 (shared budget leaves the poster no answer to a stranger closure).
2. **Finished Rescue privacy.** Clean on every server path read: `buildFinishedView` is the single exit for the Past list and for `Focus`, `CoarsenFinishedRescue` changes latitude, longitude, geohash, description and distance together, `reportViewToResponse` blanks a description again as a second guard, and the voted Activity cards blur through `CoarsePoint`. Live Rescue and finished Flood, Shelter and Power stay exact. The browser never reads `description` of an approximate report (feed.js, map.js, activity template). No moderator or other endpoint exists yet. Residual items only: IN-05 (id enumeration returns live exact reports at any distance, by design D-11).
3. **Reader place search.** Clean on the questions asked. The budget is keyed `place:<verified account id>` and checked before any upstream call. The cache is a 256 entry bounded map with a bucketed key. Input is 3 to 200 runes and the centre is range checked. Errors are fixed plain sentences. The route sits inside the verified account group, so a signed out caller gets 401. The reader lane takes a token with `Allow` and never leaves debt, so it can delay a reporter by at most one refill (about 1 s, inside the reporter's 1.5 s wait) and cannot starve one. Minor items: IN-04, IN-08.
4. **View, category and report parameters.** Strict parsing, fail closed `ViewOf`, one `now` per read, window edges (`>` against `windowStart`, `<=` and `>` against `now`) agree between Go and SQL. One real defect: WR-02 (the open candidate cap silently drops Resolved reports).
5. **Front end state machine.** No `innerHTML`, `outerHTML`, `eval` or `document.write` in any reviewed script. `app.js` has exactly two `fetch(` calls and `map-tools.js` one. The view is never written as `view=active`. Polling skips Past. Findings: CR-01, WR-03, WR-04, WR-05, IN-07.
6. **CSS and markup.** Judged from the stylesheet text and its arithmetic only: nothing was rendered, so the phone widths 320, 360 and 390 are reasoned, not measured. Font sizes (14, 16, 18) and weights (400, 600) are tokens; corners are 8px; targets use `--touch-target-min`; no gradient, no pill, no emoji; no hex colour in an added line. A handful of documented literals are noted as IN-09.
7. **Dashes.** No em dash or en dash (U+2014, U+2013) in any line this phase added to a non generated file, including `docs/TRUST-MODEL.md` and the regenerated swagger files (byte scan of the diff against `4e5a051`).

## Critical Issues

### CR-01: The store keeps the first `focus` object forever, so a report opened from a link outside the radius never refreshes and its take back, vote and Undo state freeze

**File:** `web/static/js/app.js:369-371`, `web/static/js/map.js:1164-1167` and `1219-1245`
**Issue:** `state.focus` is set from the response that carried `?report=ID` and is never replaced: every later response has no `focus` object, and `fetchReports` leaves the old one in place. `map.js` `focusPinReport` re-adds `focus.report` to the pins on every render whenever the report is not in `state.reports`, and `updatePopupCard` is then fed that frozen copy. For a report outside the list radius (the D-11 link case: Updates, a moderator link, another device, a searched place) this gives, in order:
- The poster or resolver taps "Undo" in the opened report. The server records the take back, the toast says "Taken back. The report is open again.", the refetch lands, and the popup still reads "You marked this resolved" with Undo and "2 undos left", because `your_resolution`, `view` and `undos_left` are the first response's. A second press gets the 409 "You have no resolved mark on this report to take back."
- After Confirm or Dispute `your_vote` stays null, so `aria-pressed` snaps back and the reader re-presses.
- After Yes, mark resolved on such a report `view` stays `active`, so Mark resolved is still offered and the take back block never appears (only the 8 second toast Undo works).
- Trust counters, `undos_left`, `history` and `expires_at` driven state are the first response's forever, and the pin survives a place search or Back to my location because only the tab and chip are checked.

This is the core mechanic's own screen showing a state that contradicts the server on the one path D-11 and D-22 say must work.
**Fix:** Do not render from a cached `focus.report`. Keep sending `report=ID` on every list request while the linked report is the open selection, so each answer carries a fresh `focus`, and stop sending it (and drop `state.focus` and the pin) when the popup closes or the tab, place or chip changes:
```js
// app.js: setFocusId stays the one setter; fetchReports no longer clears it on success.
// It is cleared by feed.js / map.js when the linked popup closes or the tab,
// place or chip changes, and state.focus is replaced by every answer:
state.focus = (body && body.focus) ? body.focus : null;
```
Assigning `state.focus = body.focus` alone is not enough, because later requests do not send `report`.

## Warnings

### WR-01: The two undo limit can be exceeded under concurrency, and the documented bound ("by one") is wrong

**File:** `internal/service/trust.go:472-507` (docs claim: `docs/TRUST-MODEL.md:551`, `03.1-HANDOFF.md` "Accepted race (T-31-09)")
**Issue:** Steps 6b (standing resolve exists) and 6c (`used < UndoLimit`) read, then step 7 inserts, with no transaction, lock or conditional insert. N parallel `POST /api/reports/{id}/unresolve` requests from one account, sent while `used` is 0 or 1, all pass both checks and all insert, so the count overshoots by N minus one, not by one. The extra rows are no ops only while no resolve lands between them. An account can interleave `resolve` (never limited) with the late take backs (a `U` that passed its checks before the first `U` wrote, then an `R`, then that `U`) and take back a resolve more than twice, flipping a closure on and off in front of others. It changes no rating and no one else's vote, so it stays a Warning, but the limit is the owner's explicit rule (D-22) and the documented guarantee (T-31-09) is false as written.
**Fix:** Make the check and the write one statement, so the database enforces the limit:
```sql
-- name: InsertUnresolveIfBudget :execrows
INSERT INTO votes (report_id, account_id, kind, value, geohash_cell)
SELECT @report_id, @account_id, 'resolution', 'unresolve', @geohash_cell
WHERE (SELECT COUNT(*) FROM votes
        WHERE account_id = @account_id AND report_id = @report_id AND kind = 'resolution'
          AND value = ANY(@spending_values::text[])) < @limit;
```
Zero rows affected maps to `ErrUndoLimitReached`. A `pg_advisory_xact_lock(hashtextextended('undo:'||account||':'||report, 0))` taken before 6b is the smaller change. If the race is kept, correct the three documents to say "bounded only by how many requests the caller can have in flight".

### WR-02: The open candidate cap silently drops Resolved reports in a busy area, with no cut flag and wrong "last 24 hours" counts

**File:** `internal/store/queries/history.sql:61-88`, `internal/service/historyread.go:93-103` and `301-325`
**Issue:** The Resolved group (closed, not yet expired) can only come from `OpenReportsInArea`, which is every unexpired report in the radius ordered nearest first with `LIMIT 1000`. Live reports are the vast majority of that set in exactly the emergency this app is for, so they fill the cap and push the farther resolved ones out. The comment's claim (b) that live reports "can never crowd expired ones out" is true only for the expired set; the Resolved group is crowded out by live reports by construction. Nothing tells the reader: `CutResponse.resolved` is set only when a group exceeds 25 after classification, never when the candidate read was capped. `RecentHistoryCounts` reuses the same read, so the empty Active tab can say "1 was resolved" when 7 were.
**Fix:** Surface the cap honestly: have `historyCandidates` report `len(open) == HistoryOpenCandidateCap` (and the same for the expired set), carry it as `truncated` on `HistoryPage` and in `CutResponse`, and have the Past tab show the existing cap line. Narrowing the open set with an `EXISTS` on a resolution row would fix the cause, but it breaks the stated rule (history.sql point (d), the `History` comment T-31-29) that no SQL predicate touches votes, so it needs that rule changed deliberately and its pinning comment updated.

### WR-03: On a tab, chip or place change the old rows stay on screen under the new heading until the answer lands

**File:** `web/static/js/feed.js:1305-1326` (`switchTab`, `selectTabOnScreen`), `web/static/js/feed.js:575-588` (`updateFeedHeading`), `web/static/js/app.js:285,319-322`
**Issue:** `switchTab` sets the store, calls `showTab` (which rewrites the heading and the note immediately) and then `fetchReports()`. `fetchReports` treats rows on screen as a background refresh, so it neither notifies nor shows the skeleton. For the length of the round trip the list still holds the previous tab's rows under the new heading: live Active rows under "Past reports / Resolved and expired reports from the last 7 days", or Past cards under "Nearby now". On the slow links this app targets that is seconds. D-13 says finished things must never read as live; here live reports sit under a Past heading and a tap on one opens a vote control against the wrong tab. A render in that gap (any `notify`) also takes `renderPastGroups` over Active rows, finds no `history`, and flashes the "No past reports nearby" block.
**Fix:** Mark the list as loading until the answer is applied without emptying the store, so the pinned `isStale`, `rowsMatchStore` and `TestFeedErrorStateKeepsStaleRows` literals stay green: set a `data-loading` attribute on `.pane--list` in `switchTab`, `selectTabOnScreen` and the chip and place handlers (dim or hide `#report-list` and `#past-groups` in `feed.css`), and clear it in `render` when `state.status` is `ok` or `error`.

### WR-04: The action toast can stay up on a touch screen, because the resume check trusts `:hover` (likely, confirm on a phone)

**File:** `web/static/js/app.js:760-769` (`resumeToast`), with `pauseToast` at 747-755
**Issue:** `pointerleave` fires right after a touch ends, and `resumeToast` then returns early if `toastEl.matches(':hover')`. On touch browsers `:hover` is commonly sticky after a tap and stays until another element is tapped. If it is, a phone reader who touches the toast text (not the button) pauses the timer, the lift fires `pointerleave`, `matches(':hover')` is still true, and the timer is never restarted: the toast then sits above the bottom bar until the next toast replaces it. I did not observe this in a browser; iOS Safari may not apply `:hover` to a node with no click handler, so confirm with touch emulation or on a phone before spending time on it. The product is phone first, so it is worth the check.
**Fix:** Do not read `:hover`. Track pointer presence from the events and pause for a mouse only:
```js
var toastPointerInside = false;
toastEl.addEventListener('pointerenter', function (e) { if (e.pointerType === 'mouse') { toastPointerInside = true; pauseToast(); } });
toastEl.addEventListener('pointerleave', function () { toastPointerInside = false; resumeToast(); });
// resumeToast: if (toastPointerInside || toastEl.contains(document.activeElement)) return;
```

### WR-05: A refused take back does not refetch, and the Past tab is never polled, so the stale control stays

**File:** `web/static/js/votes.js:1579-1586` (`onTakeBackClick` error branch), `web/static/js/app.js:412-415`
**Issue:** On any refusal (409 "no resolved mark", 409 "used both undos", the expired refusal) the handler shows the line and returns without a `fetchReports`. The block keeps showing the Undo button and "2 undos left" from the old report. The common cause is the toast Undo and the in popup Undo both being used: the second is refused and the first one's result is never pulled in. In the Active tab the 30 second poll repairs it; in the Past view polling is skipped by design, so the stale button stays until the reader leaves the tab.
**Fix:** After a refusal run `Pinalert.fetchReports({ afterWrite: true })` before releasing the busy state, as the success path does, and let the render replace the block.

## Info

### IN-01: `Nearby` classifies with the Go clock but selects with the database clock

**File:** `internal/service/report.go:627` (and the `expires_at > now()` predicate of `NearbyReports`)
**Issue:** The list is selected by the database's `now()` and `View` is then computed by `ViewOf(vis, expiresAt, goNow)`. A report within the clock skew of expiry arrives in the Active list with `view: "past"`. The client then hides its vote controls (`isReportFaded` reads `view === 'past'`) while the row sits in Active. Not a leak (it was live when read), only an inconsistent row for a moment.
**Fix:** Pass the same `now` into the query, as the history reads do, or compute `View` from the row's own listing.

### IN-02: `undos_left` is 2 on every expired report

**File:** `internal/service/historyread.go:550-584`
**Issue:** `attachUndos` skips expired views and leaves `UndoLimit`. A poster who spent both undos reads "2" on the wire for the same report once it fades. The client hides every control for a faded report, so nothing breaks, but the swagger text says "how many take backs the calling account has left".
**Fix:** Read the counts for expired views the viewer owns, or document the field as meaningful only while the report has not faded.

### IN-03: A voted card is kept from "used both undos" only by the default value

**File:** `internal/api/handlers/activity.go:156`
**Issue:** `pr.CanReopen = false` is reset for voted cards, but `pr.UndosUsed` (new this phase) is not. It is false today only because voted cards get `UndosLeft: UndoLimit`. A later change that fills `UndosLeft` for voted cards would print "You have used both undos on this report" under someone else's report.
**Fix:** Add `pr.UndosUsed = false` beside `pr.CanReopen = false`, and pin it in `TestProfileVotedRowNeverOffersReopen`.

### IN-04: The place handler logs the reader's search text and the contact email

**File:** `internal/api/handlers/place.go:127-130`, `internal/geocode/client.go:188-190`
**Issue:** `fetch` wraps `httpClient.Do`'s error, which is a `*url.Error` carrying the full URL, the query `q` and the `email` parameter. The handler writes it with `log.Printf`. The report form's `Geocode` handler already does this, so it is a pre existing pattern, but the reader lane now sends a stream of place names tied to request time. The budget (place.go:106) also runs before `parseGeocodeQuery` and the centre checks, so a malformed request spends a token.
**Fix:** Log the error class only, or unwrap with `errors.As(err, &urlErr)` and log `urlErr.Err`. Move the `Allow` after validation if budget fairness matters.

### IN-05: `?report=ID` returns any live report, exact, at any distance, to any verified account

**File:** `internal/service/historyread.go:378-433`, `internal/store/queries/history.sql:98-109`
**Issue:** By design (D-11) a link opens outside the radius, and the id is a sequential BIGSERIAL. A verified account can walk ids and collect exact positions and text of every live report worldwide, bypassing the 50 km radius cap that every list read has. Finished Rescue reports are blurred, but a live Rescue report is exact. The only brake is that the account is verified.
**Fix:** Record this in the Phase 4 rate limit plan (a per account budget on the `report` parameter), or limit the focus read to reports within a bounded distance of the reader's centre unless the id arrived by link.

### IN-06: The poster's reopen shares the two undos, so a stranger closure can become unanswerable

**File:** `internal/service/trust.go:498-501`
**Issue:** By D-22 and D-28 a poster's reopen spends the same two. A poster who used both on their own mistaken resolve can no longer instant reopen when two nearby strangers later mark the report resolved (a resolve outranks even the critical bypass). CONTEXT calls the poster's reopen "the answer to strangers closing a report while the water is still rising". Two nearby people can still reopen it, but the poster, who certainly knows, cannot. A design call, not a code bug.
**Fix:** Put it to the owner at UAT with the other D questions, or count only `unresolve` against the poster's budget and leave their `reopen` unlimited.

### IN-07: "Back to my location" clears the place before the position arrives

**File:** `web/static/js/map-tools.js:390-404`
**Issue:** `clearPlace()` runs first, then geolocation takes up to 8 s. During that window the list is still the searched area but the place line has gone and `distanceText` returns an empty string, so rows lose their distance while still showing the searched area's reports. A second search submitted in the same window is ignored with no message (`backPending`, line 201).
**Fix:** Keep the place until `recenterOnReader` resolves, and show a status line for a swallowed submit.

### IN-08: The reader cache evicts first in, first out and keeps an empty answer for six hours

**File:** `internal/geocode/client.go:294-308`, `370`
**Issue:** 256 distinct junk queries from a handful of accounts push every useful entry out (insertion order, not use order). An upstream that answers `200 []` under load caches "no match" for six hours for that text. Bounded and harmless to correctness.
**Fix:** Do not cache empty lists, or give them a short TTL; move an entry to the back on `get`.

### IN-09: A few literals sit outside the spacing and size tokens

**File:** `web/static/css/feed.css:774` (`calc(var(--space-md) - 1px)`), `feed.css:747` (`letter-spacing: 0.04em`), `feed.css:353-354` (20px icon), `phone.css` (3px ring, 20px dot)
**Issue:** All are documented in the stylesheet comments as UI-SPEC literals, none breaks the owner's rules (font sizes, weights, corners and targets are all tokens), so this is a note and not a violation.
**Fix:** Optional: name them (`--ring-width`, `--icon-size`) when backlog 999.10 does its pass.
